# 验收矩阵、性能计量与并行实施任务包

版本：LIVE-REVIEW-ENG-1.0。日期：2026-10-20，Asia/Shanghai。

**本文件全部实施任务与 R01–R50 验收均为计划，尚未执行通过。**此前纯 SDK 假模型探针只验证了明确列出的框架机制，不代表这里的新业务、评分、采集和交接已经实现。本次只保存开发计划，不运行真实模型、TTS、生产数据库迁移、线上采集或服务更新。

本计划的完成标准是：已知根因在第一次实施时就有唯一落点与反例；从监控资料到正式复盘、再到人工采纳的链条可追溯、可恢复；模型可以自主选择调查路线，确定性程序减少重复读取与无效等待。10分钟是性能优化目标，不以删除必要资料、减少要求覆盖或冒充已完成换取。

## 1. 每个开发窗口拿到什么

交给某个窗口的最小任务包为：本文件对应 W 行、00–04 工程计划、06 旧问题预防矩阵、07 评价执行配方及上级评分政策、冻结的 contracts/schema、所需 fixture、模型和业务 API 的假服务接口、禁止修改范围。只发送一句“你做经营Agent”不足以独立施工。

每个窗口必须交付：代码改动清单、真实入口与输出合同、针对编号的自动验收结果、fixture 与版本hash、性能span样例、未覆盖项、结构审查表。测试失败不得改为默默跳过；不能把合成场景的良好经营结果描述成真实带货效果。

## 3. 分层验证，不逐小改全链真实回归

| 层级 | 执行内容 | 何时执行 | 可支持的结论 |
|---|---|---|---|
| L0 静态/契约 | 导入无副作用、schema导出、签名、ToolSpec/Skill名称、迁移/schema兼容、依赖检查 | 同根因一批改动后；通常秒级/分钟级 | 合同一致、没有明显结构漂移；不能证明真实模型规划 |
| L1 确定性单元/属性 | 归属/去重/cohort/评分/时间/缓存/键计算、状态转换 | 对应批改动后，一次运行相关模块组 | 给定输入数学和程序不变量正确 |
| L2 SDK假模型 | 本机create_deep_agent真实工具节点、主子并行/角色、完成错误/等待/摘要/取消 | W3接通以及影响SDK控制的批改后 | SDK控制机制可运行；不是供应商联网可靠性证明 |
| L3 离线端到端 | 隔离临时DB+录制/合成事件/报表+fake provider+fake voice API | 各包合并后及重要依赖/接口改动后 | 从归档到报告/采纳的应用链和恢复、错误语义连通 |
| L4 小型真实模型 | 冻结构建+安全授权adapter+同一小型synthetic样例3次 | L0–L3通过、暂无阻断且已准备好冻结证据之后 | 实际provider工具协议/规划/用量/本机性能；不证明真实直播成交效果 |
| L5 授权现场验证 | 用户明确选定的实际场次、真实经营导出、平台音频延迟与取声链校准 | 产品可用且有数据/授权时，单独实施 | 该场/该账户/该插件版本的采集和评价资格，不外推所有房间 |

先复现根因→一次修改同根因生产者/消费者→跑关联L0–L3→结构复查。只有新改动、失败或未解疑点影响L4结论时才补真实调用。若修改纯UI样式，不再跑三次模型；若改ToolSpec、provider或完成控制，则相关SDK和真实协议证据需要重新取得。

真实任务失败时先读取trace/账本/已返回结果定位，不反复“再跑一遍看看”；新增监测点应对应怀疑，例如等待门是否触发、最终wire固定包占比、哪个cohort不合格。监测点先记入开发报告，之后再决定是否展示给用户。

## 5. 性能计量：时间到底算哪一段

### 5.1 六种时间必须分列

| 时间名称 | 起止/计算口径 | 对用户表示什么 | 不可混算 |
|---|---|---|---|
| `capture_wall_ms` | 本订阅开始至停止/封存截止；另列gap与实际覆盖并集 | 监控了多久、缺了多久 | 直播监控30分钟不意味着Agent分析耗时30分钟 |
| `data_ready_to_delivery_wall_ms` | 选定ArchiveRevision及所需已确认dataset可用时刻T0，到正式DeliveryReceipt提交T1；若用户晚于T0发起另列`request_to_delivery` | 资料就绪后的真实交付等待；是优化主指标 | 排队/重算/模型/本地计算都在其内；不能只报模型活跃时间冒整体 |
| `user_wait_ms` | 持久WAITING_INPUT区间的并集，明确开始/结束/原因 | 花在补资料和人工确认的等待 | 不能静默从总wall删去；可另报`wall_excluding_user_wait` |
| `job_and_queue_wait_ms` | 受理排队、provider并发排队、异步job等待分别记录 | 系统在哪些地方排队 | 外层任务等待可能包含子job本身，不能重复相加 |
| `active_compute_union_ms` | 定义为本地实际执行span时间区间并集，含解析/统计/校验/投影等，阻塞provider等待另列 | CPU/本地工作的可观察占时 | 不是CPU占用精确计量；需要CPU time另加process/thread指标，不能从wall猜 |
| `provider_wait_union_ms` | 模型请求发送至响应/失败的区间并集；主/子/摘要/分类都有purpose | 真正花在模型等待多少墙钟 | 两个并行60秒请求union约60秒；attempt时长sum约120秒，两者都可显示但必须命名 |

附加：`critical_path_ms`从有父子/依赖边的span重建；`sdk_invocation_wall_ms`包含该次模型、工具、等待但不含整个监控时长。多个并行stage各有自身elapsed，按依赖计算总路径，不能相加得“总耗时”。`observed_active_union_ms`只能称已埋点范围；未埋点DNS/TLS/内部服务器推理保持未知。

指标输出包含：`run_id/build_id/scenario_id/attempt_index`、T0/T1、结果/缺项、输入规模、缓存cold/warm、各stage start/end、duration_ns、UTC wall time、source_instance/boot_id、真实attempt数量/用途/usage、工具总量/缓存/无新增信息计数、摘要前后输入量。原始测量用`perf_counter_ns()`，ms显示可保留三位小数；这表示记录分辨率，不保证0.001ms测量准确度。跨进程/重启不能直接相减不同monotonic时基。

### 5.3 初期目标和失败解释

- 正确性目标：fixture预期事件集合去重后100%可核；所有不能恢复的缺口100%显式列出；R中的数值断言100%匹配；不泄密、无未经确认直播写入。
- 调查效率目标：已就绪成果不重新付费生成；成功finish不多一次模型；人工/job等待不轮询模型；同依赖缓存命中可复用；无信息重复有界纠偏。
- 时间优化目标：小型资料就绪到复盘交付尽量接近或低于600,000ms，同时披露质量/覆盖；这是待测优化目标，不是SLA，也不为达标取消必要事实/报告范围。
- 源摄入可设单独本机压测profile，例如100事件/秒持续60秒，记录p50/p95写入/消费滞后、峰值队列与封存耗时；该profile是工程提议，必须记录机器和磁盘条件，不冒称真实直播流量保证。
- 三次真实任务只能报告min/median/max、每次明细与达标次数；样本仅3次不估可靠p95或声称提速有统计显著性。若要比较旧/新方案必须同fixture、同缓存、同模型/设置、同构建范围；旧播前11分钟等不能直接当新复盘的基准。

### 6.2 三次比较样例

拟建立`SIM-SMALL-01`：2个固定商品、每品2版，4个真实结构播放项；1项长开场/其余短开场；约12分钟合成播放journal，60条有标识合成评论，含购买意向、询问、抱怨、重复与歧义；12个有标识合成订单及2个成功退款，并有跨cohort/非本场反例；已确认CSV/XLSX映射；无伪造真实平台身份。

此规模只是首轮可控制fixture，生成时冻结准确数字、原件hash和全部预期，不让“约”进入实际验收断言。订单和内容均`synthetic=true`，输出必须写模拟经营分析；真实的是本机授权模型工具调用与程序运行，不是真实成交。

| 顺序 | 具体执行计划 | 防止不可比 |
|---|---|---|
| P0 预检 | L0–L3通过；manifest冻结；provider状态只读核验；剩余测试预算明确；trace/数据根可写；不需要复制令牌 | 发现阻断先修，不用真实任务替代调试 |
| P1 第一次 | 独立隔离Review数据根，从同一已确认资料/归档快照开始；指标/分类/Agent会话cold；记录完整span与成果 | 不混入旧会话、旧子结果或缓存；开始T0定义固定 |
| P2 第二次 | 同build、同fixture、同公开模型参数与预算、另一独立cold数据根；模型仍可自主选择调查路径 | 不为了工具路径相同而强制固定DAG；差异作为规划行为记录 |
| P3 第三次 | 同样配置再跑，保留每次正常/partial/失败，不只挑最快成功 | 中途若改代码/政策/prompt，停止这一组，升build后重新取得可比证据；不能混用 |
| P4 分析 | min/median/max、所有阶段/attempt用途、缓存与重复、质量/覆盖/成本/unknown，生成结果表 | 平均更快但漏要求不算改进；失败时间也列，不能删掉 |
| P5 有必要才补 | 仅新疑点追加warm复用、重启恢复或指定故障样例 | warm单独列，不与cold三个混算；网络故障样例优先fake而非付费反复制造 |

主模型决定是否委派两子Agent，三次不要求相同工具轨迹；必须满足同一Goal、报告证据与预算边界。并行/错误/等待/摘要的机制已由L2可确定性验证，真实小型用例不需要每次故意触发所有故障。

若自然授权续期未到期，不为凑场景强制刷新真实旋转凭据；续期/并发旋转/未知状态先用fake transport验证，真实自然触发只记录有无发生。未发生不能写“真实自动续期已通过”。

## 7. 每批之后的结构复查：防止越改越乱

每次完成一批同根因修改后，在进入更贵层级之前做一次结构审查；W5合并和W6冻结前再次全量审查。记录不是可选心得，需随测试报告交付。

| 审查项 | 具体查法 | 通过/不通过判据 |
|---|---|---|
| 唯一规则正本 | 列“业务规则→唯一函数→调用者→R编号”；搜索同义旧函数/旧配置 | cohort/评分/权限/完成/采纳只有一套权威实现；adapter只转格式，无第二公式 |
| 新旧路径收口 | 画实际调用图，核API→Runtime→tools/flows→service；搜索旧tool名与遗留fallback | 不保留“新流程失败自动走旧宽松路径”；兼容路径显式版本化、有期限与反例 |
| DTO与序列化 | producer/consumer/schema/ToolSpec/Skill名称比对；导出实际模型schema | 不出现多个近似Ref或任意dict接缝；null/单位/时间/来源/错误口径一致 |
| 中间件职责 | 对照四M真实hook和SDK实际栈；查重复before_model/摘要/重试 | 没有为了一个case再加互相冲突的完成门；成功写COMPLETED后不被Scope误判失败 |
| 共享上下文/状态 | 并行测试ContextVar、单例mutable字段、子state输出、checkpoint namespace | 无global current_role；无子report_ref污染主；无跨run缓存/票据串线 |
| 副作用和事务 | 查所有command/写DB/API调用者及effect分类、父子operation key | 模型无直播写；采纳唯一人工入口；同stage幂等/跨stage不同key；未知先对账 |
| 重复与性能 | 对trace作同tool+args+依赖聚类，查重复零增量、摘要、job轮询 | 合法补view不被禁止；无意义重复有证据减少；不是隐藏日志制造“更少调用” |
| 失败与恢复 | 检查断点前后正式成果、unknown、usage、wait/terminal状态 | 结果已收到可继续利用；取消后不晚到复活；缺原文不假重校验 |
| 依赖与部署 | diff package/lock、资源owner、feature gate、启动加载build | 不为单个功能引入未经核验大框架；Review失败不拖原产品；无服务端口/启动器蔓延 |
| 文档与弃用 | 同步00–07、schema/Skill/迁移/fixture；给废弃路径明确删除/适配表 | 没有仅靠解释“旧的是旧的、新的是新的”同时保留两个默认运行入口 |

结构审查发现问题应归到根因批：例如“完成身份太宽”同时修改repository查询、tool回执、middleware读取、fixture，而不是在四处各加不同条件。每批产出一张`rule_ownership.json`或等价表，并记录新增/移除分支、兼容期与受影响测试。

新发现的问题允许调整方案，但必须更新唯一落点与R编号，不能只在提示词追加一段“不要再这样做”。Skill负责方法、middleware负责运行边界、普通服务负责语义与原子性；三者不能各自复制同一规则。

## 8. 最终交付与未通过事项怎么呈现

最终报告至少给：

1. 本次build与manifest链接，新增/复用/改动模块及实际依赖版本。
2. R01–R50逐项状态：`pass/fail/not_run/blocked/not_applicable`，证据ref与原因；not_run不能以其它层通过替代。
3. 正常全链、无经营明细降级、等待续办、取消/重启、未知结果、人工采纳各自的实际轨迹与产物refs。
4. 三次同版真实任务逐次耗时/用量/覆盖/结果；哪些最小span可测、哪些仍未知；十分钟目标实际达到几次及瓶颈。
5. 问题表：新/旧、根因、严重度、代码位置、复现路径、修复或降级、对应R、下一步。已修旧问题不能继续列为当前复现，未测也不能叫已解决。
6. 结构审查结果：是否还有并列旧路径、重复schema/公式/授权/完成门、共享可变状态、SDK假设不符；若有P1不进入交付。
7. 操作说明：Agent工作区入口、左侧数据与四类评分/缺项、右侧过程开关、如何补报表、如何人工采纳下一场；不要求用户复制模型令牌。

可交付判据：关键数据与范围/权限/统计/完成/恢复/采纳R无未解P0/P1；数据不足的指标有明确资格降级而不造分；同build证据可追溯；原声播与播前关键操作保持可用。没有实际平台延迟和报表样本验证时，应明确“哪些能力待现场验证”，不把L5缺证据掩盖为上线效果已经证实。
