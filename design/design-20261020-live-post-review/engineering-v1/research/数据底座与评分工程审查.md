## 2. 构建时先锁定的12条不变量

| 编号 | 必须由程序保证的规则 | 针对旧工程反复修改的教训 |
|---|---|---|
| D01 | 每个已采用结果必须绑定明确的account/session/archive revision/policy revision，不能靠聊天摘要恢复 | 摘要丢状态、恢复后反复全量读库 |
| D02 | 来源身份在接收入口冻结；异步writer不得用落库时的新场次状态重写旧事件 | 引入队列后出现跨场串数据 |
| D03 | source event + source outbox同声播DB事务；review事件 + review cursor同review DB事务 | 将两个DB写入误当成一个原子操作 |
| D04 | outbox以至少一次交付＋唯一键幂等；不宣称外部平台/播放器恰好一次 | 断线后盲重试、重复累计 |
| D05 | 缺失是null+reason；只有已验证完整来源的真实零才是0 | 缺交易来源却得到零成交/高退款表现 |
| D06 | 金额只用整数最小货币单位及显式币种/指数；UV不可跨桶直接相加 | 浮点金额、重复人次、SKU父订单金额倍增 |
| D07 | 同一订单/退款行的多次导出是不同观察版本，不是新增成交 | 重复导入导致支付/退款翻倍 |
| D08 | 每个复盘archive revision不可变；迟到数据只生成新修订 | 旧报告分母悄悄变化、确认与实际版本脱节 |
| D09 | 播放的计划、播放器媒体回执、本机有声、平台可听四层证据分开 | `source=obs`、已准备音频被当成真正实播 |
| D10 | 内容分、经营目标分、历史相对分、数据覆盖分分别保存，不互相补分 | 高内容分掩盖低成交/缺数据 |
| D11 | 统计/资格/缓存由确定性函数实施；主Agent自由选择调查工具和先后顺序 | 固定巨型流程限制自主性，或让模型反复处理机械步骤 |
| D12 | 模型可读摘要和分页面板，但正式原件、行级来源、失败尝试留在受控存储 | 每次重复全读、摘要替代事实正本、失败用量丢失 |

## 3. 场次、来源、共享采集租约

### 3.1 三种身份不能合并

| 身份 | 示例形状 | 生命周期/用处 |
|---|---|---|
| 业务场次 | `review_session_id`，绑定声播 `voice_session_id` 与可选 `platform_session_id` | 一次商家的直播；两场复用同一外部房间仍是两个场次 |
| 采集源 | `source_key=(account_id,platform,external_room_id)` | 可服务多个只读订阅者；不等同直播场次 |
| 采集运行实例 | `capture_id, producer_instance_id, boot_id` | 显式重连或进程重启可能变；断线不自动创建新业务场次 |

`source_binding`保存不可变绑定修订：声播room/session、account、platform/external_room、purpose、publication/compiled_plan/queue/approval精确ref、绑定有效起止、来源实例、匹配依据、时区、synthetic标志。`own_room`与`external_test`分开；外部测试源不得进正式商家成绩。当前插件没有平台真实场次ID时保持null，不用外部房间号冒充。

默认同一声播业务场次同一时刻仅有一条有效经营绑定；绑定变更须关旧有效区间、产生新revision并校验期望revision。仅房间名字相同或时间接近不能自动合并。若来源接收时间的可能区间跨两场边界，保留 `ambiguous_session`，不择优归入任一场。历史已丢字段不能事后补造。

### 3.2 最小租约服务（程序，不是模型工具）

```python
async def acquire_source_lease(scope: ReviewScope, source: SourceSpec,
                               subscriber_id: str, operation_id: str) -> SourceLeaseReceipt: ...
async def renew_source_lease(lease_id: str, expected_revision: int) -> SourceLeaseReceipt: ...
async def release_source_lease(lease_id: str, operation_id: str) -> SourceLeaseReceipt: ...
```

声播的唯一source manager拥有连接；复盘侧只注册/续订/释放订阅。建议首轮租约TTL 30秒、每10秒续订，这些是待压测配置。手动UI连接保留独立manual lease。复盘结束只释放自身lease，不能断开UI/其他订阅者仍在使用的连接。全无lease且无manual intent时才停止源。应用重启后先标 `reconnect_required` 与缺口，沿现有“授权意图保留、显式连接”语义恢复，不凭旧lease自动连接陌生平台房间。

租约从未授予直播控制权限；不能插播、调序、改稿、改优惠。为UI与复盘各开一个平台WS会增加重复/不一致，不采纳。

现有 `connect_source():463–478` 每次连接会先 `_disconnect(..., persist=False)` 再建新capture，**复盘acquire不能直接反复调用它**。新增manager应先核对既有active source：同voice room、同external room/purpose时登记lease并采用当前capture；不一致时返回 `SOURCE_BINDING_CONFLICT`，不能静默替用户改来源。首版同一voice room的UI/复盘共享是必需项；跨本地room共用同外部源若尚未实现明确fan-out绑定，则拒绝第二个正式采集而不是偷偷多开WS。显式手动“重新连接”仍可创建新capture，但须保存新旧边界/缺口，不创建新业务场次。

### 4.1 新增声播文件与最小接点

|---|---|---|---|
| `app/review_telemetry/contracts.py` 新增 | `freeze_ingress_context(...) -> IngressEnvelope` | 接收时room/session/binding/capture/source event和时钟→冻结信封 | 不在writer内重读当前session |
| `app/review_telemetry/storage.py` 新增 | `append_outbox(connection, envelope) -> SourceOutboxRef` | 已开启的现有voice DB连接→outbox行 | 不自行开第二连接/提交；由调用者事务提交 |
| `app/review_telemetry/leases.py` 新增 | 上节三租约函数 | source+subscriber→lease | 唯一source manager；短事务/已有CONTROL_LOCK |
| `app/review_telemetry/writer.py` 新增 | `enqueue(envelope)`、`flush_through(fence)`、`health()` | 冻结接收项→有界writer队列/持久水位 | 无LLM、无网络归档；SQL写移出asyncio事件循环 |

| `app/live_source.py:_persist` 修改 | 现有event/records/totals事务内追加outbox | unique event→同事务outbox | 重复source key不重复统计；未知类型不进入这些业务计数 |
| `app/server.py:db` 最小兼容扩展（如需） | `db(*, write=False)`转发既有store.transaction | 保留旧调用；新增写路径可用BEGIN IMMEDIATE | 不另建相同业务数据库，不全局重写旧storage |
| `app/review_telemetry/routes.py` 新增 | 受本机认证的增量读/水位/订阅接口 | typed scope+cursor→有界page | 不向模型暴露collector token、任意路径或自由SQL |

声播现有store位于 `app/prelive/storage.py`：SQLite WAL、foreign_keys=ON、busy_timeout=15000、事务write=True用BEGIN IMMEDIATE。复用这一owner，迁移只在启动做一次；不要每次取统计时扫描历史/跑大迁移。新增worker的短事务不得在持锁期间做网络、模型、文件解析或UI广播。长期SQLite锁等待不得阻塞播放器asyncio事件循环；用worker线程/短批写，并监测实际阻塞。

### 4.2 采集项实际顺序

1. WS收到collector已交付JSON，立即取UTC高精度、monotonic、producer_seq、capture、当时的voice_session/binding revision；先冻结，后排队。
2. 最小校验与受控原件存储：保留接入边界实际收到的JSON，不承诺完整平台protobuf。未知method保留method、字段schema/长度、受控样本ref；错误保存error_code/位置，不输出凭据或原始exception repr。
3. 一个有界source writer按producer顺序规范化/写库，避免并发writer重排。可短批（建议最多50项或50毫秒触发一次，均为待压测配置），后台归档消费者不在接收关键路径。
4. 已知事件同voice事务：`INSERT event(UNIQUE source-key)`→写兼容records/totals→`INSERT outbox`→commit。outbox保存已冻结身份、source_event_id与受控payload/ref。原事件插入被去重时不再增加totals，重传接收次数可单列遥测。
5. system/connect/retry/parse_error/unknown_method走同一outbox表的不同event_type；不把它们混入评论/订单计数。
6. commit后更新已持久水位和有界UI状态。广播失败不回滚已持久事件；UI重连可读快照。review消费者按outbox游标独立拉取。

队列默认上限建议4096项，以真实压测修订；不能无界占内存。超载/写盘失败要形成 `coverage_gap`、最后成功水位、已知丢弃/未知区间，恢复时首先补记，不伪造完整。瞬间进程崩溃可能丢失尚在内存的接收项；因此完整度只能按“已持久且有健康证据”的区间计算。不能宣称进程崩溃绝无丢失，也不为监控服务失败自动停止现有直播。若后续实测必须更强恢复，再评估磁盘spool，不先引入分布式队列。

### 4.3 源端和review端两个事务怎样配合

```text
V1 voice transaction：原事件/健康事件 + outbox提交
R1 review transaction：按唯一键插review_ingress + 前移consumer_cursor提交
V2 voice：收到R1明确回执后更新该consumer已确认水位
```

V1后R1前崩溃：重拉；R1后V2前崩溃：重拉会命中唯一键，不重复指标；V2不得早于R1。source cursor是范围边界，不是消息条数。一个source event可以被两个明确业务订阅者独立读取，但同一个复盘场次不得重复累计。cursor不可由模型任意推进。

outbox清理先看全部有效consumer确认水位和保留策略；已失效consumer落后时保存 `replay_unavailable`，不能静默跳到tail。早期先不自动删原始业务事件；为磁盘容量、脱敏原件保留期和删除审计留受控配置，不让模型删除证据。

### 5.1 文件与DB不共享事务：怎样避免半成品

1. 新证据在受控临时目录写完、fsync/close、计算hash，原子rename到内容地址路径。
2. DB事务登记artifact＋业务引用；文件已存在同hash则核验复用。
3. DB提交前崩溃只会遗留未引用文件，由维护命令按保留期清理；不能将未登记文件算已导入。
4. DB存在ref但文件丢失/损坏：返回 `EVIDENCE_MISSING/HASH_MISMATCH`，阻止该依赖结果沿用；不重新编一份“相同原件”。
5. 分析原件与可显示投影分开；日志里只保留ref/hash/字节数/错误码。Windows受控目录ACL、HMAC秘钥使用本机安全存储；不把原始买家联系方式、cookie、鉴权头放入模型上下文。

当前normalize的viewer_hash是无盐SHA截断，不应冒称已经采用作用域HMAC。新接收边界有原始user ID时生成账户/场次作用域HMAC并最小化保存；旧资料只有旧hash的保留legacy_hash类型，不从hash猜回原ID，也不能声称可与新HMAC或交易买家跨域准确匹配。

|---|---|---|
| `server.py:Room.set_current` | `attempt_created`、必要时前attempt中断 | attempt、epoch、cycle、occurrence、compiled_entry、product/script/module/sentence、publication/queue ref |
| `prepare`就绪/失败 | `audio_asset_ready/prepare_failed` | attempt、audio ref、受控error_code；音频就绪不是实际发声 |
| `Room.acknowledge`校验成功后 | `media_playing/progress/waiting/ended/failed/blocked` | player_owner/client_instance/client_event_id/client_seq、server_receive clock、client媒体position、muted/volume、ack_validated=true |
| `Room.action`人工操作 | `human_control_requested/accepted`和相应状态变化 | action_id、类型、前后queue ref、affected attempt、actor；不能把已接受命令当媒体实际已执行 |
| `advance`循环边界 | `cycle_started` | cycle_index单调增加，原队列position不重新算长/短开场 |
| `/ws`owner接管/断连 | `player_connected/owner_changed/disconnected` | source label与可验证证据层分列；断连/stale结束已知播放段 |
| service停止/重启边界 | `session_closed/process_started/recovery_gap` | 最后持久水位、pending区间、结束原因；重启不把未结束attempt标ended |

ACK输入在校验owner/epoch/attempt后立即冻结身份和接收时间；client新增稳定client_instance/boot_id、单调client_seq和client_event_id，重发同一个事件必须保留同ID。旧客户端缺这些字段进入compatibility_partial，不伪造精确去重或校时资格。`ready`下主动补发playing与原生onplaying可能重复，派生状态机应在已playing时幂等，不新建第二段。

客户端progress约350毫秒发一次，首版可每1秒持久一条progress/heartbeat并保留所有状态转移；采样间隔是配置，不能混成毫秒级观测保证。记录 `Date.now()` 和 `performance.now()`、server_received_utc/monotonic；客户端和服务器单调时钟属于不同domain，不能直接相减。

### 6.2 journal与现有内存状态并非一个数据库事务

当前Room状态是内存，不能承诺“journal提交与所有播放状态原子”。设计将遥测记为**观察事实**：`media_ended`只证明合法owner报告媒体结束，`control_accepted`只证明后端接受请求。producer按同源顺序持久，seal等待已接收水位flush；队列/磁盘失败则质量降级但不为分析中断声音播放。重启后未结束区间记unknown/interrupted，不能从理论音频时长补ended。

可在关键ACK路径用一个本地短追加（异步执行，不等远端review）提高落盘可靠性，并做延迟验收；但不得把“落库后服务器尚未来得及advance即崩溃”解释为用户已经听到下一句。若实施选择全异步queue，必须在run-start/run-stop和seal显式记录已处理/未落盘水位，并接受崩溃窗的缺口。二者实现只能选一套明确语义，不能同时保留多个相互矛盾的“可靠日志”。首版推荐有界异步producer＋落盘水位＋保守质量门禁，以免监控阻塞现有播放器；磁盘健康时目标1秒内flush，实际结果单列。

### 6.3 区间重建的固定函数

```python
def rebuild_playback_timeline(events: Sequence[PlaybackJournalEvent],
                              snapshots: ContentSnapshotIndex,
                              policy: TimelinePolicy) -> PlaybackTimeline: ...
def align_event_interval(event: NormalizedEvent, clocks: ClockBundle,
                          mode: Literal['cooccurrence','response'],
                          reaction_seconds: int) -> AlignedInterval: ...
def assign_pure_module(interval: AlignedInterval,
                       segments: Sequence[ConfirmedMediaSegment]) -> TimeAssociation: ...
```

状态机：attempt_created→ready→playing segment1→waiting/pause关闭segment1→playing segment2→ended关闭segment2。每次retry/真正新播放创建新attempt；暂停恢复不是新商品曝光。实际播放秒数是已确认segment并集；5秒＋暂停10秒＋5秒＝10秒，不是20秒。同一句循环播放可同source_sentence/audio ref，但attempt/cycle不同。

留存/曝光的高等级证据仍需来源验证：HTMLAudio回执≠实际有声≠OBS采集≠抖音观众听见。平台延迟用至少5个分布在开中末的实测音频标记建立区间与漂移；平台评论运输延迟另测，不能拿推流延迟替代评论接收延迟。

本地模块区间[s,e)，平台事件发生可能区间[u,v]，已校准推流延迟[d_low,d_high]、反应滞后[0,R]时，相关本地内容范围 `[u-d_high-R, v-d_low]`。整个范围落在同一实际segment/module才标pure；否则mixed/unassigned。分钟桶不可扩展为60个伪秒点；跨模块分钟桶不按秒拆UV/订单。一条事件主表最多一个严格归属，探索15/30/60秒及支付1/3/5/10分钟窗分别保存，不能累加为更多成交。

导入整稿 `origin=imported` 当前整体作为product_intro；保留merchant_original评价，不能语义分段后冒称原生五模块时间。活跃编译仍是一个开场＋intro＋selling＋campaign＋cta（无活动可四段），不为评分恢复transition；位置1、6、11用长开场，手动跳播仍按原保存位置。

## 7. 封存、迟到数据和修订

```python
async def request_close(session_id: str, expected_revision: int,
                         operation_id: str) -> CloseReceipt: ...
async def seal_archive(session_id: str, fence: ProducerFence,
                        mode: Literal['complete','partial'], operation_id: str) -> ArchiveRef: ...
def append_archive_revision(base: ArchiveRef, changes: ArchiveChangeSet,
                             expected_head: ArchiveRef, operation_id: str) -> ArchiveRef: ...
```

1. `collecting→closing`：冻结本场结束时间和接收fence，保留仍服务其他订阅者的采集连接，不用断开共享源来表示本场完结。
2. producer报告已接收seq、已持久seq、pending与drop/unknown。等待到fence的flush；建议初始drain上限10秒，超时出partial而非无限等。
3. review消费到固定outbox截止水位；验证原件、内容快照、健康、时钟、事件数/范围，生成manifest。只有manifest/引用自身一致才能seal；complete只指约定归档完成，不证明全平台数据全收、经营成功或退款最终成熟。
4. 同一review transaction写archive revision r1与head CAS。报告/指标固定引用r1。
5. 关播后付款/退款、迟到评论、人工报表补充生成r2，parent=r1，列新增/替换来源与变化原因。旧r1报告/分数不重写；前端提示可用r2重新复盘。
6. 仅因新报表不相关字段变化，不使所有内容审核重跑；由实际依赖hash决定失效。若内容事实被撤回则相应审核/建议不可继续复用。

冻结水位是每source/capture的真实高水位和当前manifest列表，不是按全局seq差估事件量。只读归档历史时提供 `from_start/from_seq/to_seq/time_range` 显式参数及返回expected_count/has_more/next_cursor；现有after=0 UI保持不变。

## 8. 手动经营报表：预览、映射、检查、正式采用

### 8.1 为什么不直接把Excel扔给模型计算

模型可以帮解释未知表头、建议映射、阅读备注；它不能决定金额单位、订单主键、跨桶去重人、同单退款队列，也不应该用自然语言重新求和。首版只支持已授权的CSV/XLSX经营明细/汇总；图片/PDF经营报表可保存为证据但不直接升格可计算交易来源，除非经过逐值复核的新adapter。不得借用商品资料OCR结果来悄悄计算GMV。

| 步骤 | 函数签名（拟议） | 做什么/返回 |
|---|---|---|
| 保存上传 | `register_export(upload_ref, scope, source_meta, operation_id)->ImportRef` | 路径/大小/压缩展开配额、mime/header、hash；存受控原件，拒绝路径越界，不执行宏/公式/外链 |
| 读取预览 | `preview_export(import_ref, parser_policy)->ExportPreview` | csv标准库固定编码候选并回显；xlsx openpyxl read_only，data_only；未缓存公式值为unknown，不执行Excel公式；列/行/来源样例脱敏 |
| 字段/口径映射 | `propose_export_mapping(preview_ref, template_ref?)->MappingDraft` | 已知模板确定性识别；未知表头由模型辅助提议；关键口径需用户确认，不取模糊最大相似度自动合并商品 |
| 校验 | `validate_export(import_ref,mapping_ref,scope)->ImportValidation` | 粒度、时区、时间窗、单位、父子订单、重复、缺关键字段、SKU映射、控制数/金额对账；给行级错误和缺项 |
| 提交 | `commit_export(import_ref,mapping_ref,validation_ref,expected_session_revision,operation_id)->ImportReceipt` | 固定映射/源文件hash后同review事务提交facts与ref；参数变更要新preview/validation，旧确认失效 |

可选模板应标明来源页面/版本、导出生成时间、数据统计时间窗、币种/金额字段定义、订单粒度(parent/child/order_item)、PV/UV、行是否快照或增量。没有真实样表前不能预先宣布当前抖店某字段永远可导出。

### 8.2 导入层必须处理的反例

| 问题 | 正确行为 |
|---|---|
| 一父单总实付100元，两个SKU行都出现父单100元 | 不sum为200；需要真实子单/行级实付或授权分摊规则；无法确定则只父单总额，不评SKU成交 |
| 两份重叠导出包含同一已支付订单 | 保留两份原件和来源行，projection按已确认权威观察版本选一份；不双计 |
| 同订单退款申请100元、后来成功退款60元 | 只把成功60计入退款；申请不是成功，状态快照不能sum成160 |
| 订单有多个独立部分退款 | 用稳定refund_id+order/item关联累计真实成功事件；同退款多状态取当前观察版本，不重复事件 |
| 币种未知，100是元还是分不明 | amount_minor=null，阻止经营金额分，列必填映射；不让模型猜 |
| XLSX金额是带千分位/货币符号的文本 | 严格Decimal解析、已确认币种/单位换算；超过合法精度或范围报错，不用float四舍五入掩盖 |
| 源是按分钟UV，两个桶各100曝光/10点击 | 保留每桶；没有整体去重不能合成200曝光/20点击=10%整模块UV率 |
| 支付明细里没本场归属，只知道支付时间相近 | 不能自动认领本场订单；若来源仅覆盖整场权威汇总则按汇总级展示 |
| 商品名称近似但SKU不明 | unresolved_product_mapping；用户指定后生成mapping revision，不能覆盖商品库 |
| 一行坏数据 | 原行+错误码保留；可提交partial但必须显式缺口，不能静默删行后宣称控制总数一致 |
| 买家姓名/电话/地址 | 不进Agent。原件受控保留，分析投影只保留必要HMAC/opaque订单与SKU关联；公共观众ID与交易买家ID不可强行join |

首版必填最低：source、scope/account、export/统计窗、timezone、grain、row semantics、货币单位（涉及金额时）、正式商品/SKU映射或明确只有全场、可追溯行来源。缺点击曝光仍可算有资格的净额；缺金额可做互动内容版，不把缺可选数据当整个Agent报错。

## 9. 订单、支付和退款队列：函数必须按定义实现

```python
def select_created_order_cohort(facts, scope: CommerceScope,
                                 created_window: TimeWindow, grain: OrderGrain) -> OrderCohort: ...
def evaluate_cohort_payment(cohort: OrderCohort, observations,
                             as_of: AwareDatetime) -> CohortMetric: ...
def select_paid_cohort(facts, attribution: AttributionSpec,
                       grain: OrderGrain, as_of: AwareDatetime) -> PaidCohort: ...
def calculate_successful_refunds(paid: PaidCohort, refund_observations,
                                  as_of: AwareDatetime) -> RefundMetric: ...
```

**创建→支付**：C是指定本场/商品/创建窗的订单集合；分母为同grain去重的|C|，分子为C中截至as_of已支付的成员数。某分钟3笔旧单付款、2笔新建单，不能算150%；应查2笔新单自己的支付状态。

**支付与退款**：P是有权威本场归属的固定支付订单/行队列，paid_minor为P按既定金额口径的原实付，refunded_minor为P关联的成功退款截至as_of总额；净额=paid−refunded。退款观察龄期和历史一致；D+1的零退款不能与历史D+14比较。退款不得用另一个订单群体或全店跨期分子。缺退款明细只显示“退款未补齐”的支付初报，不命名成熟净额。

**看播/点击→支付**：必须有同粒度嵌套用户队列或平台明确同口径原生率。仅有观看UV与付款人数两个汇总，不证明分子属于分母；禁止跨公共观众HMAC和商业买家ID猜测关联。保留平台汇总原指标也必须携带其原生定义，不自行赋予个体归因语义。

**每小时**：完整整场600元/60分钟=600元/小时；采集器漏10分钟不把分母改50分钟变成720。若只评价可观测时段，要同时限定该时段的经营分子，不能用整场分子除局部时长。

### 10.2 首轮数值规则，全部是可版本化项目政策

| 评分卡 | 程序规则 | 不可越过的资格 |
|---|---|---|
| 经营目标完成 | `min(100,100*X/goal)`；保留未封顶完成率与差额 | goal>0；净额来源和as_of明确；缺goal/金额→null，实际经营事实仍显示 |
| 历史越高越好 | r=X/B；r≤1时60r；r>1时min(100,60+80(r−1)) | B>0，可比历史冻结；有上界率且1.5B>上界时用T=min(1.5B,U)重映高段；B=U→null |
| 历史越低越好 | 0≤X≤B：100−40X/B；X>B：max(0,60−60(X/B−1)) | 不把沉默/少提问默认视为好；退款必须同队列、同龄 |
| 内容完成 | 每模块4项，每项0/12.5/25，程序加总 | 某项依据未知→该项null、整段待补证，不对剩余项重标100；严重错误独立flag |
| 数据覆盖 | Q01/Q02/Q03各自×100；模块摘要取必需项min | 必需项任一未知→摘要null；Q04/经营来源额外门禁，不能被高覆盖补掉 |

统一实际来源枚举只在公共DTO定义一次：`public_platform/local_player/official_merchant_export/manual_note/synthetic`，旧草案/第三方字段在边界映射。`synthetic`不能仅靠文案标识，存储和查询硬过滤，模型不可将模拟场纳入真实历史。

基线初版：28天内最新最多20个合格可比场，商家/账号/商品或SKU、指标、来源、币种、grain、退款龄期相同；价格差≤5%、付费流量比例差≤10个百分点、开播时段差≤2小时是筛选提示，条件未知不默认相同。整场/商品场至少5场，5–9场暂定；模块用专项门槛≥10次且≥3场替代5场门槛，并始终暂定。逐场同口径指标中位数，不用无限累计一场大流量压过其余场。

覆盖初版：Q01观测≥98%、Q02播放器记录≥98%才进入整场模块资格，Q03内容定位≥99%才给整场模块排名；Q04还要求实测延迟/纯窗口。在线候选值未与后台核实不能算人分钟；核实后按最长15秒hold积分，缺口不无穷carry。细句延迟边界宽度>5秒默认不做细句排名。这些都是可调政策，不是抖音行业标准。

Wilson仅对合法二项count（0≤success≤trials，独立观察含义成立）使用；不能套金额、人分钟密度或把多次循环曝光当独立人。分母<100、成功<10、区间很宽提示样本不足；0正预测的意向precision=null，不能设100%。评论初批50条或全部较少样本，商品归属accuracy目标90%、意向precision目标85%，正预测<10标尚未验证；保留TP/FP和抽样方案，而非拿模型confidence当真实概率。

### 10.3 内容审核不每次循环调用模型

复用键必须包含实际依赖：选中稿件/模块ref、product facts ref、customer briefing ref、campaign/current goal ref、rubric/prompt/model version与影响项。整稿四项结构化评估通常一次完成，返回原句ref、事实依据ref、等级、error flags；数值由程序计算。相同文本但商品功效撤回，或优惠本场更改，都不能复用旧审核。对完全相同依赖的50次循环只评一次内容；循环出现次数只影响时间/响应统计。

| 时间线 | `archive_revision+timeline_algorithm+clock_bundle_ref` | 固定修订重用；补回执/校时修订只重建受影响窗口 |

| 基线 | `current_metric_context+policy_ref+candidate_archive_refs` | 固定快照复用；不每轮自动挑新历史 |
| 内容审核 | 上节完整dependency hash | 不因新无关订单重评文稿；事实/活动变化重新评影响项 |
| 评分 | `metric_ref+baseline_ref/goal_ref/assessment_ref+policy_ref` | policy换版生成新score，不回写旧成绩 |

工具层提供 `get_metric_panel`、`build_scorecard`；后者内部机械步骤为资格→必要缓存/计算→基线→映射→引用封装。主Agent可选择只查一个商品、一个分数、一个问题，或调用工具流；不强迫每次跑所有23指标/四卡/两个子Agent。

重复相同读工具直接返回cache_hit/result_ref/available_sections/缺项；“没有新信息但继续同参读取”遥测为no_progress，不以更多LLM调用假装修复。跨阶段state摘要只放已完成/缺项/精确refs；所有内容/数值仍由正式存储读取，不由摘要重建。并行子Agent锁定同archive/policy/baseline，只有各自临时发现，不竞争写最终报告。

## 12. 可观测性：本次必须一开始就留的细粒度数据

| 阶段 | 必须记录的量 | 判断什么 |
|---|---|---|
| 入口→voice持久 | receive_to_enqueue、queue_wait、normalization、raw_write、sqlite_lock_wait/transaction/commit、pending depth、drop/missing | 是否采集本身拖慢或丢失；队列身份是否被冻结 |
| voice→review | outbox_poll/bytes/page_count、replay/dedup、commit、consumer_lag、watermark distance | 是否重复扫历史/错误cursor/积压 |
| 播放journal | ACK reject reason、duplicate、state transition、flush latency、heartbeat gap、binding success | attempt/epoch/owner是否串错，pause/resume是否重复算 |
| 导入 | file_register/parse/map/validation/commit耗时、rows_read/invalid/selected、control-total差异、人工等待独立 | 解析慢还是模型理解慢，金额是否正确 |
| 指标/评分 | cache_hit、input_rows、eligibility reason、calculate/baseline/score耗时 | 重算哪里浪费，缺数据是否被错误补0 |
| 模型分析 | 每次attempt/provider request/公开usage/取消/未知/parse reject、wall time与重试owner | 供应商返回即记usage，再记本地验证；验证失败也不能丢账 |

计时使用同一进程monotonic_ns测elapsed，展示毫秒（并非测量精度必然为1ns）；UTC高精度用于跨源对齐，附precision/uncertainty。人工等待单列，不从总wall time消失。整场采集时长、导入等待、模型复盘计算时长、下一场人工采纳分别报告，不能把直播2小时也算“Agent分析2小时”。P50/P95必须附样本数，单次耗时不命名P95。

建议首轮工程门槛（待真实量级校准）：前台事件循环不被SQLite长锁阻塞；99%的已接收遥测在正常磁盘下1秒内flush；封存10秒内完成或显式partial；同依赖重复指标/评分模型调用=0；1小时/50k事件离线统计目标≤5秒，达不到先记录SQL/IO瓶颈而非砍有效分析。不是已达标承诺，也不强制为追10分钟目标删流程。

## 14. 给总计划的关键结论

1. **优先实现冻结场次身份、唯一source/outbox、player journal和报表口径四件事**。缺其中任一，增加更多Agent/Skill只会更快地产生不可验证结论。
2. 所有精细数字必须带来源粒度和资格；商品整场官方经营分可以成立，即使句级Q04不成立。不能用数据门禁把已有可靠整场经营事实一起抹掉。
3. 评分公式是普通受测函数、数据映射是明确adapter、内容标准放按需Skill、上下文只放索引与正式ref、模型负责调查/解释。这样既减少机械重复，又保留主Agent规划能力。
4. 历史播前三轮迭代最值得前置的不是复制一堆校验，而是唯一正本、精确引用、幂等事务、适量读取、可复用缓存、失败记录和批量故障验收；禁止检查层各自重算同一套规则。
5. 本稿未验证真实导出字段、OBS/平台回听、Social枚举、上游完整性或新的性能门槛；这些是实施验收项，不是设计时可以宣布成功的项目。
