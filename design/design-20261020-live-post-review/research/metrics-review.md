# 播中采集与播后评价：指标、归因和建议契约

修订阅读提示：本文保留初稿指标研究，其“不建议百分制”的旧产品建议已由同目录上级《直播评价体系与数值评分细则.md》（LIVE-SCORE-0.1）替代。当前采用目标分、单项相对分、模块内容分和数据覆盖分分开呈现；仍保留本文的分母、来源和归因约束。最终计分政策以新细则及评分政策JSON为准。

日期：2026-10-20（Asia/Shanghai）。性质：独立设计研究；未采集真实直播，未启动服务，未修改业务代码。适用场景：中小商家、相对固定商品、声播声音人；播中只记录，播后生成复盘，下一场采用建议仍需商家决定。

## 1. 核心结论

评价应分成三张相互解释的表：**经营结果、内容表现、数据可信程度**。最终关注退款更新后的有效成交；互动是解释成交路径的辅助信号。不能把点赞、评论和在线人数加权成一个“成交能力分”，也不能没有订单就宣布直播成功。

首期不建议产生 0–100 总分或先验行业及格线。先回答：本场到底观测到了什么；和本商家同商品、近似价格/流量/时段的历史相比，哪些结果变化；哪些变化与具体话术共现；还缺什么证据；下一次只改变哪些内容来验证。没有合适历史样本时，本场作为基线，不进行好坏排名。

存在三个不同交付级别：

| 本场真实数据能力 | 能交付的复盘 | 不得宣称 |
|---|---|---|
| A：只有声播播放日志和公开评论/点赞/进场等 | 播放完整性、已观察互动、问题与购买顾虑、话术和互动的时间共现、待验证的改稿建议 | 精确留存率、真实成交、退款后效果、商品点击转化 |
| B：A + 授权官方房间/商品汇总导出 | 整场或商品级成交/点击/退款结果，按官方导出粒度做漏斗；和本商家可比基线比较 | 将整场订单按话术时长摊给模块，或给每句话算成交因果贡献 |
| C：B + 带明确商品、房间、业务时间的授权交易明细/细粒度官方趋势 | 商品级、时段级经营结果；具备严格数据条件时展示模块期间或滞后窗的相关成交 | 仅凭“订单付款时播到这句”认定这句带来订单；把相关窗口相加当成独立增量 |

本设计不承诺任何插件一定能取得 B、C 数据。主设计应先查本地适配器和历史实测证据，再生成本场 capability manifest；本文件只规定拿到或拿不到数据时如何评价。

## 3. 首先纠正实际话术结构

当前声播代码有七个历史模块键，和“一版播放七个模块”不同：

- `app/prelive/module_generation.py` 的键为 `opening_long`、`opening_short`、`product_intro`、`selling_points`、`campaign`、`cta`、`transition`。
- `app/prelive/playback_compiler.py` 的实际生成稿编排是：**选中的一种开场 + 商品介绍 + 卖点 + 活动 + 促单，共五个模块**。第 1、6、11…个保存的商品版本位置选长开场，其余选短开场。手动跳项仍按原位置。
- `app/prelive/whole_script_generation.py` 明确不生成衔接模块。不能为复盘另加复杂衔接。
- 导入原稿保持原文，通过 `product_intro` 承载，不应凭空认为原稿已分五段或七段。
- 互动目前可在句子 `kind=engagement` 中出现；可加分析侧内容标签，不应在报告里虚构一个已经存在的独立互动模块。

因此评价对象由**实际播出日志**决定，保留 `module_key`、句子标识、原稿标识；分析标签是另一列。原稿若需要辅助切段，结果必须标 `inferred_section`，不能覆盖真实播放结构。长、短开场不能互相当作同一种内容直接排名。

## 4. 具体需要保存的数据

### 4.1 声播内部事实（采集基座，首期必须）

| 数据组 | 最小字段 | 使用目的 |
|---|---|---|
| 场次身份 | `session_id`、平台房间真实 ID（可空）、商家/账号 ID、开关播业务时间、时区、实际连接区间 | 保证场次不串联；没有平台房间匹配时不得归入平台成交 |
| 播前冻结快照 | 商品 ID/修订/哈希、SKU、商品名/别名、日常价/本场价/币种、优惠条件、有效起止、可售/库存已知状态、语言、TTS 提供方/音色/语速、主题 | 解释价格、库存、语言等变化，定位可复现的下一场改动；不是重新分析全量商品资料 |
| 实际队列与执行 | 队列修订、`occurrence_id`、保存位置、循环编号、实际执行序号、商品/话术方案及修订、所选长/短开场、模块/句子 ID、文本哈希 | A 的第 1 版播两轮是两个 occurrence；不会被视为同一次播放、也不会把旧稿表现归到新稿 |
| 音频实际状态 | 准备、播放器开始、结束、中断、跳过、暂停、恢复、错误；客户端时间、服务端时间、单调时钟时长；音频 ID/哈希 | 以实际已播放而非排队/生成完成判断内容曝光。服务器开始返回不等于观众听到 |
| 人工行为 | 用户切换、暂停、重排、插播的事件和理由（若已有），价格/库存外部变化时间 | 当场不让 Agent 自动执行；商家已有人工操作仍照实记录为混杂条件 |
| 播出健康 | 无声、缓冲、断流/断线、播放器 heartbeat、重连、OBS/平台状态（只有真实接入才填） | 内容低互动可能是未正常播出；本地播放器正常不能证明平台推流正常 |

应记录真实 `played_start` / `played_end`。`planned_start`、估算音频时长不得伪装实际播出。没有平台回路，必须区分“本地音频已播”和“平台直播确已听到”。

### 4.2 公开互动适配器候选字段（按本地已实现能力启用，不假定全有）

| 事件 | 最小原始字段 | 能分析什么 | 必须防止的误解 |
|---|---|---|---|
| 评论 | 平台事件 ID、平台时间（若有）、接收时间、消息正文、匿名化用户键、语言、是否已知官方系统消息 | 用户问题、价格/使用/物流顾虑、商品兴趣、重复未答问题，和当时播放内容的共现 | 评论“买了”不是已支付订单；机器人/重复刷屏和真实多人关注不同；昵称不用于推断年龄/收入 |
| 点赞 | 单条数量/累计数量的**原始语义**、事件 ID、时间、匿名用户键（若有） | 点赞增量/速度；仅作为低成本互动线索 | 同一人可多次点赞，点赞数不是人数；增量与累计不能相加 |
| 进场 | 事件 ID、时间、匿名用户键（若有）、事件含义 | 已观察进场事件量、已观察重复进入 | 通知可能被采样或合并，不能声称全量 UV 或完整分母 |
| 在线快照 | 原始人数值、观察时间、字段定义、快照更新序号/来源 | 可观测在线曲线、持续区间下的观众分钟近似 | 在线下降不是精确离场人数，更不证明离开者是刚进的那批人 |
| 关注/分享 | 真正事件的类型、值/数量、时间、匿名用户键（若有） | 已观察关注/分享动作 | 普通评论“已关注”不等于正式关注事件；缺失不填 0 |
| 礼物/连击 | 事件/连击 ID、礼物 ID、数量、状态（若有） | 排除娱乐互动对评论/点赞变化的干扰 | 礼物收益不是商品成交；不使用礼物价格推算 GMV |
| 房间状态/系统通知 | 原始类型、状态、时间、房间 ID、断连/结束/错误 | 判断采集区间和异常 | 前端 websocket 仍连着不等于平台有数据或直播仍在播 |
| 商品卡/上架/讲解/购买通知 | 仅当适配器确实解析并实测该消息时保存原字段及商品键 | 辅助说明正在展示何品、可售状态变化 | “有人下单”播报可能非完整或非支付事件；不计入正式订单、金额和买家 |

匿名用户键仅为本场/授权范围内去重，不为跨平台画像拼接；公开用户 ID 不等于已经授权的交易买家 ID，不擅自关联身份。

### 4.3 商家授权数据（取得后才能开启经营评价）

| 数据 | 需要字段 | 获取不到的降级 |
|---|---|---|
| 房间总体 | 真实房间/场次键、统计时段/更新时间、曝光次数/人数、观看次数/人数、人均/次均观看时长、平均/峰值在线、关注/评论/分享人数或次数；各自定义 | 显示缺失；公开事件数独立保留，不能补到官方 UV |
| 流量来源 | 自然/付费/搜索/关注等原始渠道、按渠道的曝光/观看/点击/成交、投流消耗和变更时刻、口径版本 | 不能拆自然与付费时，版本优劣结论降为带混杂提示的观察；不猜平台推荐算法 |
| 商品漏斗 | 平台商品/SKU 键与本地映射、曝光/点击/加购人数或次数、成交人数/件数/订单数/金额、时间粒度、归属范围 | 只能到真实粒度，只有整场汇总就不能按模块拆 |
| 订单与退款明细 | 稳定订单/子单 ID、商品/SKU、币种、下单/付款/关闭/退款发生时间、状态更新时间、支付额、退款额、部分退款、来源场次（若有）、订单取消/风控排除状态 | 只有汇总时保持官方口径，不能伪造单单明细；没有来源场次不按付款时间硬归入本场 |
| 成本（可选） | 商品成本、平台佣金/服务费、履约/优惠承担、投流、TTS/模型费用，各自覆盖范围 | 不计算毛利/净利或付费 ROI；净有效成交不是利润 |

首期可用安全导入官方 CSV/XLSX，不必等待未核实的官方开放接口。导入时预览字段映射、场次/币种/时间口径；订单更新按业务主键合并，不能一份新表又计一遍。

## 5. 数据可信度不是一个分数

每个指标分开附带四个维度，不能用“平台可信”掩盖局部缺失：

1. `provenance`：`internal_playback` / `authorized_platform_export` / `public_connector` / `human_annotation` / `model_inference`。
2. `measurement_status`：`observed`（直接记录）、`derived`（明确公式）、`estimated`（带假设）、`unavailable`。
3. `coverage_status`：`complete_for_declared_scope` / `partial` / `unknown`；说明声明的范围是什么。客户端无法证明平台已发全量，不能仅凭没断网标完整。
4. `attribution_level`：`platform_session_attributed` / `product_attributed` / `temporal_association` / `unattributed`；“来源可靠”与“能归到这个模块”是两件事。

可信标签还需：源 schema 版本、证据引用、数据截止点、分母定义、缺失/冲突原因、统计粒度、适用时区、是否含付费、成熟度。模型给“高信心”不能提升原始数据级别。

## 6. 时间对齐和归因

### 6.1 三条时间线

每条事件保存 `source_event_time`（可空）、`received_at`、`ingested_at`；声播另存 `client_monotonic_ms` 与服务器时钟锚点。统一以 UTC 落盘，界面按 Asia/Shanghai 展示，保留原始时区。校准服务器/播放器时钟偏差，记录估计误差，不悄悄改原始事件时间。

声播本地音频 → OBS → 平台 → 观众，有传输延迟；观众看完 → 输入评论/下单，也有行为滞后。首期用人工标记/测试音频与回看记录测量可观测延迟范围，保存 `estimated_stream_delay_ms` 和不确定区间。没有测过就标未知；不能硬设“零延迟”或默认几十秒。

### 6.2 不同事件的对齐办法

| 事件 | 推荐对齐 | 边界 |
|---|---|---|
| 本地播放状态 | 客户端真实播放点 + 时钟锚定；实际事件区间 | 暂停/切项不使用原排程推断 |
| 有平台时间的评论/互动 | 平台事件时间，保留接收延迟 | 仍不能知道该用户当时是否完整听过该模块 |
| 只有接收时间 | 接收时间区间并标记迟到/时钟不确定 | 模块边界附近事件可关联多个候选模块或“无法定位”，不得强归唯一模块 |
| 官方分钟级趋势 | 对应分钟时间桶，覆盖多个模块时保持分钟粒度 | 不把这一分钟 5 单任意平均给这分钟的两段话术 |
| 已知支付/订单时刻 | 同商品、同场次已归属订单的时段共现 | 付款是前面多段内容共同影响的结果，不能把订单因果归给付款那句话 |
| 关播后或跨场订单 | 优先官方来源场次/归因字段；缺少则列未归属、商家汇总或多个接触场次 | 不重复归到每一个听过的模块/场次，不因支付在下场发生就强行搬到下场 |

先提供一个主分析窗和预先配置的滞后敏感性窗；值由试播延迟与业务购买周期标定，不能看完数据后选择最好看的窗口。重叠窗口只用于敏感性分析，不求和成总成交。

### 6.3 并行听众和循环播放

一人可跨多个模块和循环；模块样本不独立。**不能将连续每秒在线快照当作独立的 N 个观众样本**，也不能累加各模块 UV 作为本场 UV。只有真实、合规且可完整关联的进入/离开/心跳轨迹，才考虑 cohort 留存；公开进场通知不满足这个条件。

## 7. 评价体系：最终结果、漏斗、诊断、质量

| 层级 | 指标与明确计算 | 前置条件 | 解释 |
|---|---|---|---|
| 最终经营结果 | 已支付商品金额、已支付订单/子单数、购买人数、件数，均按当前声明粒度 | 授权交易/官方统计，去重、状态定义、场次归属可信 | 成交规模；不能只看流水忽略退款 |
| 有效成交（截至时点） | 同一归属订单集合：有效支付金额 − 已成功退款金额；部分退款只减实际退款额 | 原支付与退款同口径、同币种、同集合；取消未付款不计支付 | 当前已知净额，**不是未来不会退、不是实收结算、不是利润**；平台风控/排除状态单列 |
| 订单有效性 | 全额退款/取消/部分退款/仍在售后中的订单、净保留件数（若有件级信息）分别列 | 稳定子单与状态 | 不把“付过款的订单数”直接减“退款事件次数”；一个订单可多次退款 |
| 看播成交转化 | 同场次已归属去重买家数 / 同口径去重观看人数 | 同人群范围、同时间窗、官方 UV/买家定义，非公开进场通知替代 | 人数比例，与订单/人次口径不同；分母 0 或不全 → unavailable |
| 商品曝光点击 | 商品点击 UV / 商品曝光 UV；或 PV/PV，分开命名 | 同商品、同群体、同口径 | 卡片吸引/需求兴趣；不是口播完整触达 |
| 点击成交 | 商品成交买家 UV / 商品点击 UV | 定义和归因一致 | 点击后购买效率；不能用订单数除点击人数后叫人数转化率 |
| 单位流量经营 | 净有效成交 / 去重观看 UV × 1000（系统自定义，明确与官方 GMV GPM 区别） | 真实观看 UV、同场次订单集合和成熟度 | 自家流量效率，不做行业通用定标；只有观看次数则用另一指标名 |
| 内容诊断 | 问题/顾虑类别、商品明确提及、重复未覆盖的问题、真实已观察评论者数、互动密度 | 评论事件、证据引用、产品指代明确 | 辅助定位下次讲什么，不能用问题多直接判差；好内容也可能引发更多提问 |
| 播放质量 | 计划/实际已播模块、错误/静音/缓冲区间、采集缺口、实际有效播出时长 | 真正状态事件 | 避免将技术问题当内容问题；独立于经营好坏 |

“没有数据显示成交”不等于“本场零成交”。只有授权订单源声明完整、相应集合确实为空才显示 0。

## 8. 模块目标与可用指标

各模块共同服务成交，但近端职责不同。按职责诊断，不给每段硬性要求“立刻下单”。

| 实际模块/内容标签 | 近端目的 | 首期公开数据能做的评价 | 订单/官方数据齐全后可补 | 不应该做的判断 |
|---|---|---|---|---|
| 长开场 `opening_long` | 新一组开头明确本场主题、商品需求，帮助刚进入者了解 | 是否真实播出；主题/需求相关评论；当段在线/进场趋势的共现 | 有真实 cohort 才能测新进入者短时留存；官方同类时段趋势 | 第 1 项在线上升就说长开场留人；长开场直接比短开场平均在线 |
| 短开场 `opening_short` | 快速进入此品/此版本，减少重复客套 | 时长、重复程度、当段可观测互动；与同保存位置条件下短开场比较 | 合格对照场次/相同队列位置表现 | 因短所以一定更好，或要求短开场讲完所有资料 |
| 商品介绍 `product_intro` | 让顾客知道是什么、适合谁、关键规格 | “这是什么/哪个款”类问题和已讲信息是否对得上，误解/指代不明样本 | 商品卡点击趋势（时间共现） | 问题变少即证明理解率高；沉默者是否理解无法观测 |
| 卖点 `selling_points` | 需求—特点—用途解释，处理真实购买顾虑 | 场景/用法/差异/限制问题、正负表达及证据；哪些顾虑多次出现而正文未覆盖 | 同品点击、后续成交/退款问题关联；多次对照支持具体卖点试验 | 提问最多的品必定最受欢迎；“能用吗”也可能是适配障碍 |
| 活动 `campaign` | 让价、门槛、领券、叠加、截止条件清晰可理解 | 价格/券/组合条件问题、明显误解、文案与已确认事实冲突 | 领券/加购/点击/下单/支付漏斗（有权数据才有）；退款原因是否与承诺有关 | 一段活动结束无订单就说促销无效，或自行给更低价建议 |
| 促单 `cta` | 清楚说明下一步可做什么，避免冗长重复 | 行动入口问题、愿望表达、重复催促体验；有事件时的点击共现 | 同商品、已归属订单在预先定义时窗内的共现，保留滞后敏感性 | 支付发生于 CTA 就全归功 CTA |
| 互动句 `kind=engagement`/分析标签 | 让观众表达问题、参与互动 | 互动请求后的实际响应及主题、回答人数下界、重复刷屏占比 | 有完整观看 UV 才能算合规参与比例 | 回复多=成交好；没回复=没人听/没人买 |
| 原稿（未结构化） | 原样播放商家稿 | 句子/时间区间的互动问题、语言和播放质量；可辅助人工切段 | 取得明确模块标注后再按真实段落比较 | 用模型推断段名当已确认执行模块；强行补七段 |

`transition` 不作为首期评价对象，除非实际旧稿确实播出它；报告只描述观测到的历史段，不要求为了复盘重新生成衔接。

## 9. 模块级曝光分母与代理指标

必须分开四种不同概念：

1. **播放量/播放时长：**播放器完成多少次模块、多少秒。这是内容执行事实，不是观众曝光。
2. **在线观众分钟估计：**在有定义且覆盖可用的在线快照区间，计算 `∫ online(t) dt / 60`。只在连续覆盖区间插值，断线缺口不填 0。它是同时在线人数的时间积分近似，不是模块 UV、不是完整听完人数。
3. **已观察互动者：**去重公开事件中发言者，范围是“已观察”，不是所有观众。点赞没有用户键就不能推去重点赞人数。
4. **真实模块触达/完成率：**需要能说明某一观众实际看到/听到本模块的完整轨迹；首期通常没有，明确 unavailable。

可报告 `相关问题数/模块分钟`，如果具备可用在线快照还可另报 `相关问题数/100观众分钟`。这些叫问题密度，不叫观看评论转化率。缺在线时只报原始数和时长，不能拿进场数凑分母。

在线前后差额仅是人口净变化：例如开始 100、期间观测 20 次进场、结束 90，并不能在采样/时间口径未确认的情况下推算 30 个离开，更不能算出哪些人因为本段离开。累计观众增量也不能替代入口 cohort。

## 10. 商品兴趣与话术弱点如何输出

商品兴趣不做一个任意综合分；为每品并列呈现：明确商品提及的已观察评论者数、购买意愿表达、适配/价格/物流问题、商品点击（若有）、已归属净成交（若有），再显示各自曝光时长/可用分母。多个商品同名/指代模糊时不硬归商品。

建议的语言模板：

> 商品 2 在 20:10–20:14 两次卖点段中，出现了 6 位已观察用户的尺寸提问，其中 4 人在介绍已经结束后仍问安装条件。当前评论采集有 1 个缺口，没有逐人留存数据，不能说明这些问题导致流失。建议下次在该品商品介绍中提前说明已确认的安装适用条件；需要商家补充的限制另列。下一场固定价格/优惠，比较同位置、同类流量下的明确安装问题密度与商品点击表现。

数字仅为模板示意，不是本次实测。建议不能把“尺寸未知”改成编造尺寸，也不能用点赞猜商品功效。话术改动候选应回到事实正本和已确认活动条件。

只有观看/互动缺乏成交时，可写“商品 2 有较多已观察兴趣线索，可考虑下一场把它放到靠前位置进行验证”，不得写“商品 2 卖得最好所以自动移到开头”。即便有订单，先控制它本来播得更久、价格更低、库存更足等差异。

## 11. 必须记录与控制的混杂条件

| 条件 | 必须记录 | 首期处理 |
|---|---|---|
| 平台自然流量/推荐变化 | 有权渠道趋势；无数据时标未知；时段进场/在线的代理另列 | 不把平台推流增长判为开场文案功效；自然/付费不可拆时降低比较结论 |
| 付费投流 | 计划、真实开始结束/预算变更、花费、付费渠道流量 | 期间单列或同投流条件比较；没数据不算 ROI、不用自然流量解释 |
| 价格/优惠/库存/上下架 | 当前事实快照与变更时间、库存未知状态 | 降价或缺货会改变转化；缺货区间不判 CTA 差；本期不自动设计更低价格 |
| 固定队列位置/循环/初始爬坡 | 保存位置、实际序号、循环次数、已播时长、长短开场 | 长开场总在 1/6/11、有时正逢流量变化；与相同类型/近似位置比较，保留剩余混杂 |
| 商品与用户构成 | 商品/SKU、已知语言、渠道、新老客（仅有权数据） | 不从昵称推断性别年龄；不同商品点击/成交不直接拿来证明文案强弱 |
| 时间与节日 | 星期、时段、季节、活动节日、会话时长 | 先比本商家相近条件；大促与平日不硬比 |
| 声音与技术 | 音色/语速/语言、实际静音/缓冲/推流异常 | 播音故障区间单列；普通话和其他语言不合并评平均 |
| 人工动作/画面/演示 | 用户临时切项、商品画面/视频、平台可观测状态 | 有画面变化也可影响效果，声音人不是无画面；未接入的变化请用户标注 |
| 外部竞争/物流 | 已知异常或商家注记，未知不臆测 | 放入替代解释，不让模型编“竞品大促”成为事实 |

观察研究只能给“关联、可能解释、验证建议”，不能在未随机/未排除混杂时写“原因已经确定”。比较先同商家同商品；没有同条件基线，不以其他主播行业均值下结论。

下一场可采用小范围、预先声明的方案 A/B，多轮平衡队列位置与时段，其他事实尽量保持一致。并不要求首期自动执行实验，也不在本场根据 AI 临时修改。由于重复观众和平台非平稳，简单轮播 A→B 不是随机独立实验，应标探索性；不能以一次 A/B 得出稳定提升率。

## 12. 小样本、置信区间与“不足以评价”

- 报告先展示原始计数、曝光/观看的真实分母、缺失覆盖和可比场次数，再给变化率。基线为 0 时不显示“增长无穷大”。
- 没有业务标定，不写“至少 100 人”或“下降 20% 一定异常”等任意硬阈值。用置信区间宽度、可比历史量、实际业务差异说明证据是否足够。
- 若数据满足去重二项比例的条件，可计算 Wilson 区间，极小样本可用精确区间。它不能修复采样偏差/身份不完整，也不适合将每秒在线快照当作 N 次独立试验。
- 若同用户跨多轮、分钟间相关，应以场次/独立区块作为汇总比较单位；足够数据后再考虑区组自助法/分层模型，首期不套复杂模型制造精度。
- 多段模块、多SKU、多个滞后窗同时“挑最好”会放大偶然差异。预先指定主要指标和主比较，其他为探索发现；下次验证再看。
- 输出状态建议为 `observed_only`、`comparison_available`、`inconclusive`、`supported_direction`，每条说明为什么。`supported_direction` 也不等于因果已证明。

## 13. 订单、退款、跨场与评价成熟度

### 13.1 订单去重和归属

业务主键使用平台+店铺+订单/子单 ID。同一支付的状态更新不是新订单；部分退款按退款流水 ID 和业务更新时间幂等合并。订单事件、退款事件、订单当前状态分别存，不能简单 append 汇总。

有正式场次归属字段则遵循它并记录口径。只有店铺全天订单而没有直播来源时，可显示“店铺同期成交（未归因）”，不能混入本场 GMV。跨场重复触达可保留多个接触点作为解释，但官方归属金额只计一次；另一套分析模型如采用分摊，必须另列、总额守恒、不得与官方数混加。首期不需要自创分摊模型。

### 13.2 成熟度状态

| 状态 | 何时形成 | 能说什么 |
|---|---|---|
| 采集结束初稿 | 声播/公开互动已关窗，订单可能尚未导入或尚在更新 | 互动、技术、内容问题初稿；成交结果待补 |
| 交易暂定 | 有当前付款和退款快照，尚未到声明观察截止 | 截至某时间的有效支付与已知退款；清楚提示仍会变化 |
| 指定观察窗已完成 | 采用的订单/售后观察窗已到，并已对账覆盖 | 在该观察窗内的结果已较完整；不是永不变化、不是平台财务最终结算 |
| 修订版 | 迟到订单、退款、导出纠正导致结果变化 | 保留旧报告与当前报告差异，更新下一场建议适用性，不静默覆盖 |

观察窗取当前平台数据口径和商家业务，不把历史帮助文章的“14 日”自动写死。可设多次回补时间，但定时计划由主实现和用户授权范围决定；本任务只是设计。每次输出必须有 `as_of`、`data_cutoff`、`order_window`、`refund_window`、`coverage`，不能因为播完半小时就给“净有效成交最终结论”。

## 14. 一次可读复盘报告应该是什么

建议主页面按以下顺序，避免 20 张图掩盖商家该改什么：

| 区域 | 内容 | 验收要求 |
|---|---|---|
| 本场结论 | 3–5 句：成交评价可不可做、最明显事实、最值得验证的建议 | 缺订单直接写无法判断成交；不拿互动代替购买 |
| 数据账本 | 本场时段、源、字段/口径、覆盖缺口、更新时间、成熟度 | 零与未知区分；公开与授权分开 |
| 经营表 | 真实拿到的支付/退款/有效成交/流量/点击，及可比基线 | 每个率可展开分子分母；币种一致 |
| 商品兴趣与问题表 | 每品提及、问题类别、点击/购买（各自有无数据），播放时长 | 显示不明确归属；不合成无依据兴趣总分 |
| 时间线 | 实际商品—版本—模块/句子，与在线/评论/授权趋势叠加 | 点击结论能看原句和原事件；技术缺口阴影，相关窗口不冒充归因 |
| 模块诊断表 | 模块目的、真实观测、基线、限制、下次动作 | 每一条有证据；弱项可为待验证而非宣判 |
| 下一场建议 | 优先处理商家资料、话术、活动解释、素材/演示、排序/语音等可改内容 | 每项写具体目标、改哪里、保留哪些事实、怎么验证、需用户确认什么 |
| 不能下结论/待补数据 | 缺订单、流量来源、延迟、库存等 | 告诉用户最小还需什么，不要求无关全量数据 |

建议分事实、解释假设、行动三列。例如“促销条件提问集中出现”是事实；“说明顺序可能导致理解负担”是假设；“下次把领券前提提前，并保持价格不变”是验证动作。不能三者揉成“已找到转化低原因”。

## 16. 为实现者准备的最低验收集

| 场景 | 应输出 | 必须拒绝或降级的行为 |
|---|---|---|
| 只有公开评论、进场，无订单 | 可追证据的顾虑/兴趣与技术复盘，成交 unavailable | 不填零 GMV、不算成交率、不判商业成功 |
| 在线快照100→90，观测20进场但通知采样未知 | 在线净变与观测进场分列 | 不推出30离场，不算精确留存 |
| 点赞一条累计100、下一条累计120 | 按确认语义记增量20或保持原始待确认 | 不计220次新点赞；累计重置不记负互动 |
| 同一用户一秒刷20条 | 保存原始，摘要去重，同时显示消息量与观察到的去重评论者 | 不当成20个潜客 |
| 断线三分钟，重连后收到迟到评论 | 缺口标记、迟到事件回补、新报告修订 | 不填静默为0，不把迟到全归当前模块 |
| 分钟级5单覆盖3个模块 | 保留该分钟时段关联 | 不均分5/3，不选CTA全归属 |
| 同订单先付100、后退30、再退20，重复导入两表 | 支付100、退款50、截至时点有效额50；状态可回溯 | 不重复记付款或退款，不把退款事件数当订单数 |
| 全天订单无房间来源 | 同期店铺成交单列未归因 | 不硬算本场成交 |
| 跨场付款，官方归属上一场 | 只在正式归属场计一次；下场仅显示同期发生而非归属 | 不两场重复计成交 |
| 价格从129降到99同时换稿 | 事实显示两项均变，不能分离文案效应 | 不宣称新稿带来全部增量 |
| 卖点段断音、评论下降 | 技术异常优先、内容评价受限 | 不自动判卖点差并删掉 |
| 长开场与短开场分处不同流量位置 | 分组比较，说明位置混杂 | 不直接排名长短开场优劣 |
| 原稿无模块边界 | 原句/时间区间复盘；推断段落有标识 | 不强说七模块已执行 |
| 报告后补退款使净额下降 | 新修订、差异、反馈适用性更新 | 不静默改历史或仍展示原报告为最终 |
| 反馈目标引用的商品价格已更新 | 播前重新评估适用性，提示陈旧证据 | 不直接采用旧促销建议 |
| 模型建议实时插播/换品 | 报告中改为下场候选；执行工具拒绝 | 不因模型规划自动新增本期禁止动作 |

验收以 deterministic fixtures 为主，覆盖所有来源/缺失/去重/时间/退款边界；再用一场授权录制或商家历史导出做离线回放核对。先验证数据和公式，再验证模型建议事实与证据；不为每秒事件调用大模型。

## 17. 推荐实现优先级

1. **先获得可复盘的播放真相。** 内部冻结快照 + 实际模块/句子播放事件 + 采集健康 + capability manifest。没有这个，再多互动也无法定位是哪一版话术。
2. **接入现有公开连接器的真实字段。** 保留原始语义，去重、迟到、缺口、计数 reset、字段可用性。先让“观测到什么”和“没有能力观测什么”清楚。
3. **加入授权官方导出。** 商品映射、时区、订单退款对账；否则第一阶段只能做互动与内容复盘，不能验收用户最关心的成交。
4. **程序生成统计包。** 计数、分母、时窗、质量、同比基线由程序确定；模型读取统计证据与必要原句，提出少量下场可执行建议。
5. **反馈给播前。** 以不可变引用和适用条件读取，不当自动修改指令。复盘本期不提供直播控制权限。

后续再做更细粒度授权数据、稳定延迟标定、可比场次积累与小改动实验；不要为了“AI智能”先堆多个实时分析 Agent。真正的首期价值是用可信证据告诉商家下一场该改什么、为什么、怎样判断改好，而不是播中自主动作。
