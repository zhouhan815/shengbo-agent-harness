播中播后综合 Agent 设计方案

版本：LIVE-REVIEW-1.0 设计稿　日期：2026年10月20日

本方案服务于固定商品较多、希望降低直播成本的中小商家。首期在直播期间记录数据，关播后分析表现，并输出下一场的话术、展示和配置建议。直播内容的插播、改稿、切品、重排、改价和发券均不由本 Agent 自动执行。

本次交付设计，不启动新的直播采集，不修改声播或播前 Agent 的业务代码。旧的播中、播后方案保留；本稿作为新的首期范围。后续若恢复自动运营，再在保留的旧方案上评估。

用户已确认：可以手动导出经营报表。因此首期标准交付采用“实时采集＋关播后授权报表导入＋经营复盘”，不等待交易API。公开互动版仅作为缺报、数据不合格或等待报表时的降级。具体表头、时间粒度、场次归属和可导出的退款截止目前还未检查；这些决定能否进一步评价模块级时间关联。

1 核心决策

决策首期做法目的
播中做什么程序持续采集公开互动、真实播放过程及采集健康状态；商家可另行提供经营报表减少模型成本，并保留可复盘证据
播中不做什么不进行 AI 运营决策，不自动插播、改话术、切商品、改播放顺序或优惠先验证数据和评价体系
播后由谁判断一个 Deep Agents 主复盘 Agent，自主选取证据和分析工具；复杂任务可选派内容或经营专题子 Agent保留规划灵活性，避免为简单报告固定增加多轮协调
数字由谁计算有版本的指标函数与查询服务，模型负责解释和提出可验证建议防止模型凭印象编算转化率
业务好不好首先看可核验成交与退款；再按流量、兴趣、购买路径定位瓶颈互动热闹不能替代成交效果
没有订单怎么办只交付互动和内容诊断，成交结论为“无法判断”不能把没有数据写成零成交
建议怎样使用输出带证据、目标稿件版本和验证办法的建议包；用户采纳后才交给播前处理本 Agent 不直接写商品库、正式稿或直播队列

新增归档建议使用既有唯一采集连接：标准化持久化与归档outbox同事务提交，由旁路消费者异步写完整归档，失败可重放；不要在实时接收或播放回调中等待LLM／远端归档。播放侧不能跨两套数据库声称已有同事务保证，应在已有状态事件产生处做可恢复本地journal／outbox，明确顺序、落盘确认与过载缺口。这里的“原件”指接入边界实际收到的数据，不承诺还原上游未输出的完整平台protobuf。

共享连接需有独立订阅／租约：停止一次监控只停止本场归档订阅，不顺带断开仍被声播UI或其他消费者使用的来源。来源连接的最终关闭由现有所有者按消费者和房间状态管理。新方案不得为了“重连复盘”偷偷重置正在使用的采集源。

3 总体结构

播中 · 普通采集程序
抖音公开事件声播实际播放回执连接健康与人工场记
↓ 按本场绑定、原件和时间线归档
关播后 · 数据基础
授权经营报表导入固定归档修订程序计算指标与数据资格
↓ 主Agent按问题选择工具和证据
播后 · Deep Agents 主复盘Agent
自主取证与诊断可选内容专题可选经营专题
↓ 可读报告 ＋ 下一场建议候选
用户选中建议 → 显式关联下一场 → 播前核版本后处理

没有任何自动插播、改稿、重排、改价或发券通路。

这是一张依赖图，不要求 Agent 每次走同一条分析路线。采集、去重、按时间聚合等机械步骤由程序保证；Agent 可以只研究用户指定商品、追加一个假设核查、跳过没有数据的分析，或在证据不足时停止下结论。

4 从开监控到交付报告的九步

步骤输入执行动作输出验证与失败出口
1 绑定本场声播场次、外部房间、实际播放列表、商品及稿件修订建立唯一 monitor_session_id；区分外部固定 room_id 与本次开播实例；记录监控开始是否晚于开播；固定商品映射、币种、目标和对照条件SessionManifest、实际稿件快照、能力清单错房间或无法确认商品映射不混入本场；中途进入监控明确标部分覆盖
2 开启采集已确认绑定和可用数据源订阅现有公开事件；在声播已有播放事件产生处增加归档旁路；采集连接状态、心跳、缺口；保留人工标记的优惠／投流／库存／技术事件三路独立事件流：观众、播放、健康／场记先看连接／落盘，不以没有评论判断断连；重连只恢复采集，不触碰播出内容
3 播中落盘原始事件和回执原始数据先持久保存，再标准化、去重和形成分钟快照；保留消息时间与接收时间、原字段、计数单位和口径状态；失败事件进入隔离区可恢复游标、去重映射、原件索引、监控面板不中断正常声播；无法落盘时显示明确缺口；不靠有限长度 UI 日志重建整场
4 关播封存关播／停止监控信号、最后游标排空本地缓冲，标出尾部缺口，生成 ArchiveRevision；暂停不等于关播；进程重启后同场继续，不把新开播混入旧场一份不可变归档清单及覆盖区间“已封存”不等于“数据完整”；超时输出部分归档，迟到数据以新修订补充
5 补充经营资料用户有权导出的直播概览、商品、订单、退款和可选投流资料读取实际表头和口径；映射商品／SKU；识别 shop 单与 SKU 子单；按来源及截止时间保存；列出缺少什么会限制哪些结论经营数据集、导入映射、DataGap清单不要求公开插件补订单；仅有店铺总订单、无法对应本场时不强行计入本场成交
6 计算指标固定归档修订、可信字段和指标定义计算整场、商品、稿件和实际模块出现次数的统计；标记未知、样本、覆盖、延迟和成熟度；按可比条件选择历史基线MetricPanel、模块时间线、可比性说明缺分母不算比率；部分采集不外推完整观众；模型不自行补数
7 Agent 取证复盘当前目标、数据能力、指标索引、历史基线先找主问题，再查询有关片段、问题原文、实际稿件和商品事实；必要时并行查内容与经营证据；把观察、解释假设和建议分开带 evidence_ref 的 Findings某时段涨跌不直接写成话术造成；无新证据不反复读同一日志
8 形成报告与建议经核对的 Findings 与指标给出成交结果、漏斗瓶颈、商品兴趣、稿件／模块表现、疑问异议和技术质量；每条建议说明改哪里、为什么、怎么验证ReviewBundle、可读报告、NextSessionFeedback候选程序核数值、引用与范围；不强制再派一个评委 Agent 或无休止重写
9 用户采纳与后续修订用户选中的建议、当前正式稿件版本导出／交接被采纳建议给播前；退款或迟到数据到齐时另出报告修订AdoptionDecision、建议交接包、版本差异采纳不等于修改成功；播前重新核版本并保留原有话术／语音批准流程

步骤2的三路采集并行；步骤5经营资料可在关播后稍晚补齐。步骤6统计可以按修订缓存；步骤7是否拆专题由主 Agent 根据任务决定。数据未补齐时，步骤8可以先发布“互动复盘版”，之后另发“经营补充版”，不覆盖旧结论。

5 要采集什么数据

5.1 场次和内容坐标

这些字段让“20点03分的评论”能够关联到“本场 A 商品第2版的卖点段”，属于本项目的数据基础，不依赖抖音插件提供。

数据项最小字段来源与采集方式用途及限制
本场身份merchant_id、monitor_session_id、shengbo_session_id、platform、external_room_id、可得的 external_broadcast_id、开播／监控／关播时间用户确认绑定、声播和平台实际状态同房间不同日期必须分开；没有平台开播实例ID时使用本地绑定版本并记录不确定性
商品映射internal_product_id、product_revision/hash、platform_product_id、SKU、映射确认人／时间声播商品库和商家报表同名不是同商品，SKU映射不明的交易单独隔离
稿件与编排script_revision/hash、variant_id、playlist_revision/hash、item_id、position、opening_type实际采用的播放配置快照记录实际采用版，不用未采用的候选；重排或人工变更追加新快照
模块与句子module_key、module_revision、sentence_id、句子原文ref、计划时长声播正式稿件与编译结果不凭自然语言猜商品版本；原稿导入可能只有一个模块
播放尝试playback_attempt_id、cycle_index、item_occurrence_id、module_occurrence_id、started/ended/interrupted、实际时间与证据来源播放器确认回执、声播事件同一句重播必须保留不同attempt；排队／服务端计时不等于真实发声
人工事件event_type、发生时间、目标商品、说明、是否用户确认场记按钮／用户上传资料包括切品、暂停、缺货、价格调整、投流起止和外部故障，首期只记录

新名称到现有字段必须显式映射：playback_attempt_id=attempt_id、item_occurrence_id=occurrence_id；额外保留 compiled_entry_id、original_position、source_sentence_id→编译后sentence_id、module_ref、publication_ref和approval_ref。运行身份还包括boot_id／source_instance、owner_id和epoch；不同进程启动的单调时钟不能直接相减。以实际回执和身份变更记录重连后的尝试，不按相同文字或queue_id把它们拼成一次。

attempt内另记连续播放区间segment_index：playing→暂停／缓冲／结束分别闭合区间，恢复后开启新区间。实播时长为有证据区间的并集，而非简单ended−started；多次playing可能是同一尝试恢复，不能重复计算模块出现次数。断连或缺终态的尾段保留unknown，不能拿理论音频时长补成完成。

5.2 观众与互动数据

数据项记录内容现有工具情况可以分析什么／不能分析什么
评论message_id、文本、用户会话化匿名键、消息时间可得性、接收时间、来源方法、原件ref历史已收到，现有标准化器支持可分析问题、异议、购买意向；不能把“已下单”评论当支付
成员／进场消息原事件类型、用户键、平台原计数、发生／接收时间历史已收到只称“观测到的进场消息／用户”；可能抽样、聚合或不全，不当全量进入人数
点赞原count、total、count含义状态、消息ID及时间历史已收到点赞消息先辨增量／累计；没有已核口径则只报消息数，不报准确点赞总数
在线快照原数字／展示文本、采样时间、字段来源、metric_definition_status有历史人数快照，现有口径未完整核验校准后可看在线趋势；不能据人数下降推出某个观众离开
累计展示统计原文、数值、counter_scope、baseline、reset标记有历史展示统计保留原始口径；开监控前的累计不能计为本监控新增观看
关注／分享原Social action及可得字段、解析版本曾有原Social消息，当前未稳定分清关注与分享只记录待解释事件；经逐类型核验后再启用关注／分享率
礼物／粉丝团事件类型、数量、价值单位若真实可得作为可选原始信号，不当成交可补充互动背景；礼物价值不计商品销售额
离场与停留真实离场事件或官方聚合停留指标当前公开事件工具没有完整能力证据首期不从“没发言”或“在线变少”计算个人停留、流失率、1分钟留存

支付SKU子单键、父单键、支付时间、实付分摊、数量、币种、统计口径、平台直播归属同上，优先最小字段支付金额、支付子单、买家数等；没有可靠买家键不能算去重买家
退款与售后refund_id、关联子单、申请／成功时间、实际退款金额、退款数量和状态后续补充退款明细或经营汇总净成交与退款成熟度；退款申请不能直接当退款成功
投流与外部变化流量渠道、投流起止、消耗、价格／优惠／库存变化用户提供的报表和场记排除“投流增加被误称话术提高留存”等混杂因素
成本货品成本、履约费、平台扣费、投流支出、税等实际可得项可选，不作为首期阻断资料齐全时另算贡献／收益；只有GMV不能判断利润

首期不承诺存在通用、免授权的抖音成交API。授权经营报表应先检查真实表头、账号权限和指标口径。公开事件与经营报表彼此补充，不能相互假冒。

6.1 先判数据够不够，再评价经营好不好

模式实际具备什么能交付什么不能交付什么

整场／商品经营复盘再有本场与商品级授权报表支付、商品点击、购买漏斗与商品对比把整场总点击或订单均摊成模块级转化

6.2 五层评价与指标定义

下列公式是本项目拟采用的计算契约，不能冒称与平台界面所有同名指标天然一致。平台原报表值和本地重算值分列；单位、去重口径、区间、来源和截止时间一致才可比较。

层次要回答的问题关键指标和计算约束不足时怎样显示
数据可信度本场监控了多少、缺了什么已观测有效时间／目标时间；最长缺口；播放映射覆盖；字段解析与金额核对情况先列可评价范围，不用缺失给内容扣分
播出与承接观众是否有机会听见、流量是否接住有确认的播放时长、技术中断；可信在线快照的时间加权均值；官方人均观看时长只有公开快照时只报观测在线趋势，不命名精确留存
商品兴趣与理解观众关心哪个商品、哪里没讲清商品点击UV／商品曝光UV（同口径）；可归属商品的购买意向、顾虑与规格问题；每百观测在线人分钟的有效问题数没点击只称表达出的关注与疑问；评论多不自动等于兴趣高
购买转化吸引之后是否真正购买支付买家UV／看播UV；商品支付买家UV／点击UV；支付订单／创建订单；支付金额、件数没可靠UV或归属则不算该率；独立给数量和缺项
有效成交成交是否保留下来同一已支付订单队列实付金额减已成功退款金额；退款金额率；支付与净金额／有效直播小时必须标 as_of 与退款观察窗口；不等于平台结算、到账或利润

补充规则：

  • 千次观看支付金额：仅当本场看播UV可得且同口径，计算支付金额／看播UV×1000；不能把进场消息数当UV。没有UV时可以报支付金额／有效直播小时，但不能改名为观看转化效率。
  • 金额以整数最小货币单位保存，按币种分组；运费、优惠分摊和税是否计入在定义中声明。支付父单、子单、件数和买家数各算各的，不能相加。
  • 在线人分钟只是一种基于有效快照的曝光机会代理：在允许的采样间隔内积分在线值并除60；超出允许缺口不外推。它不是完整真实商品曝光人数。
  • 订单支付时间落在卖点段，只能称“支付发生时间关联”；购买决策可能来自之前的介绍、价格或详情页。平台给出的场次／商品归属优先于本地时间猜测。
  • 同一订单最多进入一个严格归属的主成交总量；探索性多窗口关联单列，不能把同一订单重复加给多个模块后再汇总。
  • 退款按原支付订单队列追踪，区分已申请、审核中、退款成功；无法追踪的样本标不完整。初报、补充报和成熟报是同一场的不同修订。

6.2.1 成交、退款与每小时指标的精确分母

指标本项目的精确口径启用条件与反例

7.1 评论理解规范

评论可多标签：购买意向、价格、规格、适用场景、效果证据、优惠规则、运费时效、信任顾虑、投诉、无关和疑似重复。标签不是新的商品事实。商品归属按明确名称／SKU、可核验回复上下文、当前讲解商品等证据分级；只有“多少钱”而多个商品同时讨论时允许 unassigned，不能强制归当前商品。

“已付款”“买了”只归购买自述，不写支付订单。相同文案重复或疑似机器人单列，不能无依据删真实观众；保留规则版本、排除理由和原件。一次模型分类可批处理，重复提问和原文不整场塞给主Agent；每个主题保留计数、覆盖范围、代表证据及反例。

7.2 对比与归因规范

  1. 优先比较同商家、同商品／SKU、相近价格优惠、流量来源、时段、开场类型和数据完整度的多次播放；不直接与完全不同商品比较绝对评论数。
  2. 本场多个段落的在线人数不一样，先报讲解时长及有效观测在线人分钟。代理归一化不足以消除所有差异，尤其不能代替真实商品曝光。
  3. 分别列内容开始前、内容期间、内容后窗口；窗口长度依据已测平台延迟和购买路径标定。没有校准时，不默认“之后30秒的订单都属于上一句”。
  4. 分钟聚合跨越两个模块时标 mixed；没有更细证据不按秒数给订单或独立用户分摊。合计型金额若做展示分摊，必须标估算且不进入归因指标。
  5. 样本量、分子、分母、独立播放次数、覆盖与可比性同时展示。不同播放次数不能当成独立观众样本。小样本写“证据不足”，不硬定涨跌阈值。
  6. 初期没有可靠历史基线时不给百分制总分，也不套行业所谓优秀线。用户可以设本场支付／净支付目标；未设目标时只给事实和对比，不擅自宣判成功。
  7. 若要验证改稿效果，用事先记录的对照方案，尽量只变一个因素，多次轮换相近条件，记录投流／库存／价格；时间轮换仍是准实验，不能包装为随机观众A/B因果试验。

经营专题子Agent经营数据完整且需要复杂商品／漏斗对比时分析可选只读计算结果及口径，不接触未脱敏订单明细

首期默认一个主Agent即可，不为每种指标建Agent。若使用两个专题子Agent，它们读取同一个 archive_revision，可并行调查；主Agent负责合并冲突、说明证据不足，不共享可写报告正文。并行必须有收益，不能为了“多Agent”增加固定调用次数。

首期模型优先复用本机已授权的gpt-6.1-sol适配来源和安全续期机制，不要求复制令牌。这个Agent不生成新的直播话术或语音，因此不需要在复盘链路调用DeepSeek文案生成或TTS；后续用户采纳建议后，由播前按原流程处理。指标、原件和报告优先本地SQLite与受控文件存储，不新增数据库服务器来完成首期。

以上是新方案的逻辑职责，尚未注册或实现；不复制播前庞大的运行控制器，也不沿用其数字编号来冒充已写中间件。后续实现可复用经过核对的公共日志、授权模型和引用工具库，但建立独立只读业务客户端。

固定上下文只保留：本场目标、归档修订、字段能力、主要指标、当前问题、已查证据摘要和未决缺项。价格、优惠、订单、时间、未知状态与引用保持精确；大量评论按主题／商品／时间索引，摘要保留反例和数量口径。摘要不能生成丢失的原证据，跨场记忆不覆盖正式事实。

权限硬边界：不注册 insert/interrupt/switch_product/reorder/start_tts/change_price 等工具；服务层也拒绝这些受控动作，不能只靠提示词说“不要做”。启动／停止监控属于用户确认目标后的采集控制，不等于控制直播内容。数据断连自动重连是采集维护，不触发运营干预。

9.4 恢复、调试和预算

  • 采集重启：从已持久化游标和本场绑定继续，去重后追加；缺口保留，不伪造补齐。
  • 复盘重启：恢复同一归档修订，复用指标和已完成专题；新归档修订另开修订任务，不在旧报告里悄换数据。
  • 分类缓存：绑定评论批次hash、标签／提示词／模型版本；没有变化不重新分类。
  • 模型失败：保存已返回结果、校验状态和实际用量；未知结果先对账，不盲目重发。模型不可用仍交付程序统计和未完成分析清单。
  • 初始试跑预算建议：一份标准报告共享最多12次模型请求、40次只读工具调用；分类、主Agent、子Agent和摘要共同计数。这个上限待实测标定，大场次可在明确范围下续办；超预算输出 partial，不删证据或强行凑完整结论。
  • 执行过程开关默认关闭；打开按工具／专题／完成检查分卡展示脱敏参数、结果摘要、进度、耗时和证据入口。后台安全记录独立保存，不要求公开隐藏推理。

10.2 来源和证据分层

15 研究依据与版本边界

  • 本地抖音与声播审计：见 research 下的能力矩阵、旧方案及播放事件审计；历史实测用于证明当时消息可收，不承诺今日连通性。
  • douyinLive上游项目：用于核对公开事件工具与本地WebSocket职责；项目自身不保证各类业务消息完整接收。本方案仍以本机固定版本及受控房间复测作为接入依据，不自动升级或扩大数据能力。
  • DouyinLiveRecorder上游项目：媒体录制工具，作为可选音视频证据来源，不当成交数据源。
  • 抖音电商学习中心 单场直播分析：历史方法说明，用于核对观看、点击、成交、退款和时间线应分层分析，不作为当前账号可调用API或固定界面合同。
  • 抖音电商学习中心 订单报表导出说明：说明存在商家订单导出及订单粒度差异；实际字段以用户授权报表为准。
  • Deep Agents 总览与子Agent说明：参考其按需工具、上下文隔离和委派职责；当前已安装版本以本地0.7.25为实施基线，不直接套用新版文档才有的功能。

本方案的指标公式、权限和交付契约为针对本项目的设计选择；不是平台官方统一评分标准。后续正式构建前，先确认数据样例与采集能力，再细化具体函数签名和实现任务，不从这份设计自动启动运营动作。
