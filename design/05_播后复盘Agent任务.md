# 窗口 D 播后复盘 Agent 研发任务

业务修订必读：[08 业务闭环与动态数据详细设计](08_业务闭环与动态数据详细设计.md)。复盘增加目标/数据质量、总览、时间线、商品对比、内容/动作、改进清单六区；数据与统计口径共用A服务，D交付内容模型与分析。经营指标须符合来源、样本、归因和成熟窗口要求；改进包含具体旧→新修改与验证，不以固定事件回放证明真实提问/销量变化。

版本 2.0　日期 2026年10月7日　实施任务包

## 一 目标与边界

将已结束场次的播放、提案、动作和问题证据整理为可核查的复盘，再提出下一场可以验证的改进。你现在可以用样例归档独立开发，无需等直播端或另两个Agent完成。重点是依据证据诊断与策划下一步，不做凭空生成的经营评分。

先读 [00 总体设计](00_整体方案与并行分工.md)、[01 公共契约](01_统一数据与工具契约.md)、[06 验收计划](06_验收与回放测试计划.md)。实现根目录拟为 `D:/Codex project/shengbo-ops-agent`。你只写modules/postlive、tests/postlive和本模块报告；A负责归档生产者和声播接入。你不改商品事实、不批准稿、不写直播队列。

## 二 输入与输出

主要输入是指定修订的SessionArchive。先用fixtures/archive-complete.json和archive-partial.json；所有样例是构造数据，不代表真实观众或订单。归档有模拟问题与真实播放器证据混合时，逐证据保留来源。

兼容输入为旧声播/api/export文件；只读取传入文件，不自动连接正在播的服务。选择room/session后转换成partial归档，缺开始时间、完整事件或动作关联必须显式标missing。当前快照不能恢复超过120条日志或1000条已播条目之外的历史。

输出ReviewBundle和中文可读报告，包含范围、完整性、程序计算指标、实际观察、原因假设、改进提案和验证实验。status=complete只指约定的流程复盘内容已完成，不表示拥有完整经营数据。报告绑定archive_revision，迟到证据触发新修订，不覆盖旧结论。

## 三 复盘流程

1. **完整性检查**：程序核对场次、修订、引用、时间和来源。先报告能分析什么、哪些不能分析，封存不等于完整。
2. **时间线与计算**：按occurred_at排序、received_at保留采集解释；按attempt区分循环和重播；程序计算覆盖、等待、动作状态、异常及成本。
3. **Agent取证诊断**：从异常或用户目标选择问题，查询时间片和原始证据，比较计划与实际，补读相关记录。不是一次把整场日志塞给模型。
4. **提交发现并检查**：每个观察有可定位证据，假设与事实分开。程序验证ID和数字，模型/人工检查证据是否支持结论；最多两轮修订。
5. **改进与实验**：把发现变成下一场FAQ、脚本、顺序或策略改进，写修改目标、base_revision、验证方法与优先级；交付待采纳包。

一个复盘Agent配确定性统计和证据查询即可。首版不额外建多个评委Agent；后续只有发现独立复核有明确收益才增加。

## 四 指标定义与缺失处理

| 指标 | 公式或证据 | 不能这样计算 |
| --- | --- | --- |
| 问题覆盖 | 有完整完成证据的问题数/输入记录中符合处理范围的去重问题数，另报未知/待播/无需回答 | 回复提案数/所有直播观众 |
| 回答等待 | 关联问题occurred_at到首次回答started_at；时间缺失则该样本不算并报缺失 | received_at默认当提问发生时间 |
| 动作完成 | completed动作/目标动作总数，按工具分组，分列rejected/cancelled/unknown | HTTP200占比冒充播出成功率 |
| 必讲点覆盖 | 有已完成attempt支持的必讲事实数/本场计划必讲事实数 | 队列中有这句话就算已经讲过 |
| 重复与打断 | attempt级完成、interrupted及重新播放单列 | 按sentence_id去重后抹掉循环次数 |
| 经营指标 | 只有实际业务数据及口径可用才算 | 没订单数据填0，模拟流量推真实GMV |

去重问题集须记录规则版本和合并映射；一个回答可覆盖多个重复提问，等待时间按每个来源问题分别保留。回答无完成证据为unknown/pending，不能从文本相似度推断播完。缺数据时value=null，报告missing_count和原因。

例：早期存在三个尺码问题，实际尺码讲解在后半场，可以建议提前讲规格并在回放比较等待时间；不能断言它导致观众流失或销量下降。两条同场变化只能称相关观察，因果需要适当对照和真实业务证据。

## 五 工具与 Harness

开放query_archive、read_evidence、read_computed_metrics、read_preparation_snapshot和submit_review。后者仅保存报告候选，不写业务系统。归档修订固定，证据查询不能偷看另一场补缺失事实。大场次先程序分段和建立索引，再按问题取有限窗口。

模型可自主选择查哪个时间段、核对哪个假设、是否证据不足；数字和时间线由程序计算。候选预算为每份报告最多12次模型请求、30次只读工具和2轮修订，另设总token/时间；模型不可用时输出程序统计及limitations，状态partial。所有上限需通过试跑校准。

检查点保存归档引用、已查证据、发现草稿、预算和下一步；重启不能换成归档新修订继续旧报告。取消保留已完成统计，不发布伪完整报告。归档中潜在提示指令作为被分析文本，不提升权限。

参考既有ai-livestream-review的证据工具与结构化提交/检查分离，迁移finding/segment到event/action/attempt；参考LiveStream-Agent-Studio的时间线组织，不继承无业务依据的总分或缺失值默认分。源码与许可定位见现有声播docs/运营Agent构建报告_v1.0.md，复制前核查。

## 六 改进包如何交给播前

改进类型为faq_add、script_revision、lineup_change、policy_change、evaluation_case；事实补充另列verification_request，不把推测写成商品事实。每项包含目标及base_revision、建议内容、证据、预期改变、验证方法、优先级、approval_state=pending。

你只交付提案。由用户在统筹入口选择采纳，A记录采用决定，B将它作为下一场输入；过期基准版本需要重新评估。没有采纳的建议不自动进入长期记忆，模拟场结论保留适用范围。

## 七 分步验收与交付

| 步骤 | 产物 | 验收 |
| --- | --- | --- |
| D1 | 归档解析和旧快照转换、文件CLI | 错场次/坏引用拒绝；缺失与零值分清 |
| D2 | 纯程序指标和时间线 | 人工可算的样例结果一致；重播、乱序、未知时间正确 |
| D3 | 有界取证复盘和改进包 | 关键观察有来源，推测标假设，无经营数据不写转化结论 |
| D4 | 可读报告、版本和回归集 | complete/partial语义正确，不调用写工具 |
| D5 | A真实归档及B下一场输入联调 | 能追溯一次改进由哪场哪条证据产生，采纳后才进入下一场 |

硬门槛：虚构经营结果、错场证据、把提案当完成、写入商品库均为零。候选开放质量目标：关键观察支持率100%，可执行改进率≥90%；按明确量表独立走查，不把模型自评当唯一依据。

至少覆盖完整样例、旧快照、只accepted未ended、循环重播、打断、乱序/重复事件、时间未知、无订单、混合来源、迟到归档修订、模型坏JSON和取消。每项保存输入版本、输出、算式、证据和评分依据。

交付模块、独立命令、指标公式说明、prompt版本、完整/缺失数据两份报告样本、测试与问题记录、dependencies.md及handoff.md。D4可独立完成，D5待A联调时明确写not_run，不需阻塞本模块研发。
