# 声播业务服务与事务工程规格

版本：PRELIVE-ENGINEERING-2.0，2026-10-15。状态：待实施的后端工程规格；本分册不包含业务代码。接口、类型和文件均为拟建合同。

本分册固定声播业务服务的命令、数据、事务、后台执行和兼容改造。调用者按本文实现类型化 HTTP 客户端；Deep Agents 主 Agent 调用这些业务工具，子 Agent 的临时报告先进入 Agent 暂存区，再经 accept_analysis_report 导入声播。手动跳播使用原编排位置；follow_up 串行、new_task 独立、replace 撤销旧写权；采用 snapshot 与 start 是独立人工动作。

## 2. 唯一提交链与所有权

```text
声播准备服务保存 SessionDraft + ContextBundle + ScriptChangePlan
  → 声播按冻结输入生成/修订模块（不改 room 当前配置）
  → 编译 PlaybackPlan（用户指定顺序，程序决定开场模式）
  → 人工审核精确话术/编排/音色并批准 → 按 AudioRequirements 完成缺失音频
  → publish_preparation：一个事务冻结尚未采用的 publication candidate/snapshot
  → create_review：对候选整包生成可读检查包
  → 用户 adopt_snapshot：CAS 更新 room 配置与 adopted_publication_id，不 start
  → 用户 start(adopted_publication_id, review_snapshot_hash)
```

本设计不定义前置 `publish_session_draft`。草案保存不是发布；Agent 的最终 publish 是候选整包完成，不是用户采用。生成、编排、TTS 都可针对草案完成，只有显式 `adopt_snapshot` 更新房间的正式待播配置。创建空 room 可以提前进行，但它不生成真实直播 `session_id`，也不改变当前直播。全局商品库操作可以没有 room/session 引用，不能为了调用商品接口伪造直播场次。

| 对象 | 权威所有者 | 写入规则 |
| --- | --- | --- |
| 正式 product | 声播商品库服务 | 4A 经校验后 CAS 保存；研究记录只给来源与依据，不成为第二份正式商品 |
| SessionDraft | 声播准备服务 | 2B 起保存，允许部分字段与未知项，不能被 `Room` 当正式配置读取 |
| 模块/脚本修订 | 声播脚本服务 | 不可变内容记录；当前选择保存在准备产物，不由 worker 自动挂 room |
| PlaybackPlan/AudioRequirements | 声播编译器 | 确定性产物；绑定输入修订和编译器版本 |
| publication | 声播发布服务 | 不可变候选整包；是否采用由独立 AdoptionReceipt 表达；room 只保存用户已采用指针和正式配置引用 |
| live session | 声播播放器服务 | 仅人工 start 创建；冻结 publication、音色及队列；准备 Agent 无该权限 |
| Agent checkpoint | Deep Agents 应用 | 保存计算位置与产物引用；不能作为声播业务提交的证据 |

历史 product_snapshot、ContextBundle 中事实快照用于追溯，不是可独立编辑的商品库。房间不能保存自己的商品正本。

### 2.1 唯一业务权威与双数据库边界

| 声播 DB：用户可编辑业务权威 | Agent DB：执行与临时数据 |
| --- | --- |
| product、room、preparation、SessionDraft、已接受商品分析/场次分析/顾客研究、ContextBundle、ScriptChangePlan、Playlist、脚本/模块、音频需求/清单、publication/adoption、run_authorizations、generation/text/audio jobs、业务事件与回执 | run、branch、question、staged artifact、scheduler、inbox、Deep Agents checkpoint、运行观测 |

所有业务产物一经接受就由声播版本化保存。用户编辑研究、计划或草案也调用声播命令层产生新版本；Agent DB 仅保存声播引用和缓存，不保存另一份可独立编辑的业务正本。大原文和图片通过受控 blob 导入声播内容寻址存储，声播事务只引用已导入且 hash 已验证的 BlobRef；禁止依赖另一个数据库可原地修改的正文或任意本机路径/URL。

accept_analysis_report 将 Agent 暂存结果导入声播，原子保存分析/研究artifact、依赖和 preparation 当前引用，再返回权威回执；Agent 消费回执更新本地执行投影。不存在跨库双写事务。权威 run grant、写代数、真实业务写入及撤销全部在声播同库事务检查。撤销请求未收到声播回执时，本地只能是 cancel_pending，不得报告已撤销写权。

## 3. 版本层次与字段合同

禁止用一个 `revision` 同时表示商品版本、运行轮次和脚本版本。

| 名称 | 含义 | 何时变化 | 校验者 |
| --- | --- | --- | --- |
| `revision` | 数据库当前业务记录 CAS 版本 | 任一成功写入，包括旧 API 写入 | 声播仓库 |
| `preparation_revision` | 声播准备任务目标/输入集合版本 | 用户资料或需求、商品引用、场次要求变化 | 声播准备服务 |
| `draft_revision` | 某 SessionDraft 内容版本 | 配置草案有变化 | 声播准备服务 |
| `artifact_revision` | 不可变产物的版本 | 形成新产物 | 产物存储 |
| `script_revision` | 同一话术版本的修订序号 | 局部模块更新后产生新 script ID | 声播脚本服务 |
| `module_revision_id` | 不可变模块内容 ID | 该模块实际重写 | 声播脚本服务 |
| `plan_revision` | 用户编排、开场映射及其依赖版本 | 顺序、文本修订、循环或相关设置变化 | 编译服务 |
| `generation_epoch` | 内容依赖代数；不代表权限 | 影响生成/编排/音色输入的内容变化 | 声播准备服务/worker |
| `write_generation` | 声播权威 run grant 写权限代数 | 显式 cancel/replace 撤销旧 grant | 声播 run_authorizations，与写提交同事务检查 |
| `input_hash` | 某项工作消费的精确输入哈希 | 被消费字段或引用变化 | 程序计算 |
| `publication_id` | 一次不可变可播整包 ID | 成功发布新包 | 发布服务 |
| `session_id/epoch/attempt_id` | 真实播出场次/播出位置/单句尝试 | start、跳播/重试、句播放尝试 | Room |

新 HTTP 统一返回 envelope；旧 API 保留原 body。`revision` 不放进 `ProductInput` 的严格字段，避免被 `extra=forbid` 拒绝；现有 script.body.revision 继续表示脚本修订，与数据库列分离。

`MutationContext`不自带虚构preparation；WorkScope.catalog的preparation_id必须None，preparation scope必须指真实room对应prep。全局商品维护不需要伪造直播间；grant的资源scope可以是明确catalog对象/创建范围。所有命令通过可信HTTP身份注入Principal与MutationContext，模型不能自行传principal或扩大scope。

```python
class RecordRef(BaseModel):
    kind: str
    id: str
    revision: int
    content_hash: str

class MutationContext(BaseModel):
    operation_id: str
    grant_id: str | None                # human/controller可信身份可为空；agent必有grant
    expected_write_generation: int | None
    expected_generation_epoch: int | None
    expected_versions: list[RecordRef]
    request_hash: str                   # 服务端重算；scope来自可信调用上下文

class ProductSaveRequest(BaseModel):
    product_id: str | None
    expected_revision: int | None   # 新建必须 None，更新必须精确值
    schema_hash: str
    patches: list[FieldPatch]       # set/clear/preserve，保存前materialize成完整ProductInput
    identity_decision_ref: str | None
    fields: ProductInput             # canonical完整字段，必须与materialize(patches)一致
    field_dispositions: list[FieldDisposition]
    source_manifest_refs: list[ArtifactRef]

class ProductSaveReceipt(BaseModel):
    operation_id: str
    status: Literal['committed']
    product: RecordRef
    product_payload: dict          # 完整已校验字段，另含服务端ID/SKU/display_number
    changed_paths: list[str]
    invalidation_event_id: str | None
```

### 3.1 动态商品schema与set/clear/preserve

```python
class FieldPatch(BaseModel):
    path: str                       # RFC6901 JSON Pointer，必须属于当前schema
    op: Literal['set', 'clear', 'preserve']
    value: Any | None = None

def get_business_schema() -> BusinessSchemaEnvelope: ...

def materialize_product_patch(
    schema: BusinessSchemaEnvelope, previous: dict | None,
    patches: list[FieldPatch], *, source_dispositions: list[FieldDisposition],
) -> ProductInput: ...
```

`get_business_schema`直接从当前ProductInput/RoomCommerce生成JSON Schema，canonical hash作为schema_hash；工具每次新run先读取，不能只复制文档字段清单。`materialize_product_patch`对每个path先查schema、类型、允许清空规则与grant修改范围；路径重复、父子路径重叠、未知path一律拒绝。列表字段首期整体set/clear，不实现含糊的数组位置增删。preserve不允许携带value，不产生实际写入；clear不允许携带value，按schema置空值/空列表/None，必填名称/价格不能clear；set即使value=null也必须符合nullable规则。

算法：复制previous或schema允许的创建初始对象→应用set/clear→保留其余明确preserve字段→仅在已获准的可见性/控制字段改变时计算派生清空（超出allowed paths则返回范围冲突）→仅对已获准set/clear的卖点字段维护兼容派生→ProductInput.model_validate→全字段处理清单比对→返回。创建时必须满足所有必填字段；更新缺省path等于preserve，未知不能自动清空旧值。`core_selling_points`与旧`selling_points`同时set且不一致返回`CANONICAL_FIELD_CONFLICT`；仅在本次获准set/clear时优先标准列表并派生旧prose；旧客户端明确改prose时按授权清列表。两个字段均preserve时逐字保留，不为同步或格式化而重写；原值不一致给advisory。本次仅改价格不能取得卖点字段写权。

schema_hash与当前服务不一致返回409 `SCHEMA_CHANGED`及新hash，调用者重新读取并逐字段重校验，不静默忽略新增/删除字段。FieldDisposition也按当前schema覆盖全字段，不能只检查卖点。ProductInput校验后逐项对比preserve字段与previous的canonical值/hash；若schema迁移或验证器隐式归一导致未授权字段改变，返回SCHEMA_MIGRATION_REQUIRED或SCOPE_CONFLICT，不顺带提交。商品图片若来自BlobRef，由catalog adapter读取声播已验证blob，转为当前ProductInput支持的受限data URI；任意URL、本机路径或未导入hash不得直接成为image。

补充约束：

1. `product_id=None` 的幂等重放必须返回第一次创建的 ID，不能再创建一个商品。
2. 已有 SKU/型号身份冲突时，`identity_decision_ref` 必须可查证用户对具体对象的决定；相似度不提供覆盖许可。
3. 内联`field_dispositions`覆盖实际schema全部字段；必填缺失阻塞，非适用/未知可选有记录。save_product同一事务注册字段处理清单和source_manifest_refs审计artifact，返回引用；不要求预先存在assembly_ref或field_disposition_ref。
4. 更新字段采取明确 set/clear/preserve 语义。隐藏可选字段沿用现有“清除有效值”的规则；“未知”不能清除已知旧值。
5. 所有 `*_ref` 必须验证 preparation/room 可访问范围；不能让调用者给另一个任务的 artifact ID 即跨任务读取。

### 4.2 仓库签名及 SQL 边界

```python
@contextmanager
def unit_of_work(store: SqliteStore, *, write: bool = True) -> Iterator[UnitOfWork]: ...

def read_record(uow: UnitOfWork, kind: str, identity: str) -> RecordEnvelope: ...

def compare_and_swap(
    uow: UnitOfWork, *, kind: str, identity: str,
    expected_revision: int, body: dict,
) -> RecordEnvelope: ...

def insert_once(uow: UnitOfWork, *, kind: str, identity: str, body: dict) -> RecordEnvelope: ...

def begin_operation(
    uow: UnitOfWork, *, principal_id: str, operation_id: str,
    action: str, request_hash: str,
) -> OperationTicket | MutationReceipt: ...

def finish_operation(uow: UnitOfWork, ticket: OperationTicket, receipt: dict) -> None: ...

def append_event(uow: UnitOfWork, stream_id: str, event_type: str, payload: dict) -> EventRef: ...
```

`records` 增加 `revision INTEGER NOT NULL DEFAULT 1`，不改变原 kind/id/body 主键。CAS 使用 `UPDATE records SET body=?,revision=revision+1 WHERE kind=? AND id=? AND revision=?`；影响行数不是 1 就回滚并返回 409。新增写使用 `BEGIN IMMEDIATE`，所有读取/校验/编号/SKU/写入/回执/事件在同一个连接内执行。不得在 UoW 中调用当前 `server.get/put`，它们另开连接会破坏事务。

补充表：

| 表 | 唯一约束与用途 |
| --- | --- |
| `operation_receipts(principal_id,operation_id,action,request_hash,response_json,created_at)` | 唯一键 `(principal_id,operation_id)`；同 key 同参数直接返回原回执；不同参数 409 `IDEMPOTENCY_KEY_REUSED` |
| `product_skus(sku_id PRIMARY KEY,product_id UNIQUE)` | 唯一 SKU 在同一事务维护；旧数据迁移先检测冲突，不能自动合并商品 |
| `sequences(name PRIMARY KEY,next_value)` | 原子分配 display_number，不以 `max(all_of())+1` 分配 |
| `outbox(stream_id,seq,event_id UNIQUE,event_type,payload)` | 提交与失效事件同事务；消费者按 seq 幂等处理 |
| `run_revocations(run_id PRIMARY KEY,reason,revoked_at,operation_id)` | 不可逆run撤销tombstone，授权前后都可登记；issue_grant同库检查 |
| `run_authorizations(grant_id PRIMARY KEY,run_id,write_generation,status,scope_json,revoked_at)` | status=`active/revoked`；所有 Agent 写提交同事务核验 grant 与 write_generation，撤销后旧结果不能提交 |
| `job_items(job_id,item_id,status,lease_owner,lease_until,attempt,...)` | 唯一 `(job_id,item_id)`；一个租约持有者能提交 |
| `live_slot(slot_id PRIMARY KEY,session_id,room_id,state,start_operation_id,...)` | slot 固定为 1；持久“首期单直播间”与 start 幂等 |

`operation_receipts` 只保证声播本地动作重复提交不重复生效，不声称 DeepSeek/MiniMax 远端调用恰好一次。事务里不能持锁等待模型、TTS、网络或长文件扫描。

### 4.3 save_product 事务

```python

    request: ProductSaveRequest, *, mutation: MutationContext,
    principal: Principal, store: SqliteStore,
) -> ProductSaveReceipt: ...
```

执行顺序：权限→规范化 request hash→BEGIN IMMEDIATE→幂等查询→声播同库核验 grant.status/write_generation/允许对象和字段→读当前商品及预期 revision→验证身份决定与字段处理清单→规范化当前商品和明确 patch→校验 SKU/必填/图片/知识文档→分配新商品编号或保留旧编号→CAS/insert→记录变更路径与失效 outbox→保存原回执→COMMIT。回执即权威完成证据，适配层再 GET 可确认字段回读与 revision。指明“只改某字段”时 payload 的每个改变路径都须在 grant/目标补丁 allowlist 内，不能用完整商品请求覆盖其他字段。

无变化更新返回原 revision 与 `changed_paths=[]`；同一次业务保存不能仅因更新时间变化造成无意义失效。若客户端丢失响应，用原operation_id调用`read_operation_receipt`查询，不换ID再创建。

### 4.4 cancel/replace 与真实提交的序列化

```python
def revoke_grant(
    run_id: str, grant_id: str | None, *, expected_write_generation: int | None, reason: Literal['cancel', 'replace'],
    operation_id: str, principal: Principal,
) -> RevocationReceipt: ...

def check_grant_in_transaction(
    uow: UnitOfWork, *, grant_id: str, expected_write_generation: int,
    action: str, resource_id: str, changed_paths: list[str],
) -> None: ...
```

`revoke_grant`在声播`BEGIN IMMEDIATE`内先写不可逆run_revocations tombstone（即使grant尚未生成），再把已存在grant标revoked、write_generation加一、关联待提交job标取消、写回执和事件。issue_grant同事务先查run tombstone，命中拒绝，迟到授权不能复活。业务提交检查与撤销锁定同一个库：若业务提交先提交，撤销回执列已生效操作；若撤销先提交，后到业务提交返回 `GRANT_REVOKED`。这是可实现的线性化边界，不要求撤销已成功保存的商品。

前端或 Agent 本地先记 cancelled 不构成撤销。必须等待声播 RevocationReceipt 才向调用者报告“旧写权已撤销”；未拿到回执保持 cancel_pending 并按 operation_id 对账。`follow_up` 请求只加入当前 task 的串行队列，当前 run 完成后按新输入建立下一 run；不会默认 revoke。`new_task` 新建独立任务/grant；`replace` 先拿旧 grant 撤销回执，再给替代任务发新 grant。

## 6. 模块补丁与脚本版本

统一模块键：

```text
opening_long / opening_short / product_intro / selling_points / campaign / cta / transition
```

`opening_long/opening_short` 是互选开场文本；`transition` 可按需关闭。无活动时 `campaign` 为明确 disabled，不生成空泛活动承诺。`ScriptVariant` 表示 A 商品第 1 版这条版本线；`ScriptRevision` 是该版本线的一次不可变修订。

```python
class ModuleAction(BaseModel):
    key: ModuleKey
    action: Literal['generate', 'patch', 'reuse', 'disable']
    target_ref: TargetRef            # 明确商品/版本/模块/段落/字段
    expected_base_revision: str | int | None
    base_module_revision_id: str | None
    dependency_refs: list[DependencyRef]

def generate_module_patch(

def validate_module_patch(
    candidate: ModulePatchCandidate, plan_item: ScriptPlanItem,
    base: ScriptRevision | None, context: ContextBundle,

def commit_module_patch(
    candidate: ModulePatchCandidate, *, job_id: str, item_id: str,
    lease_token: str, expected_generation_epoch: int,

```

`generate_module_patch` 先读取原文和计划，给 DeepSeek 只请求允许变化的模块 JSON，不能要求它顺便重写整稿。`validate_module_patch` 检查模块 allowlist、需要模块存在、句子结构/长度/简体、引用合法、关键报价和活动条件、旧模块不能越界修改；沿用当前基础检查并限制一次自动纠正，不新增独立语义审查 Agent。

提交过程：

1. 外部模型响应在事务外形成 candidate，失败不修改正式脚本。
2. 声播同库事务内重新核查 grant/write_generation、租约、preparation 当前 epoch、冻结依赖 hash、目标基准修订与允许修改的字段/段落。明确只改某段时，对其他段落逐字/hash保留。
3. 新内容建立新的 ModuleRevision；reuse 模块保持原 module_revision_id，不重编号、不改变正文。
4. 构造新 ScriptRevision，保留同 variant/version_number，script_revision 加一，parent 指旧稿。
5. 逐模块 Receipt 保存 old/new ID、精确改动范围、依赖版本、原因和正文使用年龄；活动更新不重置 selling_points 的使用年龄。
6. 更新准备产物引用和 job item 完成状态；**不调用旧 `attach_scripts`**。
7. 旧输入时保存可审计 candidate 引用，item 标 `superseded`，不把结果挂到当前准备记录或 room。

`body` 等组合哈希由程序按模块引用计算；单模块复用不等于整稿 commerce_signature 直接判旧。`commerce.script_is_stale` 为旧稿兼容入口，新稿按实际 module dependency hash 判断可复用与否，正式开播仍检查整包当前性。

## 7. 持久任务与旧输入 fence

### 7.1 状态和响应

| 对象 | 状态 |
| --- | --- |
| Job | `queued/running/succeeded/partially_failed/failed/interrupted/cancelled/superseded` |
| JobItem | `queued/leased/running/succeeded/failed/interrupted/cancelled/superseded` |
| 外部调用尝试 | `not_sent/sent/result_received/timeout_unknown` |

`202 accepted` 含 `job_id/status/events_cursor`，不等于生成完成。查询返回 `items` 的输入 hash、已复用/新生成计数、失败分类、产物 ref 与可重试性。旧 `completed/error/not_run` 由兼容 adapter 投影，新服务内部只使用上表语义。

```python
def enqueue_job(request: JobRequest, *, mutation: MutationContext, principal: Principal) -> JobReceipt: ...
def claim_item(worker_id: str, *, lease_seconds: int = 120) -> ClaimedItem | None: ...
def renew_lease(claim: ClaimedItem) -> None: ...
def commit_item(claim: ClaimedItem, output: ItemOutput) -> ItemCommitReceipt: ...
def reconcile_expired_leases(*, now: datetime) -> RecoveryReport: ...
def retry_failed_items(job_id: str, item_ids: list[str], *, mutation: MutationContext) -> JobReceipt: ...
def cancel_job(job_id: str, *, mutation: MutationContext) -> JobReceipt: ...  # 仅取消该job；整run取消另走revoke_grant
```

worker 循环：claim→读取冻结 context→检查取消/epoch→事务外执行→检查输出→声播同库事务内 grant/write_generation/lease/epoch/dependency fence→保存结果及事件。item 的 lease_token 变化后旧 worker 不得提交。外部请求可长于租约时，heartbeat 续租；续租失败后禁止发新请求，已发请求返回只能登记结果。仅在Agent库检查cancelled不能替代同库grant校验。

### 7.2 哪些变化使什么失效

| 变化 | 可复用 | 必须重新计算/完成 |
| --- | --- | --- |
| 活动或优惠变化 | 商品、有效研究、未引用活动的主体模块及其音频 | 两种开场、campaign，引用旧条件的 cta/其他模块；计划与最终发布 |
| 商品库出现新head | 已固定旧ref的准备和批准仍保存；无关差异只提示 | 消费字段有差异时采用/start需保留或刷新决定；当前停售/明确撤回硬拦截；真正refresh后才失效受影响内容与整包批准 |
| 仅顺序变化 | 商品、研究、主体模块、未变文本的内容缓存 | 原序号开场映射、缺少的开场文本/音频、PlaybackPlan |
| 仅音色变化 | 全部文本、顺序与开场模式 | 对新声音指纹缺失的音频、manifest/publication |
| 用户取消 | 已提交商品、已完成不可变产物和有效音频缓存 | 停止新任务；未提交结果不推进当前准备状态 |

旧任务可贡献有效内容缓存，但不能把旧 plan、旧活动、旧音色重新激活。不要仅比较 room 是否仍含 product_id 就允许 attach，这不能证明输入仍有效。

### 7.3 重启与远端超时

启动时按 job lease 状态恢复，不在 GET `/jobs` 查询时改变任务业务状态。旧服务 `list_jobs()` 的“TASKS 不存在就 interrupted”判断只用于旧任务迁移。

模型生成与 TTS 不是可查询恰好一次事务。sent 后超时且未知远端完成情况，记录 `timeout_unknown`；若本地已有同 key 有效 WAV，优先回读。无结果查询能力时保持 timeout_unknown 并返回需对账/人工明确重试的状态；不能自动重复付费调用。明确用户重试必须新建 attempt 并保留原 attempt 的未知与可能重复计费事实；不能声称远端 exactly-once。业务状态提交仍受幂等和 fence 保证不重复生效。

## 8. 编译 occurrence、跨圈长短开场和手动跳播

### 8.1 数据结构与签名

```python

    occurrence_id: str               # 同一 script 重复出现也必须不同
    product_id: str

    compiled_entry_id: str

    scripts: Mapping[str, ScriptRevision], *, compiler_version: str,

def collect_audio_requirements(plan: CompiledPlaybackPlan, voice: VoiceConfig) -> AudioRequirements: ...
```

用户决定 order，编译器不选择优先卖哪个商品。列表不按 script_id 去重。输入引用必须同商品、同 preparation 范围、无缺失模块；发现必要开场文本缺失返回 `MISSING_MODULE` 和精确 module/variant 需求，主 Agent 只补写该部分再重编译。

### 8.2 确定性公式

令原始 occurrence 数为 `n`，`r` 是从 0 开始的完整圈数，`i` 是 1-based 原始 item 位置：

```text
global_position = r * n + i
opening_mode = long if (global_position - 1) % 5 == 0 else short
```

非循环只编译 `n` 项。循环编译超周期 `L=lcm(n,5)` 项（最多原始列表的五圈），存 `L` 个可引用 entry 后重复超周期。`L` 同时是 `n` 与 5 的倍数，所以超周期重复不会把长开场位置重置错。不是每一圈强制第一个商品长开场。

例：原顺序 `[A第1版,B第1版,A第2版]`，`n=3,L=15`。第一圈全局 1/2/3 为长/短/短；第二圈 4/5/6 为短/短/长；第三圈 7/8/9 全短；第四圈 10/11/12 为短/长/短；第五圈 13/14/15 全短；下一超周期的 16 再长。

需要准备的音频由超周期内实际引用模块去重收集。非循环某 occurrence 只需一种开场；循环 n 非 5 的倍数时同 occurrence 在不同圈可能需要两种开场，应准备两种实际会用的声音，而非“本轮只选短就宣称永久循环齐备”。

### 8.3 手动跳播合同

```python
async def jump_to_entry(
    room_id: str, *, publication_id: str, target_compiled_entry_id: str,
    target_supercycle_index: int | None, expected_session_id: str,
    expected_epoch: int, action_id: str, principal: Principal,
) -> PlaybackActionReceipt: ...
```

调用者必须给已编译 entry ID。它已经固定 occurrence、原编排圈相位和 opening_mode。`target_supercycle_index=None` 表示当前超周期；显式跳至其他超周期必须给整数。实际全局位置为 `target_supercycle_index*L+phase_index+1`。跳过多少项、重播多少次不会改 mode。

如果用户只指定 product/variant，可信选择层先解析为某个明确 entry；有多个候选时返回候选或采用当前圈中的下一项并在回执中明确，不由模型猜一个同商品同版本出现项。插播不增加 occurrence 计数。当前 `Room.action` 的 sentence级 reorder 不应直接改变 v2 原编排语义：新版播前重排必须新编译 plan；播中临时控制仍保持原 publication 的 mode。


音频需求至少绑定 `spoken_text_hash/provider/model/voice/normalized_style_hash/renderer_version`；每个需求关联 module_revision_id 和 sentence_ref 方便监控，但内容缓存键不必包含无关 plan_revision，从而能重排复用。

TTS 具体步骤：

1. 同一提交事务验证当前human AudioApprovalReceipt、精确review_hash/requirements/voice/readset与费用上限，再从冻结requirements读句子；缺批准不创建可执行任务。每项claim事务再查批准/授权/epoch并预留请求预算，不从当前script重新读可变内容。
2. `speech.cached_audio` 验证现有 WAV；有效即复用。
3. 对同房间 audio_key 加受控同 key 锁；再次查缓存，避免两个 worker 同时付费。
4. 事务外调用 `speech.render`，目标先用受控 temp 目录；验证 WAV 帧数、采样率、时长和内容文件 hash；`os.replace` 原子移动到最终音频目录。
5. 事务内再次校验批准仍active且精确绑定、item lease/run grant/preparation epoch/readset；更新AudioManifest需求映射和job成功回执。撤销或旧输入仅留缓存，不激活。
6. 若第五步发现旧输入，仅保留有效缓存，不改变当前 manifest。文件先落盘而后数据库提交失败会留下可复用孤立缓存，不会留下假 ready 清单。

manifest ID 用规范化 JSON hash，不拼接 `tts.values()`；因为字段值未来可能含 dict/None，且字典字段顺序不是协议。manifest 明确 `required_total/ready_total/missing/corrupt/stale`。`all_ready` 必须 requirements 非空且所有必需项绑定有效文件、voice 指纹一致、依赖当前；不能只比较一个 count。

正常播出仍只读本地 WAV，找不到必须报错，禁止进入常规在线 TTS 补偿。现有插播在线 TTS 保持原独立路径，不纳入首期播前 Agent 新能力。

### 10.1 publication 请求与原子动作

1. 权限验证准备任务和候选目标房间归属；候选发布不会覆盖活动 session。

5. 从 draft 构造候选 room config 内容用于检查，product_ids仍只引用；commerce为本场覆盖；保存候选基准 room revision。**不写 room 正式配置和 adopted 指针。**
6. 同一声播事务写 publication candidate、preparation 的候选ready引用、幂等回执与 outbox，任一步失败全部回滚；Agent库随后按回执更新投影。

回执返回 `publication_id/publication_hash/base_room_revision/readiness=ready_to_adopt或needs_revision_choice/adoption_state=unadopted/review_ref`。纯文案/语音审核可在仍合法固定旧内容上完成；若普通新head的消费字段差异未决，candidate可保存但readiness=needs_revision_choice，采用/start前必须决议。ready_to_adopt不表示已经采用、更不表示已播出；不生成真实session_id。同房间可以保存多个候选，但只有用户显式采用且CAS成功的候选成为正式配置。

### 10.2 review 快照

```python
def create_review(publication_id: str, *, principal: Principal) -> ReviewPacket: ...
def validate_publication_current(publication_id: str, *, expected_hash: str) -> PublicationCheck: ...
```

ReviewPacket 包含 candidate publication hash、base/current room revision、正式商品引用与所有配置字段、研究和计划来源入口、模块差异、用户顺序/长短开场、音色/音频状态、adoption状态、阻塞与非阻塞待办。这里只规定后端查询结构，不设计页面。

review snapshot hash 是全部关键 refs 和当前检查结果的摘要；review创建后实际绑定的商品ref/房间/模块/音频或动态head差异、当前控制/选择证据变化，旧hash不得采用/开播。普通新head不改旧内容，重建动态ReviewPacket并让用户选择保留/刷新；keep仅刷新检查快照，不重发immutable Publication或使音频批准失效，实际refresh才按受影响内容重建候选。不能由 Agent 自己把“看过”当作人工采用或开播确认。

### 10.3 人工 adopt_snapshot

```python
def adopt_snapshot(
    room_id: str, publication_id: str, review_snapshot_hash: str, *,
    expected_room_revision: int, operation_id: str, principal: Principal,
) -> AdoptionReceipt: ...
```

仅人工身份具备 `snapshot:adopt`。同库短事务校验房间不是活动中、snapshot当前性、expected_room_revision、显式采用对象，随后以候选配置更新room并CAS递增版本，设置`adopted_publication_id`，写不可变AdoptionReceipt/operation/outbox。其他候选保留、不采用。这个动作不创建live session，不发送播放命令，不输出声音。

回执返回 `room_revision_after/adopted_publication_id/adoption_id` 和供start使用的最新检查快照hash。采用期间文件可能变化时仍在start再次验证。两个候选同时被采用时只有一项CAS成功，另一项回读当前配置并请求明确重新采用，不能last-write-wins。

### 10.4 人工 start

```python
async def start_prepared_room(
    room_id: str, publication_id: str, review_snapshot_hash: str, *,
    expected_room_revision: int, action_id: str, principal: Principal,
) -> StartReceipt: ...
```

`principal` 必须具备人工 `live:start`，准备 Agent 凭据不具备。start必须引用room已采用的publication，未adopt的candidate即使完整也拒绝。adopt和start是两个独立动作；不逐句/逐稿重复批准，但本次新增TTS前的本场整包文案批准（见10）。现有旧播放测试不代表新批准门槛已实现，必须新增门槛回归。

启动流程：

1. 持有进程内 `start_lock` 与目标 Room.lock（固定顺序获取，所有调用一致）；回读 publication 与 room config，必须匹配adopted_publication_id和AdoptionReceipt。
2. 读/验review hash、精确固定源ref、模块、编排和必需WAV；用evaluate_revision_currentness核对当前可售/撤回控制及每个消费差异的保留/刷新回执。未决差异返回PRODUCT_REVISION_CHOICE_REQUIRED，停售/明确撤回返回PRODUCT_UNAVAILABLE/SOURCE_WITHDRAWN；不因普通新head直接强制刷新。其他陈旧返回REVIEW_STALE/PUBLICATION_STALE/AUDIO_MISSING。
3. 一个短写事务登记 action_id 幂等、领取 `live_slot=1`、创建持久 live_session 的 `starting` 记录，绑定 publication，提交。
4. 事务外从不可变 plan 载入内存 Room 队列，冻结音色，生成首次 epoch/attempt；不在线合成常规音频。
5. 更新 live_session 为 `running`；返回 session_id/publication_id/OBS 既有 `/live/{room_id}` 地址与当前状态。无 player 连接仍可处于 preparing，沿用现有行为。
6. 第三步提交后进程崩溃，恢复服务把 starting/running 标 `interrupted`，释放 live slot 或等待明确恢复策略；默认不重启扬声器播报。相同 action_id 回读原 session 结果，不创建第二个 session。

步骤 3 到 5 不可能形成内存与 SQLite 的单个物理事务，因此必须保留 starting 状态及恢复逻辑，不能宣称“整次开播是单 SQLite 事务”。首期运行服务器固定单 worker；多 worker 部署若未实现跨进程播出 owner，启动时明确拒绝配置，而非只靠 Python `start_lock`。

## 14. 最小可实施任务切片与验收

| 顺序 | 交付函数 | 必须先具备 | 单元/合同验收 |
| --- | --- | --- | --- |
| S1 仓库与CAS | UoW、operation receipts、save_product | 当前schema纯函数抽取 | 同key创建一次、同key异参拒绝、并发SKU唯一、旧写revision递增、事务失败无半写 |
| S2 草案与模块 | save_session_draft、submit/commit patch | S1+冻结ContextBundle | 不改room生成、只改活动保留主体、未知条件不造价格、旧epoch无激活 |
| S3编译与TTS | compile plan、requirements、manifest | S2+script modules | n=1/3/5/6/10循环mode、重复occurrence、缺模块返回、所需音频齐备、只补缺失 |
| S4发布与采用 | publish_preparation、create_review、adopt_snapshot | S1–S3 | candidate不改room；adopt需人工且CAS；任何一步失败全部回滚，review与实际包一致 |
| S5人工start接入 | start_prepared_room | S4+现有Room ACK/owner | 重放start单session、过期review拒绝、常规无在线TTS、单live slot、starting重启不自动播 |
| S6旧协议回归 | route adapters/migrations | S1–S5 | 商品字段、优惠、房间隔离、旧稿、音色、OBS owner与epoch全部历史行为保持或有明确协议升级 |

补充强制故障点：模型返回前取消；模型返回后提交前改活动；音频文件已移动但DB提交失败；publication写到一半抛错；发布后商品价格变化；start占slot后进程崩溃；同audio_key双worker；旧lease持有者迟到。每个案例检查业务终态、回执、版本与事件，不以日志文字“成功”判定。

设计验收指标：CAS/幂等/旧epoch/越权反例全部阻断；未修改模块内容hash与module ID完全不变；TTS新合成集合等于有效缓存之外的required集合；publication内所有依赖可读且hash匹配；声播GET/read-only接口无业务状态变更。性能/费用阈值须实施真实模型探针后标定，设计阶段不编造延迟或成功率。

## 15. 必须保持的工程不变量

1. 唯一Agent发布操作是最终`publish_preparation`，只形成unadopted candidate；不得恢复“先把草案发布到room再生成”或Agent自动采用的旧设计。正式room只由用户adopt_snapshot更新，start独立。
2. 主 Agent 使用类型化 HTTP 客户端；子 Agent不拿声播写入或人工start凭据；CLI只作诊断薄壳，首期不强制MCP。
3. ContextBundle是完整输入ref和精确规则，不是只有摘要；脚本生成服务显式吃bundle，不暗读最新room作为输入。
4. 模块键统一 `opening_long/opening_short/product_intro/selling_points/campaign/cta/transition`。
5. 手动跳播使用原编排 entry 的 mode；跨圈按全局原序号1/6/11，插播不计数。
6. 声播run_authorizations及业务写提交同库事务，权限代数统一叫write_generation。Agent数据库只保存执行/临时数据及声播引用；follow_up串行，new_task独立，replace/cancel拿声播撤销回执后才称写权撤销。
7. 本文件没有实现任何新接口，函数签名是工程合同；后续实现仍需按具体类型声明、依赖注入和测试补齐。

## 16. 原文导入与接受分析的精确事务

### 16.1 Blob导入

```python
def import_blob(
    content: bytes, *, declared_sha256: str, media_type: str,
    original_name: str, mutation: MutationContext, principal: Principal,
) -> BlobReceipt: ...

def read_blob(blob_ref: BlobRef, *, byte_range: tuple[int, int] | None,
              principal: Principal) -> BlobReadResult: ...
```

调用者是文件接收/解析适配层，不是模型自由构造二进制。声播command transport中的payload是受限base64；原始文件按配置默认25MiB上限、PNG/JPEG/WebP图片另按当前4.5MB图片字段限制处理；超过上限返回413而不是截断。服务计算SHA256、检查声明与内容一致、media白名单、文件头/编码、文件名只作元数据不作路径；blob path固定为受控根目录下`sha256[:2]/sha256`。禁止执行宏、文档内命令或通过附件获取额外权限。

事务边界：先暂存同文件系统临时文件并校验→原子rename到hash位置→声播短事务核验grant/write_generation与幂等、注册blob记录、artifact可访问范围、回执。若事务失败，文件可能成为孤立缓存，不能成为可引用业务artifact；后续成功重放可领养同hash文件。blob本体不可变，用户替换文件必须生成新BlobRef，不修改旧路径内容。`read_blob`检查blob记录ready、hash、principal scope与范围；不接受任意文件路径，404与403按实际资源区别返回。

### 16.2 接受临时分析报告

```python
class AcceptAnalysisReportRequest(BaseModel):
    preparation_id: str | None
    expected_preparation_revision: int | None
    report_type: Literal['product_analysis', 'session_analysis', 'audience_research']
    logical_report_id: str | None
    expected_report_revision: int | None
    input_dependency_refs: list[ArtifactRef | RecordRef | BlobRef]
    generation_epoch: int | None
    payload: ProductFactsReport | SessionConfigReport | AudienceScenesReport
    source_blob_refs: list[BlobRef]
    user_edit_target: TargetRef | None
    frozen_readset: FrozenReadsetEnvelope  # 程序从branch manifest/工具读取轨迹构造，非模型自由填

def accept_analysis_report(
    request: AcceptAnalysisReportRequest, *, mutation: MutationContext,
    principal: Principal,
) -> AnalysisAcceptanceReceipt: ...
```

调用者：主Agent的合并工具，或用户明确编辑已接受报告的后端命令。子Agent仅能提交Agent暂存报告，不能自发提升为正式研究。`logical_report_id`空表示新报告，非空表示同报告的新修订；报告旧版本不可变。原文payload完整上传/已导入blob引用，不能只传AgentDB staged_artifact ID让声播自行读另库。

内部算法：

1. 按report_type解析严格schema，拒绝类型不匹配；事实候选/证据/假设/未知分栏，研究假设不得直接覆盖正式商品事实。
2. 事务外验证已导入blob内容与引用位置，记录canonical content_hash；长内容的不可变blob替代内联正文。
3. 声播`BEGIN IMMEDIATE`：检查operation原回执、grant/write_generation/目标对象权限、expected报告revision与完整业务readset；preparation head或epoch变化时按16.3精确证明未消费的输入未变后重绑定，不以粗revision直接判三路报告全stale。catalog必须preparation_id=None，只更新全局分析head。
4. 校验所有source已在声播、引用的页/段落/单元格范围可定位；原始附件里的指令仍是数据。用户指定段落时比较base_revision并禁止其他段落变化。
5. 保存不可变analysis artifact revision及source refs，CAS更新同报告head；preparation scope才同事务更新对应分析分支引用，catalog不创建或修改preparation。
6. 按变化路径计算下游失效：顾客场景研究变化只重算消费它的卖点/模块计划；纯编辑展示标题不使所有TTS失效。generation_epoch由声播失效计算递增，不接受模型任意填写新epoch。
7. 写AcceptanceReceipt与outbox后提交；Agent根据回执保存ref。未知提交结果用原operation查询，不重复创建报告。

返回：`accepted_artifact_ref/preparation_ref/changed_paths/invalidated_refs/next_generation_epoch`。CAS冲突返回409、grant撤销403、blob未导入或hash变化409，所有失败不更新head。接受动作不会保存正式商品、采用snapshot或开播。

### 16.3 三路报告类型与readset重绑定

| worker role | wire report_type | payload唯一类型 |
| --- | --- | --- |
| product_facts | product_analysis | ProductFactsReport |
| session_config | session_analysis | SessionConfigReport |
| audience_scenes | audience_research | AudienceScenesReport |

报告同时保存冻结业务readset（ref、消费path、该path内容hash），而不是把preparation整对象hash当所有分支的输入。同批三份报告从prep@N开始，先接受product报告只追加analysis_refs导致head变N+1，这个索引追加不是另外两份报告的业务输入，不能让它们全部stale。

`FrozenReadsetEnvelope`包含origin_manifest_id、origin_manifest_hash、dependencies:list[DependencyRef]、source_refs及envelope_hash。dispatch的可信ContextService按任务类型建立最低必需输入集合；worker读取工具只允许该集合，新增网络来源由工具服务追加不可变来源记录。主接受适配器从BranchTask和读取轨迹取得完整envelope，不允许模型临提交删掉依赖。声播验证服务调用身份、envelope规范hash、来源refs与分配范围后保存该完整manifest，再执行逐path比对；人工编辑既有报告则从声播旧报告metadata继承readset并追加真实编辑输入，不采信浏览器自填“未消费”声明。

接受算法：主Agent先回读当前prep head并带其expected revision提交；服务同事务验证grant与scope→读取报告冻结readset的每个实际消费字段→与当前声播内容逐项比hash。若仅容器head、分析索引、未消费字段变化，可证明独立输入未变，则保留原origin refs、建立effective readset重新绑定当前版本，并产生RebaseReceipt(old_head,new_head,unchanged_paths,proof_hash)。再用当前expected CAS接受报告并追加引用。三份报告因而可顺次成为N+1/N+2/N+3，不能覆盖彼此引用。若主Agent读后又发生并发写，CAS409后重新回读重试；不能在服务里无限last-write-wins。

若价格/规格/用户目标等真实消费输入变，返回INPUT_STALE及精确paths/refs，拒绝该份报告并只重算受影响分支；无法证明未消费也拒绝。epoch不同本身不是无条件允许重绑理由，必须完整readset证明且显式回执。accepted报告只追加索引不递增内容epoch；接受报告更新已被下游消费的业务结论时，才按依赖触发内容失效。catalog报告及read_analysis_report允许scope=catalog且preparation=None，不读写prep。

## 18. Undo必须是新CAS补偿

```python
class UndoMutationRequest(BaseModel):
    original_operation_id: str
    target_ref: RecordRef
    expected_current_revision: int
    restore_paths: list[str]
    before_image_ref: BlobRef | ArtifactRef

def undo_mutation(
    request: UndoMutationRequest, *, mutation: MutationContext,
    principal: Principal,
) -> CompensationReceipt: ...
```

调用者：用户明确撤销，或授权范围内的可逆补偿计划；不是cancel的自动副作用。命令回执必须保留before_image_ref、changed_paths、after_hash。undo先查询原回执与变更路径，确认restore_paths属于原改动且当前actor有权限；读取before_image和最新目标，按expected_current_revision做新CAS，保存新revision和补偿回执，触发相关依赖失效。历史版本、operation和publication始终保留。

如果原操作后同字段被别人改动，返回409 `UNDO_CONFLICT`及冲突路径，不能强制把旧before_image整包覆盖回去。无关字段可以保留，但必须由明确paths patch形成新版本。撤销商品创建只在无其他业务引用时执行允许的archive补偿，不物理删除历史；有引用时返回需人工处理。撤销采用snapshot需要用户显式采用另一个仍有效候选，不能把旧room revision数字倒退；live session已start时本期拒绝undo采用配置，先人工停止。

第3—19节为领域参数签名，正式HTTP公开handler统一采用`handler(args,mutation,principal)`；其领域实现通过私有`_apply_xxx(uow,args)`接收当前事务。execute_command只解析/鉴权/dispatch，不包第二层UoW。模型/TTS请求是事务外工作，submit、claim和commit分别使用各自短run_mutation；不能在一个长事务内await它们。query只用一致读事务，不能调用写handler或开启嵌套写事务。

注册表每项实际包成`HandlerSpec(handler, mode='sync'|'async')`，mode由代码固定。`async execute_command`对sync handler经`anyio.to_thread.run_sync(partial(...))`调用，对async handler显式await；query同步SQLite读取也在受控线程执行，连接在对应线程/UoW内创建。不能直接return一个coroutine当回执，不能把async函数传入同步apply_in_uow。`start_prepared_room`是async公开handler：先拿async start/Room锁，分别在线程内执行短`run_mutation`登记starting与最终状态，两个事务之间await内存播放器装载/通知；不在SQLite写锁内await。preview仅submit同步命令，真正TTS由后台runner执行。下节30项字典列出精确handler映射；实现registry构造器为start标async，其他纯提交命令标sync并进行启动校验。

## 22. 最终复查：版本选择与运行收尾的服务接线

本节与16 §3、§8一致。`record_product_revision_choice`为第30个command，不增加主Agent工具；入口必须是可信human Principal、对精确diff的实际选择，不能用Agent自填decision_ref。

```python
class RecordProductRevisionChoiceCommand(BaseModel):

                        principal, _apply_revision_choice)

def _apply_revision_choice(uow: UnitOfWork, args: ProductRevisionChoice,
        principal: Principal) -> RevisionChoiceReceipt: ...

def evaluate_revision_currentness(selected_refs: list[RecordRef],
        choices: list[RevisionChoiceReceipt], current_controls: list[ProductControl],
        readset: list[DependencyRef]) -> RevisionCurrentnessReport: ...
```

固定算法：验证human权限/操作幂等→同UoW回读prep所选旧ref、观察到的当前head、canonical diff与当前控制→若不匹配返回DIFF_STALE；停售/撤回拒绝keep→keep写独立choice artifact/索引/outbox，**不**更改prep内容revision/generation_epoch→refresh调用既有`_apply_refresh_product_reference(uow,...)`，不嵌套公共事务；返回精确ref、diff与回执。refresh只更新商品引用和影响清单，不自动取得改话术/付费权，后续按原Goal决定或另请求明确改稿。选择后有新head须重新比较，旧选择不批准未知差异。

| 接入点 | 检查与输出 |
| --- | --- |
| publish_preparation | grant仅在候选写入时检查active；同库固定输入合法，currentness决定ready_to_adopt或needs_revision_choice，不偷偷刷新 |
| create_review | 纯读，ReviewPacket包含head_diff、current_controls、pending_choices、choice_refs；动态hash覆盖这些证据 |
| create_text_review / approve_text_for_audio | 复用中央currentness；仍合法旧固定文案可审/合成，说明差异与后续采用门槛；硬拦截不批准新合成 |
| adopt_snapshot / start_prepared_room | 同事务重查当前控制与已处理消费差异，回执固定choice_refs；keep合法旧版即可，不要求生成run仍active |
| revoke_grant / job claim/commit | 撤权事务令后续claim、submit、绑定失效；已合法提交成果保留，迟到外部结果仅可留缓存，不激活旧引用 |

`RunClosureReceipt`属于Agent运行库，声播不跨库读取它来授权human采用/start。声播以自身业务回执、内容、批准和当前性判断；运行器可以把closure_ref投影给用户。终结run仅撤销未来写权，不使合法Publication或已保存资料失效。尚未受理/未提交job撤销，已提交项写入撤权回执；未知供应商结果留可对账状态，不把unknown当免费重试。
