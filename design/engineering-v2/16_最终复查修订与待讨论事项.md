## 2. 图执行排他，不用业务租约冒充checkpoint保护

首期固定一个Agent服务进程，但必须实做独占：

```python
class InstanceLock:
    def acquire(self, normalized_data_root: str) -> LockHandle: ...
    def release(self, handle: LockHandle) -> None: ...

class GraphExecutionRegistry:
    async def acquire_thread(self, thread_id: str, invocation_id: str) -> GraphHandle: ...
    async def cancel_and_join(self, handle: GraphHandle, *, deadline: float) -> DrainResult: ...
    async def assert_no_live_owner(self, thread_id: str) -> None: ...
```

Windows实现使用真正的OS文件排他锁（原生适配或已锁版本的锁库），不以“写了PID文本”代替排他。启动在打开saver和恢复任务前取得同数据根锁；第二进程即使换端口也拒绝。锁持有至所有图调用退出且saver关闭。

同thread执行锁覆盖 `aget_state → select_input → ainvoke/astream → 最终aget_state`；主和分支都遵守。DB租约过期仅表示需要收敛旧owner，不能直接启动同thread的新invoke。失租先停止新动作、取消并await旧调用退出；无法取消的调用保持draining/reconciling，不释放图执行锁。不凭固定超时或PID数字猜旧checkpoint写入者已死。

业务撤权回执与执行者完全退出分开记录。用户可以看到“业务写权已撤销，旧调用仍在退出”；不能因此再启动同thread恢复。新PID只在OS锁已可取得时恢复；未来多进程需要另设计saver fencing，本期不声称支持。

## 3. 统一终结服务：成功、失败、阻塞都收尾

```python
async def terminalize_run(
    run_id: str, requested_outcome: RunTerminal, *, cause: TerminationCause,
) -> RunClosureReceipt: ...

async def reconcile_finalization(run_id: str) -> FinalizationProgress: ...
```

调用方为Coordinator/RunExecutor，不向模型提供此工具。`finish_turn`只提交待核验结果；Coordinator在最终回执给用户前完成关闭。WAITING_USER/WAITING_JOBS不是终态，不撤销其仍需工作的授权。

1. Agent事务保存requested_outcome/cause、设置内部FINALIZING，禁止新的本地派发和claim，保留冲突scope slot。
2. 若从未派发grant且能在同Agent事务禁止未来授权，可直接走本地关闭；否则以稳定operation对声播revoke并查回执。这里复用撤权技术，不把失败伪装成用户取消。
3. 取消未领取分支/声播项，通知在途工作退出；已发出的供应商请求可能仍返回，已发生费用不抹除。声播revoke后的迟到结果仅可留缓存，不能激活业务引用。
4. 图执行者按第2节退出；未知的供应商结果保留unknown及后续查询入口。撤权未知或同thread仍可能写checkpoint时，保留FINALIZING/needs_reconciliation，不先释放可产生冲突的slot。
5. 再核验既有业务成果依赖，保存RunClosureReceipt（requested_outcome与收尾复验后的actual_outcome）和最终状态/continuation_options，释放scope slot。重复finalizer回读同回执。

完成之后撤销的是**继续写入权**，不追溯撤销已经合法保存的商品、报告、稿件、批准或候选。Publication由业务引用/人工批准/当前性决定有效性，不因其生成run已正常关闭而失效。最终结果复验检查business readset和ClosureReceipt，不再要求已关闭run的grant仍active。否则会形成“成功关闭导致自己成功无效”的循环。

`runs`增加finalization_phase/requested_outcome/closure_ref和派发冻结标记；状态新增FINALIZING。关闭阶段下次启动先对账，不再启动模型尝试重新“完成”已完成动作。用户取消/replace仍保留CANCELLED/SUPERSEDED含义，和完成/失败共用技术性收尾。

## 4. 最终请求窗口与attempt账本

不新增自定义第十Middleware。M6做受管循环预算，模型适配器在最终公开请求序列化后、网络发送前做准确到所用估算器的请求窗口保护：

```python
def estimate_final_provider_payload(payload: ProviderPayload,
                                    profile: ProviderProfile) -> TokenEstimate: ...

async def reserve_attempt(scope: ModelCallScope, purpose: ModelPurpose) -> AttemptTicket: ...
async def mark_attempt_sent(ticket: AttemptTicket, payload_hash: str) -> None: ...
async def settle_attempt(ticket: AttemptTicket, result: KnownModelOutcome) -> None: ...
async def reconcile_model_attempts(owner: str) -> AttemptRecoveryReport: ...
```

估算含system blocks、最终messages、过滤后tools schema、response schema及供应商编码开销，预留输出/工具往返和估算误差。M3/M4/SDK摘要之后仍要过最终保护，不能只检查request.messages。使用模型profile和实际token估算器版本，无法安全估算时保守拆分或明确CONTEXT_LIMIT，不静默删Goal/价格/版本/批准。

`model_attempts`持久状态：reserved→sent→succeeded/known_failed/outcome_unknown，或者reserved→aborted_before_send。网络发送前先持久sent；崩溃后sent未结算按unknown，不能因未见响应就免费重试。已发调用的次数不退还；没有usage则未知，不补造0元。取消用专用BaseException路径/受控结算兜底再原样抛出；记录失败保留缺口，不能因此重调已收到响应。

SDK压缩等旁路同样经过适配器窗口检查并记录独立attempt/purpose；M6受管主/worker次数上限不冒充所有调用或总金额封顶。若外层ticket覆盖主请求，摘要子请求应另建child ticket，不复用同ticket计两次；trusted CallContext负责关联，不允许模型指定预算身份。首期同时保留主循环、摘要、文案、TTS各自计量。

## 5. 跨夜等待与授权

单机首期 `run_authorizations.expires_at=None`，含义为到明确终结/取消/replace之前有效，而不是永久允许任意后续任务。scope、Goal、write_generation、租约和取消tombstone仍逐次检查；关闭由第3节统一撤销。部署者以后启用TTL时必须先补有限可信续期，不能临时改数据库或让模型重授权。

文案批准和业务事实仍受当前性/有效期限制：跨夜活动过期、资料撤回、改稿/改声/重排，照旧需要处理。基础设施等待本身不强迫用户重复批准同一有效稿件。用户可查看并取消等待中的任务。

## 6. 审稿“修改”及问题失效的闭环

`edit_text`是审核卡的合法真实答案，**不是批准**。答案先落QuestionService再supersede旧展示快照；原Goal范围内按同run/thread恢复，M3给出用户修改原文/精确目标，主重做相关计划/文案/编译，再提出新版审核。原Goal仅audio_prepare等不包含改稿时，提出范围扩展并用replace关闭旧任务后另建，不将follow_up排在仍WAITING_USER的自己后面。

如果用户在编辑器手改导致open问题过期，QuestionService保存可追溯的system resolution `target_superseded`并唤醒原interrupt，使工具返回stale/需重读，不假造人工同意。新问题绑定新对象/hash。恢复载荷使用02 §9唯一QuestionResumeEnvelope：human_answer＋answer_event_ref，或system_resolution＋system_resolution_ref；记录类型与传输载荷分开。旧问题不能既被删除/失效又让执行永久等一条再也不能回答的问题。

## 7. 全字段处理不等于全字段重写

`assemble_product`新增可信 `allowed_write_paths` 和 `selling_point_action=preserve/set/clear`。所有字段都必须处理，但未获准改动的已有字段必须preserve。卖点preserve时不要求proposed_points、不顺带格式归一或写空；set只在新建或已有允许路径内，clear必须明确许可。

两个兼容卖点字段只在有权set/clear时一起按现有规范维护；原字段不一致而本次只改价格时，原样保留并给advisory，不能为了同步它们越权重写。研究新结论可作为影响建议，不会自动取得商品字段/旧稿的写权限。

## 8. 商品新旧版本选择：用户已确认规则

用户2026-10-16选择：**展示新旧差异，让用户选择保留旧版或刷新；已停售或明确撤回的信息必须拦截。**

| 情况 | 处理 |
| --- | --- |
| immutable旧修订仍存在，新head产生 | 旧草案/旧稿不自动切换；展示差异，不一概要求更新 |
| 无关字段变更 | 提示即可，不因新head使已批文本/音频失效 |
| 本场消费字段有差异 | 采用/开播检查展示具体新旧值和受影响句，要求保留或刷新决定；不偷偷替换 |
| 用户保留 | 保存绑定prep/所选旧ref/观察到新head/diff hash的RevisionChoiceReceipt；不改文本/顺序/音色，原有效音频和批准不因选择本身失效 |
| 用户刷新 | 进入既有refresh_product_reference规则，仅更新精确引用和影响清单；不自动改稿。原Goal已含改稿或另有明确授权时才执行必要局改并重审；不扩出未获准字段 |
| 当前已停售、修订/信息明确撤回、活动自身过期 | 强制blocking，保留选择不能绕过；旧资料仍可历史查看 |
| 选择后又有新head | 旧选择不批准未知新版差异；重新比较并展示新变化，当前正文仍不自动改 |

```python
class ProductRevisionChoice(BaseModel):
    preparation_id: str
    pinned_product_ref: RecordRef
    observed_head_ref: RecordRef
    diff_hash: str
    choice: Literal['keep_pinned', 'refresh']

def evaluate_revision_currentness(
    selected_refs: list[RecordRef], choices: list[RevisionChoiceReceipt],
    current_controls: list[ProductControl], readset: list[DependencyRef],

def record_product_revision_choice(args: ProductRevisionChoice,
    mutation: MutationContext, principal: Principal) -> RevisionChoiceReceipt: ...
```

该新command仅可信human可调用，聊天也须绑定真实当前决定，不作为Agent自选保留的工具。声播同一事务校验ref/新head/diff/控制状态并保存回执。`refresh`通过同UoW私有实现调用已有刷新逻辑，不嵌套公共run_mutation。`keep_pinned`写独立choice artifact/索引和事件，不推进内容generation_epoch、不改Preparation内容refs，不使自身批准失效。

统一当前性函数由publish/create_review/approve/adopt/start按所需阶段调用；纯审核TTS可生成仍合法的固定文本，但采用/start必须已有相关差异决定且无强制阻塞。动态ReviewPacket/hash包括当前差异、control和choice证据，AdoptionReceipt/StartReceipt保留本次选择refs；immutable Publication和音频资产不为保存一个选择而重写。当前不可售/撤回标记属于可变控制信号，不能藏在旧revision里忽略。

首期只定义播前/采用/start校验，不引入播中运营Agent。当前正在播放的不可变快照不被商品普通编辑自动重排或改稿；直播中的撤回处置属于后续播放器控制设计。

## 9. 经营建议与“二号商品”身份

RF08改为：“**模拟上场二号商品表现较好，建议本场放到开头讲解。**”原文保留销售比较的模拟性质及观察限制，不宣称提前就会提升转化。

`ordering_suggestion`保存来源场次/商品编号映射、精确product_ref、依据、限制及建议动作。它不是新的执行指令，也不直接写Playlist。用户采纳后，若多个已选版本/occurrence均对应该商品，要明确移动一个已选项还是整个商品组；不按裸“2”猜第2张卡或第2版。未在当前货盘选择该商品时不自动加入。

本次fixture以符号ref表示“二号商品”，测试加载器必须绑定另一个明确测试商品及来源编号映射；不按名称连接正式商品。原测试目标保持顺序，因此RF08处理为defer（有价值、待决定），不把经营建议笼统称为错误。另附用户明确采纳时的正向测试场景，采纳仍需由实际测试请求形成决定回执，fixture不能自授权。

## 10. 部分成果与下一步

```python
class ContinuationOption(BaseModel):
    option_id: str
    source_run_id: str

```

既有run GET返回continuation_options，不加新的恢复数据库。WAITING_USER补答原问题；WAITING_JOBS继续监听；FINALIZING先对账；BLOCKED/FAILED/已取消等终态在用户明确“继续未完成部分”后形成新的合法run，复用已保存product/script/job refs和成果，不继承被撤销的grant。还在原Goal内且原run未终结的重试使用已有job/原operation规则。

Continuation只是安全投影，不执行按钮自身的文字；可信入口回读当前对象和剩余要求再冻结新Goal。付费unknown先对账，不能用“继续”自动重复扣费；成功音频/已保存新商品不重做。此机制不绕过Goal/费用/采用或start决定。
