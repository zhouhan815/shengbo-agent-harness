## F-D01 · P2 · 固定商品引用与采用前强制刷新互相冲突

| 项目 | 说明 |
| --- | --- |
| 位置 | `01_类型与持久化.md:304`；关联 `03_声播业务服务与事务.md:496/525`；相反约定见 `13_任务识别与历史上下文设计.md` §4 |
| 当前冲突 | 01写“显式引用旧商品的草案维持该revision……采用前必须刷新和重查”。13明确当前场次固定P@4，即便catalog head更新到P@5也只提示，未经用户明确刷新不替换。03“当前源版本”没有说明是所选精确版本还是catalog head，容易延续前一条强制升级语义。 |
| 触发 | 用户已审稿、生成声音并发布基于P@4的候选；另一个商品资料任务只修改P@5的内部备注，或者只为下一场修改资料。用户没有选择刷新当前场次。 |
| 影响 | 实施者可能强迫场次刷新P@5，导致已批准文案、编排或声音包无故过期；或者按另一份规范完全不检查当前可售状态。两个极端都来自“精确引用当前性”与“全局最新状态”混在一起。 |

| 验收 | P@4已批准，P@5只改未消费备注：批准不失效、不强制刷新，采用和启动仍用P@4；用户明确刷新P@5：精确引用变化后重新计划/审核；全局归档、不可售等强制状态变化：即使所选P@4不可变也阻断，给出具体限制证据。 |

| --- | --- |
| 位置 | `09_复盘输入与话术闭环设计.md:279`；相反约定见10 §2 H11、§7 |
| 当前冲突 | 09写“原批准对改变部分失效”，读起来像其余部分仍持有效批准。10已选择整包review_hash批准，改一个实际使用句子也使旧整包批准stale，随后审核新包；复用的是音频资产，不是旧批准的片段权限。 |
| 触发 | 复盘使一个selling_points句子被替换，其余稿件、声音、顺序都不变。实现按09做逐句批准状态，并把旧批准拼接到新包。 |
| 影响 | 出现第二套隐含“增量批准”系统，无法用单个整包review_hash证明当前playlist/文本/声音都由同一次明确审核覆盖。可能错误发布新包，或接口状态与前端审核状态分裂。 |
| 最小修订 | 09该行改为“旧整包批准stale；重新审核当前整包；相同文本/voice的既有音频缓存可复用，新批准后只补实际缺项”。不新增逐句批准类型。 |
| 验收 | 一个实际使用句子变化后旧批准立即stale；prepare/claim/commit/publish都拒绝旧批准；用户批准新整包后未变音频命中缓存，供应商请求数仅等于新缺项；复盘未采用建议的说明变更、且实际绑定输入不变，不制造音频重合成。 |

## 结论与复核方法

上述三项都是同一设计内的合同歧义，能在进入编码前通过小范围文字和验收用例修订解决，不需要用户改变产品目标。推荐先同步01/03/09/10，再由总体审查复验；仅修订新增分册、不修订旧分册会把两个相反实现同时留给下一位开发者。

未发现必须新增第四个分析 Agent、第二套业务数据库或新的排序/批准服务才能解决的问题。本文没有把文档静态一致性当作真实模型行为、HTTP事务或播放验证已经通过。
