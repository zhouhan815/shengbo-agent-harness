# 2026-10-16 最终复查：运行时、恢复与上下文边界

本轮为设计审查，没有构建或运行业务 Agent，没有调用模型、TTS 或修改声播数据。按 `agent-harness-design`、`deep-agents-core` 检查现有 00/01/02/05/10/11/13，并交叉查看 03/04/06/14 的服务边界。下列为尚需明确的设计缺口，不将已有授权、readset、人工审核、未知写结果对账等完整机制重复列为问题。

## 审查结论

主/子 Deep Agent 的角色隔离、唯一持久派发路径、声播业务权威、不可变 Goal、全文按需上下文、音频人工门槛的方向成立。最值得在实施前补齐的是：**执行线程与 checkpoint 的排他保护，以及父 run 失败时后台任务的统一收口**。其余三项属于较小但会影响成本解释和长任务恢复的合同缺口。

| ID | 级别 | 结论 | 建议处理 |
| --- | --- | --- | --- |
| RT-01 | P1 | 租约 fence 保护业务提交，尚未保护同 thread 的 SDK checkpoint 写入 | 首期进程独占＋图 thread 执行锁；失租必须等旧调用确实退出后再接管 |
| RT-02 | P1 | BLOCKED/FAILED 的父 run 没有统一收敛已派发后台工作 | 统一终结路径：禁止派发、撤权对账、收敛子任务与业务 job、保留已提交成果 |
| RT-03 | P2 | M6 示例只统计 messages，漏掉实际 system/tools，和全文预算设计不一致 | 以最终 provider 可见请求估算；超限前拒绝调用，不能靠 messages 长度假称守住窗口 |
| RT-04 | P2 | grant 有 expires_at，但跨夜人工等待后的过期处理未定义 | 首期选择明确的不过期到显式终结政策，或设计可信有限续期；不由模型续权 |
| RT-05 | P2 | 模型尝试预占在取消/进程退出后缺少持久收敛语义 | 区分 reserved/sent/known/unknown；取消不直接释放 sent 费用，恢复可查询和展示 |

## RT-01：SDK checkpoint 写入不受业务租约 fence 自动保护

**位置：** `02_运行时与中间件.md` §4.2、§5.3、§8（约 226、321、720–763 行）；`01_类型与持久化.md` §5.3（约 296 行）；`05_实施顺序与验收.md` SDK-14。

**触发：** 旧 main/branch 正在等待慢模型或工具，heartbeat 因阻塞/错误失去租约；Supervisor/恢复器依据过期租约启动新 attempt，仍使用 `main:{run_id}` 或 `branch:{task_id}`。旧协程尚未完全结束，其模型结果晚到。M1/M2 与业务 fence 能拒绝后续业务写入，但 SDK 可能先把模型结果/节点状态写进同一个 saver thread。

**用户影响：** 新执行的消息、pending 节点、压缩文件或中断位置可能被旧执行追加/覆盖；下一次恢复从错误分支继续。数据库中“只有一个有效业务提交者”不等于“只有一个 checkpoint 写入者”。

**最小补法：** 首期既然限定本机单应用 worker，就把这一限制做成真实独占约束：

1. 进程启动先取得同数据根的 OS 排他锁，持有至 saver、工作协程都关闭；第二进程拒绝启动。
2. 每个 graph thread 有进程内执行锁，锁覆盖从 `aget_state/select_payload` 到 `ainvoke/最终状态读取` 的整段，且只在旧协程实际退出后释放；不能因 DB lease 到期立即释放。
3. heartbeat 失租必须取消并 `await` 旧 invocation 收敛；无法证明已退出时保留 `reconciling`，不对相同 thread 启动新调用。
4. 新 PID 只在取得 OS 锁、确认旧 owner 已退出后按持久记录恢复。未来要多进程再引入可验证的 saver fencing/等价机制，而非仅靠业务 epoch。

**验收：** 用可取消和暂时不可取消的 fake model 分别阻塞；强制租约到期、投递恢复唤醒，记录 checkpoint 写入和 graph 并发。旧调用未退出时相同 thread 的新 invoke 次数为 0；退出后只恢复一次；第二进程在同数据根启动失败；旧进程结束后新进程能恢复同 thread。

## RT-02：终态失败需要统一关闭仍持有写权的后台工作

**位置：** `02_运行时与中间件.md` §7.2、§8、§10（约 705、743–747、795–829 行）；`01_类型与持久化.md` §5.1；`03_声播业务服务与事务.md` §7。

**触发：** 主 Agent 已派发多个分支或文案/TTS job，随后因预算耗尽、不可恢复 DomainError、记录设施不可用等进入 `finish_invocation_blocked_or_failed`。现有取消/replace 会远端 revoke；普通 BLOCKED/FAILED 的收尾没有指定同等的授权关闭和后台任务收敛。

**用户影响：** 页面已显示本次失败/阻塞，active slot 可能释放；旧 voice grant 下的后台 job 却继续领新项、提交或产生费用。接下来新 run 开始，用户无法判断哪些成果属于失败任务后仍在发生的动作。

**最小补法：** 设计 `RunFinalizer.terminalize_run(run_id, requested_outcome, cause)`，供 COMPLETED/READY_FOR_REVIEW/BLOCKED/FAILED 的最终关闭使用；与取消共用撤权技术，保留各自业务终态含义。先原子冻结本地派发，再对真实已派发 grant 执行稳定 operation 的 revoke，对账后取消未领取分支/业务项、收敛在途结果。已提交成果保留，晚到文件可缓存，不能重新绑定目标。需要继续等待的 WAITING_JOBS/WAITING_USER 不使用终结路径。撤权未知时内部保存 finalization phase 与 requested outcome，不先声称“已停止”，不先释放会有冲突的 slot。

**验收：** 启动并行分支和多项 TTS stub，在主模型预算耗尽及 trace 写故障两个位置注入 barrier。最终关闭提交后，新 provider dispatch 数为 0、旧业务绑定次数为 0；已提交合法产物仍可读；revoke 超时显示收尾对账，不能提前给出全停回执；重复 finalizer 不重复撤权/取消；WAITING_JOBS 不误停正在工作的子任务。

## RT-03：最终请求窗口预算必须包含系统观察和工具 schema

**位置：** `02_运行时与中间件.md` §6.7（约 555–559 行）使用 `count_tokens_approximately(request.messages)`；同文件 §6.4 将业务关键观察追加到 `system_message`；`13_任务识别与历史上下文设计.md` §6.2 要求计算系统提示、工具 schema、关键观察及余量。

**触发：** messages 很短，但 Skill 目录/系统提示、M3 关键观察、几十个 typed tool schema 已很大，或后续供应商消息序列化额外展开信息。只计 messages 的预占估计低于 24000，真实输入可能已超过配置上限。

**用户影响：** 所谓受控压缩没有及时触发，模型请求失败/被供应商截断；预算和调试数字无法解释实际输入，关键约束也可能丢失。

**最小补法：** 将 `estimate_final_model_request(request, provider_profile)` 作为统一估算入口，计算 system blocks、最终 messages、当前过滤后的工具 schema、response schema 和供应商开销，保留估算误差余量；在 M3/ToolPolicy 修改后、真实 provider 请求前执行。摘要等旁路单独估算/记录，不能误称覆盖。超限返回可恢复的 `CONTEXT_LIMIT`，按既定拆分/分页方案处理，不能默默删 Goal/权限/价格。

**验收：** messages 仅 100 tokens、system/tools 超过限额时 provider 调用次数为 0；给定同一最终请求，budget 与 trace 的估算输入一致；压缩后在 capture 的实际请求中仍有精确 Goal、版本和批准条件。

## RT-04：人工等待期间授权到期的策略应在实施前冻结

**位置：** `01_类型与持久化.md` run_authorizations 表含 `expires_at`（约 132 行）；`02_运行时与中间件.md` §2.2 等待仍保留 active slot、§9 恢复；`10_人工确认与语音门槛设计.md` §8。

**触发：** 用户晚上停止操作，次日批准同一审核卡，文案与相关 refs 没变，但 run grant 已过期。M1/voice 正确拒绝过期 grant，然而没有明确从 WAITING_USER 到“可恢复有限授权”或“终结并创建后继”的路径；issue_grant 又是 run_id UNIQUE 和稳定 operation 幂等。

**用户影响：** 用户做了合法确认仍无法继续；如果实现者临时延长过期授权，可能绕过撤权 tombstone、扩大期限或重复启用旧费用额度。

**最小补法：** 首期可直接选择“grant 不做墙钟自动过期，随 run 显式撤销/终结”，字段允许 null，审批和业务条件本身仍按当前性检查；若坚持 TTL，则必须增加可信、可对账且不扩效果的有限续期机制，要求原 Goal/actor/对象未变、无 revoke tombstone、费用批准仍有效，并在 resume 前完成。不能让模型调用“重新授权”，也不要求用户因纯基础设施到期重复批准同一稿件。

**验收：** 推进时钟跨过一晚/TTL 后恢复；按所选政策要么正常继续、要么清楚等待可信续期，不能无入口永久占 slot。撤销、replace、过期事实/改稿后，旧批准和旧授权均不能复活。

## RT-05：模型预算 ticket 的取消和崩溃需要确定的状态转换

**位置：** `02_运行时与中间件.md` §6.7（约 553–570 行）；`01_类型与持久化.md` Agent SQLite 表与 §5.3；`11_原始运行记录与调试台设计.md` usage/取消记录。

**触发：** `reserve_model_attempt` 后协程收到 `asyncio.CancelledError`（不属于普通 Exception），或进程在 provider 发出之后被终止，`close_attempt` 未执行。现有示例只有正常/Exception 分支，BudgetLedger 的持久状态及启动收敛未列入表与恢复算法。

**用户影响：** 预算可能长期留在无法解释的预占状态；若实现者恢复时直接清除，则可能把已发出但未获结果的费用当成未发生，并无意扩大重试次数。

**最小补法：** 定义持久 `model_attempts`，稳定 attempt_id 绑定 run/invocation/span，区分 reserved、sent、succeeded、known_failed、outcome_unknown、aborted_before_send。provider 前显式标 sent；取消用 finally/专用 BaseException 分支保存真实已知状态再原样抛出。启动把孤立 reserved/sent 按可证明发送与否收敛；sent unknown 不退还尝试计数、不假装费用为 0，展示未知 usage，受剩余次数和原重试政策约束。记录失败不能诱发已获模型响应的无条件重调。

**验收：** 分别在 reserve 前、reserve 后未 sent、sent 后、已响应 close 前注入取消/崩溃；恢复后每次实际发出调用均有唯一 attempt，已发次数不清零；未知费用明确；未发调用不计为确定已收费；主/三个 worker 并发预占不能超过既定父 run 尝试上限。

## 无需询问用户即可落实的建议

RT-01、RT-02、RT-03、RT-05 均属于既定单机、可恢复、可观察、不重复收费目标下的工程补全，不需再询问需求。RT-04 首期建议选不过期至显式关闭的简单授权政策；这不改变活动有效期、对象 CAS、文本批准或用户可随时取消的业务边界。若产品未来要求自动会话过期，再单独设计 TTL 续期。

以上均为静态设计推演；实施后必须按所列 barrier、新 PID、真实 saver 和 provider stub 断言验证，不以本报告代替运行通过。
