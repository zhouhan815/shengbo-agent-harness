# 最终复查：中小商家操作旅程

审查日期：2026-10-16。范围：`PRELIVE-2.2`工程设计，重点03、04、06、09、10、12、13、14。仅审查文档，不表示这些接口、页面或Agent已实施。采用`agent-harness-design`的目标—动作—反馈、部分失败、恢复和证据检查方法。

审查立场：客户是商品相对固定、人员较少的中小商家。目标是在Agent中完成播前准备，声播提供业务后端和人工确认入口；声音播放可独立完成，视觉素材本期只给准备建议，不强迫上传。以下只列5项具有明确操作后果的P1/P2，不把已经设计的能力重新包装成缺口。

## 1. 已能串通的两条旅程

| 旅程 | 用户实际动作 | 设计应提供的连续出口 | 已有依据及判断 |
| --- | --- | --- | --- |
| A1 首次上传 | 上传商品截图、资料和本场要求 | 解析任务、来源定位；先辨商品，再决定新建或更新；必要问题合并展示 | 04§2、§7及10的H02/H05已覆盖；同名不覆盖、未知不补造 |
| A2 商品与顾客 | 提供最低身份，允许资料内分析或已明确的网络调研 | 事实和顾客场景可并行；主Agent汇合，保存全字段商品及可复用研究 | 04§4/§5、13§3覆盖；报告accepted与商品入库不是同一动作 |
| A3 本场与稿件 | 说明活动、语言、音色、版本要求 | 本场只存引用及覆盖；完整上下文汇合后按模块生成；保留全部依据 | 03§2、04§6、09§6覆盖；不把本场优惠写进日常商品正本 |
| A4 素材准备 | 查看建议或上传已有商品图 | 可执行的素材清单、文件/建议/缺失状态；声音链路继续 | 14§5/§6覆盖；可选视觉缺失为advisory，不应阻止纯声音候选 |
| A5 选稿重排 | 选择版本、拖动或选择分组/穿插/随机 | occurrence独立；预览无写入、应用后保存、重编译开场；不偷偷选品 | 12§1—§6已覆盖；同一版本重复播放不去重 |
| A6 审稿与声音 | 审核整包后批准；或提出修稿 | 批准后仅合成本场缺失音频；改稿应能立即继续，不陷入排队等待 | TTS强制门槛已覆盖；“修改文案”恢复分支存在M01问题 |
| A7 候选 | 看候选、差异和缺口 | 明确声音就绪、未采用、未开播；采用与开播独立 | 03§10和14§1覆盖；新源版本如何影响候选需M02统一 |
| B1 只更新资料 | 已选商品，上传新资料，说“更新这个商品” | 只更新商品、维护相关研究、列出话术影响；不改稿、不TTS | 13§1及§8.1、14验收矩阵覆盖；显式单字段修改需M03避免卖点顺带重写 |
| B2 复用历史 | 不重复解释旧顾客研究 | 查同product_id/context旧研究全文；证明复用或增量分析；保存有效绑定 | 13§3已覆盖；未知市场不能变成已研究的特定市场 |
| B3 部分失败 | 商品已保存，研究因能力不足未完成 | 告知已保存什么、欠什么，以及从哪一步继续；不再新建同名商品 | 后端部分成果保护已有；可执行的继续入口需M05补齐 |

## 2. 待补问题及最小修订

### M01 — P1：审稿卡选择“修改文案”可能被自己的等待任务卡住

| 项目 | 内容 |
| --- | --- |
| 触发 | 用户到语音批准卡，发现一句有误，选择“修改文案”，然后说出修改要求 |
| 文档证据 | 10§8写“该修改作为新follow_up/replace意图排队，原问题superseded”；01/02的WAITING_USER保留scope slot，follow_up在前驱完成后才启动 |
| 缺口 | 这里不能把follow_up和replace当可互换选择。原run仍在interrupt等待，问题却superseded；新follow_up又等待原run结束，可能没有任何事件能解除等待 |
| 最小修订 | 固定一种可执行路径：原Goal及grant范围内的修稿，将`edit_text`作为真实问题答案恢复原run，保持未批准并重做所需计划/稿件/编译/审核；超出Goal时走既有replace撤权路径。如果实现选择任何修稿都建新run，也必须明确走replace，不准把它排在仍WAITING_USER的原run后 |
| 验收 | 从H10点edit_text→提交一句修改→无需手动取消旧任务就执行；原批准不存在/失效；新版再次审核；无两个同时可写run、无TTS提前调用；页面重开仍能继续 |

### M02 — P1：固定旧商品版本与“采用前必须刷新”的规则需唯一化

| 项目 | 内容 |
| --- | --- |
| 触发 | 本场引用P@4，商品库更新P@5。商家只要更新商品、不要求改稿；随后准备采用原候选 |
| 文档证据 | 13§4写当前本场继续P@4、只提示新版；01§失效写“采用前必须刷新和重查”；03§10.2/10.4写商品/当前源版本变化则旧hash不得采用；10§7又按实际消费路径区分无关字段 |
| 缺口 | 实现者可能采用全head严格相等，也可能允许旧ref永远通过。前者会因内部备注改变反复逼商家刷新、重批；后者会放过已知被纠正的报价/适用限制。固定历史引用、提示更新与新一场可播性是不同判断 |
| 最小修订 | 将规则写进一个权威的当前性函数并由03调用：历史P@4始终可读且不自动刷新；比较本场实际消费路径和有效期。无关变更仅提示新版；相关事实被纠正/失效时，本场增加明确blocking impact，要求用户决定刷新及必要修稿，而不是自动改稿。新的head本身不等于应重写所有内容；批准、候选、采用和start共享同一结果。若首期选择“任何head变化都强制刷新”的保守策略，也须明确写为一致策略并披露此操作成本，不能两种策略并存 |
| 验收 | P@5只改内部备注：原稿/音频/批准不因无关变更失效；P@5纠正本稿引用的价格或适用限制：全局更新仍可完成且旧稿不被改写，但候选采用/start被阻断并定位具体旧句；显式刷新后只修复相关模块再审核 |

### M03 — P1：全字段组装示例无条件改卖点，可能违反单字段更新目标

| 项目 | 内容 |
| --- | --- |
| 触发 | 用户明确“只把该商品日常价178改为199，其余保留”；顾客研究被判定可复用 |
| 文档证据 | 04§5的`assemble_product`对所有字段先生成处理清单，随后无条件把`core_selling_points`、`selling_points`覆盖为主模型的`proposed_points`；正文又说price等保留原值、修改受Goal/grant限制 |
| 缺口 | 主Agent每次4A都重新提议卖点时，可能把商家手写卖点改掉；如果grant严格禁止，这个“必须set卖点”的示例又会让合法价格修改不断失败。语义上的“全字段完整”应是逐项set/clear/preserve，不是每次重写所有字段 |
| 最小修订 | `assemble_product`接收由原Goal和真实依赖变化决定的`selling_point_action`及允许路径集合：`preserve`时原样保留两兼容字段，不要求新points；仅新商品或范围内确有卖点维护时校验并set。研究变化对未获准字段只生成影响建议。主Agent不得把泛化的catalog_update覆盖显式“只改价格”约束 |
| 验收 | 价格-only：仅价格路径发生diff；原卖点文本、结构和hash逐字保留，研究可reuse，脚本/TTS/playlist写次数0；新商品：卖点完整且有事实依据；用户明确授权更新卖点：只更新允许路径并保持双字段规范 |

### M04 — P2：“二号商品卖得好”须映射上场稳定商品，不能理解成本场第二张卡

| 项目 | 内容 |
| --- | --- |
| 触发 | 复盘建议“二号商品上场表现较好，建议本场放到开头讲解”；本场卡片已拖动，第二张卡甚至是同商品另一版本 |
| 文档证据 | 09的RecapScope保存product/variant refs；12的卡片序号随位置改变、一个商品可有多个occurrence；当前RF08原文还使用“第2版移到第1版前” |
| 缺口 | 自然语言中的商品编号、播放位置、话术版本不等价。若只改建议措辞而不保留来源场次映射，主Agent可能移错商品，或把同商品所有版本都提前 |
| 最小修订 | RF08保留经营意义，并绑定来源场次/商品显示编号→精确product_ref的解析记录。展示“二号商品【名称】（上场商品编号）”，不是裸“2”。建议只生成有依据的ordering suggestion，不视为用户授权。用户采纳时再确定是先讲该商品哪一个已选版本，或按其明确方法把该商品组放前；未在本场选择该商品时不能借建议自动加入。本次fixture继续标synthetic，不编真实销售数据 |
| 验收 | 调换卡片顺序后，复盘仍指同一product_id；不能把“商品2”误作“第2版/第2项”；无采纳决定零playlist写入；用户只同意把某一已选项放首位，不移动该商品其他项；身份无法唯一映射只问这一个问题 |

### M05 — P2：部分成功和BLOCKED已有后端状态，但商家缺一个精确的“从这里继续”交接

| 项目 | 内容 |
| --- | --- |
| 触发 | 新商品已保存，研究/某版稿件/某句TTS失败；用户第二天重新打开，说“继续刚才的” |
| 文档证据 | 03持久任务与13研究绑定保护已提交成果；14允许BLOCKED保存已完成部分；06有成果和缺口，但没有统一描述下一动作如何引用原目标和部分成果 |
| 缺口 | “已保存商品、还缺研究”若只在聊天文本，下一run可能重新走新建商品、重付费或要求重传资料；BLOCKED是终态，不能把它当仍可直接resume的WAITING_USER。原问题仍open时，补材料又应满足问题而非无端新建run |
| 最小修订 | 用既有run查询/成果投影增加结构化`continuation_options`：原run、当前对象refs、已完成receipt、未完成requirements/blocker、可执行动作及其scope要求。WAITING_USER走原question回答；WAITING_JOBS只监听；BLOCKED/FAILED由明确“继续未完成部分”形成新follow_up/replace目标并复用已提交refs。新任务不继承已撤销grant，付费未知结果先对账。不要创建第二套恢复数据库或自动执行按钮 |
| 验收 | 新品保存后研究能力缺失→重新打开→补充材料/选择允许的资料内分析→沿原product_id继续，不重复建商品；稿件部分成功只补失败项；TTS unknown不自动重付；原Goal要求仍全部留存；终态和下一动作来源可在trace定位 |

## 3. 本轮没有发现需要扩大首期范围的事项

| 事项 | 保留结论 |
| --- | --- |
| 声音与视觉 | 视觉清单可缺文件；本期不生成视频、不配置口播画面hook，不因视觉缺失阻塞声音候选 |
| 自动营销决定 | Agent可分析、建议及说明依据；选品、主推次序、降价仍由用户决定。复盘建议不等于已被采纳 |
| 确认数量 | 明确商品和字段、已有授权且无冲突的更新直接执行；不增加“确认保存”“确认生成”一串泛泛弹窗 |
| 日常商品和本场 | 商品库唯一正本，本场存精确引用和覆盖；不能为每房间复制一个可编辑商品库 |
| 记录与验收 | 以真实refs、回执、逐项diff检查，不以聊天说“好了”替代；不要求模型公开私有思维链 |

## 4. 需要问用户的问题

本轮上述5项均可按既有授权作工程修订，不必再向用户询问已经确定的范围。RF08“二号商品”的具体真实商品身份与指标，属于未来导入真实复盘时的资料澄清，不是本轮synthetic fixture的阻塞问题。首期不因这次审查扩大到转化预测、利润策略、选品系统或播中控制。

本文件是文档走查结论，尚未执行真实商家可用性测试、模型识别测试或故障注入；上述验收项均待实施后运行。
