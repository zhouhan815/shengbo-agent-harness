## 2. 唯一提交链与所有权

```text
准备服务保存 SessionDraft + ContextBundle + ScriptChangePlan
  → 声播按冻结输入生成/修订模块（不改 room 当前配置）
  → 编译 PlaybackPlan（用户指定顺序，程序决定开场模式）
  → 按 AudioRequirements 完成缺失音频
  → publish_preparation：一个事务冻结尚未采用的 publication candidate/snapshot
  → create_review：对候选整包生成可读检查包
  → 用户 adopt_snapshot：CAS 更新 room 配置与 adopted_publication_id，不 start
  → 用户 start(adopted_publication_id, review_snapshot_hash)
```

本设计不定义前置 `publish_session_draft`。草案保存不是发布；Agent 的最终 publish 是候选整包完成，不是用户采用。生成、编排、TTS 都可针对草案完成，只有显式 `adopt_snapshot` 更新房间的正式待播配置。创建空 room 可以提前进行，但它不生成真实直播 `session_id`，也不改变当前直播。全局商品库操作可以没有 room/session 引用，不能为了调用商品接口伪造直播场次。

| 对象 | 权威所有者 | 写入规则 |
| --- | --- | --- |
| 正式 product | 声播商品库服务 | 4A 经校验后 CAS 保存；研究记录只给来源与依据，不成为第二份正式商品 |
| SessionDraft | 准备服务 | 2B 起保存，允许部分字段与未知项，不能被 `Room` 当正式配置读取 |
| 模块/脚本修订 | 声播脚本服务 | 不可变内容记录；当前选择保存在准备产物，不由 worker 自动挂 room |
| PlaybackPlan/AudioRequirements | 声播编译器 | 确定性产物；绑定输入修订和编译器版本 |
| publication | 声播发布服务 | 不可变候选整包；是否采用由独立 AdoptionReceipt 表达；room 只保存用户已采用指针和正式配置引用 |
| live session | 声播播放器服务 | 仅人工 start 创建；冻结 publication、音色及队列；准备 Agent 无该权限 |
| Agent checkpoint | Deep Agents 应用 | 保存计算位置与产物引用；不能作为声播业务提交的证据 |

历史 product_snapshot、ContextBundle 中事实快照用于追溯，不是可独立编辑的商品库。房间不能保存自己的商品正本。

### 2.1 Agent 数据库与声播数据库之间的边界

Agent 的任务状态/检查点可以在独立数据库；声播只把已接收的 SessionDraft、ContextBundle 输入、计划及 `accepted_preparation(preparation_id,preparation_revision,generation_epoch,grant_id)` 保存为冻结执行输入。大原文允许内容寻址导入并建立受控引用，不允许 worker 对任意 Agent 本机路径或 URL 随意抓取。权威 run grant、业务写入、job 结果和撤销记录必须位于声播同一 SQLite 事务域。

发布事务中“准备完成”指声播 `accepted_preparation` 的完成状态，不是跨库原子修改 Agent checkpoint。Agent 根据 PublicationReceipt/operation 查询幂等更新本地投影。输入同步或撤销未收到声播回执时，本地状态是 `sync_pending/cancel_pending`，不宣称已撤销声播写权。两个独立 SQLite 的“双写成功”不能当成分布式事务。

## 3. 版本层次与字段合同

禁止用一个 `revision` 同时表示商品版本、运行轮次和脚本版本。

| 名称 | 含义 | 何时变化 | 校验者 |
| --- | --- | --- | --- |
| `record_revision` | 数据库当前业务记录 CAS 版本 | 任一成功写入，包括旧 API 写入 | 声播仓库 |
| `preparation_revision` | 准备任务目标/输入集合版本 | 用户资料或需求、商品引用、场次要求变化 | 准备服务 |
| `draft_revision` | 某 SessionDraft 内容版本 | 配置草案有变化 | 准备服务 |
| `artifact_revision` | 不可变产物的版本 | 形成新产物 | 产物存储 |
| `script_revision` | 同一话术版本的修订序号 | 局部模块更新后产生新 script ID | 声播脚本服务 |
| `module_revision_id` | 不可变模块内容 ID | 该模块实际重写 | 声播脚本服务 |
| `plan_revision` | 用户编排、开场映射及其依赖版本 | 顺序、文本修订、循环或相关设置变化 | 编译服务 |
| `generation_epoch` | 禁止旧工作结果提交到当前准备状态的代数 | 影响生成/编排/音色输入改变或取消 | 准备服务/worker |
| `scope_epoch` | 声播权威 run grant 写权限代数 | 显式 cancel/replace 撤销旧 grant | 声播 run_authorizations，与写提交同事务检查 |
| `input_hash` | 某项工作消费的精确输入哈希 | 被消费字段或引用变化 | 程序计算 |
| `publication_id` | 一次不可变可播整包 ID | 成功发布新包 | 发布服务 |
| `session_id/epoch/attempt_id` | 真实播出场次/播出位置/单句尝试 | start、跳播/重试、句播放尝试 | Room |

新 HTTP 统一返回 envelope；旧 API 保留原 body。`record_revision` 不放进 `ProductInput` 的严格字段，避免被 `extra=forbid` 拒绝；现有 script.body.revision 继续表示脚本修订，与数据库列分离。

```python
class RecordRef(BaseModel):
    kind: str
    id: str
    record_revision: int
    content_hash: str

class MutationContext(BaseModel):
    operation_id: str               # 可信适配层稳定生成，重放不得更换
    preparation_id: str | None      # 全局商品任务允许 None，不伪造场次
    preparation_revision: int | None
    grant_id: str
    expected_scope_epoch: int
    request_hash: str               # 服务端再次计算，不能信任模型声称值

class ProductSaveRequest(BaseModel):
    product_id: str | None
    expected_revision: int | None   # 新建必须 None，更新必须精确值
    fields: ProductInput
    identity_decision_ref: str | None
    field_disposition_ref: str
    source_manifest_ref: str

class ProductSaveReceipt(BaseModel):
    operation_id: str
    status: Literal['committed']
    product: RecordRef
    product_payload: ProductInput  # 可读回全部字段，另含服务端 ID/SKU/display_number
    changed_paths: list[str]
    invalidation_event_id: str | None
```

补充约束：

1. `product_id=None` 的幂等重放必须返回第一次创建的 ID，不能再创建一个商品。
2. 已有 SKU/型号身份冲突时，`identity_decision_ref` 必须可查证用户对具体对象的决定；相似度不提供覆盖许可。
3. `field_disposition_ref` 覆盖实际 schema 全部字段；必填缺失阻塞，非适用/未知可选有记录。来源元数据保存在准备产物，不硬塞旧商品接口。
4. 更新字段采取明确 set/clear/preserve 语义。隐藏可选字段沿用现有“清除有效值”的规则；“未知”不能清除已知旧值。
5. 所有 `*_ref` 必须验证 preparation/room 可访问范围；不能让调用者给另一个任务的 artifact ID 即跨任务读取。

### 4.2 仓库签名及 SQL 边界

```python
@contextmanager
def unit_of_work(store: SqliteStore, *, write: bool = True) -> Iterator[UnitOfWork]: ...

def read_record(uow: UnitOfWork, kind: str, identity: str) -> RecordEnvelope: ...

def compare_and_swap(
    uow: UnitOfWork, *, kind: str, identity: str,
    expected_revision: int, body: dict,
) -> RecordEnvelope: ...

def insert_once(uow: UnitOfWork, *, kind: str, identity: str, body: dict) -> RecordEnvelope: ...

def begin_operation(
    uow: UnitOfWork, *, principal_id: str, operation_id: str,
    action: str, request_hash: str,
) -> OperationTicket | MutationReceipt: ...

def finish_operation(uow: UnitOfWork, ticket: OperationTicket, receipt: dict) -> None: ...

def append_event(uow: UnitOfWork, stream_id: str, event_type: str, payload: dict) -> EventRef: ...
```

`records` 增加 `record_revision INTEGER NOT NULL DEFAULT 1`，不改变原 kind/id/body 主键。CAS 使用 `UPDATE records SET body=?,record_revision=record_revision+1 WHERE kind=? AND id=? AND record_revision=?`；影响行数不是 1 就回滚并返回 409。新增写使用 `BEGIN IMMEDIATE`，所有读取/校验/编号/SKU/写入/回执/事件在同一个连接内执行。不得在 UoW 中调用当前 `server.get/put`，它们另开连接会破坏事务。

补充表：

| 表 | 唯一约束与用途 |
| --- | --- |
| `operation_receipts(principal_id,operation_id,action,request_hash,response_json,created_at)` | 唯一键 `(principal_id,operation_id)`；同 key 同参数直接返回原回执；不同参数 409 `IDEMPOTENCY_CONFLICT` |
| `product_skus(sku_id PRIMARY KEY,product_id UNIQUE)` | 唯一 SKU 在同一事务维护；旧数据迁移先检测冲突，不能自动合并商品 |
| `sequences(name PRIMARY KEY,next_value)` | 原子分配 display_number，不以 `max(all_of())+1` 分配 |
| `outbox(stream_id,seq,event_id UNIQUE,event_type,payload)` | 提交与失效事件同事务；消费者按 seq 幂等处理 |
| `run_authorizations(grant_id PRIMARY KEY,run_id,scope_epoch,status,scope_json,revoked_at)` | status=`active/revoked`；所有 Agent 写提交同事务核验 grant 与 scope_epoch，撤销后旧结果不能提交 |
| `job_items(job_id,item_id,status,lease_owner,lease_until,attempt,...)` | 唯一 `(job_id,item_id)`；一个租约持有者能提交 |
| `live_slot(slot_id PRIMARY KEY,session_id,room_id,state,start_operation_id,...)` | slot 固定为 1；持久“首期单直播间”与 start 幂等 |

`operation_receipts` 只保证声播本地动作重复提交不重复生效，不声称 DeepSeek/MiniMax 远端调用恰好一次。事务里不能持锁等待模型、TTS、网络或长文件扫描。

### 4.3 save_product 事务

```python
def save_product(
    request: ProductSaveRequest, *, mutation: MutationContext,
    principal: Principal, store: SqliteStore,
) -> ProductSaveReceipt: ...
```

执行顺序：权限→规范化 request hash→BEGIN IMMEDIATE→幂等查询→声播同库核验 grant.status/scope_epoch/允许对象和字段→读当前商品及预期 revision→验证身份决定与字段处理清单→规范化当前商品和明确 patch→校验 SKU/必填/图片/知识文档→分配新商品编号或保留旧编号→CAS/insert→记录变更路径与失效 outbox→保存原回执→COMMIT。回执即权威完成证据，适配层再 GET 可确认字段回读与 revision。指明“只改某字段”时 payload 的每个改变路径都须在 grant/目标补丁 allowlist 内，不能用完整商品请求覆盖其他字段。

无变化更新返回原 revision 与 `changed_paths=[]`；同一次业务保存不能仅因更新时间变化造成无意义失效。若客户端丢失响应，用原 operation_id 查询 `/operations/{id}`，不换 ID 再创建。

### 4.4 cancel/replace 与真实提交的序列化

```python
def revoke_grant(
    grant_id: str, *, expected_scope_epoch: int, reason: Literal['cancel', 'replace'],
    operation_id: str, principal: Principal,
) -> RevocationReceipt: ...

def check_grant_in_transaction(
    uow: UnitOfWork, *, grant_id: str, expected_scope_epoch: int,
    action: str, resource_id: str, changed_paths: list[str],
) -> None: ...
```

`revoke_grant` 在声播 `BEGIN IMMEDIATE` 内把该 grant 标 revoked、scope_epoch加一、关联待提交job标取消、写回执和事件。业务提交检查与撤销锁定同一个库：若业务提交先提交，撤销回执列已生效操作；若撤销先提交，后到业务提交返回 `GRANT_REVOKED`。这是可实现的线性化边界，不要求撤销已成功保存的商品。

前端或 Agent 本地先记 cancelled 不构成撤销。必须等待声播 RevocationReceipt 才向调用者报告“旧写权已撤销”；未拿到回执保持 cancel_pending 并按 operation_id 对账。`follow_up` 请求只加入当前 task 的串行队列，当前 run 完成后按新输入建立下一 run；不会默认 revoke。`new_task` 新建独立任务/grant；`replace` 先拿旧 grant 撤销回执，再给替代任务发新 grant。

```python
) -> JobReceipt: ...
```

`SessionDraft` 至少包含 room 引用、主题/目的/日期时区、product_ids、commerce、语言/音色/版本数/循环、明确用户选择、复用来源及未知项。完整配置字段按当前 `RoomCommerce` 校验。未齐的草案允许保存，但返回 `blocking_gaps`；未知金额不能通过默认 0 伪装齐全。

`ContextBundle` 冻结三路完整输入及来源引用：全部商品字段及 revision、完整研究及 evidence/hypothesis、完整 SessionDraft 及 revision；还包含旧稿全文/模块、用户决定。内容可大时按 ref 按需读取，但不能只保存摘要。模块任务要携带自己引用的精确 source paths 及其 hash，使局部失效可计算。

`commerce.quote(product, {"commerce": draft.commerce})` 可直接计算草案报价，完全不需要先写入房间配置。新生成适配必须从 ContextBundle 构造 effective product，禁止 `run_job` 再读 `settings(room_id)` 作为隐式生成输入。

因现有 `generation_facts` 把全部 KNOWLEDGE 排除，新模块服务须补充 `selected_knowledge_refs`：仅将计划明确要求的关键适用限制/活动条件放入对应口播，完整知识仍可回读并供 Q&A，不能一律塞入口播或一律排除必要限制。

## 6. 模块补丁与脚本版本

统一模块键：

```text
opening_long / opening_short / product_intro / selling_points / campaign / cta / transition
```

`opening_long/opening_short` 是互选开场文本；`transition` 可按需关闭。无活动时 `campaign` 为明确 disabled，不生成空泛活动承诺。`ScriptVariant` 表示 A 商品第 1 版这条版本线；`ScriptRevision` 是该版本线的一次不可变修订。

```python
class ModuleAction(BaseModel):
    key: ModuleKey
    action: Literal['generate', 'patch', 'reuse', 'disable']
    target_ref: TargetRef            # 明确商品/版本/模块/段落/字段
    expected_base_revision: str | int | None
    base_module_revision_id: str | None
    dependency_refs: list[DependencyRef]
    generation_instruction: str
    must_preserve_paths: list[str]
    acceptance_rules: list[RuleRef]

def generate_module_patch(
    context: ContextBundle, plan_item: ScriptPlanItem,
    base: ScriptRevision | None, *, model: CopywritingModel,
) -> ModulePatchCandidate: ...

def validate_module_patch(
    candidate: ModulePatchCandidate, plan_item: ScriptPlanItem,
    base: ScriptRevision | None, context: ContextBundle,
) -> ModulePatchValidation: ...

def commit_module_patch(
    candidate: ModulePatchCandidate, *, job_id: str, item_id: str,
    lease_token: str, expected_generation_epoch: int,
) -> ScriptPatchReceipt: ...
```

`generate_module_patch` 先读取原文和计划，给 DeepSeek 只请求允许变化的模块 JSON，不能要求它顺便重写整稿。`validate_module_patch` 检查模块 allowlist、需要模块存在、句子结构/长度/简体、引用合法、关键报价和活动条件、旧模块不能越界修改；沿用当前基础检查并限制一次自动纠正，不新增独立语义审查 Agent。

提交过程：

1. 外部模型响应在事务外形成 candidate，失败不修改正式脚本。
2. 声播同库事务内重新核查 grant/scope_epoch、租约、accepted_preparation 当前 epoch、冻结依赖 hash、目标基准修订与允许修改的字段/段落。明确只改某段时，对其他段落逐字/hash保留。
3. 新内容建立新的 ModuleRevision；reuse 模块保持原 module_revision_id，不重编号、不改变正文。
4. 构造新 ScriptRevision，保留同 variant/version_number，script_revision 加一，parent 指旧稿。
5. 逐模块 Receipt 保存 old/new ID、精确改动范围、依赖版本、原因和正文使用年龄；活动更新不重置 selling_points 的使用年龄。
6. 更新准备产物引用和 job item 完成状态；**不调用旧 `attach_scripts`**。
7. 旧输入时保存可审计 candidate 引用，item 标 `superseded`，不把结果挂到当前准备记录或 room。

`body` 等组合哈希由程序按模块引用计算；单模块复用不等于整稿 commerce_signature 直接判旧。`commerce.script_is_stale` 为旧稿兼容入口，新稿按实际 module dependency hash 判断可复用与否，正式开播仍检查整包当前性。

## 7. 持久任务与旧输入 fence

### 7.1 状态和响应

| 对象 | 状态 |
| --- | --- |
| Job | `queued/running/succeeded/partially_failed/failed/interrupted/cancelled/superseded` |
| JobItem | `queued/leased/running/succeeded/failed/interrupted/cancelled/superseded` |
| 外部调用尝试 | `not_sent/sent/result_received/timeout_unknown` |

`202 accepted` 含 `job_id/status/events_cursor`，不等于生成完成。查询返回 `items` 的输入 hash、已复用/新生成计数、失败分类、产物 ref 与可重试性。旧 `completed/error/not_run` 由兼容 adapter 投影，新服务内部只使用上表语义。

```python
def enqueue_job(request: JobRequest, *, mutation: MutationContext, principal: Principal) -> JobReceipt: ...
def claim_item(worker_id: str, *, lease_seconds: int = 120) -> ClaimedItem | None: ...
def renew_lease(claim: ClaimedItem) -> None: ...
def commit_item(claim: ClaimedItem, output: ItemOutput) -> ItemCommitReceipt: ...
def reconcile_expired_leases(*, now: datetime) -> RecoveryReport: ...
def retry_failed_items(job_id: str, item_ids: list[str], *, mutation: MutationContext) -> JobReceipt: ...
def cancel_job(job_id: str, *, mutation: MutationContext) -> JobReceipt: ...
```

worker 循环：claim→读取冻结 context→检查取消/epoch→事务外执行→检查输出→声播同库事务内 grant/scope_epoch/lease/epoch/dependency fence→保存结果及事件。item 的 lease_token 变化后旧 worker 不得提交。外部请求可长于租约时，heartbeat 续租；续租失败后禁止发新请求，已发请求返回只能登记结果。仅在Agent库检查cancelled不能替代同库grant校验。

### 7.2 哪些变化使什么失效

| 变化 | 可复用 | 必须重新计算/完成 |
| --- | --- | --- |
| 活动或优惠变化 | 商品、有效研究、未引用活动的主体模块及其音频 | 两种开场、campaign，引用旧条件的 cta/其他模块；计划与最终发布 |
| 商品事实变化 | 未消费该字段的研究或模块，可经依赖验证复用 | 消费字段的研究/卖点/模块；review 当前性 |
| 仅顺序变化 | 商品、研究、主体模块、未变文本的内容缓存 | 原序号开场映射、缺少的开场文本/音频、PlaybackPlan |
| 仅音色变化 | 全部文本、顺序与开场模式 | 对新声音指纹缺失的音频、manifest/publication |
| 用户取消 | 已提交商品、已完成不可变产物和有效音频缓存 | 停止新任务；未提交结果不推进当前准备状态 |

旧任务可贡献有效内容缓存，但不能把旧 plan、旧活动、旧音色重新激活。不要仅比较 room 是否仍含 product_id 就允许 attach，这不能证明输入仍有效。

### 7.3 重启与远端超时

启动时按 job lease 状态恢复，不在 GET `/jobs` 查询时改变任务业务状态。旧服务 `list_jobs()` 的“TASKS 不存在就 interrupted”判断只用于旧任务迁移。

模型生成与 TTS 不是可查询恰好一次事务。sent 后超时且未知远端完成情况，记录 `timeout_unknown`；若本地已有同 key 有效 WAV，优先回读。无结果查询能力时可按显式配置进行最多一次相同输入的付费重试，账本保留“可能重复计费”，不能声称远端 exactly-once。业务状态提交仍受幂等和 fence 保证不重复生效。默认不在未知网络重试中无限扣费；达到上限返回可恢复失败。

## 8. 编译 occurrence、跨圈长短开场和手动跳播

### 8.1 数据结构与签名

```python
class PlaybackOccurrence(BaseModel):
    occurrence_id: str               # 同一 script 重复出现也必须不同
    product_id: str
    script_revision_ref: ArtifactRef
    user_ordinal: int                # 1-based 原始编排位置

class CompiledEntry(BaseModel):
    entry_id: str
    occurrence_id: str
    phase_index: int                 # 0-based 超周期位置
    original_round_index: int        # 超周期内第几圈，0-based
    original_item_ordinal: int       # 本圈原始位置，1-based
    opening_mode: Literal['long', 'short']
    module_revision_ids: list[str]
    sentence_refs: list[SentenceRef]

def compile_playback_plan(
    draft: SessionDraft, occurrences: list[PlaybackOccurrence],
    scripts: Mapping[str, ScriptRevision], *, compiler_version: str,
) -> CompiledPlaybackPlan: ...

def collect_audio_requirements(plan: CompiledPlaybackPlan, voice: VoiceConfig) -> AudioRequirements: ...
```

用户决定 order，编译器不选择优先卖哪个商品。列表不按 script_id 去重。输入引用必须同商品、同 preparation 范围、无缺失模块；发现必要开场文本缺失返回 `MISSING_MODULE` 和精确 module/variant 需求，主 Agent 只补写该部分再重编译。

### 8.2 确定性公式

令原始 occurrence 数为 `n`，`r` 是从 0 开始的完整圈数，`i` 是 1-based 原始 item 位置：

```text
global_position = r * n + i
opening_mode = long if (global_position - 1) % 5 == 0 else short
```

非循环只编译 `n` 项。循环编译超周期 `L=lcm(n,5)` 项（最多原始列表的五圈），存 `L` 个可引用 entry 后重复超周期。`L` 同时是 `n` 与 5 的倍数，所以超周期重复不会把长开场位置重置错。不是每一圈强制第一个商品长开场。

例：原顺序 `[A第1版,B第1版,A第2版]`，`n=3,L=15`。第一圈全局 1/2/3 为长/短/短；第二圈 4/5/6 为短/短/长；第三圈 7/8/9 全短；第四圈 10/11/12 为短/长/短；第五圈 13/14/15 全短；下一超周期的 16 再长。

需要准备的音频由超周期内实际引用模块去重收集。非循环某 occurrence 只需一种开场；循环 n 非 5 的倍数时同 occurrence 在不同圈可能需要两种开场，应准备两种实际会用的声音，而非“本轮只选短就宣称永久循环齐备”。

### 8.3 手动跳播合同

```python
async def jump_to_entry(
    room_id: str, *, publication_id: str, target_entry_id: str,
    target_supercycle_index: int | None, expected_session_id: str,
    expected_epoch: int, action_id: str, principal: Principal,
) -> PlaybackActionReceipt: ...
```

调用者必须给已编译 entry ID。它已经固定 occurrence、原编排圈相位和 opening_mode。`target_supercycle_index=None` 表示当前超周期；显式跳至其他超周期必须给整数。实际全局位置为 `target_supercycle_index*L+phase_index+1`。跳过多少项、重播多少次不会改 mode。

如果用户只指定 product/variant，可信选择层先解析为某个明确 entry；有多个候选时返回候选或采用当前圈中的下一项并在回执中明确，不由模型猜一个同商品同版本出现项。插播不增加 occurrence 计数。当前 `Room.action` 的 sentence级 reorder 不应直接改变 v2 原编排语义：新版播前重排必须新编译 plan；播中临时控制仍保持原 publication 的 mode。

## 9. Required-only TTS 与音频清单

```python
def prepare_required_audio(
    preparation_id: str, requirements_ref: ArtifactRef, *,
    expected_generation_epoch: int, mutation: MutationContext, principal: Principal,
) -> JobReceipt: ...

def render_audio_atomically(
    requirement: AudioRequirement, *, directory: Path, renderer: SpeechRenderer,
) -> VerifiedAudioAsset: ...

def verify_manifest(requirements: AudioRequirements, manifest: AudioManifest) -> ManifestCheck: ...
```

音频需求至少绑定 `spoken_text_hash/provider/model/voice/normalized_style_hash/renderer_version`；每个需求关联 module_revision_id 和 sentence_ref 方便监控，但内容缓存键不必包含无关 plan_revision，从而能重排复用。

TTS 具体步骤：

1. 从已冻结 requirements 读取句子，不从“当前 script”重新读取可变化内容。
2. `speech.cached_audio` 验证现有 WAV；有效即复用。
3. 对同房间 audio_key 加受控同 key 锁；再次查缓存，避免两个 worker 同时付费。
4. 事务外调用 `speech.render`，目标先用受控 temp 目录；验证 WAV 帧数、采样率、时长和内容文件 hash；`os.replace` 原子移动到最终音频目录。
5. 事务内对 item lease 与 preparation epoch fence；更新 AudioManifest 需求映射和 job 成功回执。
6. 若第五步发现旧输入，仅保留有效缓存，不改变当前 manifest。文件先落盘而后数据库提交失败会留下可复用孤立缓存，不会留下假 ready 清单。

manifest ID 用规范化 JSON hash，不拼接 `tts.values()`；因为字段值未来可能含 dict/None，且字典字段顺序不是协议。manifest 明确 `required_total/ready_total/missing/corrupt/stale`。`all_ready` 必须 requirements 非空且所有必需项绑定有效文件、voice 指纹一致、依赖当前；不能只比较一个 count。

正常播出仍只读本地 WAV，找不到必须报错，禁止进入常规在线 TTS 补偿。现有插播在线 TTS 保持原独立路径，不纳入首期播前 Agent 新能力。

## 10. candidate publication、人工 adopt、人工 start 的事务

### 10.1 publication 请求与原子动作

```python
class PublishPreparationRequest(BaseModel):
    preparation_id: str
    expected_preparation_revision: int
    expected_generation_epoch: int
    room_id: str
    expected_room_revision: int
    draft_ref: ArtifactRef
    product_refs: list[RecordRef]
    script_revision_refs: list[ArtifactRef]
    playback_plan_ref: ArtifactRef
    audio_requirements_ref: ArtifactRef
    audio_manifest_ref: ArtifactRef

def publish_preparation(
    request: PublishPreparationRequest, *, mutation: MutationContext,
    principal: Principal, store: SqliteStore,
) -> PublicationReceipt: ...
```

事务之前先读/验证文件与 schema，准备 manifest hash；写事务内再次核查 grant/scope_epoch、所有记录版本、内容引用、generation_epoch、任务终态和当前音频 manifest 的权威有效状态。文件损坏检查不能代替采用与开播前再次验证。完整步骤：

1. 权限验证准备任务和候选目标房间归属；候选发布不会覆盖活动 session。
2. 幂等登记；声播同库检查 grant、scope_epoch；读取目标 room 当前 revision与候选基准是否一致。出现人工修改时回读合并或标rebase_required。
3. 核查 draft/完整商品 refs/脚本模块/编译计划/requirements/manifest 相互一致；无阻塞缺项，活动期限在预期开始日期有效。
4. 冻结新 publication candidate/snapshot，包含全部内容引用、hash、voice 指纹、source revisions、编译器/提示词版本及完整检查回执；`adoption_state='unadopted'`由独立状态投影表示。
5. 从 draft 构造候选 room config 内容用于检查，product_ids仍只引用；commerce为本场覆盖；保存候选基准 room revision。**不写 room 正式配置和 adopted 指针。**
6. 同一声播事务写 publication candidate、accepted_preparation 的候选ready引用、幂等回执与 outbox，任一步失败全部回滚；Agent库随后按回执更新投影。

回执返回 `publication_id/publication_hash/base_room_revision/readiness=ready_to_adopt/adoption_state=unadopted/review_ref`。ready_to_adopt不表示已经采用、更不表示已播出；不生成真实session_id。同房间可以保存多个候选，但只有用户显式采用且CAS成功的候选成为正式配置。

### 10.2 review 快照

```python
def create_review(publication_id: str, *, principal: Principal) -> ReviewPacket: ...
def validate_publication_current(publication_id: str, *, expected_hash: str) -> PublicationCheck: ...
```

ReviewPacket 包含 candidate publication hash、base/current room revision、正式商品引用与所有配置字段、研究和计划来源入口、模块差异、用户顺序/长短开场、音色/音频状态、adoption状态、阻塞与非阻塞待办。这里只规定后端查询结构，不设计页面。

review snapshot hash 是全部关键 refs 和当前检查结果的摘要；review 创建后商品、房间、模块或音频依赖变化，旧 hash 不得采用/开播。可复用模块不会因此重新生成，但需要重新检查并发布/刷新整包。不能由 Agent 自己把“看过”当作人工采用或开播确认。

### 10.3 人工 adopt_snapshot

```python
def adopt_snapshot(
    room_id: str, publication_id: str, review_snapshot_hash: str, *,
    expected_room_revision: int, operation_id: str, principal: Principal,
) -> AdoptionReceipt: ...
```

仅人工身份具备 `snapshot:adopt`。同库短事务校验房间不是活动中、snapshot当前性、expected_room_revision、显式采用对象，随后以候选配置更新room并CAS递增版本，设置`adopted_publication_id`，写不可变AdoptionReceipt/operation/outbox。其他候选保留、不采用。这个动作不创建live session，不发送播放命令，不输出声音。

回执返回 `room_revision_after/adopted_publication_id/adoption_id` 和供start使用的最新检查快照hash。采用期间文件可能变化时仍在start再次验证。两个候选同时被采用时只有一项CAS成功，另一项回读当前配置并请求明确重新采用，不能last-write-wins。

### 10.4 人工 start

```python
async def start_prepared_room(
    room_id: str, publication_id: str, review_snapshot_hash: str, *,
    expected_room_revision: int, action_id: str, principal: Principal,
) -> StartReceipt: ...
```

`principal` 必须具备人工 `live:start`，准备 Agent 凭据不具备。start必须引用room已采用的publication，未adopt的candidate即使完整也拒绝。adopt和start是两个独立动作；不额外增加逐份脚本approve的必经步骤。现有测试明确未单独approved的稿件可以在音频齐备后播放。

启动流程：

1. 持有进程内 `start_lock` 与目标 Room.lock（固定顺序获取，所有调用一致）；回读 publication 与 room config，必须匹配adopted_publication_id和AdoptionReceipt。
2. 读/验 review hash、商品可售性、当前源版本、模块、编排、所有必需 WAV；任何陈旧返回 `REVIEW_STALE/PUBLICATION_STALE/AUDIO_MISSING`。
3. 一个短写事务登记 action_id 幂等、领取 `live_slot=1`、创建持久 live_session 的 `starting` 记录，绑定 publication，提交。
4. 事务外从不可变 plan 载入内存 Room 队列，冻结音色，生成首次 epoch/attempt；不在线合成常规音频。
5. 更新 live_session 为 `running`；返回 session_id/publication_id/OBS 既有 `/live/{room_id}` 地址与当前状态。无 player 连接仍可处于 preparing，沿用现有行为。
6. 第三步提交后进程崩溃，恢复服务把 starting/running 标 `interrupted`，释放 live slot 或等待明确恢复策略；默认不重启扬声器播报。相同 action_id 回读原 session 结果，不创建第二个 session。

步骤 3 到 5 不可能形成内存与 SQLite 的单个物理事务，因此必须保留 starting 状态及恢复逻辑，不能宣称“整次开播是单 SQLite 事务”。首期运行服务器固定单 worker；多 worker 部署若未实现跨进程播出 owner，启动时明确拒绝配置，而非只靠 Python `start_lock`。

### 11.1 错误合同

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "房间配置已被更新，请读取当前版本后重算受影响计划。",
    "retryable": false,
    "operation_id": "op-...",
    "current_ref": {"kind": "config", "id": "room-...", "record_revision": 9},
    "affected_paths": ["commerce.coupon"],
    "next_action": "read_current_and_replan"
  }
}
```

| HTTP | code | 处理 |
| --- | --- | --- |
| 400/422 | INVALID_INPUT/SCHEMA_MISMATCH | 返回具体路径，不执行写入 |
| 403 | FORBIDDEN/RESOURCE_SCOPE_DENIED/GRANT_REVOKED | 不重试；不得让模型换目标 ID 或旧grant试探 |
| 404 | NOT_FOUND | 判断引用错误或资源已删除 |
| 409 | VERSION_CONFLICT/IDEMPOTENCY_CONFLICT/INPUT_SUPERSEDED | 回读/修订计划，不能原样盲目重试 |
| 409 | MISSING_MODULE/AUDIO_MISSING/PUBLICATION_STALE | 只返回精确缺项，局部补齐 |
| 429/503 | BUSY/RATE_LIMITED/UNAVAILABLE | 只读或明确未受理动作有界退避；已受理按 operation/job 查询 |
| 504 | RESULT_UNKNOWN | 先对账，不能换 operation_id 重交 |

## 12. 一次“只改活动”的完整调用与版本轨迹

初始：P1商品record_revision=12；研究R7；draft D4；A1话术修订S8，模块`opening_long=L8/opening_short=Q8/product_intro=I3/selling_points=B5/campaign=C4/cta=T6/transition=X2`；plan V3；本机Huihui语音指纹H1；用户已采用U3；room record_revision=21。用户要求从“九折”改为“满100减20”，商品和顺序均不变。该请求在前一run结束后执行；如果前一run仍在运行且请求是follow_up，只排队。

| 步骤 | 调用与输入 | 具体执行 | 数据结果/不变量 |
| --- | --- | --- | --- |
| 1 接收 | 准备服务保存新用户要求 | 当前run完成后为此请求建立新grant；preparation_revision 9→10，generation_epoch 15→16 | P1=12、R7保持；room采用的U3不自动替换 |
| 2B 草案 | `save_session_draft(D4→D5)` | 保存满减类型、门槛100、抵扣20、币种与适用商品；scope 校验 | D5 是数据，不生成口播、不改 room21 |
| 3 报价 | `quote(P1@12,D5)` | Decimal 计算；若单件未达门槛则不得写“单件到手价减20” | quote ref K5、confirmed 状态与条件原样保留 |
| 4B 上下文/计划 | 读取 P1全字段/R7全文/D5/旧稿S8/用户决定 | 新 bundle CB9；确定改 L/Q/C，扫描实际引用促销条件的 T6，列为联动；I3/B5/X2 复用 | ScriptPlan SP9 明确7模块动作及来源，未引用旧活动的正文保留 |
| 5 提交 | `submit_script_change(SP9,CB9,epoch16,op-s1)` | enqueue Job J9，冻结输入 hash；重放 op-s1 返回同 J9 | 202 是受理，不报“话术完成” |
| 6 worker | claim J9.itemA1，模型生成 L9/Q9/C5/T7 | 按 CB9 取完整精确输入；检查价格/条件和 patch allowlist；一次纠正上限 | 形成候选，不直接 attach room |
| 7 patch提交 | lease+epoch16+依赖 hash 检查 | 新 S9 指向 L9/Q9/I3/B5/C5/T7/X2；S8 完整保留 | B5 原文、ID、使用年龄不变；room21 未动 |
| 8 编排 | 用户既定 occurrence 顺序+S9+loop设置 | 编译新 plan V4；重新引用所需长短开场；收集 requirements AR4 | 顺序不由 Agent改，循环公式明确 |
| 9 TTS | `prepare_required_audio(AR4,epoch16)` | 查缓存：I3/B5/X2 复用；只合成实际所需的新 L9/Q9/C5/T7句子 | 音频manifest AM4，逐句文件有效；没用到的开场不合成 |
| 10 候选发布 | `publish_preparation(...baseRoom21,draftD5,CB9,S9,V4,AR4,AM4)` | 一个声播事务核验grant/依赖；创建unadopted U4与回执 | room仍21且采用U3；候选生成不会改变用户配置或start |
| 11 检查 | `create_review(U4)` | 返回全部配置、模块差异、开场映射、声音齐备和snapshot hash RS4 | Agent完成标准是ready_to_adopt+候选回执 |
| 12 人工采用 | `adopt_snapshot(U4,RS4,room21,op-adopt)` | 用户显式采用；声播同事务CAS保存候选配置，room21→22，adopted_publication=U4 | 返回AdoptionReceipt与新检查hash RS4a；不生成session、不播音 |
| 13 人工开播 | `start(U4,RS4a,room22,actionId)` | 确认已采用且最新依赖有效，领取live slot，载入固定队列，生成真实session | 活动正确、主体复用、无额外常规在线生成 |

迟到分支：步骤6执行期间用户明确使用replace改为“八折”。运行服务先调用声播revoke旧grant，拿到权威回执后撤销旧写权；然后创建替代grant及epoch17。epoch16候选可留审计和缓存；步骤7必须以`GRANT_REVOKED/INPUT_SUPERSEDED`拒绝提交。若新请求只是follow_up，不取消J9，而是J9完成后串行处理新的活动变更。

并发分支：步骤9时用户在声播旧配置接口改音色，使room21→22。步骤10校验候选base_room_revision发现不一致返回rebase_required；若候选已生成则步骤12采用CAS失败。主Agent回读并保留用户新音色，只重做受影响audio requirements/manifest，不能以草案旧声音覆盖房间。

## 13. 迁移与旧接口兼容

| 项目 | 迁移方案 | 验收 |
| --- | --- | --- |
| records revision | 有版本的迁移事务加列，所有旧记录 revision=1 | 原 body、ID、历史脚本无内容变化；重复迁移无副作用 |
| 商品 SKU/编号 | 全量只读扫描检测重复，建立 registry/sequence | 冲突明确列出后停止迁移，不自动合并或重编号 |
| `server.put` | 统一调用 storage 的受控 unconditional update 并递增数据库 revision；核心多对象操作使用显式 UoW | 旧 UI 任一写入都会使旧 publication 当前性失效，不存在绕过 CAS 的静默写 |
| `ProductInput.record` | 抽取为纯 `normalize_product(input, prior, allocated_identity)`；旧 route 与新 save_product 共用 | 旧客户端未传新字段时保留已存字段，隐藏字段按原语义清除 |
| 旧配置保存 | service在事务内对最新内容合并，只更新明确传入字段，并递增revision | 保留原“用户删除不复活、后台新稿不丢失”历史测试；v2 adopted房间发生旧写入后标dirty，不能继续拿旧整包启动 |
| 旧整稿 script | module_schema_version=0；兼容现有整稿播放；进入v2需一次显式拆分并检查映射 | 不能凭 stage 自动宣称已存在正确长短开场；缺模块按需求补写 |
| 新模块 script | 写 `module_schema_version=1/module_refs`，为旧只读视图派生 blocks/sentences | 派生视图不能作为可写第二正本；新服务整稿来源仍是module refs |
| `script_order` 去重 | 保留旧字段用于legacy；v2 的 occurrences 是正式列表，兼容字段仅派生展示 | 同 script 重复 occurrence不被丢掉；不能再由旧字段反向覆盖v2 plan |
| 旧 scripts job | 兼容 adapter 可完成旧流程；与v2 preparation jobs独立标kind | 新 Agent不调用旧 create_job/attach_scripts，不存在两种任务互挂同场 |
| 旧音频 | 完整匹配 text/voice/model/style 且 WAV有效可领养进新manifest | 未使用旧长开场不会被判缺失，修改句仅新合成该句 |
| 旧开播 | legacy房间继续原接口；v2房间`/control start`必须走adopted publication验证；缺snapshot/adoption返回明确错误 | 不能用旧start接口绕过v2 review/source/adopt检查；不要求全部旧房间先升级 |
| 服务启动 | 数据迁移/lease恢复放 lifespan启动，GET保持只读 | 查询任务不会自行把另一个有效worker任务改成interrupted |

迁移前生成可恢复数据库备份，迁移日志不包含密钥。若 SKU 冲突、旧script无法无歧义拆分，仅阻塞相应迁移项/准备任务；原历史数据保持可读。需要维护的旧接口范围先列回归表，不在同一改造中重写无关 live_source/reply_lab。

## 14. 最小可实施任务切片与验收

| 顺序 | 交付函数 | 必须先具备 | 单元/合同验收 |
| --- | --- | --- | --- |
| S1 仓库与CAS | UoW、operation receipts、save_product | 当前schema纯函数抽取 | 同key创建一次、同key异参拒绝、并发SKU唯一、旧写revision递增、事务失败无半写 |
| S2 草案与模块 | save_session_draft、submit/commit patch | S1+冻结ContextBundle | 不改room生成、只改活动保留主体、未知条件不造价格、旧epoch无激活 |
| S3编译与TTS | compile plan、requirements、manifest | S2+script modules | n=1/3/5/6/10循环mode、重复occurrence、缺模块返回、所需音频齐备、只补缺失 |
| S4发布与采用 | publish_preparation、create_review、adopt_snapshot | S1–S3 | candidate不改room；adopt需人工且CAS；任何一步失败全部回滚，review与实际包一致 |
| S5人工start接入 | start_prepared_room | S4+现有Room ACK/owner | 重放start单session、过期review拒绝、常规无在线TTS、单live slot、starting重启不自动播 |
| S6旧协议回归 | route adapters/migrations | S1–S5 | 商品字段、优惠、房间隔离、旧稿、音色、OBS owner与epoch全部历史行为保持或有明确协议升级 |

补充强制故障点：模型返回前取消；模型返回后提交前改活动；音频文件已移动但DB提交失败；publication写到一半抛错；发布后商品价格变化；start占slot后进程崩溃；同audio_key双worker；旧lease持有者迟到。每个案例检查业务终态、回执、版本与事件，不以日志文字“成功”判定。

设计验收指标：CAS/幂等/旧epoch/越权反例全部阻断；未修改模块内容hash与module ID完全不变；TTS新合成集合等于有效缓存之外的required集合；publication内所有依赖可读且hash匹配；声播GET/read-only接口无业务状态变更。性能/费用阈值须实施真实模型探针后标定，设计阶段不编造延迟或成功率。

## 15. 父文档集成时必须保持的决定

1. 唯一Agent发布操作是最终`publish_preparation`，只形成unadopted candidate；不得恢复“先把草案发布到room再生成”或Agent自动采用的旧设计。正式room只由用户adopt_snapshot更新，start独立。
2. 主 Agent 使用类型化 HTTP 客户端；子 Agent不拿声播写入或人工start凭据；CLI只作诊断薄壳，首期不强制MCP。
3. ContextBundle是完整输入ref和精确规则，不是只有摘要；脚本生成服务显式吃bundle，不暗读最新room作为输入。
4. 模块键统一 `opening_long/opening_short/product_intro/selling_points/campaign/cta/transition`。
5. 手动跳播使用原编排 entry 的 mode；跨圈按全局原序号1/6/11，插播不计数。
6. 声播run_authorizations及业务写提交同库事务；Agent数据库只镜像回执。follow_up串行，new_task独立，replace/cancel拿声播撤销回执后才称写权撤销。
7. 本文件没有实现任何新接口，函数签名是工程合同；后续实现仍需按具体类型声明、依赖注入和测试补齐。
