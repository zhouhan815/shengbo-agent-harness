# 12 用户编排、拖拽与重排设计

合同增量 `PRELIVE-2.3`；工程设计，尚未实现。本文补充 [03 编译与业务服务](03_声播业务服务与事务.md)、[06 前端合同](06_前端对接合同.md) 和 [10 文案到语音门槛](10_人工确认与语音门槛设计.md)。不改变商品库权威、用户选品、精确版本引用、人工批准语音、人工采用和人工开播的边界。

## 1. 目标与不可破坏条件

用户先选定本场要播的商品话术版本，再用卡片拖动或重排改变顺序。**重排是已选项的排列，不是选品、自动追加版本、重新生成文案或实时控制已开播队列。**

| 事项 | 明确规则 |
| --- | --- |
| 一张卡片 | 一个 `PlaybackOccurrence`；同一商品同一稿件重复两次也有两个不同 `occurrence_id` |
| 商品与版本 | 由 `product_id` 和精确 `script_revision_ref` 定位；不能按显示名称合并或自动取最新版 |
| 三种重排 | 同商品连续 `grouped`、商品穿插 `interleave`、完全随机 `full_shuffle` |
| 已选范围 | 三种模式的输入、输出 `occurrence_id` 多重集合与每项精确引用必须相同；不得漏项、加项、替换版本或去重 |
| 用户的商品组顺序 | `product_group_order` 明确保存；默认按当前列表首次出现顺序，用户可在重排弹层调整；普通拖动不会偷偷改此设置 |
| 随机可复现 | 保存 `seed`、`algorithm_version`、输入 hash 和输出 hash；相同精确输入和参数必须得到相同结果 |
| 顺序保存 | 仅通过既有 `save_playlist`；拖拽和重排共用同一 CAS/权限/失效链 |
| 预览无副作用 | `preview_playlist_reorder` 是纯读 query；不保存 playlist、不改编译计划、不作废批准、不产生 TTS |
| 应用无隐式后续 | 保存新顺序后可编译新计划，但不自动批准、不自动 TTS、不采用、不开播 |

`full_shuffle` 保留商品组顺序设置供下一次切回其他模式使用，但本次算法有意不服从组顺序；界面须说明。`interleave` 的组顺序用于剩余数量相同时的确定性选择，不是承诺每一轮严格 A→B→C。这样才能优先减少同商品相邻。

## 2. 卡片列表与重排交互

沿用户截图采用纵向卡片列表，卡片左侧拖拽手柄、中间序号/商品/版本、右侧移除按钮。外框颜色表示当前选中的卡片，不能冒充当前正在播的项目。

| 位置/操作 | 显示与动作 | 服务约束 |
| --- | --- | --- |
| 标题栏 | “本场商品脚本”，显示“共 N 个播放项、M 个不同版本”与“重排”按钮 | 相同版本重复出现时 N 与 M 可不同，不笼统称 N 个版本 |
| 总时长 | 音频已齐备时显示当前编译计划单次/超周期的音频累计时长；未齐时显示“预计约…，部分音频未生成”或“暂不可估计” | 估算基于固定算法/语速说明；不得以文本估算展示精确到秒的已知时长；无限循环另标“持续循环” |
| 卡片主信息 | `01. 商品名 · 第2版`，可加修订号和用户备注 | 编号由位置派生，不当稳定 ID；后台精确引用不显示为让用户理解业务的必填项 |
| 卡片状态 | 分别显示文案、音频、审核、编排状态；有错误能定位 | 不使用一个 `Ready` 同时代表文案齐备、音频齐备、已批准和可开播 |
| 拖动 | 拖到目标位置，先本地显示；释放后提交整份顺序 CAS，显示“保存中→已保存” | 拖动行为本身是可信人工排序决定；不再逐次弹确认；失败不能假装已保存 |
| 键盘替代 | 卡片菜单“上移/下移/移至首位/末位”，与拖动相同语义 | 使不方便拖动时仍能完整操作；共用 `save_playlist` |
| 移除 | 只移除这个播放项，不删除商品或脚本；通过 `save_playlist` 保存 | 与重排的纯排列不同，记录明确移除决定；重复项不能一起消失 |
| 重排弹层 | 选择三模式、商品组顺序、可选组内随机；预览原顺序→新顺序，显示随机种子与注意事项 | 点“重排”只打开预览，未点“应用排序”不改服务端状态 |
| 再随机一次 | 更换 seed 后重新 query；原列表仍不动 | 相同 seed 重预览不能暗中换结果 |
| 应用排序 | 提交当前预览及明确人工决定到 `save_playlist`，CAS 成功后关闭弹层 | 服务端重新计算并核验预览，不相信前端任意输出列表 |
| 取消 | 关闭预览，保持原顺序和原批准状态 | 不调用写命令 |

## 3. 类型与纯读预览合同

以下为设计签名，实施时由 shared schema 生成客户端，不在前端再造平行类型。

```python
class PlaylistReorderSpec(BaseModel):
    mode: Literal['grouped', 'interleave', 'full_shuffle']
    product_group_order: list[str]       # 精确 product_id，每组恰好一次
    within_product: Literal['keep', 'shuffle'] = 'keep'
    seed: str | None = None              # 规范化 128-bit hex；需要随机时补齐
    algorithm_version: Literal['reorder-v1'] = 'reorder-v1'

class PreviewPlaylistReorderQuery(BaseModel):
    query: Literal['preview_playlist_reorder']
    preparation_id: str
    playlist_ref: ArtifactRef
    expected_playlist_revision: int
    spec: PlaylistReorderSpec

class PlaylistOrderItem(BaseModel):
    occurrence_id: str
    product_id: str
    script_revision_ref: ArtifactRef
    user_ordinal: int

class PlaylistReorderPreview(BaseModel):
    preview_id: str                      # 从 canonical request + result hash 派生
    preparation_id: str
    base_playlist_ref: ArtifactRef
    base_playlist_revision: int
    input_hash: str
    output_hash: str
    preview_hash: str
    resolved_spec: PlaylistReorderSpec
    proposed_items: list[PlaylistOrderItem]
    moved_items: list[OrderMove]
    adjacent_same_product_pairs: int
    minimum_internal_adjacent_pairs: int
    loop_boundary_same_product: bool
    warnings: list[ReorderWarning]
    readset: list[DependencyRef]
    observed_at: str                     # 不参与复现 hash
```

预览 seed 为空时，query 可在内存产生随机 seed 并返回；不写任何业务记录，不引起业务状态变化。调用方若要复现，必须带回返回的 `resolved_spec`。`grouped + keep` 没有随机步骤，seed 可以为空；`full_shuffle` 无视 `within_product`，响应明确显示参数不适用，不做第二次组内随机。

`input_hash` 覆盖输入顺序和每项精确引用；`output_hash` 覆盖候选顺序和精确引用；`preview_hash` 覆盖两者、完整 resolved_spec、preparation/playlist 的精确版本及必要 readset。所有 hash 使用既有 canonical JSON 规范，不以显示名、页面行号或不稳定序列化作为输入。相同 seed 但输入版本不同，不承诺相同输出。

## 4. 三种算法

算法是声播普通确定性函数，无须模型逐项“推理”排列，不增加排序子 Agent。

### 4.1 随机原语

```text
rank = SHA256(UTF8('reorder-v1|' + seed + '|' + occurrence_id))
随机排列 = 按 (rank, occurrence_id) 升序排列
```

使用完整 occurrence ID 作为随机项身份；重复脚本的两个 occurrence 仍会得到各自的 rank。`seed`、分隔编码和算法版本固定；不要依赖不同语言或运行时版本的默认 `shuffle()` 实现。同一组内 shuffle 和全排列可以分别增加固定域 `within_product` / `full_shuffle`，实现时将域纳入 `algorithm_version` 所指的固定编码合同；`reorder-v1` 的完整前缀分别定为 `reorder-v1|within_product|` 与 `reorder-v1|full_shuffle|`，不得由客户端自行改域。

### 4.2 grouped：同一商品的已选版本连续

1. 验证 `product_group_order` 覆盖输入中全部且仅有的 product ID。
2. 按 product ID 分组；每组保留输入 occurrence 顺序。
3. `within_product='shuffle'` 时，只在组内按上述固定 hash rank 排列。
4. 按商品组顺序拼接全部分组，重新派生 `user_ordinal=1..n`。

例：已选 `[A1, B3, A2, C5, B1]`，商品组顺序 `[A,B,C]`，组内 keep，结果 `[A1,A2,B3,B1,C5]`。不会自动补出 A3，也不会因为 B3 版本号较大就改成 B1 优先。

### 4.3 interleave：尽量穿插不同商品

1. 按 product ID 分队列；组内默认 keep，用户可选择 shuffle，版本号不强制从小到大。
2. 每次从**与上一项不同且仍有剩余**的商品中，选择剩余数量最多的一组；相同数量按 `product_group_order` 打破平局。
3. 从该组取出首 occurrence，更新剩余数量。
4. 若剩余只有上一商品，继续取该商品并统计相邻重复；不得静默丢项来伪造完全穿插。
5. 输出后计算实际相邻重复、理论下限及循环首尾提示。

```python
def interleave_occurrences(
    items: Sequence[PlaylistOrderItem], *, group_order: Sequence[str],
    within_product: Literal['keep', 'shuffle'], seed: str | None,
) -> list[PlaylistOrderItem]:
    # 设计伪代码；实现用最大堆或等价计数选择，稳定平局规则固定。
    queues = group_in_input_order(items)
    apply_requested_within_group_shuffle(queues, seed)
    output, previous = [], None
    while any(queues.values()):
        candidates = [p for p in group_order if queues[p] and p != previous]
        if not candidates:
            candidates = [p for p in group_order if queues[p]]
        chosen = min(candidates, key=lambda p: (-len(queues[p]), group_order.index(p)))
        output.append(queues[chosen].popleft())
        previous = chosen
    return with_ordinals(output)
```

对于一条有限线性序列，若总项数为 `n`、最大商品组有 `m` 项，无法避免的同商品相邻数下限为 `max(0, 2*m-n-1)`。首期实现须用枚举和性质测试检查算法达到此下限；如果没有达到，下发内部错误并保留原顺序，不把次优排列称为“最佳穿插”。

例：A 有5项、B有1项，完全不相邻是不可能的，至少3对同商品相邻；预览明确告知“商品A版本较多，已尽量穿插，仍有3处连续播放”。只有一种商品时保留各已选版本，明确“只有一种商品，无法穿插不同商品”。

无限循环的首尾相邻另算 `loop_boundary_same_product`；线性最少不等于环形最少。首期在预览中提示首尾同商品，允许用户拖动修正，不声称已经优化所有循环边界，不擅自改变用户开头和商品组顺序。未来若增加“循环边界也尽量不同”，须另定义版本化算法与验收，不能悄悄更改 `reorder-v1`。

### 4.4 full_shuffle：完全随机排列已选项

对全部 occurrence 按 `full_shuffle` 域的 hash rank 排列。这个模式允许同商品相邻，预览说明“完全随机，不保证商品交替”。不生成新稿件、不更改版本号、不改变已选次数。用户希望随机但避免同商品相邻时，应选择 interleave 并开启组内随机。

## 5. 服务函数与调用时序

```python
def preview_playlist_reorder(
    args: PreviewPlaylistReorderQuery, principal: Principal,
) -> PlaylistReorderPreview: ...

def reorder_selected_occurrences(
    items: Sequence[PlaybackOccurrence], spec: PlaylistReorderSpec,
) -> tuple[list[PlaybackOccurrence], ReorderDiagnostics]: ...

def verify_reorder_permutation(
    base: Sequence[PlaybackOccurrence], proposed: Sequence[PlaybackOccurrence],
) -> None: ...

def validate_reorder_preview_for_save(
    uow: VoiceUnitOfWork, base: Playlist, proposal: PlaylistReorderProposal,
    user_decision: VerifiedUserDecision,
) -> list[PlaybackOccurrence]: ...

def save_playlist(
    preparation_id: str, playlist: Playlist, *,
    expected_playlist_revision: int | None, user_decision_ref: UserDecisionRef,
    reorder_proposal: PlaylistReorderProposal | None,
    mutation: MutationContext, principal: Principal,
) -> PlaylistReceipt: ...
```

| 阶段 | 行动与条件 | 产出/副作用 |
| --- | --- | --- |
| 读当前编排 | 取得精确 playlist、script refs、已选 occurrence 和保存版本 | 卡片投影；不自动刷新稿件 |
| 请求重排预览 | 只读快照内核验对象权限、base revision、occurrence 完整性；执行普通算法 | 完整候选序列、seed、移动 diff、诊断和 hash；零业务写入 |
| 用户看预览 | 原顺序与新顺序并排/切换展示；可再次随机或取消 | 不作废现有批准 |
| 用户应用 | 可信人工事件绑定 base、resolved_spec 和 preview_hash；提交既有命令 | 进入一次 `run_mutation` |
| 保存事务 | 校验 CAS/权限；对 base 重算候选并核验 hash；校验 exact permutation 和人类决定；保存新 playlist revision | 与 changed event、operation receipt、失效事件同事务提交 |
| 重新编译 | 根据新原始位置编译 plan、收集 actual required 音频 | 返回缺开场模块或新 requirements；不调用 TTS |
| 后续语音 | 用户看到新精确编排和文本后重新批准 | 通过当前批准才能补缺音频 |

`PlaylistReorderProposal` 保存已解析 spec、base playlist ref、input/output/preview hashes；它不是第二套业务写模型。预览不持久保存，无须增加 `apply_reorder` 写命令或预览库；服务端保存时可用相同算法重新校验。保存成功的 playlist provenance 记录实际 spec、输入/输出 hash、可信决定和 operation ID，供复现与审计。

候选顺序与当前顺序、精确引用和编排设置完全一致时，响应 `changed=false`，不递增 playlist revision、不作废批准、不产生空变更；如需记录用户确认排序方式，可留决策/审计记录，不能为了记录一次点击制造业务失效。

大列表重算属于短 CPU 计算，实施时限制输入规模并在事务前完成候选计算；事务内检查 base/current hash 与精确输出一致性，不能把无界排序或任何外部网络放在 SQL 写锁内。若候选计算依赖的 base 已变，拒绝并重新预览，不在事务里随机改出另一结果。

### 5.1 拖拽与并发

拖拽直接发送当前完整 `occurrence_id` 顺序和 `expected_playlist_revision`，`reorder_proposal=None`。可信 human 决定绑定最终顺序；服务从当前精确项装配 payload，拒绝客户端顺便替换 script ref。若用户另行明确更换版本，走有该修改范围的同一 `save_playlist`，不借拖拽偷偷换稿。

同一浏览器快速多次拖动采用单条保存通道：合并尚未发送的本地动作；上一请求成功后以新 revision 发送最新意图。保存超时先按原 operation ID 查回执，不生成新 ID 盲重试。其他窗口先保存后，本窗口 CAS 返回 `PLAYLIST_STALE`（409）；保留本地意图并展示差异，由用户重新应用，不覆盖远端新顺序。

用户在未保存本地编排上点重排时，先完成当前保存，再基于返回 revision 查询预览；保存失败不继续使用旧服务端列表重排。首期不让 query 以任意未持久列表假装权威输入。

### 5.2 自然语言中的排序授权

| 用户表达 | 主 Agent 行为 |
| --- | --- |
| “把选中的版本按同商品连续给我预览” | 调用纯读 preview，展示候选，等待应用；不保存 |
| “按同商品连续，按A、B、C顺序，直接应用” | 可承接明确方法和应用意图；可信决定层记录授权的方法/范围，再保存该次确定候选，不追加第二次泛泛确认 |
| “把已选版本穿插随机一下并应用” | 限于当前精确已选集合，解析 interleave + 组内 shuffle，固定本次 seed 并记录实际候选；范围/模式清楚时可应用 |
| “排一下，看看哪个好卖” | 不自行决定主推商品或优先级；提供三种方式让用户选，不暗中用销售推断排序 |
| “随机排列”但未说明要避免同商品连续 | 以选项说明 full_shuffle/interleave 区别；指代不明时问清，不把两种算法混称随机 |

决定层验证来自真实用户事件，模型自由文本“用户已同意”不能造出 `UserDecisionRef`。排序授权不授权加入新商品、新版本、生成音频、采用和开播。纯读预览工具可提供给主 Agent；子分析 Agent 不需要排序写权限。

## 6. 重排后的开场、音频和失效

| 受影响对象 | 保存新顺序后的行为 |
| --- | --- |
| occurrence 身份与精确版本 | 原样保留；仅位置和 playlist revision 变化 |
| 编译计划 | 旧 plan 不再作为当前草案有效计划；重新计算原始序号、长短开场和超周期 |
| 开场分配 | 新列表第1、6、11…项为长开场；不是跟某个商品/版本永久绑定 |
| 文本缺项 | 若新位置需要另一种开场且未有文本，返回精确缺项；允许范围内仅补该模块，否则请求授权；不重写商品介绍和卖点 |
| AudioRequirements | 从新 plan 重新收集实际用到的句子；不把全部历史音频当 required |
| 原文案→语音批准 | 新顺序改变 review hash，旧整包批准变 stale，必须审核当前包；缓存齐备也不能替代批准 |
| 已有音频缓存 | 相同文本/音色/渲染指纹资产保留并复用，不因为 plan revision 改变而重新计费合成 |
| 未采用候选 | 旧 candidate 仍是可回读的历史不可变对象，不能冒充当前准备就绪；当前要重新检查/发布 |
| 已采用/正在播的快照 | 当前直播不被编辑草案重排偷偷改变；需要后续人工采用，再人工开播或另行定义播中控制 |

非循环仅合成本轮用到的开场；无限循环仍按 `L=lcm(n,5)` 编译超周期，`n` 非5的倍数时某 occurrence 不同圈可能两种开场都用到。手动跳播按**该 publication 中原 compiled entry**的原编排位置使用开场，不能用实际已经播了几条重新计数。重排与跳播是两个不同动作。

## 7. 持久化、上下文与调试记录

Playlist 增加 `reorder_provenance`（可空）和 `product_group_order`；原有 immutable revision、change_log 和 events 足够，不新建独立“排序真相库”。`reorder_provenance` 包含算法、seed、base ref、input/output hash、用户决定和 operation；直接拖拽记 `mode='manual'` 的 provenance，但 `manual` 不进入三种算法的 `PlaylistReorderSpec.mode`。

主 Agent 只需当前 exact playlist、明确用户排序意图/决定、可用模式和预览诊断。商品事实、顾客研究、活动推断不能被用于擅自给商品优先级。排序函数不用完整研究文档；只有排序导致开场缺项需要补稿时，才回到既有完整 ContextBundle 和模块变更计划。

调试台记录 preview query 的输入/输出安全原文、固定 seed、base/current revision、算法诊断、应用决定、save receipt、compile receipt、批准失效和缓存命中。预览取消可记只读交互 trace，但不能写业务 playlist；trace 的记载不等于业务变更。用户界面显示“只是预览”或“已保存”，不解析模型话术判断成功。

## 10. 复盘的排序建议与用户采纳

可以根据真实或明确模拟的依据提出“二号商品表现较好，建议放在开头讲解”。建议保存`origin_session_ref/source_display_number/product_ref/evidence_refs/limitations/proposed_action`，缺曝光和时长时不能声称转化率更高或改序有因果收益。来源编号映射到稳定商品身份，不是当前卡片位置或版本号；未知身份先问。

提出建议是只读分析，不是save_playlist授权。当前用户要求保序时保留建议待决定，不标错误、不自动改序。用户明确采纳后确定移动一个已选occurrence还是同商品整个组，按原相对顺序和精确refs构造preview→明确apply→CAS；未选择的商品不自动加入，新增货盘另需明确选品决定。对应16 REV12/13与fixture独立正向场景。
