# 01 类型、数据所有权与持久化

合同版本 `PRELIVE-2.3`。本文定义新实现的规范，现有声播不应被当成已支持。所有请求使用 Pydantic `extra='forbid'`，金额传十进制字符串，时间保存含时区 ISO 8601，ID使用UUID/受控稳定标识，哈希为规范化JSON的SHA-256。最终复查增量以[16](16_最终复查修订与待讨论事项.md)为统一合同。

## 1. 身份与作用域

```python
class WorkScope(BaseModel):
    kind: Literal['catalog', 'preparation']
    account_id: str
    preparation_id: str | None
    # preparation必须非空；catalog必须为空

class RecordRef(BaseModel):
    kind: str
    id: str
    revision: int
    content_hash: str

class ArtifactRef(BaseModel):
    kind: str
    id: str
    revision: int
    content_hash: str
    schema_version: str

class TargetRef(BaseModel):
    scope: WorkScope
    object_ref: RecordRef | ArtifactRef
    field_path: str | None = None       # schema中存在的JSON Pointer
    module_key: ModuleKey | None = None
    block_id: str | None = None
    sentence_id: str | None = None

class SelectionSnapshot(BaseModel):
    target: TargetRef
    selection_id: str
    selected_text_hash: str | None
    origin: Literal['explicit_selection', 'explicit_user_reference']

class VerifiedIntentEvent(BaseModel):
    event_id: str
    conversation_id: str
    actor_id: str                       # 从可信渠道注入，客户端不能自称agent/human
    scope: WorkScope
    text: str
    material_refs: list[ArtifactRef]
    selection: SelectionSnapshot | None
    intent_mode: Literal['follow_up', 'new_task', 'replace']
    related_run_id: str | None
    observed_versions: list[RecordRef]
```

`scope`决定业务容器，`selection`决定明确编辑对象，`view_context`只是页面观察。页面刚切到B商品，不能把已提交的A商品任务改成B。全局商品库任务没有 `preparation_id`；真正开播才有 `live_session_id`，草案不得冒充真实直播。

同一任务的原始输入不可变；用户新指令创建新run。回答已有问题、job事件、崩溃恢复继续原run。会话conversation只组织展示，可包含不同scope/run，不是图thread。

| `ProductRevisionChoice` / `RevisionChoiceReceipt` | 用户保留固定旧商品或刷新到所观察新版本的选择；绑定prep、精确新旧refs和diff hash。普通新head只提示/要求相关选择，不自动替换；停售/明确撤回强制阻断 |
| `RunClosureReceipt` | 请求终态、收尾cause、撤权回执或确定未派发证明、执行者退出证据、已完成成果、未决外部结果和ContinuationOption；不撤销已合法提交的业务产物 |
| `ModelAttempt` | 可信run/invocation/parent attempt/purpose、预占/发送/结算状态、最终公开payload hash、估算器版本、usage已知或未知；不能把无响应当未计费 |

模块枚举固定为 `opening_long/opening_short/product_intro/selling_points/campaign/cta/transition`。长短开场是二选一；无活动的campaign显式disabled；transition可disabled。

### 2.1 依赖记录

```python
class DependencyRef(BaseModel):
    ref: RecordRef | ArtifactRef
    paths: list[str]                    # 精确消费字段；整对象用['/']
    value_hash: str                     # 服务端按paths读回计算

class InputManifest(BaseModel):
    id: str
    scope: WorkScope
    target_refs: list[TargetRef]
    dependencies: list[DependencyRef]
    source_refs: list[ArtifactRef]
    instruction_ref: ArtifactRef
    schema_hashes: dict[str, str]
    content_hash: str

class MutationContext(BaseModel):
    operation_id: str
    grant_id: str | None                # human由可信会话权限授权；agent必须有效grant
    expected_write_generation: int | None
    expected_generation_epoch: int | None
    expected_versions: list[RecordRef]
    request_hash: str                   # 服务端重新计算，不信任传入值
```

`revision`是对象CAS版本；`generation_epoch`是准备输入代数；`write_generation`是run授权代数；`lease_epoch`是某次执行者租约的fencing token。四者不能混用。业务readset验证与授权fence都要通过，仅有checkpoint或正确hash不能代替授权。

两个DB都启用WAL、foreign_keys、busy_timeout。写事务短小；HTTP、模型、OCR、TTS和文件大读取不置于SQL写锁内。首期固定单应用worker，打开saver前持有数据根OS独占锁；每thread执行锁覆盖整段graph读写。数据库租约负责业务fence，不代替checkpoint排他，不能因租约到期直接启动第二个同thread写入者。声播文案/TTS job的供应商尝试仍归其业务任务账本；Agent的model_attempts不跨库抢占该真值。

### 3.3 分析从暂存到业务接受

```text
worker submit_*_report
  → Agent BranchService验证typed schema/source refs/role/task lease
  → Agent事务：staged report + branch report receipt（PREPARED）
  → JobSupervisor确认branch终态，inbox唤醒主图
  → 主工具accept_analysis_reports
  → client.command(accept_analysis_report, full immutable payload+blob refs)
  → 声播验证grant/readset/schema/hash → 同事务accepted artifact+prep refs+event
  → Agent记录远端receipt（ACCEPTED）
```

主图无需相信worker的最后一段文字。声播引用必须是自己的accepted artifact或受控blob，不能在事务中临时跨库读取Agent私有路径。导入超时用operation查询对账；同一report hash不重复创建分析版本。

```python
class GoalContract(BaseModel):
```

ActionBoundary根据可信tool_call_id派生operation_id；应用重试沿用原ID，不能每重试生成一个UUID。主图同一目标重新发起独立意图可以有新ID，但服务根据目标版本/hash和语义键防止重复创建同一生成任务。

声播执行命令共同骨架：

```python
async def execute_command(envelope, principal):
    args = COMMAND_SCHEMAS[envelope.command].model_validate(envelope.args)
    require_principal_and_resource(principal, args)
    spec = COMMAND_HANDLERS[envelope.command]  # HandlerSpec，mode在注册时固定
    # 公共handler只进入一次run_mutation；execute_command不再外包第二层事务
    if spec.mode == 'async':
        return await spec.handler(args, envelope.mutation, principal)
    return await anyio.to_thread.run_sync(
        partial(spec.handler, args, envelope.mutation, principal))

def run_mutation(command, args, mutation, principal, apply_in_uow):
    # save_product等公开函数的共同事务模板；apply_in_uow只能使用下传uow
    canonical_hash = hash_request(command, args, mutation.expected_versions)
    with store.write_uow() as uow:
        existing = operations.find(uow, principal.id, mutation.operation_id)
        if existing:
            require_same_hash(existing, canonical_hash)
            return existing.receipt
        require_principal_and_resource(principal, args)
        if principal.kind == 'agent':
            check_grant_in_transaction(uow, mutation, command, args)
        check_readset_and_cas(uow, mutation, args)
        receipt = apply_in_uow(uow, args, principal)
        operations.save(uow, canonical_hash, receipt)
        outbox.append(uow, changes_from(receipt))
        return receipt
```

已经成功的幂等回读可在撤权后返回旧receipt，**不再次执行业务写入**；权限仍须允许读取该操作。若operation_id相同payload不同，返回 `IDEMPOTENCY_KEY_REUSED`。约束校验失败整个事务回滚。

## 5. 任务模式与状态机

### 5.1 Run状态

```text
QUEUED → ASSESSING_INTENT（phase=intent，Goal/grant为空）
ASSESSING_INTENT → WAITING_USER（resume_phase=intent） / AUTHORIZING / RUNNING
AUTHORIZING → RUNNING（phase=execute，Goal已首次冻结）
RUNNING → WAITING_JOBS / WAITING_USER / FINALIZING
WAITING_USER → ASSESSING_INTENT或RUNNING  # 按可信resume_phase恢复，同run/thread新invocation
WAITING_JOBS → RUNNING                 # 已授权execute阶段，新的invocation
执行/授权失败 → FINALIZING              # 从未派发授权也须保存本地关闭证据
FINALIZING → COMPLETED / READY_FOR_REVIEW / BLOCKED / FAILED / CANCELLED / SUPERSEDED
用户取消：任一未关闭状态 → CANCELLING → FINALIZING → CANCELLED
replace旧run：CANCELLING → FINALIZING → SUPERSEDED；新run另建
```

`BLOCKED`是对本次无法自动继续的终态说明（带具体blocker），不同于有可回答问题的WAITING_USER。主工具 `finish_turn` 返回的disposition必须覆盖 `COMPLETED/READY_FOR_REVIEW/WAITING_JOBS/BLOCKED`；WAITING_USER来自真实interrupt而非模型自报。COMPLETED/READY_FOR_REVIEW/BLOCKED/FAILED是待关闭结果，先经RunFinalizer完成撤权和执行者收敛，再持久化RunClosureReceipt并向用户发布终态。FINALIZING仍是非终态；对账未知时保留slot，不新跑模型重复完成业务。

| 意图 | 持久行为 | 对旧任务写权 |
| --- | --- | --- |
| `follow_up` | 新run排在同scope前序后；冻结原target/base；只可沿前序同链replacement续接 | 不撤销、不打断 |
| `new_task` | 新独立run；同scope保守串行，其他scope可并行；共享商品仍CAS | 不撤销 |
| `replace` | 确认关联旧run，远端撤权并收到回执、旧执行者退出且关闭回执保存后，新run再进入active | 撤销旧write_generation；不同时写旧thread/checkpoint |
| 回答decision | 保存同问题版本答案，恢复原run/thread | 沿用原授权范围，不扩大 |
| 手工保存 | 立即通过声播CAS命令；写变更与失效事件 | 不是replace；旧job在提交时因readset过期被拒 |

“follow_up”的作用是接着前任务做事，不是允许凭旧版本覆盖其他人的修改。队列激活时 `SelectionService.rebind_own_chain()` 只接受前驱run自产的replacement链；发现外部写入则 `TARGET_CHANGED`，回读差异或补问。

### 5.2 原子性不跨数据库

`submit_intent`先记录QUEUED/不可变用户事件，激活后ASSESSING_INTENT；同一主图只读识别、必要澄清后，Coordinator在Agent事务首次freeze_goal并登记AUTHORIZING及稳定grant operation（只读Goal跳过grant）。声播 `issue_grant` 回执落盘后才phase=execute/RUNNING。崩溃后先查询该operation，不能重建无关grant。若远端拒绝授权，进入FINALIZING保存拒绝/未派发或撤权证据，执行者退出、RunClosureReceipt落盘后才FAILED并释放scope槽。

取消步骤固定：

1. Agent事务把run设CANCELLING、记录revoke operation、停止新工具/claim。
2. 调用声播 `revoke_grant(grant_id, expected_write_generation)`。
3. 声播同库事务为run写revocation tombstone，将已存在授权标revoked/递增write_generation，并取消仍排队的相关生成项；与业务提交/迟到issue_grant按写锁先后线性化。
4. 收到可查回执后，RunFinalizer进入FINALIZING，取消未领分析任务和业务项，等待主/子执行者实际退出；仍在途的供应商结果保持unknown，迟到结果不得激活业务。
5. 撤权与执行者退出证据齐备后，同Agent事务保存RunClosureReceipt，设CANCELLED或SUPERSEDED并释放scope槽；网络未知或旧thread仍可写时保持FINALIZING/needs_reconciliation，前端显示“收尾对账/正在退出”，不能提前承诺停止完成。

撤权之前已成功提交的可逆结果保留并展示；撤权之后旧任务不得再提交。取消不等于回滚全部已生效改动，用户要撤销时执行有前提条件的inverse command。

若QUEUED任务的issue_grant从未派发，Agent库先原子冻结未来授权派发、保存确定未派发证据后本地关闭；AUTHORIZING已发请求但回执未知则必须按run_id远端撤权，不能凭查询not_found判断未来不会授权。只读无grant任务可本地关闭，但仍等待图执行者退出并保存关闭回执。正常成功、预算耗尽和异常失败复用同一RunFinalizer，不只在用户取消时清理后台写权。WAITING_USER/WAITING_JOBS不关闭、不撤销仍需推进的合法授权。

### 5.3 租约

`claim`在短事务内CAS修改owner、lease_epoch+1、lease_until；heartbeat只在owner+epoch仍匹配时续租；所有结果提交再检查epoch。等待时主invoke lease释放，scope active slot保留；子任务使用自己的租约，不要求已经结束的父invoke继续持锁。失租先停止新动作并取消/await原调用；同thread执行锁在调用完全退出前不得释放，DB租约到期本身不能授权另一个graph writer。

建议默认：lease 60秒，20秒heartbeat；单次HTTP30秒、模型120秒；超时上限和并发来自配置。持久恢复先查询外部operation/job，再恢复checkpoint，最后处理尚未交付的新inbox。不能一启动就把全部RUNNING改失败或全部重跑。

## 6. 版本、冻结与失效

每次人工/Agent命令都写change_log和outbox，包含修改路径及新ref。`invalidate_dependencies(change)`沿精确依赖索引标记实际输入已改变的分析/模块/计划/候选stale；不删历史产物。显式引用旧商品的草案维持该revision，普通新head不等于所选输入已改变，不自动切换、不一概作废批准。无关字段变更仅提示；消费字段有差异时，采用/start前展示新旧值和影响，用户明确保留或刷新。停售、具体资料/修订明确撤回、活动自身过期属于当前硬限制，不可用保留旧版绕过。

`refresh_product_reference`只由用户明确选择/指令触发，读取新商品精确ref，保留合法本场overlay，检测冲突；它不是每次read自动换新。`record_product_revision_choice`为human-only固定命令，记录精确旧ref/所观察新head/diff hash及保留或刷新选择；不向主Agent开放替人选择工具。保留回执写独立artifact/索引，不推进内容epoch、不改脚本/voice/顺序、不使自身批准失效；选择refresh与既有刷新私有实现共用一个UoW，不嵌套公共事务。实际刷新绑定引用或文案后整包批准stale，未变音频按内容键复用。选择后新head再变需重新比较；已采用publication永远不变。

job完成如果epoch过期：

- 读取精确依赖均未变时，由 `rebind_unchanged_item(old_item,new_manifest)`验证并产生新绑定，不悄悄修改旧manifest；
- 有变或无法证明时记stale，旧内容仅作可复用缓存；
- 新计划未显式引用旧结果，就不能把该结果标当前ready。

## 8. 统一错误与恢复动作

| code / HTTP | 含义 | 调用方处理 |
| --- | --- | --- |
| `VALIDATION_FAILED` 422 | 类型/优惠/schema非法 | 显示field_errors；修参数，不原样重试 |
| `PRECONDITION_REQUIRED` 428 | 缺基准revision/选区 | 读回对象并明确目标；不降为盲写 |
| `VERSION_CONFLICT` 409 | CAS失败 | 返回expected/current refs和diff；不自动覆盖 |
| `TARGET_CHANGED` 409 | 选区或外部替换变化 | 人工查看差异/重新选择；只能本链自动续接 |
| `INPUT_STALE` 409 | readset或generation_epoch变化 | 局部回流/重新绑定未变项 |
| `GRANT_REVOKED` 403 | 取消/替换后的写权失效 | 终止该run写操作；保留已提交证据 |
| `DEPENDENCY_NOT_READY` 409 | 缺已接受资料/用户顺序/音频 | 等待或补问，不伪造默认 |
| `JOB_UNKNOWN` 202 | 供应商或HTTP结果未明 | 先对账；不能当失败直接重复付费 |
| `CAPABILITY_UNAVAILABLE` 503 | OCR/搜索/音色未配置或不支持 | 保留已完成部分、给替代输入/本机选项；不静默换供应商 |
| `IDEMPOTENCY_KEY_REUSED` 409 | 同operation不同请求 | 程序错误；停止自动重试并记录 |
| `RESYNC_REQUIRED` 409 | 事件cursor过旧 | 重取workspace snapshot |

错误对象包含request_id/operation_id、retryable、field_errors、current_refs、suggested_action，不包含密钥、堆栈或原始私有prompt。

## 11. 复盘、人工语音批准和原始追踪的附加不变量

复盘及其适用/处置结果存声播 `business_artifacts`，原文存受控blob；`Preparation.recap_refs`只保留明确绑定的版本。主Agent/生成服务必须可回读全部已绑定原文，不从聊天摘要重建。替换或解绑复盘使受影响bundle/plan失效，不追改历史脚本；下次生成仍须显式计划。详细合同见09。

待审核请求纯读可重建，批准回执是声播业务真值。`AudioRequirements`在批准前冻结且不含批准ref；TTS job、音频绑定和Publication携带 `approval_ref/review_hash`；缓存文件不是批准记录。旧批准不能批准新的文字、顺序或音色。命令 `approve_text_for_audio/revoke_text_approval` 由human Principal提交，模型参数与自由聊天均不能充当批准回执。详细合同见10。

各服务独立的 `observability.sqlite`新增 `trace_events/trace_payloads/trace_exports`，Agent运行库只保留trace关联refs；仅存执行事实，不成为另一套商品或计划正本。每个事件同时带run、branch、invocation、span、parent_span、tool_call、operation、job等可用关联ID；事件按自身流单调seq追加。跨两个数据库不伪造全局原子时序，使用caused_by和声播outbox游标对齐。载荷hash/原始安全正文与前端摘要分别保存；不将实时运行中的模型原始上下文发给普通业务SSE。详细schema及存储失败策略见11。

## 12. PRELIVE-2.2类型与权威补充

| 类型／规范位置 | 保存与关键边界 |
| --- | --- |
| TaskKind／TaskAssessment（13） | 主模型提议、本地Agent运行产物；计划不得改变冻结Goal或grant；Spec关联放runs，不形成不可变artifact互相回填循环 |

GoalContract九种objective与13的细类一一映射；script_change区分patch/new_variant由目标动作记录，不暗中增加权限。并非每个Goal都需完整本场；例如facts_analysis可只交ACCEPTED报告，catalog_update需商品、有效研究维护和影响清单但不改稿。研究binding和素材属于长期业务持久化，不写入Skill正文或仅依赖StateBackend文件。

## 13. 意图候选与Goal冻结

新增ASSESSING_INTENT只承担同主图只读任务识别。runs.phase=intent时goal_ref/grant_ref为空，intent_event_ref必须真实不可变；WAITING_USER保存resume_phase。IntentAssessmentProposal/Receipt/AuthorizationEvidence按13唯一schema。`save_task_assessment`根据可信phase仅接受对应discriminator，模型不提交phase/actor/授权。

`freeze_goal`要求未冻结、候选及真实许可依据当前、scope slot/invoke lease有效，按固定政策编译Goal并保存一次；幂等重放返回同Goal，异候选不能覆盖旧Goal。该事务安排授权/执行事件，不在SQL写锁里调用声播。已冻Goal的范围改变仍是新run/replace。未派发授权前取消可本地原子禁止未来派发；AUTHORIZING在途未知继续使用声播tombstone。

State、TaskAssessment和runs不形成循环回填：Goal先冻结，执行Assessment引用Goal，AcceptanceSpec单向引用Assessment，runs再分别关联Spec/Result；不把后生成Spec写回不可变Assessment内容。

新增验证：普通新head未改所选ref时不自动失效；消费差异须有精确human选择；停售/撤回不能保留绕过；实际refresh后整包批准stale但未变音频缓存不删；FINALIZING未知状态不得释放冲突slot；正常关闭不使历史合法成果失效；每个模型attempt均有可解释状态和已知/未知usage。


## 15. 问题恢复载荷统一合同

`QuestionResumeEnvelope`从02 §9定义导入，不在本册另造schema。唯一union为`HumanAnswerResume(resolution_kind="human_answer", answer_event_ref)`或`SystemResolutionResume(resolution_kind="system_resolution", system_resolution_ref)`，均extra=forbid。opaque ref须经QuestionService回读原持久记录并验证run/decision/revision/interrupt；系统仅可使旧问题stale，不能批准、提供用户patch或扩scope。QuestionSystemResolution是被ref指向的业务记录，不是resume载荷本身。
