# 13 任务识别、研究复用与历史上下文

合同增量 `PRELIVE-2.3`，设计日期 2026-10-16。本文定义待实现的工程行为，补充 01、02、04；不表示 Agent、数据库迁移或这些接口已经实现。运行仍为一个主 Deep Agent、三类角色 Deep Agents、持久分支调度器；不增加路由模型、第四类研究管理 Agent 或强制走完的总工作流。版本选择、执行关闭与部分成果衔接以16的本轮最终合同为准。

## 1. 任务怎样识别，哪些工作才执行

主 Agent 使用当前同一个模型理解任务，读取当前对象与历史状态后，提交结构化 `TaskAssessment`。任务判断不是字符串关键词命中后直接写数据库；也不靠额外模型先分类，再把分类当成新授权。主 Agent 可以根据新观察修订计划，但每个动作仍受本次不可变 `GoalContract`、精确对象、可信用户决定和服务端 grant 约束。

| 层次 | 决定什么 | 不能决定什么 |
| --- | --- | --- |
| 可信用户事件与 `GoalContract` | 用户真正要求的目标、对象、允许影响、禁止影响、必须交付的证据 | 页面切换或资料中的指令不能改变目标 |
| 主模型的 `TaskAssessment` | 当前任务细类、读哪些历史、复用或重做哪些分析、派发哪些分支、缺什么、怎样验收 | 不能扩大 grant、冒充人工确认或把“建议改稿”变成“已获准改稿” |
| 固定工具与业务服务 | 校验对象/权限/版本、保存精确产物、返回实际回执 | 不替模型暗中开展另一套营销策划 |
| `CompletionGuard` 与验收服务 | 回读本次目标所需证据，判断完成/等待/阻塞 | 不要求每种任务都产出新话术、音频或直播候选 |

### 1.1 本期固定任务策略

| 主模型识别的细类 | 正常选择的工作 | 默认不做 |
| --- | --- | --- |
| `facts_only` | 提取/核对商品事实，交付报告和缺项 | 不把“分析一下”当保存商品许可 |
| `catalog_update` | 商品全字段差异处理；维护相关顾客场景研究；列出受影响话术及原因 | **没有明确改稿要求，不执行话术修改、TTS、编排或本场配置写入** |
| `session_config_only` | 读取本场和相关历史配置、整理本场差异、保存获准配置 | 不重跑全部商品事实和顾客研究，不顺带重写整场 |
| `audience_research_only` | 读取已有研究，按明确对象补充或更新研究，记录依据与未知 | 不将研究推测写成商品事实，不自动改价或创建稿件 |
| `script_patch` | 读取精确旧稿及实际依赖，计划并修改获准模块 | 不改未选模块，不自动附加编排或合成所有版本 |
| `script_new_variant` | 在完整依据下新建指定版本 | 不把“再写一版”当采用、改顺序或付费合成许可 |
| `playlist_reorder` | 使用用户选择的重排方法，处理 occurrence 顺序、编译和失效提示 | 不重新生成商品正文；开场文本确实缺失时报告所需后续动作 |
| `audio_prepare` | 读取精确编译计划、文案批准和声音要求，复用缓存并补必要音频 | 不跳过当前人工文案批准，不顺带改稿或开播 |
| `full_preparation` | 按依赖补齐商品、配置、研究、计划、稿件、编排；等待必要人工批准后准备音频和候选 | 不绕过文案到语音门槛、人工采用与人工开播 |
| `read_explain` | 查询当前成果、解释影响或方案 | 不创建业务变更和付费任务 |

这些是 `TaskAssessment.task_kind` 的细分枚举；不另造一套可绕过 01 `GoalContract.objective` 的授权枚举。复合需求记录多个 `work_items` 和依赖，而不是强迫选一个分类后丢掉其他要求。

`PRELIVE-2.2` 将 01 的 `GoalContract.objective` 精确扩展为下表九种：已有五种保持含义；新增 `facts_analysis/audience_research/session_config/playlist_reorder`，使局部任务有独立完成合同。下表是唯一对应关系，验收服务和工具策略按此使用；不可由模型仅改task_kind就切换原Goal。

| `TaskAssessment.task_kind` | `GoalContract.objective` | 补充限定 |
| --- | --- | --- |
| `facts_only` | `facts_analysis` | 分析报告，未包括商品保存 |
| `catalog_update` | `catalog_update` | 新建/更新由精确target action及用户身份决定区分；新商品同样包括研究维护 |
| `session_config_only` | `session_config` | 本场配置范围，不暗含整场改稿 |
| `audience_research_only` | `audience_research` | 研究维护与证据，不暗含商品事实写入 |
| `script_patch`、`script_new_variant` | `script_change` | 模块修改/新版本的效果及对象分别限定 |
| `playlist_reorder` | `playlist_reorder` | 只改用户所选顺序方法及必要编译 |
| `audio_prepare` | `audio_prepare` | 只准备获准音频 |

**用户已确定的默认规则：**只说“更新商品资料”，按“商品更新＋相关顾客研究维护＋受影响话术清单”执行；只有用户明确要求，才执行改稿。研究维护允许在检查后原样复用，不能为了满足字面上的“更新”而强制再调模型。

### 1.2 权限与计划的先后

首次自由文本的目标同样由主模型识别；不能先假装程序已经理解任意自然语言、冻结某种Goal，再声称模型决定任务。为此修改旧版00/01/02“提交即授权”的次序：**同一主Agent先只读识别，Goal首次冻结后才申请写grant**。

```text
submit_intent 保存原始可信用户事件/材料/selection，Goal尚未形成
  → QUEUED，取得当前作用域slot
  → ASSESSING_INTENT：同一主graph，phase=intent，只读与本地意图提议
  → 主模型调用 save_task_assessment(IntentAssessmentProposal)
  → 仅保存候选；程序验证引用/效果边界/许可依据
     ├─ 歧义：WAITING_USER，可信答复后回到ASSESSING_INTENT
     ├─ 非法：拒绝，继续范围内提议或明确BLOCKED
     └─ 可确定：Coordinator.freeze_goal，首次创建不可变GoalContract
  → 若需要业务写：AUTHORIZING → issue_grant回执 → RUNNING
  → 若全程只读：不申请写grant → RUNNING
  → 同一主graph，phase=execute，保存TaskAssessment并按目标选择能力
```

同一 `run_id`、`main:{run_id}`、同一个主图和主模型继续使用；只读阶段的模型调用计入本次run成本，不另启动分类Agent或独立router LLM。预识别阶段没有正式Goal，原用户事件/selection始终不可变；`freeze_goal`只允许从“未冻结”到“已冻结”一次，不能成为修改已有Goal的入口。

### 1.3 不能用“可信控制器”代替语义判断

模型负责理解自然语言并提出具体目标；确定性程序能证明对象归属、引用是否存在、字段/动作是否在受控集合内、选择是否匹配、决定是否真实，**不能普遍证明一段任意自由文本蕴含所有拟写权限**。授权证据按下表产生：

| 可信许可来源 | 如何形成 | 是否重复确认 |
| --- | --- | --- |
| 用户明确的结构化动作 | 可信前端提交task action、精确selection/refs及用户选择的选项；服务校验后记录原事件 | 在该动作范围内不重复问 |
| 有限、明确的文本政策 | 只接受实现中列明且测试覆盖的完整指令形式，如已选定唯一商品的“更新商品资料”；绑定本节固定默认效果，拒绝否定/引用/条件句等不匹配形式 | 能确定身份、动作和边界时直接执行 |
| 自由文本的明确范围答复 | 主模型提出候选，服务构造绑定候选hash、对象/效果的范围问题；用户可信答复经QuestionService保存 | 只有存在任务/对象/范围歧义才询问，不能每步重复确认 |
| 已冻结Goal内的计划修订 | 主模型选择其他工具/复用/分支，验证器确认实际效果仍在原Goal内 | 不额外问，不发新权限 |

有限文本政策是可审查的确定性输入格式解析，不是一个宣称能理解所有语言的关键词分类器。它只能覆盖列出的明确形式；不匹配不意味着用户一定不允许，而是进入同主模型解释＋必要范围澄清。引用材料中的“更新全部商品”等句子不能作为许可来源。

“更新资料”政策覆盖商品及相关资料内顾客研究维护、影响清单；不包括整场重写、未声明外网调研、跨商品扩展和新付费范围。用户已明确具体对象及改动时不重复问；同名身份冲突、影响范围无法确定时才问。

`IntentAssessment`的 `proposed_objective` 与效果只是候选。`IntentResolver.validate` 必须要求 `IntentAuthorizationEvidence`，仅凭候选自称“用户应该是这个意思”不能形成grant。计划运行中发现新增需求时，通过已有可信范围扩展流程形成后继/替代run与新grant，**不能重新调用freeze_goal扩大当前已冻结目标**。

`TaskKind/GoalObjective`类型在共享合同中先声明，代码片段展示顺序不构成文件导入顺序。`IntentSpan`必须包含可信event_id、offset/length与原文hash；程序校验原文存在，跨度校验本身不等于语义许可验证。

| 待实现函数 | 调用与不变量 |
| --- | --- |
| `IntentResolver.validate(event, candidate, selected_context, decisions) -> IntentResolutionReceipt` | Coordinator读取候选后调用；精确引用/归属/受控动作＋上述三种授权证据校验；无模型调用、无发grant副作用 |
| `RunCoordinator.freeze_goal(run_id, intent_receipt_ref) -> GoalReceipt` | Agent DB事务内要求phase=intent且goal_ref为空、receipt合法当前、原事件未替换、slot/lease有效；按固定政策编译Goal和原始验收要求，再一次性保存 |
| `RunCoordinator.authorize_frozen_goal(run_id) -> RunReceipt` | 仅读取已冻结Goal构造既有issue_grant请求，稳定operation ID；模型工具不能直接调用 |
| `RunExecutor.invoke_once(run_id, phase) -> TurnOutcome` | intent/execute均调用同一主图；phase来自持久run记录，不能从模型args决定 |

意图保存工具在保存候选后调用无模型的 `IntentResolver.validate` 并返回resolution_state：需要决定时由同主Agent调用已有 `request_user_decision` 暂停；答案可信落盘后同phase恢复并提交新候选。M7不允许 `needs_decision/rejected` 被当成“可授权完成”，也不让模型用一句结束语跳过澄清。只有 `resolvable` 回执交给Coordinator冻结Goal；读写阶段切换由Coordinator完成，不由工具返回任意phase写入。

## 1.5 需要同步的有限运行合同变更

| 位置 | 必须变更 | 保留的边界 |
| --- | --- | --- |
| `runs` | `phase=intent/execute`；Goal冻结前 `goal_ref=None`；增加intent_assessment_ref/intent_evidence_ref/goal_frozen_at；验收关联单独保存 | 原始用户事件/selection不可变；已冻结Goal不回填修改 |
| Run状态 | 新增 `ASSESSING_INTENT`；`QUEUED→ASSESSING_INTENT→AUTHORIZING/RUNNING`；该阶段澄清使用WAITING_USER并保存resume_phase | 同一scope slot、invoke lease、后继任务排队规则不变 |
| `RunScope` | `phase`由程序注入；intent阶段objective_ref/grant_ref可空，另有intent_event_ref；execute阶段必须已存在Goal | Worker仍只在execute阶段派发，不产生无Goal的ChildScope |
| M1 | intent阶段校验actor/read scope、slot与lease，不能要求尚不存在的grant/Goal | execute阶段沿用grant/只读Goal守卫 |
| M3 | intent阶段注入原始用户指令/选择/许可政策/对象观察；execute阶段注入冻结Goal | 不把候选当已授权目标 |
| M4/M5 | intent仅允许受限读取、request_user_decision与本地save_task_assessment；禁止dispatch、业务写、网络付费、TTS | 实际写服务继续检查正式grant，模型不能自选phase |
| M7 | intent阶段只核验已保存且当前的IntentAssessment候选回执，允许Coordinator接手校验/冻结；不按业务成果判任务完成 | execute阶段继续以Goal成果回执判断完成 |
| M9 | 记录intent/execute、候选、程序验证、许可依据、Goal首次冻结、授权回执 | 预识别自然语言结束不投影为整个用户任务已完成 |

本地 `save_task_assessment` 使用discriminated union接收意图候选或执行计划；前者只可在intent阶段调用，后者只可在execute阶段调用。它始终仅保存提议，不调用freeze_goal/issue_grant，不是“模型给自己授权”的通用工具。

未向声播派发授权的intent阶段可本地取消并冻结未来grant派发；已进入AUTHORIZING且结果未知时仍沿用声播run_revocation tombstone，不能认为“还没拿到回执”就没有在途权限。

## 2. `TaskAssessment` 类型与本地固定工具

```python
TaskKind = Literal[
    'facts_only', 'catalog_update', 'session_config_only',
    'audience_research_only', 'script_patch', 'script_new_variant',
    'playlist_reorder', 'audio_prepare', 'full_preparation', 'read_explain',
]

class PlannedWorkItem(BaseModel):
    work_id: str
    capability: str                 # 固定业务能力标识，不是任意Python函数名

    input_refs: list[RecordRef | ArtifactRef]
    proposed_effects: list[str]
    reason: str                    # 面向调试的可观察决定依据，非隐含思维链
    expected_evidence: list[str]
    status: Literal['planned', 'reused', 'blocked', 'not_needed']

class TaskAssessment(BaseModel):
    assessment_id: str
    revision: int
    run_id: str                     # 程序注入
    goal_ref: ArtifactRef           # 原Goal，不能由计划替代
    task_kind: TaskKind
    user_intent_refs: list[ArtifactRef]
    target_refs: list[TargetRef]
    observed_readset: list[DependencyRef]
    work_items: list[PlannedWorkItem]
    history_selection_refs: list[ArtifactRef]
    required_decisions: list[str]
    uncovered_effects: list[str]
    replaces_assessment_ref: ArtifactRef | None

class TaskAssessmentProposal(BaseModel):
    kind: Literal['execution_assessment']
    task_kind: TaskKind
    target_refs: list[TargetRef]
    work_items: list[PlannedWorkItem]
    history_selection_refs: list[ArtifactRef]
    required_decisions: list[str]
    uncovered_effects: list[str]
    replaces_assessment_ref: ArtifactRef | None
    # 不接收actor、grant、run、Goal或权限字段

class TaskAssessmentReceipt(BaseModel):
    assessment_ref: ArtifactRef
    validation: Literal['within_goal', 'partially_blocked', 'blocked']
    executable_work_ids: list[str]
    blockers: list[str]
    event_id: str
```

`save_task_assessment(proposal: IntentAssessmentProposal | TaskAssessmentProposal) -> IntentAssessmentReceipt | TaskAssessmentReceipt` 是 **Agent 服务本地固定主工具**；intent阶段保存候选，execute阶段程序注入 run/actor/已冻结Goal并保存计划。它不新增声播写命令，不写商品、研究、配置或话术，不冻结Goal、不申请grant；返回对应候选/计划ref、校验状态和blocker。`TaskAssessment` 可保留拒绝方案供调试，但 `uncovered_effects` 不因已保存就成为可执行权限。

执行计划没有 `acceptance_spec_ref` 字段。验收Spec可以单向引用TaskAssessment，但原始要求取自Goal/可信用户请求；`runs.acceptance_spec_ref` 与 `runs.latest_assessment_ref` 分开关联。生成验收Spec不回填已经immutable的TaskAssessment，避免“计划hash依赖Spec、Spec又依赖计划hash”的循环。后续计划修订创建新ref，runs关联可更新，旧refs永远可回读。

| 待实现函数 | 调用者 | 契约 |
| --- | --- | --- |
| `TaskAssessmentService.save(scope, proposal) -> IntentAssessmentReceipt | TaskAssessmentReceipt` | 固定主工具 | intent校验并保存候选/解析回执；execute校验目标、依赖和作用域，保存精确计划和可执行/受阻工作项；均无grant副作用 |
| `TaskAssessmentService.validate_effects(goal, proposal) -> AssessmentValidation` | save/派发前 | 以原Goal为上限；返回非法效果及缺少的决定，不自动加权限 |
| `TaskAssessmentService.observe_delta(assessment_ref, observation) -> AssessmentDelta` | 主 Agent 读取结果后 | 给出新增/失效依赖供主模型修订计划，不额外调用路由模型 |
| `CompletionService.resolve_required_evidence(goal, assessment_ref) -> GoalAcceptanceSpec` | 完成守卫 | 由原Goal与可信请求确定要求；计划仅辅助定位，不得删减原要求 |

主系统提示词/S1 必须写入任务选择规则：先明确目标与身份；先查可复用产物；只选择必要能力；分别说明“保存资料”和“改稿”的权限；发现缺口可以继续无依赖工作；所有完成声明必须有回读证据。提示词不负责强制安全，M4/M5、业务服务及完成守卫共同执行边界。

## 3. 顾客场景研究怎样长期保存与查回

研究正本存于 **声播业务库**，不是仅留在聊天、模型记忆或 Agent checkpoint 中。`audience_research` 继续是 accepted artifact；增加可检索的版本绑定与适用性记录。跨场复用通过明确 product_id、上下文和依赖查回，不能只按商品名或“最新一份”匹配。

```python
    source_manifest_refs: list[ArtifactRef]
    accepted_at: datetime
    supersedes_binding_ref: ArtifactRef | None
    compatibility_proof_ref: ArtifactRef | None

class ResearchResolution(BaseModel):
    product_ref: RecordRef
    context: AudienceResearchContext
    selected_research_refs: list[ArtifactRef]
    selected_binding_refs: list[ArtifactRef]
    action: Literal['reuse', 'incremental', 'refine', 'new', 'blocked']
    changed_dependency_paths: list[str]
    retained_insight_ids: list[str]
    invalidated_insight_ids: list[str]
    reason: str
    checked_at: datetime
    validity_evidence_ref: ArtifactRef
```

| 存储对象 | 所有者与索引 | 不变量 |
| --- | --- | --- |
| accepted `AudienceScenesReport` | 声播 `business_artifacts`，精确 ref/revision/hash | 原文、证据、假设、逐条依赖不变；更新创建新版本 |
| `audience_research_bindings` | 声播，索引 product_id＋market/channel/language＋research_ref | 只做索引与版本适用性绑定；无独立研究正文副本 |
| `ResearchResolution`/compatibility proof | 声播 accepted artifact 或确定性业务校验产物 | 记录本次查回何种研究、依据和有效范围；不改写旧研究的原始 readset |
| 主任务采用的 research refs | Preparation/ContextBundle 或全局catalog成果引用 | 本场固定精确版本；未来全局head更新不悄悄替换当前本场引用 |

### 3.1 新增固定查询与接线

| 模型工具＝声播 query key | 参数与输出 | 服务行为 |
| --- | --- | --- |
| `find_audience_research(product_ref, context, candidate_limit=10, cursor=None)` | 精确 product_ref、market/channel/language；返回候选 refs、匹配维度、依赖差异、valid/stale/partial/unknown及全文入口 | 受 account/object scope 限制；先匹配 product_id，再比较上下文与消费路径。未知维度显式unknown，不能当所有市场通用 |
| `read_session_history(room_id, preparation_id, baseline_refs=None, cursor=None)` | 当前草案/room引用、明确历史配置/采用/直播记录及差异、日期和继承适用性 | 只读当前有权对象；返回真实来源类型，没有真实live_session就不称“上次真实直播” |
| `inspect_change_impact(target_ref, proposed_or_committed_change, context)` | 已提交变更ref，或限定的只读候选patch；返回精确研究/配置/话术/编排依赖及受影响 paths/modules | 无写副作用、不调用LLM；区分potential/confirmed，不能把未提交假设当生效事实；不自动修改下游 |

以上三个 query 分别固定接到 `client.query('find_audience_research', args, scope=scope)`、`client.query('read_session_history', args, scope=scope)`、`client.query('inspect_change_impact', args, scope=scope)`，并对应注册三个主工具。`save_task_assessment` 不进入声播 command registry。本增量不增加其他声播写命令：研究接受沿用 `accept_analysis_report`；绑定/有效性产物与正式商品保存由现有接受、保存服务按下述事务规则维护。

三个查询无保存副作用。其适用性/影响预览带所读refs、paths、hash和checked_at；不能返回一个并未落盘的“新artifact_ref”。需持久保存的 `ResearchResolution` 由已有商品保存或报告接受事务保存并返回ref；纯查回复用时，可引用现有有效binding与本次只读校验快照，由完成服务再次回读验证，不为记录查询而伪造业务写命令。

角色工具仅暴露其必需读取：顾客研究 worker 可在已分配 product/context 内查研究；本场 worker 可在已分配 room/preparation/history refs 内读配置历史；事实 worker 不因读研究索引而获得其他商品权限。主 Agent 也可把已选研究/历史完整 refs 放入 InputManifest，避免重复宽查询。

### 3.2 复用与增量判定

1. 读取目标商品的精确 revision、最低身份和材料 manifest，不从聊天记忆拼对象。
2. 查回同 product_id/context 下 accepted 研究；保留候选、匹配理由与未选原因。
3. 程序对比真实消费路径及材料 hash。消费内容未变且上下文相容，可产生 `reuse` 的确定性适用性记录；**不硬跑研究模型**。
4. 纯内部备注、排序显示等未被研究消费字段发生变化，可复用；商品名、价格、规格不能一概视为metadata，必须看实际含义与依赖。
5. 新材质、适用限制、用途、目标市场或有效顾客反馈改变时，主 Agent 提议 `incremental/refine`：给 worker 旧研究全文、旧证据、新材料、实际差异及需保留/重判的 insight ID。
6. worker 交付完整新版本：保留仍有效结论与原证据，标明新增/修改/撤回项；不能只交一段“变化摘要”而丢旧研究依据。
7. 主接受 typed report，声播校验来源/readset并保存新研究版本及绑定；下游计划引用本次确定的 refs。

`market=unknown` 的资料内推断可以作为通用假设参考，不能被当成澳大利亚消费者的实证结论。跨渠道共性允许逐条复用；渠道依赖的结论需独立判定。过期网络证据并不被机械删除，而是标记需核验，不再用于未经说明的当前事实断言。

### 3.3 商品保存与研究绑定，避免版本互相使对方失效

研究通常消费材料事实、既有商品中部分字段和市场渠道，并不消费自己随后写入的卖点字段。不能用整个商品 body hash 无差别建立循环依赖。

| 场景 | 正确处理 |
| --- | --- |
| 已有商品更新前开展研究 | 输入保留旧product_ref＋新材料/事实报告refs；主汇合后保存商品新版本。原研究报告保持原始readset，业务服务另存逐path相容证明和新effective_product_ref绑定 |
| 只变化研究未消费的卖点表达 | 比较消费事实路径一致后，允许新绑定；不能改写原报告为“研究一开始就读过新版本” |
| 新商品未分配正式ID | report先保留temporary identity、来源与最低事实；商品身份确认和save_product分配ID后，同保存事务创建正式绑定。绑定前报告可作为该新商品任务输入，不得被全局同名查重误命中 |
| 保存时出现原readset外事实变化 | 不静默重绑；报告INPUT_STALE及paths，定向补研究或阻塞该项 |
| 商品保存成功，研究维护暂未完成 | 商品是已提交成果；前端展示已完成部分和缺项，不撤销商品也不声称catalog_update已全完成。仍有合法任务/问题时WAITING_JOBS/WAITING_USER；无法自动继续时进入FINALIZING再BLOCKED。终态后用户明确继续创建新run，复用原product_id/精确ref与回执，只补研究，不继承旧grant |

相容证明必须验证“候选事实→实际保存字段”的精确路径hash、目标身份和来源链，程序注入，不能接受模型一句“差不多相同”。`save_product` 在同一业务事务保存商品、FieldDisposition审计与研究绑定；若研究未满足绑定条件，明确返回待研究项。报告正文不被改写，accepted回执和有效绑定是两个可查询事实。

| 待实现函数 | 事务责任 | 返回/约束 |
| --- | --- | --- |
| `AudienceResearchService.resolve_for_product(product_ref, context, candidate_refs) -> ResearchResolution` | 只读查询或已有业务保存操作内调用 | 精确消费路径与上下文比较；无模型、无新HTTP写入口 |
| `AudienceResearchService.bind_in_uow(uow, accepted_report_ref, product_ref, identity_receipt, consumed_facts) -> AudienceResearchBinding` | 由 `save_product` 共享同一UoW，或已有 `accept_analysis_report` 更新已确定商品研究时调用 | 新品temporary key必须来自同一身份回执及source链，禁止按名字回绑；旧report不改写 |
| `AudienceResearchService.prove_compatibility(report_ref, candidate_facts, saved_product, source_manifest) -> CompatibilityProof` | 与绑定同事务读校验；实际hash计算可在锁外准备、事务内复验版本 | exact-path与来源一致才输出proof；依赖真变则INPUT_STALE，不因save_product自身revision递增而盲目stale |

已有商品新材料改变了研究必需事实时，第一轮研究只能明确标注候选假设；主Agent等待事实报告accepted后，必要时通过定向refine使用完整确切事实refs，再保存有效研究。accepted表示“报告通过接收合同”，不表示报告中的未知/假设自动成为已证实事实。

## 4. 历史商品引用与当前本场的固定版本

`read_product(product_ref)` 读取指定修订；返回 `current_head_ref` 只是告知有新版本，不能擅自改成读取head。研究查回及影响分析也必须说明相对于哪一个 product_ref。

| 状态 | 本场行为 |
| --- | --- |
| Preparation选择了P@4，商品库更新为P@5 | 当前本场继续按P@4；显示“有新修订可刷新”和影响清单 |
| 新研究仅对P@5有效 | 不自动放入P@4的ContextBundle；只有消费路径可证明一致时，建立P@4专用相容绑定，否则仍用P@4适用研究或补研究 |
| 用户明确“本场使用最新商品信息” | 由 `refresh_product_reference` 取得新引用并触发实际依赖失效；再重建必要研究/计划/审核 |
| P@5改变了本场消费字段，但未明确选择是否刷新 | 采用/start前展示新旧值和受影响句，等待用户保留或刷新决定；保留绑定精确旧ref、新head与diff hash，不能自动替用户选 |
| 用户决定保留P@4 | 可信human命令`record_product_revision_choice`保存RevisionChoiceReceipt；不改商品/稿件/编排引用、不推进内容epoch，不因选择本身使批准失效；下次head再变重新比较 |
| 普通新head只变化未消费字段 | 提示即可，不把head变动自动等同所选输入改变或批准失效 |
| 当前已停售、修订或信息明确撤回、活动自身过期 | 当前控制检查强制阻断；旧不可变版本存在、已保存保留选择都不能绕过，历史仍可查看 |
| 只要求更新全局商品 | 不连带刷新所有准备场次，也不改其旧稿；列出有权查看的受影响引用 |
| 旧稿基于旧商品，当前任务明确改为新商品事实 | 计划同时绑定旧稿base和新商品依据，差异明确；保留旧稿不能掩盖需更新的报价或条件 |

允许readset重绑的依据是逐消费路径不变，不是“这是同一个product_id”。相容绑定只证明特定研究能用于特定产品修订，不授予编辑本场或改稿权限。商品新旧选择使用01的ProductRevisionChoice/RevisionChoiceReceipt及16§8，不增加让主Agent自行“保留”或“刷新”的决定工具。真实选择经human-only命令，refresh在同一UoW调用已有私有刷新逻辑，keep只落独立索引/回执。普通head变化不是整包批准失效信号；实际refresh绑定ref/文本变化才按10使整包stale，未变声音可按内容键复用。当前可售/撤回控制是单独动态依赖，采用/start每次重查。

## 5. 本场配置怎样读取历史与判断差异

`read_session_history` 需要区分三种来源：room默认、历史Preparation草案、已采用Publication/真实LiveSession。返回精确refs和时间，不用“上一次”这个自然语言标签替代对象定位。

```python
class SessionHistorySelection(BaseModel):
    current_draft_ref: RecordRef | None
    selected_baseline_refs: list[RecordRef | ArtifactRef]
    selection_reason: str
    diff_items: list[FieldDiff]
    inheritance_items: list[InheritanceDecision]
    source_kinds: list[str]

class InheritanceDecision(BaseModel):
    field_path: str
    old_value_ref: ArtifactRef | RecordRef
    disposition: Literal['inherit', 'expired', 'override', 'needs_confirmation', 'not_applicable']
    validity_window: TimeWindow | None
    reason: str
```

本场worker执行：读当前draft→选明确历史基准→逐字段diff→核验日期/适用品/条件→列inheritance decisions→输出结构化报告。普通语言/音色/可复用主题可以预填；中秋活动不能跨过有效期默认为下一场活动；缺有效期或“今天”等相对日期用来源场次时区解释，不能按当前系统日期重解释成永久有效。历史售价可以供对比，不能覆盖用户本场新售价。

若用户只修改活动，不强制重复商品事实/研究；只查其可引用的适用研究、商品依据和受影响模块。当新活动改变目标人群或场景，影响分析提出定向研究需求；资料内维护在当前目标范围内可做，新增外网或整场重写另行确认范围。

## 6. 上下文：完整保存，不等于每次全部塞入模型

`ContextBundle` 保存能还原全部业务依据的完整原文/结构化对象/精确refs；每次模型请求使用按角色和当前动作构造的投影。摘要是导航与压缩手段，不是商品、研究或历史版本的权威替代。

### 6.1 模型输入分配表

| Agent/动作 | 始终提供（Always） | 按需读取（Progressive） | 排除（Excluded） |
| --- | --- | --- | --- |
| 主 Agent任务判断 | 当前真实指令、Goal、精确target/selection、禁做项、当前任务状态、必要决定、关键版本/差异选择/停售撤回阻塞及安全价格条件 | 完整产品/资料、历史研究、配置diff、旧稿、复盘、素材清单、历史工具结果全文 | 其他账户、无关任务聊天、密钥、未接受分支草稿冒充业务真值 |
| 事实worker | 本次事实分析要求、材料目录/最低身份、schema、已有商品精确refs、允许对象 | 源页/图/OCR、完整旧商品、被指向的事实冲突证据 | 其他worker messages、促单计划、无关研究假设、未明确的商品覆盖授权 |
| 配置worker | 本场目标、当前draft/ref、选定历史基准目录、日期时区、已知活动条件和身份 | 历史配置全文/diff、相关商品、声音选项、已接受定向洞察 | 全部商品旧稿和所有历史场次、顾客研究的未接受中间结论 |
| 研究worker | 目标商品/最低事实、market/channel/language已知与未知、旧研究索引、待判差异、范围和网络预算 | 旧研究全文/证据、新材料、顾客咨询评价、获准网络原文 | 全部本场稿件、其他商品历史、无权限搜索/费用、主Agent内部聊天 |
| 话术生成服务 | 精确模块动作、must-preserve、当前确定的价格/条件、输入ref版本、输出schema | 完整bundle中相关产品/研究/本场/旧稿/复盘，按生成输入构造器展开 | 未获准目标模块、未接受草稿、被拒绝的复盘建议作为指令 |

“始终提供关键价格”只指当前动作实际涉及的报价/条件，不能把所有商品的全部活动都常驻。长正文分页回读必须有 total/hash/next_cursor；未读完不声称已完整分析。生成输入构造器要保证本模块所需原文真正展开，不能把ref字符串当成模型已知正文。

### 6.2 长上下文处理与触发点

沿用已核验 `deepagents==0.7.25` 中的 Summarization 与 Filesystem 工具结果 offload；本期**不另造一个 ContextWindowMiddleware**。源码核验入口：`deepagents/graph.py`、`deepagents/middleware/summarization.py`、`deepagents/middleware/filesystem.py`。SDK提供按模型profile配置的压缩能力，但实际DeepSeek profile、上下文限额和可用阈值仍须实施时探针验证，不能认为SDK默认阈值必然适配所选模型。

| 时点 | 程序动作 | 需保留的证据 |
| --- | --- | --- |
| 模型请求构造前 | 计算系统提示/工具schema、当前关键观察、近期消息、准备读入片段的预算；为输出与后续工具往返预留余量 | model/profile版本、估计input、预留output/tool margin、裁剪选择 |
| 单个工具返回过长 | 全文先保存不可变业务blob或受控运行产物；给结构化摘要、关键字段、精确全文入口；SDK工具结果offload可承担传输压缩 | 原始hash、长度、摘录区间、offload ref；不丢工具错误/写回执 |
| 历史消息逼近经核验阈值 | SDK摘要较旧对话并保存可回读历史；近期必要工具调用与结果保持配对；不重复注册第二套summary | 压缩事件、摘要ref、被移出消息范围、原文入口、token前后估计 |
| 压缩之后/下一模型请求 | M3从业务真值和当前Scope重新注入目标、精确选择、禁止项、批准状态、关键价格/版本、待办依赖和refs | 本次AgentObservation及实际最终模型请求 |
| 关键原文仍装不下 | 按对象/模块拆小分析、分页精读或派有限子任务，结果形成typed完整报告 | 拆分manifest、实际读片段、未读区间/缺口；不可静默截断强行完成 |

预算配置记录 `model_context_limit / reserved_output / reserved_tool_margin / critical_projection / recent_history / retrieved_content`。这些是输入构造器的预算分区，**不是每区固定百分比的新产品规则**。只有经供应商profile和真实请求探针验证后，才能冻结数值。关键区放不下时返回明确错误或拆任务，不能优先删除Goal、身份、价格条件或人工门槛。

PRELIVE-2.3补充：最终供应商payload在M3/M4/SDK摘要之后仍经适配器保护，估算必须含system、最终messages、工具schema、response schema及编码开销，不能只算聊天tokens。每次实际尝试按01/16写持久ModelAttempt；SDK摘要另建child attempt，发送后未知不释放已发次数、不自动重新请求。跨夜等待的run grant首期expires_at=null，但时间敏感业务条件和撤回仍必须当前，不能把基础设施等待混成永久有效活动。

自定义M3与SDK摘要的真实hook顺序在SDK装配测试验证：无论摘要发生在何处，最终 `wrap_model` 看到的请求都须包含当前关键约束。摘要不能使过期批准复活，不能把历史P@4改写成当前P@5，不能把“待确认”压成“已确认”。摘要模型调用须计入可观察usage；不能宣称只统计主模型轮数就覆盖全部成本。

StateBackend中 `/large_tool_results/` 或 `/conversation_history/` 是当前thread的虚拟运行归档；不因为offload就成为业务持久研究。重启依靠checkpoint恢复运行文件，正式原件始终可由声播精确ref获取；SDK内部归档写入须可工作，模型对宿主文件写入仍禁止。

## 7. 横向信息传递：默认不互喂，必要时定向重分析

三个worker第一轮共享可信原材料/最低身份，各自独立分析；**不共享messages，不轮询对方token，不把正在生成的片段当事实**。事实和研究在4A汇合，配置和研究在4B汇合，通常已足够。

只有当一份已接受结论确实改变另一份任务的输入时，才增加显式 `InsightHandoff`。例如研究发现“购买者是照护者、实际使用者是老人”这一假设，可指导卖点和素材；若需要核实适用限制，主Agent将问题与来源定向交给事实worker，不把该假设直接写入规格。

```python
class InsightHandoff(BaseModel):
    handoff_id: str
    parent_run_id: str
    from_report_refs: list[ArtifactRef]    # 只允许声播accepted产物
    to_role: AnalysisRole
    target_refs: list[TargetRef]
    question: str
    evidence_refs: list[ArtifactRef]
    accepted_insight_ids: list[str]
    prohibited_inferences: list[str]
    required_output_changes: list[str]
    dependency_refs: list[DependencyRef]
    prior_branch_task_id: str | None
```

执行链：worker PREPARED→主接受正式报告→主判断需定向细化→保存带typed handoff的新版InputManifest→`dispatch_analysis_batch` 创建新语义task→新worker独立thread→接受新版报告→重新汇合。已有任务manifest和messages不在运行途中被别的worker改写。handoff作为运行产物保存，不增加任意发消息工具。

| 来自何处 | 可以影响 | 不能影响 |
| --- | --- | --- |
| 研究→商品组装 | 有事实支持的卖点排序、表述和需求映射；提出待核实问题 | 材质、重量、适用人群限制、库存等确凿商品事实 |
| 研究→本场配置 | 当前目标范围内的主题/表达建议；显式标建议待商家决定 | 用户已定活动、折扣力度、日期、商品选择 |
| 本场配置→研究 | 已明确渠道/市场/活动目标，定向补充相关场景 | 让研究假造本场转化证据 |
| 事实→研究 | 新规格、用途、适用限制；撤回已不成立的假设 | 将“原资料未提及”推成“商品没有该能力” |

默认每角色允许一次必要refine，受本run预算和目标约束；更多轮次须有明确未闭合问题和剩余预算，不允许三角色无限互相循环。重试同一任务与新增refine要区分：同manifest重试不生成重复接受产物；新manifest/新问题才是新task。

## 8. 完整执行样例

### 8.1 用户只说“更新这款拖鞋的资料”

| 次序 | 主Agent/程序的行动 | 数据与出口 |
| --- | --- | --- |
| 1 | 冻结明确拖鞋product_ref与新材料；不以同名覆盖另一个商品 | 原Goal、来源、身份/必要确认 |
| 2 | 主模型判断catalog_update并保存TaskAssessment | 商品＋研究维护＋影响清单，明确禁改稿 |
| 3 | 读取旧商品、历史研究、当前上下文，运行影响查询 | 旧研究全文入口、实际变更paths |
| 4 | 事实分析与必要的资料内研究增量可并行；metadata-only则研究确定性reuse | typed事实报告＋新研究或复用证据 |
| 5 | 主接受、汇合全字段、校验后保存商品；固定研究绑定到精确产品修订 | 商品回执、研究resolution与相容证明 |
| 6 | 查询哪些旧稿/本场引用可能受影响 | 精确影响清单；现有Preparation仍固定旧商品ref |
| 7 | 按本次目标验收并展示差异及待办 | 完成资料更新，提示改稿可作为下一指令；本轮不产生脚本修改/TTS |

若商品保存成功但网络研究在权限范围外，先尽资料内维护；需要网络补证则列出不足与范围请求，不能假称做过外网调研。只有原目标明确要求外网研究才按原预算执行。

### 8.2 用户只说“本场活动改成满300减60”

读取当前draft及明确历史基准→检查商品/优惠适用与矛盾→保存活动配置→列出需联动的opening/campaign/旧条件CTA。是否改稿取决于原用户目标明确包含“同步修改话术”，不能从“配置更新”的读取动作自动扩展为所有正文重写；若原目标是完整准备，按已有Goal覆盖的模块计划继续。

### 8.3 用户明确“参考上次复盘，改A商品第二版的卖点”

主Agent读取精确旧稿、完整相关复盘与逐条处置、该product_ref适用研究和本场必要条件；不派与目标无关的配置worker。只计划 `selling_points` 和已验证的必要条件联动。改稿后若用户要准备音频，仍须重新取得当前整包文案批准。

## 9. 失效、恢复与质量规则

| 变化/失败 | 检查与处理 |
| --- | --- |
| 本场明确刷新后的消费字段变化 | 研究相关insight、生成计划和整包文案批准按实际绑定输入失效；未消费字段不使全部研究报废。普通catalog新head未被本场选择时只展示差异/等待相关版本选择，不自动替换或作废批准 |
| 活动有效期结束 | 本场历史继承项过期；活动相关稿件/批准需重新核验，不抹除普通顾客研究 |
| 研究更新但本场未选择新版 | 固定原ref，提示新版本；未经明确刷新不改变现有本场输入 |
| 输入材料OCR纠正 | source提取revision更新，依赖该段的事实/研究重判；保留原图和旧文本用于审计 |
| 模型判断错任务 | 工具/授权拒绝越界；原计划保留，主按当前Goal修订；无法确认则问用户，不偷偷换Goal |
| worker并发完成 | 保持独立readset，接受其中一份仅追加索引不使另一份无关报告失效；真实输入变化只重算受影响分支 |
| 主进程重启或摘要发生 | 先取得数据根OS锁和thread整段执行锁，按run/业务refs/receipt与checkpoint恢复；FINALIZING优先完成撤权/执行者收敛，不再启动模型“重做完成”；不得依赖摘要中的“已完成”跳过实际回读 |
| 历史查询/网络不可用 | 明确缺口及可使用的资料内依据；不把unknown改为已研究/已确认 |

## 10. 实施验收用例

以下是待实施的断言，文档静态检查不能代替这些SDK、HTTP和数据库测试。

| 编号 | 输入/注入条件 | 必须观察的结果与指标 |
| --- | --- | --- |
| CTX-01 | 仅商品资料更新 | 主计划含商品＋研究维护＋影响清单；脚本/TTS/编排写入次数=0 |
| CTX-02 | 只修改内部备注，研究未消费该字段 | 研究reuse成功，额外研究模型调用=0；保留旧报告与新适用性证明 |
| CTX-03 | 商品用途/适用限制真实变化 | 只重判受影响insight；旧结论可保留者不丢，废弃者不进入新卖点 |
| CTX-04 | 新上传与已有商品同名但身份不明 | 保存商品前必须等人工身份决定，不能从名称自动覆盖 |
| CTX-05 | Preparation固定P@4，catalog head为P@5 | 所有本场生成输入仍为P@4；不相容新研究不得混用；未刷新不改本场 |
| CTX-06 | P@5仅变化研究未消费字段 | exact-path proof允许研究相容绑定；原研究readset/hash保持不变 |
| CTX-07 | 研究在商品保存前产生，保存时又改了依赖规格 | 绑定拒绝/定向重研究；不能以相同product_id跳过验证 |
| CTX-08 | 仅活动配置，历史中秋活动已过期 | 历史差异可见，过期条件不继承；无关事实/研究worker不强制运行 |
| CTX-09 | 三worker在同批并发，各自产生typed报告 | 各自独立messages/manifest；接受次序不丢报告；并行并发不超过既定3 |
| CTX-10 | 向worker注入其他worker未接受partial文本 | 不成为正式输入；若需使用必须经过accepted→typed handoff→新task |
| CTX-11 | 主模型提出整场重写或新增外网预算但Goal只有资料更新 | 在固定工具/服务层拒绝，记录scope gap；旧grant无变化 |
| CTX-12 | 任务文本由完整准备改为只读说明的新run | 只读run不写业务；不存在复用前run写授权 |
| CTX-13 | 长消息迫使SDK摘要及工具offload | 原文hash/完整回读成立；关键Goal/价格/版本/批准状态在最终模型请求前后等价 |
| CTX-14 | 摘要含旧P@4或“已批准”，实际已有新输入 | M3注入当前真值；旧批准拒绝，wrong-version写入=0 |
| CTX-15 | catalog_update已保存商品，研究维护故障 | 任务不误报全部完成；未终结时按原回执恢复合法等待/重试；已BLOCKED终结后用户明确继续创建新run复用原商品与回执，只补剩余研究，不重复建商品、不复活旧grant |
| CTX-16 | 用户只要求事实报告 | 验收通过不要求新商品/脚本；产品保存次数=0 |
| CTX-17 | 研究只有unknown市场，目标本场为澳大利亚 | 不标澳洲实证；上下文匹配差异明确，按scope研究或保留未知 |
| CTX-18 | 新商品尚无正式ID，两个同名材料分别录入 | 临时身份分离，正式保存后精确绑定；研究不能误绑定另一商品 |
| CTX-19 | 首次自由文本尚未有Goal，进入intent阶段 | 同main图完成意图读取/候选；issue_grant、dispatch与业务写次数均=0，直到Resolver合法且Coordinator首次freeze |
| CTX-20 | 主模型候选要求整场准备，用户只明确更新唯一商品资料 | 有限政策只允许catalog_update效果；候选不相容则拒绝/澄清，模型不能借候选给自己扩权 |
| CTX-21 | 意图识别需要身份/范围澄清，暂停后重启 | 保留intent候选hash/问题/phase，可信答复后继续同run；不因重启重复freeze或多发grant |
| CTX-22 | 已冻结Goal后再次调用意图候选/伪造phase | 工具阶段校验拒绝；Goal内容与grant不变；新增范围只能另建获准后继/替代run |
| CTX-23 | 生成验收Spec引用TaskAssessment后刷新计划 | 原TaskAssessment hash不变、不回填Spec；runs关联更新到新计划/适用Spec，旧版本可回读 |
| CTX-24 | P@4固定，P@5只有普通新修订 | 不自动刷新或使批准stale；消费字段差异在采用/start要求精确保留/刷新决定，未消费差异只提示 |
| CTX-25 | 已选择保留P@4，但当前停售或某修订明确撤回 | 当前控制阻断采用/start；保留回执和旧研究相容证明均不能绕过 |
| CTX-26 | 正常完成并关闭原run grant | 业务产物保留，ClosureReceipt和readset足以解释完成；human采用候选不要求旧grant仍active |

任务识别质量用版本化意图夹具评测：细类判断、必要能力召回、无关能力调用率、权限越界尝试、实际越界提交、缺确认漏检分别记录；不只以“模型分类正确率”代替业务验收。完成率以本次Goal成果证据计数，所有声称已完成的必需项必须100%可回读，实际越权提交和无身份确认覆盖必须为0。

## 11. 与既有分册的接点

| 分册 | 本增量需接入的位置 |
| --- | --- |
| 01 | TaskAssessment属于Agent运行库；研究binding/resolution属于声播；ContextBundle加入历史选择与完整研究依据refs |
| 02 | S1写入任务选择策略；M3按角色投影并在摘要后补当前约束；M4/M5校验计划不扩权限；M9记录计划/读取/压缩事件；不新增自定义middleware |
| 03 | 新增三个固定queries；接受报告/保存商品维护研究版本绑定及exact-path proof；不为计划保存新增voice command |
| 04 | 步骤按本次目标选取；2A/2B/3按需并行，研究复用优先；4A/4B正式汇合，必要handoff新任务 |
| 05/14 | 按本次Goal产出验收，不强求全链路；追加CTX用例与历史/压缩/研究版本夹具 |
| 06 | 展示任务范围、复用/更新研究理由、影响清单及可定位的历史差异；不把建议改稿自动提交 |
| 09—11 | 复盘仍是完整输入和可追踪处置；当前文案批准不被摘要/研究更新绕过；所有决定与原始调用进入调试记录 |

本期先实现可精确查回的版本化结构与refs。没有证据表明需要向量库才能查到同商品历史研究，因此不将向量检索、额外embedding调用或新的RAG系统列为必需依赖。
