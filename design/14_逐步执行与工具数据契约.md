# 播前 Harness：逐步执行与工具、数据契约

> 历史稿，已被[后端工程设计 v2](engineering-v2/00_后端工程设计.md)替代。正式函数、工具、DTO和事务边界以v2分册为准；本稿保留用于追溯。

版本：PRELIVE-HARNESS-1.0，2026-10-15。配合 [13 总体设计](13_播前Agent_Harness总体设计.md) 阅读。本文件把业务步骤拆成可选能力，不要求每次按表顺序全跑。所有新工具名、数据类型和命令均为拟建合同，不是已经存在的接口。

## 1. 一张总表：每一步由谁做

| 步骤 | 主体 | 核心行动 | 可验证产出 |
| --- | --- | --- | --- |
| 1 接收 | 准备服务＋主 Agent | 保存材料、识别最小身份、明确目标和范围 | SourceManifest、PreparationRecord |
| 2A 商品整理 | 商品资料子 Agent，可直接复用已有结果 | 提取事实/知识、匹配旧商品、查冲突与缺项 | ProductCandidate、FieldDisposition |
| 2B 本场配置 | 简单时主 Agent，复杂时本场子 Agent | 主题、活动、沿用、选择和播报设置结构化 | SessionDraft；此时不生成话术 |
| 3 顾客场景 | 研究子 Agent | 依据原资料及必要调研形成顾客/场景/需求依据 | AudienceResearch、Evidence、Hypothesis |
| 4A 完整商品库 | 主 Agent 合并＋声播保存服务 | 商品全部配置项处理，提炼有依据卖点，保存回读 | 正式 ProductRef＋全字段处理记录 |
| 4B 话术计划 | 主 Agent | 汇合三路完整输入，比较旧稿，制定模块行动 | ContextBundle＋ScriptChangePlan |
| 5 生成执行 | 声播局部工作流 | 执行指定模块，保留复用内容、保存新修订 | ScriptRevision＋ModuleChangeReceipt |
| 6 编排 | 用户决定＋声播编译器 | 编排商品/版本出现项，确定长短开场和音频需求 | PlaybackPlan＋AudioRequirements |
| 7 语音 | 声播任务和缓存 | 只补实际所需且缺失/失效的音频 | AudioManifest、JobRef |
| 8 检查 | 程序整包校验＋主 Agent 解释＋声播页面 | 展示差异与缺口，接收修改，保存检查快照 | ReviewPacket、ReviewReceipt |

2A/2B/3 可从第 1 步的共同资料并行开始。4A 依赖对应商品的 2A＋3；4B 依赖完整商品＋研究＋本场配置，另加旧稿和用户决定。资料更新只使实际受影响产物失效。

## 2. 第 1 步：接收与归档

| 项目 | 详细设计 |
| --- | --- |
| 触发 | 新商家要求、上传材料、选择已有商品、补充截图、继续准备或局部修改 |
| 上下文 | 用户最新原话；已有 preparation/room 引用；当前字段 schema；当前时间和时区；此前有效用户决定 |
| 执行动作 | ①保存原文件而非只留模型总结；②建立来源 ID、文件哈希、页/段/单元格/图片位置；③做文本抽取；④识别最小商品身份和本场意图；⑤区分商品事实、用户要求、附件中的说明与未知；⑥创建/修订准备记录；⑦给主 Agent 返回精简快照和可回读引用 |
| 工具 | `read_capabilities`、`read_business_schema`、`ingest_material`、`read_preparation`、`read_source` |
| 产物 | 原件引用、抽取产物、临时商品 ID、输入范围、`goal_revision`、SourceManifest |
| 失败出口 | 文件损坏、格式不支持、图片无法辨认时保存原件和具体失败位置，允许补文本；其他资料可继续 |
| 验收 | 可从任一提取字段回到原件位置；重传同文件不重复创造来源；商家附件中的指令不获得系统权限 |

### 2.1 文件处理方案

| 输入 | 首期拟用组件 | 需要交付的行为 | 未具备时如何处理 |
| --- | --- | --- | --- |
| 纯文字/Markdown/CSV | Python 标准库及结构化解析 | 保留段落、行和列位置；不执行文本里的命令 | 编码失败返回可说明错误 |
| DOCX | `python-docx`＋ZIP 中内嵌图片提取 | 正文、表格、图片分别索引；截图式文档不能只读段落 | 内嵌图片交 OCR，失败页请补文字 |
| 有文本 PDF | `PyMuPDF` 等本地解析 | 按页保留文字与位置；图文混排不丢图片 | 复杂页作为图片进入 OCR |
| PNG/JPEG/扫描 PDF | 本地 CPU OCR，优先评估 RapidOCR/ONNX 路线 | 中文/英文、金额、规格能定位原图；低可信片段标未知 | 先做真实样例探针；识别不清不自动填写关键价格 |
| XLSX | `openpyxl` | 表、单元格和原始值；公式读取区分表达式与已缓存结果 | 不自行执行宏，不宣称算出了未计算公式 |
| 网页链接 | 受控 HTTP 原文抓取 | 保存抓取时间、URL、可读正文和失败状态 | 登录/动态/反爬页面失败如实记录，不声称已读 |
| 音视频、旧 DOC 等 | 首期不设为必须支持 | 返回支持范围和文字/图片替代方式 | 不因有文件上传框就假定能转写所有媒体 |

上述依赖没有因为 SDK 环境准备而自动安装。OCR 探针用用户给过的商品库、话术截图以及 DOCX 内嵌截图；验收检查关键数字和来源，不只看文字识别率。

OCR 候选的一手入口为 [RapidOCR](https://github.com/RapidAI/RapidOCR)。本方案只选择其本地 CPU/ONNX 路线做待测候选，没有安装或运行，也不承诺复杂截图全部可正确解析。

## 3. 第 2A 步：商品资料整理

| 项目 | 详细设计 |
| --- | --- |
| 触发 | 新商品资料、旧商品资料变化，或有效候选不存在 |
| 上下文 | 原始材料与抽取内容；最小商品身份；实际 ProductInput schema；已有商品候选及对应知识；用户已确认身份/事实 |
| 执行动作 | ①按字段提取事实和知识；②保留原商家卖点及依据，不把它当最终顾客价值结论；③用 SKU/型号/规格/名称检索相似旧商品；④逐字段展示差异；⑤把明确同一商品、明确不同商品、无法确定分开；⑥查商品/知识/活动中价格和条件冲突；⑦生成缺项清单及用途；⑧写自己命名空间的候选报告 |
| 工具 | `read_source`、`search_catalog`、`read_product`、`read_business_schema`、`save_branch_artifact` |
| 产物 | ProductCandidate：候选字段、字段状态、来源、相似候选、差异、冲突、待确认项；不提前正式创建 |
| 与其他分支 | 研究从原始身份/资料开始即可；2A 后来确认关键事实改变时发送新快照，使相关研究局部失效 |
| 失败出口 | 识别不出商品则返回 `needs_input`；某字段未知不伪造；相似度只是检索线索，不是覆盖许可 |
| 验收 | 相同名称不同 SKU 不误覆盖；旧知识的价格冲突可定位；无卖点的半成品不硬塞入当前要求卖点必填的正式接口 |

身份合并规则：用户明确选择的既有 product_id 优先核对；SKU/型号冲突必须保留差异；模糊匹配只提供候选。新增或覆盖对象不明确时集中问一次。已确认的选择保存成带对象和输入版本的决定，不每轮重复问。

## 4. 第 2B 步：本场配置整理

| 项目 | 详细设计 |
| --- | --- |
| 触发 | 新场次、复制前场、主题/优惠/声音/商品范围变化 |
| 上下文 | 本场原话和材料；当前 room 与 commerce；旧场配置；当前日期/时区；用户商品/版本选择；本机/MiniMax 合法音色；临时商品映射 |
| 执行动作 | ①整理日期、主题、目的；②区分长期商品信息与本场覆盖；③解析用户优惠、适用商品、门槛/币种/期限/叠加条件；④识别可沿用/明显失效/需确认内容；⑤整理补充知识和播报设置；⑥缺少绑定正式商品 ID 时保留临时映射；⑦校验并保存结构化草案 |
| 工具 | `read_room`、`read_business_schema`、`read_voice_options`、`validate_session_draft`、`price_preview`、`save_branch_artifact` |
| 产物 | SessionDraft，不是话术：主题/目的、日期、商品引用/临时引用、用户优惠、本场知识、语言/音色、版本数量、循环设置、沿用决定和缺口 |
| 默认与确认 | 通用内容可默认沿用并展示；中秋等明显不适用的日期活动不沿用；缺关键优惠条件不得替用户补决定 |
| 失败出口 | 优惠组合超出现有后端支持、币种冲突、优惠条件缺失时标明具体限制；无关配置继续 |
| 验收 | 2B 没有直接生成话术；本场覆盖不污染基础价；简体普通话不把 TWD 改成 CNY；过期配送日期不自动作为本场承诺 |

当前声播支持结构化单个 Coupon 和单品 Promotion，不能据此宣称支持任意多档/叠加优惠。首期合同先兼容实际可表达的满减券/折扣；用户提出不能表达的组合时明确返回不支持或待补条件，不自动选一个“最省钱”方案。

正式 SessionDraft 需要 typed 日期、期限、继承记录；当前 room 的 `scene` 文本不能完整替代。准备存储先持有完整草案，提交时只写声播支持的字段；新字段由服务合同显式扩展，不能提交后被旧白名单静默丢弃。

## 5. 第 3 步：顾客、场景与需求研究

| 项目 | 详细设计 |
| --- | --- |
| 触发 | 新商品、关键功能/价格/适用事实变化、渠道变化、用户要求重新分析；已有有效结果可复用 |
| 上下文 | 原资料与最小商品身份；2A 已有事实片段；商家咨询/评价/经验；已知地区/渠道；本场已知主题；不等待 4A 商品库完成 |
| 执行动作 | ①分清购买者与使用者；②提出候选使用场景与需求；③先读商家已有证据；④证据不足时按问题检索原文；⑤记录支持/反例/局限；⑥分证据结论、营销假设和未知；⑦形成需求—商品属性—可能价值映射；⑧指出本商品适合准备哪些演示资料 |
| 工具 | `read_source`、`search_web`、`fetch_web_source`、`save_branch_artifact`；无商品/房间写入和直播动作 |
| 产物 | AudienceResearch：购买/使用人群、场景、需求、顾虑、证据、假设、未知、资料限制、版本及素材建议输入 |
| 两个用途 | 给 4A 的可复用卖点提供顾客需求依据；给 4B 的本场角度和讲解重点提供依据；不直接输出最终稿 |
| 失败出口 | 没有真实用户证据时注明推测；网络不可用保留渠道失败并使用现有材料；依赖关键未知事实的结论暂缓 |
| 验收 | 研究不能把“久站人群可能在意支撑”写成未经证实的医疗效果；来源支持具体观点；关键事实更正能局部校准 |

### 5.1 网络与 MCP 选择

业务运行时需要独立配置搜索能力，不能假定 Codex 的浏览工具可以被新应用直接调用。拟建统一 `SearchProvider`/原文抓取接口；首个托管搜索候选为 Tavily，开发时按官方 SDK/HTTP 文档核验，接入凭据和样例探针尚未完成。若用户不配置搜索服务，支持读取用户给定公开 URL 和本地材料，研究标记 `source_limited`，不得假装已完成网络调研。

已核对 Tavily 官方 [Search](https://docs.tavily.com/documentation/api-reference/endpoint/search) 和 [Extract](https://docs.tavily.com/documentation/api-reference/endpoint/extract) 的接口入口。搜索结果摘要和分数只用于选源；需要支持结论时再读取原文并保存证据。这里没有做厂商价格比较，也没有接通真实服务。

首期不为“小红书/X/电商评论全抓取”许诺登录或全量采集。商家导出的咨询/评价可作为上传材料。将来新增渠道 MCP 只替换搜索/读取适配器，沿用同一 Evidence 合同。原文只作为资料，不能覆盖用户目标或触发安装工具、发送消息等动作。

素材建议表至少回答：对应卖点、顾客为什么需要看、建议画面/演示、用户如何提供、是否缺资料。首期不调用视频 API，不创建播放触发器。

## 6. 第 4A 步：完成商品库全部配置

| 项目 | 详细设计 |
| --- | --- |
| 触发 | 对应商品候选与研究可用，或已有商品需更新 |
| 上下文 | 全部字段 schema；2A 的完整候选/知识/来源；3 的完整需求分析；既有商品；用户确认事实；2B 中需要厘清的价格/活动归属 |
| 执行动作 | ①逐字段列处理状态；②把事实、需求和商品属性合并成有依据卖点；③处理身份/规格/材料/价格/知识/履约/售后等全部配置；④普通 FAQ 留知识用途，重要限制按需进入后续计划；⑤展示新增/修改差异；⑥解决必填与冲突；⑦用版本条件和稳定 operation key 保存；⑧回读核对所有实际变更字段；⑨把临时商品引用映射到正式 ID |
| 工具 | `validate_product_candidate`、`save_product`、`read_product`、`record_user_decision`、`read_business_schema` |
| 产物 | 正式 ProductRef；完整字段处理清单；卖点—需求—事实映射；知识与研究关联；写入回执 |
| 并发规则 | 子 Agent 不直接提交；同 SKU 创建由唯一约束和幂等协作；已变化商品 CAS 拒绝覆盖，新事实导致相关下游失效 |
| 失败出口 | 必填缺失保持待补；可选未知允许空但有记录；保存超时进入对账；回读不同不能标完成 |
| 验收 | schema 每字段都有处理状态；正式必填无缺；可选/不适用不编值；只维护同一份正式商品；旧房间仍引用同 ID |

### 6.1 字段组与处理状态

| 字段组 | 内容举例 | 特别规则 |
| --- | --- | --- |
| 身份 | ID、显示编号、SKU、可售/归档状态 | 系统生成字段不能伪造；同名不等于同商品 |
| 展示 | 名称、图片 | 图片引用要能打开；无图片是否阻塞以实际 schema/产品决定为准 |
| 规格/物性 | 尺码、颜色、型号、材质、成分、版型 | 图片和文字冲突需定位，不凭行业常识补齐 |
| 适用/使用 | 实际适用人群、用法、重要限制 | 研究画像另存，不覆盖经确认的适用事实 |
| 价格/促销 | 币种、日常售价、长期促销归属 | 本场优惠写本场覆盖；按真实支持结构处理 |
| 卖点 | core_selling_points / selling_points | 当前服务两者有兼容同步规则；选定一个正式入口并回读，不独立维护两套 |
| 履约/售后 | 发货地、备货、配送说明、退换 | 历史日期不自动沿用；未知售后承诺不能补成“零风险” |
| 保存条件 | 存储、保质期值/单位 | 不适用明确记录，不为了全字段有字而乱填 |
| 知识 | 知识文档、标题、FAQ、注意事项 | 全量可读取；常规口播不必须讲完全部知识 |

字段状态枚举拟为 `provided / derived_supported / optional_empty / not_applicable / missing_required / conflict`。`derived_supported` 只用于有原始依据的整理/表达，不表示模型猜测的商品功能。系统生成字段记录 `system_assigned`；状态元数据存在准备记录，不强塞进现有商品 schema。

处理全部字段不等于每次重写全部字段。已有商品的新资料没有提到某字段时，默认保留已确认旧值并记录 `keep_existing`；只有用户明确清空或有效变更计划才提交清空。更新合同显式区分 `set / keep / clear`，不能把缺资料生成的 null 当清空命令。兼容当前 PUT 必填的名称/价格时从同一已校验版本补入，而不是用过期默认值覆盖。

## 7. 第 4B 步：完整上下文与模块行动计划

| 项目 | 详细设计 |
| --- | --- |
| 触发 | 新稿、资料/主题/活动变更、用户指定改稿，或经确认更换久用主体 |
| 上下文 | ①4A 全字段正式商品；②3 完整研究；③2B 完整本场配置；④已有稿件全文/模块/版本/使用记录；⑤用户决定；⑥实际生成能力 |
| 执行动作 | ①解析临时商品映射，按已授权意图新建房间或选定原房间；②将完整本场草案通过受控工具发布到空闲 room 并回读；③冻结输入清单和版本，核对三路完整引用；④读旧稿与使用情况；⑤选择本场人群/场景切入和主辅卖点；⑥逐模块决定新建/修改/复用/停用并列必要联动；⑦生成每模块要求与精确条件；⑧保存计划及保留内容指纹；⑨校验计划仍对应当前输入 |
| 工具 | `create_room`、`publish_session_config`、`read_room`、`read_script`、`read_script_usage`、`build_context_bundle`、`read_context`、`save_script_change_plan` |
| 产物 | 可回取完整输入的 ContextBundle；ScriptChangePlan；每模块动作、依据、基准、允许范围、保留指纹、完成条件 |
| 失败出口 | 任一路必需上下文缺失时，不生成一份简报冒充完整输入；版本过期只重新策划受影响范围 |
| 验收 | 计划可逐项回答“改谁、改哪段、为何、依据哪版、保留什么、关联改哪里”；生成器实际收到这些信息 |

### 7.1 模块定义

| 模块类型 | 用途 | 复用/修改原则 |
| --- | --- | --- |
| `opening_long` | 欢迎、主题、较完整引入 | 文本可备齐；循环中的长开场不能总说“刚开播” |
| `opening_short` | 换商品/版本的短引入 | 与商品及本场相符；不和长开场连续拼着播 |
| `product_intro` | 商品是什么、适用场景与基础介绍 | 无事实变化优先复用 |
| `selling_points` | 面向顾客需求展开主辅卖点 | 事实和顾客价值有关联，表达可多版本 |
| `campaign` | 本场活动、规则、范围与期限 | 没活动则明确不启用；有明确活动直接按要求更新 |
| `cta` | 促单和行动提示 | 若带旧优惠必须联动；不凭空编库存稀缺 |
| `transition` | 简短收尾、进入下一播出项 | 不擅自添加平台上不存在的按钮/购买方式承诺 |

上述为语义模块；可以包含多个 block/sentence。当前声播的 stage 字符串不是稳定模块 ID，后端需要增加映射合同。

### 7.2 变更策略

| 触发 | 默认模块行动 | 必须保留/检查 |
| --- | --- | --- |
| 新商品无稿 | 初始化所需模块及两种开场文本 | 无活动时不用虚构活动；版本差异来自角度/讲法 |
| 用户明确活动改变 | 改开场、活动，及实际引用旧条件的模块 | 未受影响主体指纹不变；主体使用年龄不重置 |
| 主题改变 | 改开场，按需要明确调整重点模块 | 不能暗中全稿重写 |
| 商品事实改变 | 改真正引用该事实的模块 | 同时更新依赖的研究与卖点，不影响无关商品 |
| 主体使用较久 | 提示建议，用户确认才刷新主体 | 使用记录未知不假定播了一周；拒绝后记录选择 |
| 仅音色 | 全文复用 | 不调用文本生成 |
| 仅顺序 | 主体复用，重算开场/必要衔接 | 缺开场文本只补缺；不重写全部版本 |

首期只提供使用时长提醒和确认换稿，不做转化收益归因。起点/记录不可靠时给出未知，不能随意设一个“已使用七天”的事实。

### 9.1 长短开场算法与例子

设一轮有 N 个出现项，当前轮次 k 从 0 开始，轮内位置 i 从 1 开始。全场序号 `p=k*N+i`，当 `(p-1) mod 5=0` 用长开场，否则短开场。

| 全场序号 | N=3 的循环播出项 | 开场 |
| --- | --- | --- |
| 1 | A 第 1 版 | 长 |
| 2 | B 第 1 版 | 短 |
| 3 | A 第 2 版 | 短 |
| 4 | A 第 1 版 | 短 |
| 5 | B 第 1 版 | 短 |
| 6 | A 第 2 版 | 长 |
| 11 | B 第 1 版 | 长 |

有限 R 轮：对每项求 k 在 `[0,R-1]` 内需要的模式并集。无限固定循环：模式经过 `5/gcd(N,5)` 轮重复，只需检查这个有限周期；展开总项数为 `lcm(N,5)`。不需要把无限队列存成无限行，也不需要直播时临时生成缺失开场。

当 N 是 5 的倍数，每个轮内位置模式固定；其他 N 下，每个位置跨周期会遇到长短两种模式。所以“只合成所需”不等于任何场景都只给每稿合成一种开场。文本仍可同时保留长/短，音频需求由真实编排决定。

手动跳播的计数口径仍待确认。本算法验收覆盖正常顺序及正常循环；不能擅自宣称跳播后严格按已播放次数重新计数已被用户认可。

```json
  "artifact_refs": [],
  "error": null,
  "next_check": {"tool": "read_job", "service": "shengbo", "job_id": "job_demo"}
}
```

### 13.2 错误与处理

| 错误码 | 模型/服务如何处理 |
| --- | --- |
| `INVALID_INPUT` | 按字段错误纠正，有界修正 |
| `MISSING_REQUIRED` | 记录缺口；不影响无关商品；集中补问 |
| `IDENTITY_AMBIGUOUS` | 展示候选差异，请用户确认新增/更新 |
| `SOURCE_CONFLICT` | 列双方来源和有效条件，不能静默选一个 |
| `REVISION_CONFLICT` | 重读当前对象，重新评估差异；不能无条件覆盖 |
| `STALE_INPUT` | 输出归档，相关任务失效；按新输入重规划受影响部分 |
| `UNSUPPORTED_COMBINATION` | 说明后端能力限制，保留用户原规则，不悄悄降级 |
| `CONTEXT_LIMIT` | 按商品/模块分解或分页；仍不足就交付明确缺口 |
| `RATE_LIMITED / TEMPORARY_UNAVAILABLE` | 适配器有界退避，计入预算 |
| `TIMEOUT_UNKNOWN` | 先对账，不自动重新提交付费/新增动作 |
| `NOT_AUTHORIZED` | 不重试扩大权限；报告具体缺口 |
| `CANCELLED / SUPERSEDED` | 不再激活旧目标；已完成有效缓存可留 |

### 13.3 幂等和恢复顺序

1. 可信服务验证 scope、对象和预期版本，登记 action 与参数哈希。
2. 同 key 同输入返回已有动作；同 key 不同输入拒绝。
3. 服务端业务写入与幂等回执尽可能在同一事务完成；仅在 Agent 包装器去重不足以保护旧后端。
4. 异步受理保存 job/输入版本，不在受理时声明准备完成。
5. 重启或超时先查 action/job/实际对象。确认未执行才重试；结果无法确认保持 unknown。
6. 子任务和 job 回来时比较当前目标/计划修订；有效内容可以缓存，旧绑定不能提交。

## 14. 数据结构：各类记录要保存哪些内容

### 14.1 不可变引用与完整输入

| 类型 | 必须字段 | 语义 |
| --- | --- | --- |
| `ObjectRef` | kind、id、revision、content_hash、read_locator | 对正式商品/稿件/配置的准确引用；旧系统无 revision 时先补，内容哈希仅作观察不能替代 CAS |
| `SourceRef` | source_id、file_hash/url、locator、captured_at、extractor_version | 页、段、cell 或图片坐标；OCR 原图和抽取结果分开 |
| `Evidence` | claim_id、claim、source_refs、支持范围、局限、observed_at | 来源支持什么，不把检索摘要当已核对全文 |
| `Hypothesis` | 内容、依据、待验证点、影响范围 | 研究假设不能填成材质/性能/库存等正式事实 |
| `FieldDisposition` | field_path、state、candidate_value、source_refs、reason、question_ref | 包括所有 schema 字段，null 与未知/不适用不同 |
| `ContextBundle` | bundle_id、商品/研究/本场/旧稿/决定 refs、snapshot、exact_constraints、required_sections、hash | 原输入完整可取回；模块执行时绑定相同输入 |

### 14.2 准备、任务和用户决定

| 类型 | 必须字段 | 所有者 |
| --- | --- | --- |
| `PreparationRecord` | id、room_ref、goal、goal_revision、status、selected_refs、input_snapshot、current_plan_refs、blockers、warnings、event_seq、created/updated | 准备服务，唯一写入入口 |
| `BranchTask` | id、parent_run、role、object_scope、input_hash、attempt、status、start/end、artifact_refs、error、usage | 任务注册器，分支不能篡改别的任务 |
| `SessionDraft` | theme、objective、starts_at/timezone、商品引用/临时映射、用户规则、期限/范围、继承记录、知识、language、voice、version_count、loop、unknowns | 准备服务，正式支持字段发布声播 |
| `UserDecision` | question_id、对象/字段/版本、answer、actor、channel_event_id、decided_at、supersedes | 可信输入服务；模型可以提出问题，不能捏造回答 |
| `ActionRecord` | action_id、operation_key、参数hash、对象/预期版本、status、receipt、job、确认时间、错误 | 动作服务；不靠聊天记录对账 |
| `QuestionBatch` | question IDs、选项/自由回答、原因、阻塞对象、输入版本、有效期 | 主 Agent 汇总；相同问题去重，相关资料变了旧答案可失效 |

SessionDraft 可以先引用临时商品，但正式 room/脚本/编排发布前必须解析到有效 ProductRef。新建房间由用户明确意图或已授权准备目标触发，不能每次补截图就创建新房间。

`save_session_draft` 仅证明草案已保存；只有 `publish_session_config` 的回执及正式 room 回读一致，才证明本场配置已落地。首期对正在直播的 room 只保存下一场草案；需要完整准备时选择/新建空闲 room，不静默修改当前直播，也不把尚未发布的草案标成整包 ready。

发布比较采用合同中明确的 `published_field_projection`，不是要求 RoomConfig 与 SessionDraft 的全部 JSON 相同。来源、研究和继承理由仍保留准备存储；会影响商品引用、报价、生成、声音或播放的必要字段必须有正式落地位置，不能因旧白名单丢弃而继续ready。用户点击启动时，声播再次验证正式对象版本并冻结对应播放快照；准备阶段的ready不是对后续编辑的永久保证。

### 14.3 话术计划与播放/语音

| 类型 | 必须字段 | 不变量 |
| --- | --- | --- |
| `ScriptChangePlan` | id/revision、bundle_ref、目标商品/版本、base_script_refs、module_actions、keep_hashes、user_decision_refs、status | 计划和输入指纹匹配；每模块动作明确 |
| `ModuleAction` | module_id/type、create/update/reuse/disable、base_ref、reason、依赖、精确条件、生成要求、允许范围、完成判据 | reuse 不调用模型重写；无效活动可disable |
| `ScriptRevision` | script_id、revision、parent、product_ref、module_refs、sentence_refs、bundle/plan_ref、主体使用信息 | 新修订保留旧稿；活动变动不重置未变主体 |
| `PlaybackItem` | item_id、product_ref、script_ref、module_refs、user_order_index | 相同 script 可出现多次，item_id 不同；不能按 script_id 去重 |
| `PlaybackPlan` | id/revision、items、loop mode/rounds、opening_rule_version、周期、manual_skip_policy、compiled_hash | 编排属于用户决定；开场映射由程序算 |
| `AudioRequirements` | playback_plan_ref、needed module/sentence keys、长短模式集合、声音参数 | 真正会播的都具备；未用模式不默认合成 |
| `AudioManifest` | requirements_hash、audio keys、有效文件/时长、失败项、job refs | 内容缓存键与计划绑定分开；文件存在不等于适配 |
| `ReviewPacket` | id/hash、所有最终refs、检查结果、diff、blockers/warnings、准备修订 | 任何有关联的人工修改都会使旧包失效 |
| `ReviewReceipt` | packet_hash、preparation/room revisions、真实用户事件、确认时间 | 不等于单稿approve；不能由模型伪造 |

### 14.4 金额与优惠数据

Money 在服务合同中使用 `currency`＋十进制字符串或精确最小单位整型，选定一种并固定；建议对 Agent 输入保留十进制字符串，由后端 Decimal 计算。不能使用二进制浮点结果直接编报价。

折扣明确表示“应付比例”：八折为 `payable_ratio_bps=8000`，不能和“优惠 80%”混用。满减记录 threshold、deduction、currency、适用范围、期限和已知叠加条件。价格试算不得把不满足门槛的单件价格称为确定到手价；未接平台发券能力，不称已经发券。

## 15. 更新失效与确认规则

| 变化 | 需要重读/重做 | 继续有效 |
| --- | --- | --- |
| 新截图但内容相同 | 来源去重/关联；核对无变化即可 | 商品、研究、稿件、音频 |
| 商品材料/功能/适用事实变了 | 2A、受影响研究/卖点、4A、相关模块与语音 | 无关商品和未引用事实的模块 |
| 本场活动/期限变了 | 本场草案、相关开场/活动/促单、关联音频和检查包 | 主体未受影响内容及使用年龄 |
| 仅顺序变了 | 编译计划、所需开场集合、缺失文本/语音、检查包 | 主体、研究、正式商品 |
| 仅音色或 TTS 声学风格变了 | 相应音频需求/缓存判断、检查包 | 文本和研究 |
| 话术表达风格变了 | 本场表达要求、受影响模块计划/生成及语音 | 未要求改动的商品事实和研究 |
| 用户拒绝主体换稿 | 保存本次决定，保留现稿 | 有效正文和缓存；不能每轮再次催换 |
| 界面编辑了商品或本场 | 新版本进入同一依赖计算 | 其他有效范围；旧 Agent 提交必须被 CAS 拒绝 |
| 主任务取消 | 后续提交失效，取消能取消的 job | 已保存正式事实及可验证内容缓存；不得自动撤销未授权事务 |

失效判断由显式字段/模块依赖与内容指纹配合，不只依赖模型猜测。模型可以建议联动范围，程序至少保证必然引用旧价格、条件或文本的绑定不可继续 ready。

## 16. 提示词与输出约束的编写顺序

| 部分 | 写什么 | 如何验收 |
| --- | --- | --- |
| 角色目标 | 本次角色产出、对象范围、完成标准 | 不把分析角色写成能直接开播的全能角色 |
| 事实与信任 | 原资料是数据、研究有假设、用户最新决定优先 | 附件里的“忽略规则/覆盖商品”不能改变权限 |
| 动作原则 | 何时查 schema、委派、取原文、询问、保存/回读 | 不靠模糊建议代替具体调用 |
| 上下文 | 当前目标、对象版本、必要来源引用 | 旧价格/旧计划不能因摘要留存而覆盖新事实 |
| 输出 | typed 报告/模块计划、证据、未知、失败/取消 | JSON 合法之外，还检查事实和业务终态 |
| 终止 | 完成/待输入/待任务/预算/无进展 | 不强求“必须完成”造成无限循环 |

开放文本质量可使用人工量表校准；程序校验金额、ID、版本和未改模块。首期不以模型自己的信心分数作为真实正确率，也不要求输出完整内部推理过程。
