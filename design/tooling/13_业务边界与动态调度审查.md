# 播前 Agent：业务边界与动态调度审查

日期：2026-10-15。用途：供整体 Harness 设计复核；本文件是只读研究所得的设计建议，不是已实现能力或正式接口合同。不修改业务基线，不包含业务实现代码。

## 1. 审查依据与结论

依据：`10_播前Agent首期流程基线.md` 全文；`08_业务闭环与动态数据详细设计.md` 的首期输入、事实依据、补问和商品/本场边界。旧文档与10冲突时采用10；用户当前强调 Deep Agents 主 Agent 自主选择并调用工作流程，以 Harness 组织执行。

建议采用 **一个 Deep Agents 主 Agent＋三类可按需调用的短生命周期专业子 Agent＋声播业务工具**。三类分别是商品资料、本场配置、顾客场景；简单本场配置可由主Agent直接处理，不必每次派全三类。这个结构支持复杂新建时真正三路并行；用户看到一个连续的准备对话；程序保持一个准备记录和正式商品源，不产生多套话术、商品或场次。

## 2. 角色、运行时 Skill 与工具分工

下表是建议的应用运行时分工。开发时的 `agent-harness-design` 和 `deep-agents-core` 是开发指导，不能直接作为电商业务 Skill 安装后就声称功能已完成。

| 单元 | 类型/职责 | 对应业务步骤 | 读取与产出 | 写权限与约束 |
|---|---|---|---|---|
| 播前统筹主 Agent | Deep Agents 主入口；理解这次需求，选择相关工作单元；合并结果、补问、解释差异并组织交付 | 1、简单2B、4A的业务合并、4B、8；按需调度其余步骤 | 本次准备清单、权威版本引用、用户决定；形成候选配置与模块计划 | 经声播受控工具保存；负责向用户集中澄清，不允许子 Agent 各自反复问同一问题 |
| 商品资料分析子 Agent | 在独立上下文中解析材料、按字段组织候选、相似商品差异与冲突 | 2A；4A必要的字段整理 | 仅本商品原文、schema、相似候选、相关用户决定；产出字段候选、证据、缺项 | 默认只读业务源；写工作产物，不直接覆盖正式商品 |
| 本场配置子 Agent | 复杂新建时与另外两路同时调度；检查本场主题、沿用资料、活动条件及播报设置 | 复杂2B | 本场原文、场次模板、可引用商品候选ID、历史活动与当前时间；产出结构化草案、冲突和待问项 | 只提交草案，不直接生成话术，不向用户独立提问或覆盖正式配置 |
| 顾客场景研究子 Agent | 根据最小商品事实及本场相关要求，研究顾客、使用情境、诉求与疑问 | 3 | 原文、稳定商品身份、已知地区/渠道和事实；产出有来源的研究与明确假设 | 默认只读业务源；研究结论不能变成未经证实的商品材质/性能等事实 |
| 本场配置能力 | 主 Agent 按需加载的业务 Skill；理解场次范围、沿用条件和活动规则 | 2B | 原场配置、本场要求、商品引用、可选音色；产出结构化草案 | 此时不生成话术，不替用户决定商品、力度或顺序 |
| 商品汇合及话术变更计划能力 | 主 Agent 按需加载的业务 Skill；汇合并检查版本，再制定各模块行动 | 4A、4B | 三路完整上下文、旧稿全文、版本与用户决定；产出全部字段处理结果和模块计划 | 保存前经程序校验依赖；研究假设在研究记录中保留，不能强塞事实字段 |
| 声播业务服务 | 确定性服务/任务，不额外设一个自由规划 Agent | 4A保存、5、6、7、8 | 商品schema和查询、差异与保存、统一话术生成、队列编译、TTS与状态、统一确认页 | 准入校验、幂等、版本/冲突控制、回读；正式数据的唯一写入口 |
| Harness约束 | 应用中间件/工具包装及持久状态 | 全流程 | 有效准备版本、任务、补问、证据、工具回执、已确认决定 | 验证依赖、限制写入、取消过期结果、恢复执行、记录可解释轨迹 |

角色数不是业务步骤数。2A和3确有独立信息工作和上下文隔离价值，适合作为子 Agent；2B复杂时增加本场worker以获得真正并行，简单时主Agent直接整理。5由声播统一生成服务执行模块计划，首期不再额外造自由写稿 Agent；必要时在该工具内部执行受控生成与结构校验。

### 2.1 两种角色方案与真正并行的取舍

| 方案 | 优点 | 局限与采用结论 |
|---|---|---|
| 主Agent＋商品/研究两类worker，2B始终由主Agent处理 | 最少角色；主Agent直接掌握本场对话 | 主Agent同批调用2A、3的原生task并等待工具批次返回时，不能假装同时继续推理2B。若先做2B再派2A/3，只是两路并行。适合简单配置，但不能作为复杂三路并行的完整解释 |
| 主Agent＋商品/本场/研究三类短生命周期worker | 三路可在同一批task中实际并发；各自产出候选，主Agent统一合并 | 多一类worker，但只在复杂2B需要推理时启用。推荐此结构；简单变更仍主Agent直办，不要求每次都派满三路 |

并行验收记录每个任务的dispatch/start/end时间与共享输入版本；三路并发样例应有真实执行区间交叠，不以“文字写着并行”作为证据。若当前供应商或运行时无法同批原生调用，工具层可采用受控批处理并发调度，但必须另测，不声称调用三次顺序task就是并行。原生工具批次存在汇合等待时，不能宣称主Agent已能消费尚未返回的部分结果；如需真正分批流式汇合，应明确异步作业/轮询适配或小批次边界及其恢复合同。

## 3. 动态选择流程的含义

主 Agent可以处理“只换音色”“上传一张补充截图”“改本场优惠”“把A第二版放第一”等局部请求，并决定仅调用需要的工作单元。业务步骤是可调用的能力及其依赖，不是每次从1跑到8的固定脚本。

| 当前变化 | 主 Agent 应选择的工作 | 程序守卫负责什么 |
|---|---|---|
| 首次导入新商品并准备一场 | 最小身份识别后并行2A、2B、3；按商品汇合4A；三路有效后4B，后续按需生成、编排和语音 | 只有同一商品且版本兼容的结果才能汇合；未解决身份/必填冲突不能正式保存 |
| 已有商品，只改已明确活动 | 更新2B→4B的相关模块行动→5→受影响音频7→8 | 主体不随活动重写，引用旧条件的促单必须联动；不得将改活动视为主体换稿 |
| 只换音色 | 读取已有效文本和队列，7→8 | 复用文本；音色变更使旧音频匹配失效；不再次搜索和重写商品 |
| 只改顺序 | 6→必要的缺开场文本5→必要音频7→8 | 重算跨圈长短开场，主体复用；旧队列关联任务不能重新激活 |
| 商品事实有改动 | 在受影响范围重新2A/3校准→4A→4B→5/7；无关商品继续 | 字段到研究、稿件、音频的依赖使旧结果失效；不能只修改UI数字 |

模型决定“接下来考虑/调用什么”；程序决定“这个动作当前是否可执行、读写哪个版本、结果能否采纳”。工作流可以是工具内部的受控步骤或专业子任务，动态总入口始终是主 Agent。没有依赖的数据就先补齐，不强行跳步；已经有效的数据可以复用，不重复全流程。

## 4. 十二条不可丢失的边界

| 编号 | 边界 | 设计落实 | 验收红线 |
|---|---|---|---|
| B01 | 统一商品源与本场分离 | 声播正式商品只存一份；2B保存本场覆盖与商品引用；不伪造开播session | 改优惠不能修改其他场次或长期基础价 |
| B02 | 4A处理全部字段 | 读取实际schema；每字段是已填/可选留空/不适用/缺失/冲突；保存再回读 | 必填未处理不能标完成；不能只输出卖点 |
| B03 | 研究与事实分开 | 2A来源可追溯；3分证据、假设与未知；最小身份后并行 | 对目标用户的推测不能当成产品性能、适用安全或库存事实 |
| B04 | 4B是完整上下文及执行计划 | 保留完整商品、完整研究、完整本场配置、旧稿全文与决定的可回读引用；模块计划明确基准修订与改动范围 | 仅一份不可还原的简报不能交给生成器；关键条件不能压缩丢失 |
| B05 | 自动修改与确认各有边界 | 明确本场活动/主题后自动生成相应定制；弱匹配新增/更新、冲突、未知承诺、主体用久换稿需用户决定 | 明确活动不重复申请生成；不能暗自换主体或覆盖同名商品 |
| B06 | 决策归属 | 用户决定选品、版本、顺序、优惠力度；Agent分析与解释，按决定准备 | 无智能排品、自动分配讲解时间、利润/折扣优化 |
| B07 | 模块化局部更新 | 新建初始化所需模块；活动变更改开场/活动及实际引用旧条件模块；正文未变保持修订或内容指纹 | 不整稿覆盖；活动更新不能重置主体使用年龄 |
| B08 | 长短开场及跨圈 | 商品＋版本出现项计数，第1/6/11项长，其余短；文本可备两套，按真正需要合成 | 不能把“5个商品”理解为5种不同商品；不能只计算第一圈 |
| B09 | 音频精确绑定与增量 | 音频引用最终文本修订、音色、TTS参数；已成功可复用；失效片段补做 | 文案/音色不匹配不能标ready；过期任务完成不能复活旧计划 |
| B10 | 受控并行与可恢复 | 子任务共享原始引用，独立候选；主Agent合并；有效修订和任务预算守卫；暂停保存决定 | 断点恢复不重复副作用；局部缺口不阻塞无关商品；子任务没有冲突写入 |
| B11 | 声播为唯一审核和播出执行入口 | Agent完成配置；声播同页展示并允许修改；本场包校验准备状态；用户最终开播 | “调用成功”不等于保存回读成功；播前Agent不自主公开开播 |
| B12 | 首期范围和验收价值 | 仅素材建议，普通KB按需，不加独立逐句语义审查Agent；简体普通话但原币种不变 | 不加视频生成/Hook、播中动作、播后闭环、自动Q&A排练和成交提升承诺 |

## 5. 五条端到端验收轨迹

以下为计划中的验收案例，不是已执行测试。每例需保留输入样本、工具请求/回执、准备修订、用户决定、最终差异与检查结果。关键数字/身份/承诺错配、未经授权开播、覆盖错商品属于阻断失败，不能被平均分掩盖。

| 轨迹 | 输入与运行过程 | 应见到的调度与证据 | 通过条件 |
|---|---|---|---|
| T01 新建完整场次 | 新拖鞋资料＋本场主题＋用户优惠及队列；至少两商品三版本 | 身份识别后2A/2B/3有重叠执行证据；4A字段清单和回读；4B关联三路完整输入；5生成模块；6编译；7任务；8审阅 | 全部schema字段有处理状态；实际需要的正式必填无遗漏；三路引用100%可读；有效价格/币种/条件一致；队列每项有可用文本音频及审核入口 |
| T02 已有稿件改活动 | 同一商品正文已有并使用；用户只将活动从旧券改成明确新优惠 | 主Agent不跑完整商品/研究流程；计划只更新开场、活动、实际引用旧优惠的促单；显示具体diff | 未受影响正文指纹一致；旧优惠残留0；主体使用记录未重置；未变化语音复用；完整上下文仍可回读 |
| T03 相似商品和资料冲突 | 同品牌两SKU，新截图价格与旧知识矛盾；另一个无关商品资料完整 | 候选对比及原文定位；对身份/价格集中补问并暂停受影响项；无关商品继续；用户确认后定点恢复 | 误覆盖0；冲突未经确认写入正式值0；无关商品可交付；回答与具体问题/准备修订绑定，恢复不二次创建商品 |
| T04 重排与循环 | 三项A1、B1、A2循环；用户把A2移第一；已有音频可复用 | 重算整个必要周期；第1、6、11项长；商品＋版本重复分别计数；缺开场局部生成与TTS；旧任务延迟返回 | 主体保持；映射与确定性公式一致；跨圈需要的模式全部可用；只补缺失/失效语音；旧plan结果不切回旧顺序 |
| T05 暂停/失败恢复＋人工改动 | TTS部分完成、一次合成失败、用户补问待答；重启后用户还在声播修改一个字段 | 从持久准备记录读取有效版本、待答、成功音频与失败项；重新核对人工改动；只恢复未完成的有效任务 | 成功任务不重复付费提交；使用同幂等键得到同操作记录；新人工事实优先进入重新核对；旧回答/任务不能覆盖新版本；最终ready检查与实际配置一致 |

T04的跨圈规则可用程序公式验证：全场实际编排出现序号为i，`(i-1) mod 5 == 0`时长开场。固定N项循环的开场模式组合周期为`lcm(N,5)`项；当N不是5的倍数，同一队列位置会在不同圈需要长、短两种模式。必须在生成需求清单时覆盖这个事实，而不是为了省事每次都重合成全部内容。

## 6. 待定事项及不阻塞设计的处理

| 事项 | 未明确点 | 当前可推进的处理 |
|---|---|---|
| 手动跳播计数 | 按原计划位置还是实际播过数决定长开场 | 播前按已确认队列位置和循环生成；运行期跳播的计数契约独立标待定，不承诺自动重算。可支持用户重新编排并生成新播放计划，不为此阻塞播前设计 |
| 动态商家字段schema | 当前声播接口可能较旧文档新增字段 | 工具必须运行时或按版本读取schema；正式合同在实现前核对；本审查不硬写字段全集进代码 |
| 用户一周换稿 | 未必有可靠使用起点/使用次数 | 无记录就询问是否希望换稿；不能推定“已播一周”；只在明确确认后改主体 |
| 搜索/OCR供应方 | SDK安装不等于渠道已接好；部分图片难识别 | 工具接口抽象为读取/抽取/搜索/原文抓取；实现时逐一探针；失败保留原图和未知项，必要时用户补充 |
| 同时人工编辑 | 保存前读取内容可能已过时 | 要求预期修订或内容指纹；冲突时重新读取、合并/补问，不自动覆盖人工新内容 |
| 自动Q&A排练 | 旧问题未明确首期采用 | 首期不添加；普通知识及FAQ可整理和按需展示，排练另行确认 |
| 实际开播与播出链接 | 本任务是播前设计，后端实际API需盘点 | 准备结果只到已审核可启动；播出/OBS链接由声播生成和展示，Agent不自主开播 |

## 7. 对主设计文档的建议

1. 先把上述角色和边界落入统一技术蓝图，再按业务步骤写“可调用能力卡”，每卡列触发、输入版本、上下文、工具、输出、禁止项和验收。
2. 把主Agent的“可自由规划”与程序的“不可违反依赖/版本/确认”同时写清楚；不能仅在系统提示词要求守规矩。
3. 单独给出自动、需补问、需换稿确认、最终开播确认四类门槛，避免把所有生成都放进繁琐审批，或把所有写入都视为自动安全。
4. 不为对应Learn Claude Code章节而增加消息总线、持久团队、后台shell、独立压缩器等机制；有业务需要时再明确Deep Agents原生语义映射。
