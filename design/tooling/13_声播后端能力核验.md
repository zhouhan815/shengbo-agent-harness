## 1. 核心结论

| 设计问题 | 核验结论 | 对 Harness 的影响 |
| --- | --- | --- |
| 声播是否可作为后端 | 可以。商品、房间、优惠、稿件、TTS 任务、播放器均已有本地 HTTP 接口 | Agent 调服务，不操作声播数据库或复制商品库 |
| 是否必须做 CLI | 首期不必以 CLI 为依赖；先实现类型化 HTTP client 与 Deep Agents 工具适配 | 如要命令行排障/其他 Agent 使用，再给相同 client 加薄 CLI 外壳 |
| 是否必须做 MCP | 当前单机 Python Deep Agents 可直接调用类型化 Python 工具，无需先多建协议层 | 跨语言/跨客户端时再把相同业务 client 暴露为 MCP；不复制校验规则 |
| 原有生成服务能否直接完成 4B/5 | 不能完全完成。已有分段存储和编辑，但公开生成入口仍按“整商品、整版本”生成 | 需要模块计划、完整上下文输入、局部生成/复用及提交回执接口 |
| 原有 TTS 是否要重写 | 不宜重写。已有句级内容寻址缓存、后台任务、逐项进度与失败保留 | 增加按播放项编译后的所需句集合与版本 fence，复用实际合成能力 |
| 原有就绪是否足够 | 不足以代表新准备包就绪。`all_ready` 仅代表选中稿件音频齐全，陈旧状态另列 | 新准备包校验需要整合资料、决策、话术、开场、计划、TTS 一致性 |
| 是否已有强制逐稿确认 | 没有。存在 approve 接口，但当前开播允许 draft 话术配齐音频后使用 | 新方案采用一次整包检查/确认，不能未经用户要求重新引入每稿强制确认 |
| 是否已有可靠并发保护 | 播中动作有有限保护；商品、房间、生成任务尚无完整版本 CAS/持久幂等 | 后端服务层需补版本条件、持久操作回执与旧任务失效屏障 |

## 3. 商品库与本场配置的所有权

| 对象 | 当前事实 | 应保留的约束/缺口 |
| --- | --- | --- |
| 正式商品 | SQLite records 中 `kind=product`；字段结构见 ProductInput 与 ProductFields | 唯一正式商品源归声播。Agent 只保存候选、来源与字段处理状态，不直接写数据库 |
| 商品字段 | 名称/图片/价格/币种/卖点/促销/知识文档；SKU、可售状态、规格、材质、成分、适用人群、存储与保质期、发货、售后、使用说明、FAQ 等 | 4A 必须处理所有 schema 字段，未知/不适用等元数据保存在准备记录，不能硬写不支持的商品字段 |
| 核心卖点 | 显式提交 core_selling_points 时同步成 selling_points；旧客户端更新 selling_points 时清空结构化列表 | 不能独立维护两份相互矛盾的卖点；工具应选定结构化入口并回读 |
| 商品 ID/SKU | 系统生成 ID 和显示编号；SKU 非空且唯一，无 SKU 时用 ID | 相似匹配是 Agent 辅助判断；正式覆盖需要明确 identity，不按名称猜着覆盖 |
| 房间商品 | `product_ids` 引用正式商品，删除引用清理本房间相应覆盖，不修改库商品 | 继续保留共享商品库；不能每个房间复制一份商品资料 |
| 本场业务 | commerce.scene、coupon、promotion、knowledge_documents、product_overrides | 可保存场景说明、单品价格/折扣/赠品/发货覆盖、全场优惠范围等 |
| 优惠计算 | Decimal 计算；同币种检查、门槛、单品互斥、范围校验、文字与数值冲突检查 | 当前是一个 Coupon 对象，不应宣称已有任意多级券组合/完整订单篮定价；用户决定力度，后端负责计算 |
| 主题/目的/日期/沿用规则 | 可放 scene 文字；目前没有完整独立 typed session campaign draft / 有效期 / 继承决策模型 | 准备记录保存明确结构；最终映射支持字段。需要正式持久 typed 字段时增补后端合同，不能向 room PUT 随意添加会被丢弃的字段 |

## 5. TTS 与后台任务：复用方式和边界

| 项目 | 当前实现 | 新 Harness 应怎样使用 |
| --- | --- | --- |
| 声音来源 | system/Huihui 和 MiniMax 若干预设音色；有 model 白名单；本机声音由 RealtimeTTS + Windows SAPI 产生 WAV | 模型只选合法配置；密钥由声播服务持有，工具输出不含凭证 |
| 内容缓存 | audio_key 绑定文本、provider、voice、model、风格配置；cached_audio 校验 WAV 和时长 | 复用缓存标识，避免另造一套与声播不一致的 TTS key |
| 文件写入 | 先写 partial WAV 再替换正式文件；房间分目录 | 保留有效结果；已取消/旧计划任务产生的音频允许作为内容缓存，但不得激活旧稿/旧队列 |
| 异步任务 | job/items 持久进度，内存 TASKS 执行；同房间同 kind 运行中拒绝重复任务 | 后台任务返回 job_id，Agent 查询或等事件，不能阻塞模型回合等待整场语音 |
| 部分失败 | 已完成文本、音频、manifest 保留；错误与未运行项可见 | 局部重试；脚本任务重新提交目前会再产新版本，不能把音频缓存重试规则套到脚本重试 |
| 重启 | list_jobs 把无在执行 TASKS 的 queued/running 标 interrupted | 已有“标中断”，未具备持久执行器自动精确续跑；新计划需要明确恢复策略 |
| 取消 | 内部捕获 CancelledError 保存中断 | 没有公开 cancel endpoint/取消令牌；线程中的网络调用不保证被 asyncio 取消停止 |
| 输入冻结 | 音频 job 保存 tts、script ID；脚本每项开始时重新读当前有效商品/配置 | 整任务输入并不完整冻结；必须补 expected input revision 与提交前检查 |
| 过期附加 | attach_scripts 只检查商品是否仍属于房间，然后追加脚本列表 | 用户重排/更新计划后，旧任务仍可能附加旧结果。需要 plan revision fence 才能防止旧计划复活 |

## 6. 版本、幂等、就绪和人工确认

| 项目 | 已具备的事实 | 设计必须补足/注意 |
| --- | --- | --- |
| 商品/房间版本 | updated_at 秒级时间；SQL INSERT OR REPLACE | 不是 CAS；并发改写可覆盖。新增单调 revision/ETag 与 expected_revision，由后端事务判断；包装器先读后写不足以消除竞态 |
| 稿件修订 | revision、parent_id、新 ID；保留 product_snapshot | 还需模块依赖与计划 revision；结构化编辑生成的新记录元数据不能假定完整继承，需统一修订保存服务 |
| 话术陈旧 | commerce_signature 覆盖一组选定生成字段；旧稿 fallback 比对部分字段 | 这是现有最低保护，不是完整研究/活动/规则上下文版本；新上下文应有 manifest/hash，不只比较价格和卖点 |
| 开播前保护 | 检查本场商品归属、稿件陈旧、音频齐全；同一时间只开一个房间 | 保留作为播放器后端检查。播前 Agent 到 ready_for_review 即可，不自动 start |
| 音频 all_ready | 只看缓存文件完整 | configuration_stale 独立；最终 ready 须同时检查文本/商品/活动/顺序/音色绑定、阻塞项及确认快照 |
| approve | 有单稿操作；当前开播路径不校验 approved | 不把“已approve数量”作为新主门槛。整包人工确认针对 preparation revision / review snapshot，并在用户编辑后重新计算差异 |
| 播放动作幂等 | action_id 内存字典，最多 500 条；expected_epoch/session_id可选；播放器 ACK 绑定 epoch+attempt | 仅本进程播中动作有限去重；不等于商品/房间/生成任务持久幂等 |
| 写入幂等 | 未见商品/房间/任务 API 的持久 idempotency key | 新增 operation_id + payload hash + receipt，重复同 key 同输入返回同结果，异输入409；与业务提交同事务 |
| 准备包场次 | 目前 runtime session_id 在开播时生成 | Agent 自己用 preparation_id，不伪造 session_id；房间 room_id、准备包 preparation_id、实际开播 session_id 分开 |

## 7. 接入层建议：HTTP + Python client 为首期主线

| 层 | 责任 | 首期建议 |
| --- | --- | --- |
| 声播业务 HTTP 服务 | 唯一商品/房间/稿件/音频服务；验证业务规则、CAS、幂等、准备包提交 | 必须复用并补接口合同；不能由 Agent 直接调用 put/db |
| 类型化 Python client | 参数校验、HTTP 超时、结构化错误、引用回读、回执识别 | 首期必需；不 import server，因为有读环境、seed、房间初始化等导入副作用 |
| Deep Agents 工具 | 将 client 方法封装为窄工具；区分读取、保存、付费生成；限定 room/preparation scope | 首期必需；主 Agent 组织并调用，研究子 Agent默认无写权限 |
| CLI | `shengbo ... --json` 薄命令行；复用同 client/Schema；供人排障、集成脚本和其他语言 Agent | 可选的小交付；不让 Agent 为调用既有 HTTP 而每次启动 PowerShell/拼 shell |
| MCP server | 复用同 client 暴露工具，统一 auth/context/schema | 后置选项，当前不必全部 MCP 化；MCP 不替代后台任务/数据库/幂等逻辑 |
| 声播 UI | 展示本场商品/设置/模块计划/稿件/顺序/音频/差异；用户确认和开播 | 按用户定位补整包 review；不是 Agent 的主要操作通道 |

API 目前仅允许 localhost/127.0.0.1，写请求带 Origin 时检查端口一致；没有跨机器业务鉴权/租户体系 ([server.py:691](<D:/Codex project/ecommerce-voice-agent/app/server.py:691>))。首期本机 client 合适；后续远程部署不能仅把 localhost 改成公网地址就认定已可安全复用。受控工具应避免暴露通用 HTTP/SQL/任意脚本执行工具。

工具返回建议统一成 `ok / operation_id / resource_ref / resource_revision / input_manifest_hash / receipt / warnings / error_code / retryable / next_action`；大正文返回稳定 artifact 引用加预览，模型按模块取回完整上下文。不能以“只返回摘要”取代完整来源保存。

## 9. 各环节契约验证与评价指标

| 环节 | 必测案例 | 可量化通过标准 |
| --- | --- | --- |
| 字段映射 | 完整样本、可选未知、明确不适用、资料冲突、相似但不同SKU | 所有 schema 字段都有处理状态；必填缺失不能标完成；正式回读与已确认候选一致 |
| 商品/房间写入 | 同revision并发编辑；HTTP超时后重试；同operation不同payload | 同一版本仅一笔更新成功；重试不新增重复记录；异payload拒绝 |
| 本场优惠 | 币种不一致、门槛、优惠文字矛盾、单品互斥、未保存预览 | 输出与后端 Decimal 结果一致；不确定不称已确认到手价；预览不改正式配置 |
| 模块生成 | 只改活动；改活动导致促单引用联动；只改音色 | 未要求改动的正文内容hash保持；必要联动被列入计划；音色变化不触发文本重写 |
| 播出编译 | A1/B1/A2；重复同script；1/6/11；三项循环；重排后长短切换 | 独立播出项不丢；周期映射准确；实际会播的开场都有文本与所需语音；不播多余长短开场 |
| TTS | 部分缓存、损坏文件、同文换音色、局改一条句子、失败恢复 | 缓存有效不重新付费合成；只补缺失/失效；文件和manifest绑定正确 |
| 旧任务 | 任务运行中修改商品/活动/顺序；旧任务晚于新任务完成 | 旧结果不能回写新计划/恢复删除项；有效内容缓存仍可复用；回执标清superseded |
| review | 查看后用户编辑；Agent恢复旧检查点；draft文本+完整音频 | 旧确认失效且展示差异；不越过用户开播；保持当前允许draft准备的规则 |
| client/CLI | 服务未启动、超时、400/409/502、路径/字段错误 | 结构化错误清楚区分重试/需补充/版本冲突；不泄露密钥；CLI与Python工具同Schema同结果 |

现有测试已覆盖若干基础（缓存复用、损坏重建、后台部分失败、房间引用与优惠隔离等），可作为后续回归基础；新增验收必须针对新业务合同，不能把旧测试名称当作新 Harness 已通过。

## 10. 设计移交时的关键提醒

1. 现有 API 和拟新增工具名必须分列。不要把 `ProductInput` 支持字段误写成已有 Agent 解析/OCR能力。
2. 分段保存不等于模块局部生成；句级缓存不等于已支持只合成长短开场的当前需求。
3. runtime epoch 不等于准备包 plan revision；检查点恢复不等于后端副作用幂等。
4. 当前后端没有任务取消入口、完整 CAS 和持久幂等，不能靠“主 Agent 记住别重复调用”代替。
5. `all_ready=true` 不包含 `configuration_stale=false` 的含义；整包ready还需要依赖和用户决策。
6. 未确定的“手动跳播后长开场按原队列还是实际播放次数计算”保留待确认。播前静态编译可先按已确认1/6/11规则设计，不默定播中语义。
7. CLI可提高人类排障和后续复用便利，但首期核心是稳定、可验证、可恢复的业务动作合同。Deep Agents通过类型化工具调用该合同，不需要先建一个万能shell工具。
