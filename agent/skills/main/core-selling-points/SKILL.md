# 核心卖点：把产品特征转成购买理由

目标产物是商家可以复用的“卖点名称：卖点内容”，不是规格说明书、资料核对提示或直播口播整稿。你写营销正文，现有wf_selling_points负责引用、版本和人工确认；无需新增模型审稿节点或固定大工作流。

## 用哪些上下文

- 当前商品精确版本的完整已知字段、消费者知识文档、FAQ，以及用户本次补充。缺少现成卖点不是商品不能用：区别真实事实不足与尚未把已有事实写出价值。
- 正式、适用当前商品的顾客场景研究；用户的经营背景、目标人群与本次重点。没有正式研究且任务需要人群分析时，由统筹Skill调用既有audience_scenes，不能把自己猜的一段分析说成已保存报告。
- 顾客可以有不同购买动机。商家做培训不意味着只有学员能买，实际适用范围与本次优先人群分开。用户明确确认的适用对象可以用于本轮；不要继续沿用已被确认替代的“待确认”，也不要扩展出年龄或效果保证。
- 参考资料只提供写法，不能提供本商品事实。首次使用或风格被否定时，读[真实样例与推演](references/value-writing-examples.md)，不必每轮重读。

## 怎样写

先在已有信息中寻找“特征/功能 → 哪类顾客遇到什么问题 → 能带来什么实际价值 → 具体场景”的对应关系，再选购买价值较高且互有区别的角度。允许把有依据的功能转成日常利益、使用画面和适度情绪表达，不要求每句都照抄参数。不要将常识用途也写成审计报告；未知性能和结果保证仍不能补造。

- 名称用易理解、有记忆点的利益或亮点，通常6至16字；正文通常1至2句，解释产品如何在该情境中帮到顾客。长度服务于清楚表达，不机械凑字数。
- 用顾客能想象的动作与场景，说明省下什么麻烦、得到什么练习/使用机会或体验。可以用合理类比、痛点和轻度营销润色；不靠“必备神器、效果翻倍”等空泛口号代替产品依据。
- 购买理由可以围绕功能、组合设计、使用便利、适配人群或场景展开；不是每个规格必须各占一条。材质/颜色只有与本商品的真实购买动机有关时才单列。不能从材质名称直接推导轻量、耐用、减震等未知性能。
- 用户要求多类人群时，让不同角度覆盖其主要需求。培训场景可描述课外自主练习、把课堂练习延续到课外；独立新手也有自身购买动机。用途或目标可以写“练习、熟悉、寻找”，不能偷换成“保证提升、几天学会、替代教练”。不要把这种示例固定成所有商品的模板。
- “材质说清楚”“套装看清楚”“选购更有底”等只说明信息透明，不能充当核心卖点。重复强调一个人能用却换几个标题，也不算多条独立购买理由。
- 正文保持自然有吸引力。逐项证据放evidence，审计限制放limitations；真实影响适配/安全或优惠成立的必要条件仍须自然保留。不要把“未实测、不承诺、仅供核对”等审计句反复塞进营销正文。

提交前在当前写作轮次完成一次自审：①顾客能否想象使用动作/场景；②购买理由能否由本商品事实解释；③是否覆盖本次目标人群；④是否存在重复凑点或可随便套在任何商品上的空话；⑤是否新增了未知性能或保证。普通商品可以有共通利益，不为制造“独家差异”编造竞品不具备的能力。发现具体问题就局部修改，不循环开启新的模型审核。

## 交给现有工具

由主Agent一次组织整组items，引用已验收的研究ref，调用wf_selling_points.propose。每项selling_point、audience_need、use_scene、limitations均为字符串；evidence才是数组。多个限制合并为一段limitations字符串，不提交限制数组。selling_point保存“名称：内容”；不要把标题、评分或参考商品另加成工具不接受的参数。propose之前必须已有当前商品正式generation回执；offer的parameters仅product_ref，写作方向放用户答复或propose.direction，不传给offer。

依据必须逐字定位当前商品真实字段；允许knowledge、target_audience以及/knowledge_documents/数字/content。研究只指导选择、排序和表达，不代替产品事实。按统筹Skill保留生成意愿与候选保存的两个既有门禁；“帮我生成/测试”不等于批准保存。用户看过候选并明确确认后，才由现有save入口入库。
