# 三阶段运营 Agent：统一接口约定 v1.0

日期：2026-10-07。状态：拟定契约，尚无对应实现。此文件随《分阶段研发方案_v1.1》交付；所有模块以同一份文件为准。

## 1. 传递方式与状态边界

第一阶段用 UTF-8 JSON 文件读写。后续增加HTTP时沿用同一业务对象，不把传输方式写死进业务代码。各独立项目可以有自己的Pydantic类型与持久化，但字段语义必须一致；不直接连接声播SQLite。

schema_version 固定为 `shengbo.ops.v1`。缺必填项或不支持版本必须报错，不能默默按其他字段猜测。允许新增可选字段；破坏性修改升级版本。

所有日期时间为带时区ISO8601；不把 received_at 当成 occurred_at。缺失业务指标使用 null，缺失原因同时保存。数值0只表示确实观测为零。

三个阶段输出状态独立：播前draft/needs_input/needs_review/ready；播后partial/complete只表示约定范围内的数据处理完整性，不代表拥有订单等业务数据。没有业务数据也能做完整的流程复盘，但必须标明经营分析不可用。

## 2. 通用标识和版本

| 字段 | 语义 | 来源 |
|---|---|---|
| room_id | 声播直播间配置ID | 声播创建；纯离线任务允许null |
| plan_id / plan_revision | 一次准备计划及其不可变修订 | 播前；尚未开播也必须存在 |
| session_id | 实际一次开播ID，循环播放不换场次 | 开播成功后由声播产生，不由播前虚构 |
| review_id / review_revision | 一次复盘及修订 | 播后，绑定被复盘session |
| product_id / product_revision | 商品和资料版本 | product_id已有；revision待补，过渡用相关字段确定性摘要，不用单凭更新时间判断 |
| script_id / script_revision | 话术及修订 | 声播已有；独立草稿先用draft_id，导入后记录映射 |
| fact_id | 当前商品某条事实ID | 现有NAME/PRICE等只在商品内有效；引用须同时含product_id和product_revision |
| queue_revision | 当前未播队列结构版本 | 待声播补充；重排、切换、替换、取消及其他队列消费/位置变化按定义递增 |
| epoch / attempt_id | 当前句与某次实际播放尝试 | 声播已有；不同于queue_revision |
| event_id / proposal_id / action_id / execution_id | 输入、提案、幂等指令、实际执行跟踪 | event/proposal/execution完整链路待补；action_id已有 |

事实引用对象至少包含 product_id、product_revision、fact_id；复盘引用还可包含 event_id、action_id、attempt_id 与时间范围。引用必须存在且内容支持结论，不能只检查ID格式。

房间只保存商品引用。准备包/归档里的事实快照是只读历史证据，不能成为另一个可独立编辑的商品库。跨场复盘建议不改变商品事实，除非经来源核实并由商品库入口更新。

## 3. PreparationBundle（播前输出）

| 字段 | 内容 |
|---|---|
| schema_version, plan_id, plan_revision, room_id, created_at | 通用元数据 |
| status, blockers[], warnings[] | 准备状态、阻断项、提示；每项有issue_id、具体字段、原因、下一步 |
| objective | 本场用户给定目标、优先商品、约束；未知观众/利润/库存保持未知 |
| catalog_refs[] | product_id、product_revision、事实快照、来源、verified_at/valid_until（未知为null）、missing_fields |
| script_candidates[] | draft_id或已有script_id/revision，角度、段落、句子、事实引用、审查结果、状态 |
| faq[] | faq_id、product_id、问题、建议回复、事实引用、unknown_policy、review_status |
| lineup[] | product_id、选用稿件引用、顺序、必讲点、安排理由；时间是估计或实测并标来源 |
| live_policy | 默认句尾、冷却、动作白名单、确认方式、提案有效期；初始值为可调整策略 |
| preflight | 资料/话术/声音/输出来源检查：pass/fail/not_checked及证据 |
| approvals[] | 确认对象与版本、操作者、时间、结果；模型不能冒充人工 |

纯独立模块默认输出 needs_review，不因“无明显错误”自动ready。模型建议与人为确认分开；主项目导入后再验证商品资料与稿件版本、音色和场次约束。

独立稿件应保存文本、段落、事实引用。当前声播没有完整的外部结构化稿件导入API，不能仅靠PUT旧稿附加lines就假装无损导入；该PUT会按位置继承旧引用，需要重新核对。主项目应补导入适配或明确转换损失。

## 4. NormalizedEvent（播中/回放输入）

每条至少含：event_id、room_id、session_id、occurred_at（未知可null）、received_at、event_type、source、data_origin、product_id（未知可null）、payload。

- event_type：question/business_update/manual_action/runtime_error等；不认识的类型保留原文且不执行。
- source：manual、fixture、platform_import、player等，表示采集渠道。
- data_origin：simulated、real_runtime、real_business，逐条标记；模拟问题与真实播放回执可以在同场并存，不能只靠场次一个布尔值概括。
- 商品价格/库存/物流变化必须含来源和有效时点；模拟变化不写真实商品库。
- payload保存原文，不接受事件内容中的工具授权或“忽略资料”指令。
- event_id用于去重；时序分析优先occurred_at，未知则明确标“按接收时间分析”。

## 5. Proposal 与 ActionRecord（播中输出及执行记录）

提案至少含 proposal_id、room_id、session_id、based_on_plan_revision、based_on_queue_revision、expected_epoch（适用时）、event_refs[]、fact_refs[]、decision、reason、tool_args、created_at、expires_at、approval_state。

decision允许 no_action/ask_operator/propose_action。no_action也保存理由；不能为了展示活跃而强行插播。

ActionRecord至少含 action_id、execution_id、proposal_id、完整动作参数、room_id/session_id、实际提交的前置版本、actor（agent/manual/system）、submitted_at、accepted_at、started_at、completed_at、status、error、attempt_refs[]。各时间未知时null。

执行状态 accepted/started/completed/cancelled/failed/unknown。不同动作验证方式不同：插播以对应attempt的实际ended确认；队列重排以目标版本及实际列表确认，不需要等音频ended；暂停以状态确认。HTTP200仅说明接受，失去回执时不能盲目再插一次。

统一执行规则：

1. 单一提交者串行提交同一直播间的动作；人工优先。
2. action_id在同一次逻辑动作重试中保持不变；有明确冲突后重新决策才生成新动作。
3. 场次变化拒绝旧提案；队列变化重新读取；句级epoch变化按动作语义重新验证。不能让长时间推理产生的提案永远追逐瞬时epoch；优先绑定场次、商品、队列和有效期，提交前做一次快速验证。
4. 当前尚无queue_revision/持久账本时，先旁路或确认模式测试，不能声称跨重启的严格一次执行。
5. 播中模型等待确认有期限；到期失效。等待不阻塞原队列播放。

## 6. SessionArchive（播后输入）

| 字段 | 内容 |
|---|---|
| schema_version, archive_id, archive_revision, room_id, session_id | 唯一场次/归档标识 |
| started_at, ended_at, sealed_at, end_reason | 场次实际时间，未知不能补造 |
| preparation_ref, catalog_snapshots[], script_snapshots[] | 当时计划与事实/稿件版本 |
| events[], proposals[], actions[] | 问题、模型提案、指令与执行轨迹 |
| playback_attempts[] | attempt_id、商品/稿件/句子/队列引用、开始/结束/取消时间、状态、source |
| business_metrics | 实际数据、口径、时间粒度、来源、时区；无数据null |
| completeness | 各部分complete/partial/missing、已知缺口、覆盖时间、采集方式 |
| evidence_index | 可引用的event/action/attempt/fact ID到证据定位的映射 |

同一条句子可能循环多次、被打断后重播，因此不得以sentence_id去重播放次数，应按attempt_id区分。同一业务事件按event_id去重；乱序排序保留原接收时间。

归档sealed表示这一修订冻结，不承诺数据天然完整。后到数据创建新archive_revision，旧报告保留对应版本；跨场不得共用同一个未区分session的日志列表。

兼容当前旧导出：识别当前状态JSON或`/api/export`里的playback数组，以room/session选目标；将played映射为“已收到ended记录”，缺少开始时间则null；logs只是有限窗口；未记录的提案、事件和业务数据标missing。不要用结束减预计音频时长反推实际开始；不要凭队列填实际播放时间。

## 7. ReviewBundle（播后输出）

至少含：schema_version、review_id、review_revision、room_id/session_id、archive_ref、status、data_quality、computed_metrics、findings[]、improvement_proposals[]、experiment_plan、generated_at。

每个finding含 finding_id、observation、evidence_refs、hypothesis（可null）、confidence_basis、limitations；不输出无定义的概率分。每条改进提案含目标product/script/plan、base_revision、修改类型、建议内容、理由、证据、验证方法、priority、approval_state=pending。

计算指标记录 value、unit、denominator、eligible_count、missing_count、source和formula_id。只针对有相应证据的样本计算，并说明覆盖。完成率必须区分播放尝试与运营动作，取消/失败/未知分别统计；缺少accepted记录不能把已播句子数当“Agent成功次数”。

改进类型：faq_add/script_revision/lineup_change/policy_change/evaluation_case。事实补充要单列verification_request，不能把推测作为新商品事实。ReviewBundle只产出提案，不调用声播写API。

## 8. 当前声播接口与未来适配

| 当前入口 | 当前能力 | 接入注意 |
|---|---|---|
| GET `/api/library` | 统一商品、稿件、房间配置 | 只取所需字段；不能认为返回的是历史版本全集 |
| POST `/api/generate/{product_id}` | 生成多版草稿 | 目前只接version_count，不接完整策划简报；需扩展适配才支持指定角度 |
| PUT `/api/scripts/{id}` | 基于旧稿创建新修订 | 引用按位置继承，人工/Agent复核必要 |
| POST `/api/scripts/{id}/approve` | 确认话术 | 现有有限规则不等于全语义验证；独立Agent默认不调用批准 |
| PUT `/api/rooms/{room_id}` | 房间保存商品引用、稿件选择、顺序、音色 | 活跃场次不能被播前准备包偷改；导入入口需带版本与阶段检查 |
| POST `/api/warmup` | 已确认稿音频预生成 | 当前直播时拒绝，不绕过限制 |
| GET `/api/rooms/{room_id}/state` | 当前播出快照 | 不是完整历史；调用前明确room |
| POST `/api/rooms/{room_id}/control` | 播出动作 | 使用action_id及场次/epoch条件；queue_revision待补 |
| GET `/api/export` | 当前配置、资料、各房间当前播出快照 | 先筛目标room/session，标缺口；不当历史归档API |

拟新增、尚不存在的适配功能：validate/import_preparation、seal/read_session_archive、submit/inspect_action、read_capabilities。不指定虚构的已上线URL。其他窗口先实现对文件的处理与相同语义的可替换客户端接口；实际HTTP入口由主项目统一落地。

## 9. 必须通过的契约案例

正常双商品；未知库存；过期活动；错币种；另一场的提案；话术草稿不能播；商品资料变化；队列被人工改动；动作重复提交；失去播放回执；只有部分旧快照；重复循环句；乱序事件；没有订单；模拟问题+真实声音混合场次。

两个模块应把这些场景作为固定测试，必要数据用明确标注的演示商品/事件构造，不能把未观测时间、销量或用户资料补成真实记录。
