# Agent Harness 入门教程与资料导航

本教程面向希望理解 Agent 产品设计、暂时不需要阅读大量代码的读者。我们先弄清运行逻辑，再理解多 Agent 协作，最后给出学习路线。阅读后，你应该能说明模型和 Harness 各自负责什么，以及一个 Agent 如何行动、记住进度并证明任务完成。

整理日期为 2026 年 10 月 7 日。主要参考来新璐维护的 Learn Claude Code、他的原始访谈节目笔记，以及 Anthropic 官方文档。下面的中文解释为重新组织的学习笔记，具体设计建议会明确标注。

## 一 从一次模型调用理解 Harness

向模型发送一句要求，模型会产生文字或工具调用请求。要把请求变成实际工作，还需要程序准备输入、执行工具、保存结果，并把结果交给模型继续判断。围绕模型的这套运行设施，就是 Agent Harness。

这里可以先区分三个东西。模型提供理解和判断能力；工具完成具体操作；Harness 把模型、工具、上下文和执行规则组织成一个能够持续运行的系统。换一个业务领域，往往主要改变工具、知识和约束，基本运行逻辑仍然可以保留。

最核心的运行循环可以写成：

目标和当前信息 → 模型决定下一步 → 运行时检查并执行工具 → 获得真实结果 → 更新上下文 → 模型继续判断。

当模型认为可以结束时，还需要检查完成条件。这个循环会持续到任务完成、需要用户输入、遇到无法处理的问题，或者达到预先设定的资源限制。

举一个通用例子：要求 Agent 查清一个软件报错。模型可能先请求读取日志，读完后再请求查看相关代码，接着决定是否修改，最后运行测试。读取日志时发现的新情况，可以改变后续行动。这就是反馈在发挥作用。

### 你要掌握的第一个判断

看一个 Agent 设计时，先问：它能够观察什么，能够执行什么，执行之后怎样知道结果？只有任务描述和角色名称，还不足以回答这三个问题。官方架构说明同样把收集上下文、采取行动和验证结果放在一个循环里。

来源：[Claude Code 官方运行机制](https://code.claude.com/docs/en/how-claude-code-works)。

## 二 来新璐怎样拆解这套系统

访谈用三个层次介绍 Harness。可以把它理解为逐步解决三类工程问题。

| 层次 | 要解决的问题 | 典型机制 |
| --- | --- | --- |
| 执行能力层 | 模型怎样真正开展工作 | 工具调用、执行环境、权限检查 |
| 上下文与状态层 | 任务变长以后怎样继续工作 | 技能加载、上下文整理、记忆、持久进度 |
| 治理与编排层 | 多个任务和多个 Agent 怎样可靠协作 | 分工、依赖、隔离、结果验证、停止条件 |

第一层让一次行动能够发生。第二层让行动能够跨很多轮甚至跨会话延续。第三层处理多人分工一样的组织问题：谁能做什么，前置任务完成了没有，交回来的结果是否可信。

Learn Claude Code 的教学方式，是先写一个小循环，再逐步加机制。读它时，可以不断问同一个问题：这一课解决了前一课的哪个具体缺陷？这样比记住十几个模块名称更有用。

### 理解他的核心主张

他倾向于把任务相关信息和可用行动提供充分，让模型根据环境选择方法，减少预先写死的提示词步骤。我的理解是：设计者把目标、工具和边界说明白，给模型保留基于反馈调整路径的空间。

这是一种设计取向，不能直接推导成“所有固定流程都没有价值”。当前教程的 s16 就专门讲固定编排的实现。可以同时保留确定的流程约束和模型的局部判断。

来源：[原始访谈及时间轴](https://www.xiaoyuzhoufm.com/episode/69f2e83fbb3ffa11e59dec82)、[教程中文入口](https://github.com/shareAI-lab/learn-claude-code/blob/main/README-zh.md)。

## 三 读教程时要抓住的几个模块

### 工具与权限

工具把模型的决定转成外部操作。一个完整工具需要说明输入参数、返回结果、失败信息以及生效条件。模型请求调用后，运行时校验参数和权限，再执行并返回结果。权限的执行不能只依赖提示词里的提醒。

### Hooks 扩展点

Hook 是在某个执行时刻自动运行的一段程序，例如工具执行前检查权限、执行后记录结果、准备退出时检查任务。它通常用于确定的检查和处理，不需要每次都由模型判断是否调用。

### Skills 技能

Skill 保存可复用的方法、说明和辅助资源。运行时先提供简短目录，模型需要某项技能时再加载正文。这能减少每轮携带无关说明。技能文档负责指导，实际操作仍通过工具完成。

### 上下文 状态与记忆

上下文是模型本轮能看到的信息，容量有限。状态记录任务现在进行到了哪里。记忆保存未来还会用到的知识或经验。三者需要关联，但不能互相替代：摘要可能丢失细节，过期记忆也可能影响判断。

教程通过整理工具输出、压缩历史、保存文件和按需召回来处理长任务。使用时还要保留目标、限制和证据的来源，让压缩后的 Agent 能重新定位原始资料。

### 任务系统与后台工作

任务系统记录任务标识、依赖、负责人和完成状态，使进度能够持久保存。后台工作让慢操作继续执行，并在结束后向主循环发送通知。已经启动和已经完成，是两个需要分开记录的状态。

### 完成验证

模型停止请求工具，不一定意味着任务已经成功。教程 s17 把停止提议再交给独立判断器检查。判断器本身也有局限：没有真实证据时，它无法凭空验证结果。因此应先定义怎样证明完成，再决定何时停止。

这些解释对应当前教程 s02 至 s12，以及 s17 的重点机制。具体章节与代码见本地参考索引。

## 四 多 Agent 协作怎样建立在 Harness 上

子 Agent 是一次具有独立任务、上下文和工具配置的运行。主 Agent 交给它必要的信息；它开展工作，交回结果。独立上下文可以减少主对话的负担，也便于给不同任务配置不同权限。

上下文隔离不自动产生文件或数据隔离。两个 Agent 即使互相看不到对话，仍然可能修改同一份资源。运行时需要另外处理资源范围、任务认领和冲突。

### 三种常见组织方式

串行适合有明确依赖的任务，前一步结果决定后一步输入。并行适合可以独立开展的调查，等结果到齐以后再汇总。持续团队适合需要保留身份、互相交接并反复领取任务的长期工作。

后两种方式都会增加协调成本。是否增加 Agent，应该比较完成质量、耗时、调用费用和失败率，而不能只看分工图是否复杂。

### 一次交接至少说明什么

交接内容应包含目标、输入资料、可用工具和权限、预期输出，以及完成证据。子 Agent 返回时还要说明未完成事项和不确定性。结果采用约定结构，才能由下游程序检查和复用。

一个可靠的验证角色还需要自己的证据和检查标准。让另一个模型说“看起来没问题”，仍然不能替代实际测试。

### Harness 与 LangGraph 的关系

Harness 描述围绕模型需要提供的整套运行能力。LangGraph 是可用于组织状态、执行路径和持久化的实现工具。学习 Harness 是先决定需要什么；选择框架是再决定如何实现。

这里提出的设计原则是：固定的资源约束、依赖和校验交给程序，随证据变化的分析与行动选择交给模型。具体比例要通过测试调整。Anthropic 的编排文章同样介绍独立验证、并行汇总和恢复，并指出多 Agent 必须值得其协调成本。

来源：[官方子 Agent 文档](https://code.claude.com/docs/en/sub-agents)、[官方动态工作流文章](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)。

## 五 怎样学习并检验自己理解了没有

### 推荐阅读顺序

第一轮先读 s01 和 s02，理解循环与工具；再读 s03 和 s04，理解权限和扩展点。能用自己的话说出“模型提出动作以后，程序做了什么”，就完成了这一轮的目标。

第二轮读 s07、s08 和 s09，理解技能、上下文和长期记忆；补读 s05 与 s10，理解步骤清单和持久任务。读完应该能解释：关闭会话后，哪些东西还在，哪些东西需要重新提供。

第三轮读 s06、s13、s16 和 s17，理解子 Agent、团队、编排与完成判断；再用 s15 查看机制如何接到同一个运行循环。s11、s12 和 s14 可按后台任务、调度和外部工具接入的需要补读。

### 四道自测题

1. 模型说要删除一个文件，是否已经删掉？参考答案：还需要运行时检查并执行工具，并返回结果。
2. 给 Agent 加一份技能文档，是否等于已经有对应操作能力？参考答案：文档能指导方法，实际行动需要可用工具和权限。
3. 两个子 Agent 使用独立对话，是否一定不会互相覆盖修改？参考答案：不会自动隔离共享资源，需要另外设计。
4. Agent 回答任务完成，如何确认？参考答案：检查事先定义的证据和实际状态，必要时执行独立验证。

### 后续学习怎样评价质量

先准备一组能够重复运行的任务，分别观察是否达成目标、工具是否执行正确、失败能否恢复，以及总耗时和费用。增加记忆、团队或复杂编排后，仍使用相同任务比较。只有实际改善了结果，才能说明新增机制有用。
