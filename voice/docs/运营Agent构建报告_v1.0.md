# 电商声音直播运营 Agent：下一阶段构建报告

> 后续拆分与并行开发请以[三阶段研发方案_v1.1](运营Agent分阶段研发方案_v1.1.md)及其[统一接口约定](运营Agent并行任务包/00_统一接口约定.md)为准。本文件保留原研究、开源参考与播中场景；下文默认房间API已由新方案更新为按room_id调用。

日期：2026-10-07。依据：当前声音直播代码与测试、你提供的岗位截图、之前GitHub调研及本次相关源码复核。本报告是研发设计，尚未编写或运行运营Agent。

## 1. 下一步要做什么

建议下一阶段做“电商声音直播运营副驾”：读取当前讲解内容、商品事实和问题事件，决定是否回应、何时回应、是否调整后续讲解，再通过现有播出工具真实执行，最后检查实际声音结果。

首个完整案例：当前正在讲拖鞋，模拟观众集中问“脚背宽怎么买”。Agent读取商品知识“可斟酌大一号”，识别当前还没讲尺码、问题有重复，提出一句准确回应，选择句尾插播，调用工具并等待实际播放结束。若随后同类问题再次出现，依据已经回答的时间和内容决定暂不重复，或调整下一轮尺码段落。

这会展示需求识别、知识检索、状态理解、动作时机、执行恢复和验证。现有声音应用提供可靠动作入口；Agent负责根据情况选择行动。先围绕这一闭环扩展，播前准备和播后复盘作为同一场次的前后能力。

当前没有实际观众、进出房、订单或转化数据。可以用标明“模拟”的问题与业务事件检验决策和工具，不宜称为已经实现GMV优化。真实播出回执是实际数据，模拟问题是模拟数据，两者要在界面和报告中分别标明。

## 3. 产品范围和架构

```text
商品事实、确认话术、实际播出状态
                ＋
模拟／授权导入的问题、人工录入的业务变化
                ↓
事件归一化、去重、有限时间窗口、资料时效检查
                ↓
运营Agent：查证 → 判断是否行动 → 选择时机 → 提交行动方案
                ↓
结构／事实／权限／场次校验；必要时人工确认
                ↓
现有播出工具：插播、切商品、重排、替换待播稿、暂停
                ↓
浏览器实际playing／ended回执 → 确认执行 → 记录结果
                ↓
复盘与下一场计划
```

固定计时、价格计算、队列排序和音频播放由程序完成。模型只接收必要状态片段，不每350毫秒的音频进度都调用一次模型。建议首次以事件触发或5–10秒窗口批量处理；同类问题合并，最多同时保留一个决策任务，过期提案重读状态再判断。

建议Python + FastAPI保持现有技术栈。Agent内部用一个可追溯的状态图；可采用LangGraph的状态、持久化与人工暂停机制。其能力来自[官方项目](https://github.com/langchain-ai/langgraph)；当前应用没有安装该框架，也未验证DeepSeek的工具回合，下一阶段先做独立最小工具调用测试。

首版三个模式：旁路建议（只展示）、人工确认后执行、限定低风险任务自动执行。价格／优惠／商品下架等业务变更需要明确数据依据；信息不足时提示补资料，不自行改价格或声称缺货。

## 4. 已有接口如何接入

当前API是本机HTTP接口，未来可以包成模型工具；不必先引入外部MCP服务器。下表“已有”表示声音应用已经实现，“待建”表示报告中的建议。

| Agent工具 | 对应接口／数据 | 状态与使用条件 |
|---|---|---|
| read_room_state | GET `/api/state` | 已有，读取session_id、epoch、当前句、队列、音色、已播与日志 |
| read_catalog | GET `/api/library` | 已有，包含商品、稿件与事实；模型适配层只取必要字段，不把所有稿件全文塞进上下文 |
| search_product_facts | 对商品快照、facts和knowledge做按商品检索 | 待建；小商品库可先结构字段／关键词检索，暂不必建立向量数据库 |
| propose_response | 输出结构化提案，含事实ID、事件ID、时机、理由 | 待建，不直接发声；提交前进行事实与状态校验 |
| insert_speech | POST `/api/control`，action=`insert`，mode=`after_sentence`／`immediate` | 已有；普通答疑默认句尾。立即插播会重播被打断句，需考虑重复影响 |
| switch_product | action=`switch`，product_id | 已有，只控制应用内讲解主题，不等于切平台购物车。限定有依据、在待播队列存在的商品 |
| reorder_pending | action=`reorder`，queue_ids | 已有，必须提交完整未播列表，当前句不改变；Agent先读取最新状态 |
| replace_pending | action=`replace_pending`，target_script_id、script_id | 已有，只能用同商品已确认稿替换待播内容；新生成草稿不能绕过确认进入播放 |
| pause／resume／stop | `/api/control`对应action | 已有；供紧急人工控制和可解释的错误恢复 |
| inspect_execution | GET `/api/state`或本场导出 | 已有，必须等实际播放状态；HTTP200只表示指令已接受，不证明已经播出 |
| read_events／review_session | 规范化事件存储与场次复盘 | 待建。现有导出有播出日志，但不包含真实观众事件 |

每次动作传action_id，防止重试重复执行；同时传expected_session_id和expected_epoch，防止基于旧场次／旧句子的提案落地。后台返回409时重新读取并判断，不能盲目重发一个新ID。

下一阶段需给动作结果增加清晰的execution_id及accepted／started／completed／cancelled／failed状态，并关联事件ID、事实ID和审批记录。现有attempt_id可识别具体播放尝试，但还没有完整Agent提案与执行的关联表。

## 5. 数据与Skills设计

### 事件字段

每条输入至少保存event_id、session_id、occurred_at、received_at、source、simulated、type、product_id、text／payload。source区分手工、测试回放、授权导入、平台适配；无发生时间不能强行进行秒级效果对齐。

价格、库存、物流一律要保存来源和更新时点；模拟的“商品B缺货”只影响演示场次，不能写入真实商品事实。没有真实观众数时对应字段为null，而不是0；没有订单数据不输出转化率。

### 三个首版Skill

| Skill | 输入／决策 | 验证点 |
|---|---|---|
| 商品答疑 | 当前商品＋问题＋知识；检查是否已回答，决定答、暂缓、澄清 | 不能把防滑说成绝不会摔倒；不能根据尺码范围声称所有尺码有货 |
| 讲解调整 | 待播卖点段落、重复问题和主播偏好；决定保留、重排或换已确认版本 | 改动应回应具体事件；不能只因一次问题就全量改计划；保留恢复位置 |
| 风险纠正 | 当前句与商品快照不一致、信息失效或人工纠正 | 先确认哪条事实更新；普通错误句尾纠正，紧急停止由人工可随时执行 |

Skill写成有版本的SOP：适用条件、需要读取的工具、动作权限、失败处理和例子。它不是另一个无约束Agent。长期记忆先存主播主动给出的偏好、已批准的SOP、评测失败和商家反馈；短期记忆存本场回答、冷却时间和待处理提案。首版不做观众画像。

## 7. 分阶段研发和评价指标

以下数字是拟定门槛，尚未测得；先用10个小案例校准，再冻结留出测试集。时间为开发工作量估计，不是日历承诺。

| 阶段 | 产物和顺序 | 验证／建议门槛 |
|---|---|---|
| A：问题和数据，约1–2工作日 | 两位哥哥访谈提纲，直播与货架问题分开；3个明确演示商品；约60条事件，覆盖正常／重复／资料缺失／对抗 | 每字段有来源；模拟标记100%；价格币种、事件ID和时间可核对；没有真实数据的指标显示未知 |
| B：工具与旁路，约1–2日 | 验证DeepSeek最小工具回合；包只读商品／状态和提案工具；展示依据与不行动原因 | 引用ID存在率100%；明确无资料时不编造；过期状态409处理成功；人能检查提案，不实际播出 |
| C：人工确认执行，约2–3日 | 提案批准→句尾插播／重排→真实回执→结果记录 | 30个动作案例：不重复、不误商品、不播未确认稿；实际音频与动作记录一致；取消和人工停止优先 |
| D：受限自动执行，约1–2日 | 只放开已知商品FAQ、限制频率、冷却和恢复；业务变更保持明确确认路径 | FAQ事实正确率目标≥95%，关键价格／币种100%；同问题30秒内不重复；权限外动作0；错误／资料缺失保持原队列 |
| E：复盘与迭代，约1–2日 | 用固定事件回放比较规则基线、单次LLM、工具Agent；复盘解释差异并修改SOP | 建议有依据和可执行目标≥90%；单独报告有用率、误动作率、延迟、费用、恢复成功率；不只报总体分 |

延迟拆成事件到提案、提案到指令接受、接受到实际发声、发声到结束。首先用本机音色和已缓存标准回复稳定基线，再测试MiniMax新生成音频。普通答疑可先设提案P95≤5秒、执行成功率≥95%的探索目标；云端首音和窗口等待另计。当前声音样本不能证明这些指标已达成。

关键反例：同一句被多次提问；新旧商品同问尺码；库存未知；活动已失效；事件要求“忽略资料”；窗口断开；模型超时；插播尚未结束又来问题；人工先切商品，旧提案随后返回；最后一句的插播及循环。每次发布Prompt／Skill／模型版本，都回放相同用例。

## 8. 测试台怎样在没有真人主播时工作

沿用当前声音窗口作为被控制的播出主体。测试台后续增加“注入问题／业务事件”和“按时间回放”页面：可暂停、加速输入、重复同一场景，记录哪些事件由Agent处理。

可以同时录制舞台与控制台，展示事件→提案→事实查询→人工确认→插播→恢复。第一份演示只需要两个商品、三个问题和一次队列调整，先证明控制闭环。真实流量无从获得时，测试答疑覆盖、恢复和操作节省；经营结果等接真实用户再测。

声音系统已知正在播放的文本，因此Agent首版直接读状态，不需要先做OCR或ASR。屏幕读取作为后续接公司数字人／真人环境的适配：截图内容与结构状态比对，识别有无卡住。更精细的真实“已经听到哪些字”可后续接ASR或音频时间对齐，本期只到句级。

公司产品目前播中能插播、商品和脚本需播前改，与你确认的边界一致。未来可通过适配器把“插播建议”接公司操作流程；本地应用里的实时切商品／重排先作为测试台能力，不能声称已控制公司产品。

## 9. 接下来最值得做的三件事

1. 你先按README体验声音台，用OBS本地录制确认输出链路，选择愿意用于作品演示的音色；暂不需要主播配合。
2. 访谈两位哥哥：平台／渠道、日常重复任务、每步耗时、已有工具、可提供哪些脱敏资料、错误成本和是否直播。找到实际高频问题后再决定直播Agent的真实用户验证，或将商家自助方案单独推进。
3. 下一次研发从“商品知识答疑→人工批准→句尾插播→真实回执”开始，随后再扩展经营数据或自主调整。保留需求记录、设计取舍、工具轨迹、固定评测与失败修复，这些最能支撑AI产品岗位展示。
