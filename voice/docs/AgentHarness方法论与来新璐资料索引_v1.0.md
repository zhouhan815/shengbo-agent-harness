## 2. 从资料提炼的设计框架

访谈将 Harness 分为执行、上下文与状态、治理与编排三层。这里把它转成后续设计文档需要回答的问题；右栏是针对本项目提出的验证方法，不是原资料给出的测试结论。

| 层次 | 需要设计什么 | 验证机制与评价指标 |
| --- | --- | --- |
| 执行能力 | 模型可以观察什么、调用哪些工具、如何拿到真实执行结果 | 用可重复场景检查参数、回执和实际状态是否一致；记录工具成功率、错误分类和耗时 |
| 上下文与状态 | 本轮需要哪些信息，哪些信息持久保存，中断后如何恢复 | 中断再恢复；检查目标、商品标识、任务进度和未完成动作是否保留，记录恢复成功率和上下文大小 |
| 治理与编排 | 谁可以执行、谁负责验证，任务如何分工、何时结束 | 注入重复请求、过期状态和非法动作；检查拦截、去重和停止条件，记录违规执行数、重复动作数及完成率 |

核心运行方式：获得目标与当前状态 → 模型选择下一步 → 运行时检查并执行工具 → 返回结果 → 再观察、再决策 → 检查完成条件。

### 2.1 目标与方法分开

任务描述写清预期结果、可用资源与完成证据。对需要判断的环节，让模型根据观察决定调查或处理顺序。固定的数据校验、资源锁定、状态转换等由代码执行。

这并不意味着拒绝工作流。教程 s16 专门展示把确定的编排写进可信脚本；方法上的重点是避免把所有判断提前写死在提示词链路里。

### 2.2 工具必须有明确契约

每个工具写清输入、输出、权限、失败形式和生效时机。模型提出调用，运行时负责执行；生成了一段动作文字不等于动作已经完成。

对声播，优先设计商品读取、队列查询、插播、切换、暂停等业务工具。工具的实际清单、参数和可用阶段需要在后续设计时对照当前代码复核，不直接复制教学项目的通用 shell 权限。

### 2.3 技能、状态、记忆分别管理

- 技能：可复用的方法和操作说明，先提供简短索引，需要时加载正文。
- 状态：当前直播间、队列、播放进度和动作执行记录，应以应用的权威数据为准。
- 记忆：经过验证的长期经验，保存证据来源、适用范围与版本。

不能用对话摘要替代播放状态，也不能把模型总结出的建议直接当作已验证运营经验。

### 2.4 子 Agent 的价值来自清楚的工作边界

一个子任务具有独立输入、有限工具和明确输出时，才适合交给子 Agent。例如独立检查商品事实或分析一批异常。任务交付应包含结构化结果、证据引用、完成状态及未解决问题。

“播前、播中、播后”首先是业务阶段，不自动等于必须运行三个常驻 Agent。是否拆成独立 Agent，要用任务质量、耗时和调用成本比较，而不是按数量判断先进程度。

### 2.5 提出完成与验证完成分开

模型不再调用工具，只说明它希望结束当前轮次。运行时还要检查验收证据是否齐全。对可确定验证的事项，优先使用程序检查；涉及质量判断时可以增加独立评审。

独立模型评审依然可能出错，不能代替真实工具回执、播放记录或测试结果。

### 2.6 固定流程与自主判断可以组合

后续可以采用“可信编排 + 阶段内自主循环”：编排负责依赖、持久化、预算和交接，阶段内模型负责分析与工具选择。LangGraph 可作为实现部分运行机制的候选，Harness 则是决定这些机制应该怎样设计的方法；两者不属于同一层级的替代选项。

## 4. 对后续声播设计的调整建议

以下是基于上述资料的项目设计建议，尚未通过应用实验验证。

1. 先定义共同 Harness：目标、观察接口、工具执行器、状态存储、权限策略、动作记录和完成验证。
2. 再定义播前、播中、播后各自需要的信息、技能、工具权限与交付物；阶段内允许模型根据证据选择下一步。
3. 播前与播后可以分别开发和测试，交接使用带版本的结构化产物。只有读取历史快照的播后任务才能与当前直播独立运行。
4. 播中依赖声音人应用的真实动作和回执。先做模拟场景，再检查接入后的音频与界面状态；不能把模拟观众数据解释成真实经营改善。
5. 评估先比较单 Agent 与少量子 Agent：同一组任务下看交付质量、完成率、成本和延迟；收益足够再扩展团队。
6. 保留 DeepSeek 的模型选择，不因为参考 Claude Code 就默认更换模型或套用 Claude SDK。工具调用和结构化输出适配需要单独验证。

后续每一份设计文档统一包含：目标与完成证据、输入和观察、可调用工具、技能和知识、状态与记忆、协作交接、权限与失败处理、测试场景与评价指标。
